## 1. A lost line over syslog

3. **Defect, high confidence (R1).** raqib/forward.py:151:
   `STAMP = re.compile(r"\d{4}-\d\d-\d\dT\d\d:\d\d:\d\d(\.\d{1,6})?Z\Z")`
   - In a str pattern, `\d` matches any Unicode decimal digit.
      - event.instant (raqib/event.py:90 TIME, :152 strptime) accepts such digits too. CPython's _strptime `%Y` is
     `\d\d\d\d` with no ASCII flag, and int() reads Arabic-Indic digits.
      - So an ASCII line whose year is written as JSON escapes (for example
     `\u0662\u0660\u0662\u0666-11-03T07:51:21.000Z`) passes classify and STAMP. forward.py:418-419 `.encode("ascii")`
     then raises UnicodeEncodeError.
      - It raises in the main thread, inside wire_len, called from unsent and too_long in go_on. Nothing catches it
     before run() at forward.py:1864, which ends the run `unforeseen`.
      - Every restart resumes before that line and dies again. One line from a writer of the events file (the watched
     account, per FORWARD.md N-9) stops syslog forwarding for good. HTTP, both shapes, is not affected.
   - It contradicts Q7 and FORWARD.md:198-200 ("that field is `-`"). FORWARD.md:354-359 (N-9) does not list it.

4. **Suspicion, medium confidence: the forwarder's own close loses `written` bytes over tls.**
      - SyslogSend.exchange (forward.py:808 `sock.sendall(...)`, :815 `return Result("taken")`) never reads from the
     socket. Send.run then closes it at once (forward.py:702-706). There is no close_notify (Q5).
      - A TLS 1.3 server sends NewSessionTicket records after the handshake. OpenSSL, Go and Python servers do this by
     default. The client never reads them.
      - On Linux, closing a TCP socket with unread received data aborts the connection (RST, RFC 2525 2.17). Whatever
     of the batch is still unsent or unacknowledged is thrown away. If close came first, tickets that arrive at the
     closed socket draw the same reset.
   - Over loopback nothing is in flight, so the TLS test (tests/test_forward.py:2379) passes. The rig has no tls case.
      - Over a real path, a batch larger than what was acknowledged by close time (up to 512 KiB) can lose its tail on
     every connection, after the cursor has passed it.
      - FORWARD.md:34-37 and THREAT_MODEL.md:1264-1268 put this kind of loss on "a collector that closes its end".
     Here the forwarder's own close causes it.
   - I could not run it. Windows close behaviour was not checked.

5. **Docs contradict the code, high confidence on TLS 1.3 semantics.**
      - THREAT_MODEL.md:1261-1263 names "TLS with client certificates on its side" as the answer. The forwarder cannot
     present a client certificate (no option).
      - Under TLS 1.3 the server rejects a missing client certificate only after the client's handshake is done
     (certificate_required alert). do_handshake succeeds, sendall succeeds, and the batch is `written`.
      - So every batch passes, `failing` stays null, `--status` says OK, and the collector keeps nothing. This goes
     against A3.
   - Neither document says it.

6. **The code never looks for a closed peer, high confidence.** There is no read for EOF or RST after writing, no
  SO_ERROR check and no half-close.
   - With one connection a batch, up to one whole batch (100 lines, 512 KiB) per connection can be lost unseen.
      - A collector that accepts and at once closes every connection loses every batch while the status stays OK.
     rsyslog past MaxSessions and syslog-ng past max-connections behave this way, from what I know of them.
      - FORWARD.md:36-37 says the loss "while the bytes are on their way". It does not say how much, or that a
     collector at its session limit loses everything.

7. Questions (a), (c) and (d):
      - (a) Partial write: confirmed no loss. Any exception in sendall fails the whole batch (`write`, `late` or
     `tls`), so the cursor passes none of it, and the next try resends it whole from the cursor on a new connection.
     Messages already written arrive twice (duplicates, which is fine). The cut frame is followed by the same message
     whole. But with `--framing newline`, a collector that takes a cut last line at end of stream keeps half an event.
     That contradicts THREAT_MODEL.md:1268-1270 ("no message is half an event"). Low-medium.
      - (c) udp: the socket is not connected (forward.py:817-833). Any OSError (ENOBUFS, EMSGSIZE, no route) is
     `write` and nothing passes. EMSGSIZE is not reached on Linux or Windows below 65000. On Linux an ICMP refusal is
     never seen, so a down collector gets everything `sent` and loses it. Only the first getaddrinfo address is used
     (forward.py:820), while tcp tries each in turn. With `--plain` and a name that has both AAAA and A records,
     datagrams may go to an address where nothing listens. Low-medium.
      - (d) Confirmed: SyslogSend returns only `taken` or `failed`, and carry adds `stopped` or `stuck`. No path
     treats a syslog failure as `refused`. ask_first and settle are never reached for syslog, and resume does not load
     in_question.

## 2. The message (E1)

9. The header matches RFC 5424:
      - PRI = facility*8 + severity. Facility is checked 0..23 (forward.py:924-930; ASCII digits only, at most two),
     so PRI is at most 190.
   - VERSION 1. APP-NAME raqib. PROCID `-`. SD `-`. One space, then the MSG.
      - HOSTNAME and MSGID are checked against an explicit ASCII range (PRINTUS), 1-255 and 1-32, else `-`. No space
     or newline can enter them.
   - Severity becomes an integer.
   - The octet count is len(message) in bytes (forward.py:434), and syslog_len agrees (tested at :2279).
   - TIMESTAMP is the only header field open to the event: finding 3.
   - STAMP checks shape, not ranges. Ranges are left to event.instant.

10. The MSG never holds LF: whole lines are split on `\n`, and _bare strips trailing CR and LF. It can hold a raw CR
  or TAB in the middle, since JSON allows them as whitespace. With `--framing newline`, a collector that breaks lines
  on CR (Splunk's default LINE_BREAKER, from what I know) splits one message in two. Low: a writer of the file can
  already write any event.

11. Q8: no BOM is right. The line is ASCII, MSG-ANY.

## Q1 to Q11

- **Q1.** Not safe as a process: it is outside Scope by the HANDOFF's letter (finding 1). The code is harmless. Cost:
  a precedent of acting on a permission that is not recorded. Q1's text is now stale.
- **Q2.** Safe. Cost: a raqib from before this task reads a state holding `write` as UNREADABLE (3).
- **Q3.** Safe for the cursor. Cost: IANA lists 514/tcp as `shell` (rsh) and 601 as syslog-conn. A forgotten port
  writes events into whatever listens on 514, all counted `written` and lost. An explicit port would make that mistake
  a usage error.
- **Q4.** Safe for the cursor, which is the line's. Cost: neither the state nor --status says the facility or the
  framing. A restart with another framing to a strict collector is silent loss, every batch `written`; another
  facility can reroute events at the collector unseen.
- **Q5.** On the question asked, safe: a TLS peer delivers each record it received whole, and a missing close_notify
  only marks the end as unexpected. Cost: the unread-record close of finding 4. Without close_notify, the collector
  also cannot tell a cut stream from a batch's end.
- **Q6.** Safe. Cost: none (an explicit `--framing octet` with udp is refused too).
- **Q7.** The rule is right but not as built: finding 3 breaks it for TIMESTAMP. Cost of the rule itself: a non-ASCII
  or spaced host gives HOSTNAME `-`, so collectors that group by the header host lump such hosts together.
- **Q8.** Safe. Cost: none (the line is ASCII).
- **Q9.** Safe against the promise (`sent`). The reason given does not hold: with one socket a batch, an ICMP refusal
  seen on a later send would be about a datagram of the same batch. Cost: on Linux a down loopback collector is never
  seen, so every line is `sent` and lost while the status is OK (A3).
- **Q10.** Safe as a rig fact on loopback. Cost: X24 can be MISSED under load because rmem_max caps the buffer. The
  stand-in does not hold the TIMESTAMP `-` rule.
- **Q11.** Safe. The HTTP assertions are unchanged (finding 2). Cost: E7's "untouched" is not literally met.
