## Q-1 (blocking) No construct compares a value with the session's starting value, and a code rule cannot be counted inside Scope
What the rule language has:
- `require:` is demand only. compile_rule rejects it on any other kind
  (raqib/rules/engine.py:285-288, ADR-0002 D-1). Tried on the tree:
  `HEAD-UNMOVED.yaml: require: only a demand requires evidence on another
  line (ADR-0002 Amendment D); kind anchor must not have one`.
- Its nodes (before, after, until) are predicates on one line with
  literal arguments (engine.py:409-485). `eq` takes a scalar written in the
  rule (:409-414). The one op that names another field, `outside`, reads
  that field from the same line (:445-456). No node reads a value from
  another line, so "close equals start" cannot be written as evidence.
- `aggregate: {distinct: git_head, over: 1}` fires when there are MORE than
  N distinct values (:723-725). That is HEAD-MOVED, the opposite rule.
  aggregate has no "at most" form and cannot also require an edit.

Why a code rule cannot be used inside Scope:
- The gate counts the catalog YAMLs, silence.RULE_KINDS and
  cross.RULE_KINDS, and nothing else (tools/gate.py:214-262, :253). A code
  rule in engine.py, or in a new module, would leave the kinds line at
  `anchor=4`, not E4's `anchor=6`.
- `raqib report`, `rules`, `watch` and `eval` run silence, the catalog and
  cross.findings, and nothing else (raqib/cli.py:333-339; eval.py:96-101).
  watch takes cli.run_rules (cli.py:742). check-rules measures the catalog
  plus cross.check (cli.py:479-481).
- raqib/rules/silence.py, cross.py, tools/gate.py, raqib/cli.py and
  raqib/eval.py are outside Scope. So is a new module.
- `holes:` and `fp_budget` are YAML keys (G-6), and E4 counts the two rules
  as YAML: "5 + 1 + 11".

Options:
- (a) A YAML construct in engine.py. The rules are
  `raqib/rules/catalog/{HEAD-UNMOVED,INDEX-UNTOUCHED}.yaml`, kind anchor.
  The gate, check-rules, watch and the page take them with no change.
  A sketch: anchor only, never with aggregate or require.

      match: <the triggers: ok edits>
      unchanged:
        field: git_head                               # compared as eq compares
        from: {field: phase, eq: session_start}       # the session's starting line (Q-4)
        to: {field: phase, in: [stop, session_end]}   # its closing line (Q-4)

  It gives one finding per session that has at least one true trigger
  between `from` and `to`, when the field on `to` equals the field on
  `from` and both are non-null. The finding cites `from`, the triggers and
  `to`, with the ts of `to`. It is unknown (partial, cause per seq, as H-3)
  when there is no `from` line, no `to` line after the last trigger, a
  value that is null or missing, an unknown trigger, or (Q-5) two
  different cwds.
- (b) `require:` allowed on anchors, with a new shape `{same: <field>,
  from: <node>, to: <node>}`. This changes D-1 ("demand only").
- (c) A code rule, raqib/rules/tree.py, with its own RULE_KINDS that the
  gate reads, as CROSS-SOURCE did (ADR-0003 C-1). That adds tree.py,
  tools/gate.py, raqib/cli.py, raqib/eval.py and tests/test_gate.py to
  Scope. E4's README sentence would become "5 silence rules, 3 code
  rules, 9 YAML rules", and the holes and fp_budget would be Python
  constants.

Reading I would build: (a). It keeps the comparison visible in the public
rule (A8), the fixtures and the benign corpus measure it like the other
anchors, and E4's counts hold as written. The name, the shape and the
start/close choice (Q-4) are the Table's call.

## Q-2 (blocking) The three keys are unknown fields to the fixture checker, and raqib/rules/trace.py is outside Scope
- JSON fixtures and eval events are held to trace.strict_problem
  (raqib/rules/fixtures.py:66-69; raqib/eval.py:81). It rejects any field
  that is not in trace.FIELDS (raqib/rules/trace.py:140-145, :161-163).
- Tried with a fixture made from a real prototype hook line:
  `line 1 is not a sound trace record (unknown field(s) git_error,
  git_head, git_index_sha256)`.
- A `.log` fixture is read leniently (fixtures.py:44-48), so it would
  load. But then the keys are not checked anywhere, and a misspelled
  `git_haed` would pass as a "does not apply" negative. strict_problem
  exists to stop exactly that (trace.py:148-152, A6).

Options:
- (a) Add raqib/rules/trace.py to Scope. FIELDS gains the three keys, and
  strict_problem checks their shape (git_head 40-hex or null,
  git_index_sha256 64-hex or null, git_error one of the closed set of Q-7
  or null) and that they appear only on session_start, stop and
  session_end lines.
- (b) `.log` fixtures only, with the keys unchecked.

Reading I would build: (a).

## Q-3 (blocking: decides what "clean" means after M4.3) "Null or no start = unknown" makes many traces INCOMPLETE
How an unknown turns into INCOMPLETE:
- A rule's unknown lines become a `partial` note (engine.py:657-666).
- Any note that is not `disabled` makes `report` INCOMPLETE, exit 3
  (report.py:136-141). watch reads the result the same way.

What E2 and E3 as written would make INCOMPLETE:
- Every trace written before M4.3 that has an ok edit: its boundary lines
  carry no keys. tests/fixtures/file-tools-d7841d1-claude-code-2.1.301.log
  (2 ok edits) is `RESULT: CLEAN (exit 0)` today under `report --scope .`.
  It would be INCOMPLETE.
- Every session with an edit in a directory that is not a git repository
  (`git_error: "no repo"` at both ends). The same holds for a session
  started in a subdirectory of a repository, because nothing walks up
  from cwd (Q-7).
- Every proxy session with edits. The proxy writes no git keys: its
  conversation boundaries are out of scope.
- tests/test_demands.py:718-735 runs the real hook in a temporary
  directory that is not a repository. It asserts CLEAN for this project's
  close shape (edit, gate, landed: commit), so it would fail.

Options:
- (a) As written: such traces are INCOMPLETE.
- (b) As ADR-0003 C-2 ruled for CROSS-SOURCE: a session whose start line
  carries no git keys (written before M4.3, or by the proxy) is not judged
  and writes no note. "no repo" at both start and close means "does not
  apply" (no note). Every other null is unknown (partial), and so is
  "no repo" on one side only. That covers the agent moving `.git` away
  during the session.
- (c) A note with a status of its own that report does not count as
  incomplete. This changes report.py beyond "(ids)".

Reading I would build: (b). The literal text of the HANDOFF and the brief
is (a).

## Q-4 Which start and which close
- Claude Code writes a Stop at the end of every turn, so a session has
  many stop lines and at most one session_end. A resume, a /clear or a
  compaction writes another session_start.
- EDIT-NO-TEST makes every stop a deadline (G-10). Done that way here,
  turn-level judging fires on every turn whose edits are committed only
  in a later turn.

Options:
- (a) Session level. The start is the session's first session_start. The
  close is its last stop or session_end in the trace. The triggers are the
  edits between the two. One finding per session.
  - Edits after the last close are unknown ("no close came"), as G-10's
    partial.
  - In a live watch, a finding made at turn 1's stop vanishes when a later
    turn commits (E-3's vanishing; recorded).
- (b) Turn level: each stop is compared with the boundary line before it.
- (c) The close is session_end only. With none, the session is unknown, so
  a live watch is INCOMPLETE until the session ends.

Reading I would build: (a).

## Q-6 Which edits are triggers
- (a) Any ok post of Edit, Write, MultiEdit or NotebookEdit (the HANDOFF
  text). An edit of /tmp/x, ~/.claude/... or a file in another repository
  then makes a session fire that has nothing to commit in its own
  repository.
- (b) Only edits whose input_meta.path is under the line's own cwd:
  `not: {field: input_meta.path, outside: cwd}`, an op that exists today
  (engine.py:445-456). Edits elsewhere are not triggers, which is a listed
  hole.
- In both cases a .gitignored path (build output, .env) is an edit that is
  never committed by design. That is a false-positive source and is listed.
  An edit whose post never came is unknown (G-7), as in require.

Reading I would build: (b).

## Q-7 E1: the record and the closed set of git_error strings
The HANDOFF names three reasons (no repo, unreadable, budget). The brief
adds "index too large" and a reason for a symlinked `.git`. The prototype
needed three more. This is the shape I would build:

- **Keys.** `git_head`, `git_index_sha256` and `git_error` go on every
  hook session_start, stop and session_end line.
  - All three are always present: a value or null, and git_error is null
    when both values were read.
  - They come after `cwd` and before `source`, which stays last
    (ADR-0003). A line written before M5.2 is still a byte prefix of the
    new one, less its closing brace. The golden test (tests/test_proxy.py:348-367)
    gains the three keys on its three boundary lines only.
- **git_error.** It names the first failure in read order (.git, HEAD, the
  ref, the index). A value read before a later failure is kept, for
  example a git_head with "no index". The set:
  - "no repo": there is no cwd/.git.
  - "symlink": a symlink where a file or directory is read (Q-8).
  - "gitdir": a `.git` file that is not one `gitdir: <path>` line, whose
    target is not a directory, or (Q-8) whose target is a UNC or device
    path.
  - "unreadable": an OSError; a file that is not a regular file; a HEAD,
    `.git` file or ref over 4 KiB; a HEAD that is neither 40-hex nor
    `ref: refs/...`; a ref name with a `..`, `.lock` or a part that starts
    with `.`.
  - "no ref": the ref HEAD names is in neither a loose file nor
    packed-refs (an unborn branch, or a linked worktree, Q-9).
  - "no index": there is no `.git/index` yet.
  - "index too large": the index is over 64 MiB.
  - "budget": the 50 ms ran out.
- **Reads.**
  - lstat of cwd/.git.
  - A `.git` file (at most 4 KiB), followed once and relative to cwd. Its
    target must be a directory, not another file.
  - HEAD (at most 4 KiB).
  - One loose ref (at most 4 KiB), else packed-refs, read line by line
    until the ref is found or the budget runs out.
  - The index, read in 1 MiB chunks into sha256.
- **How files are opened.** Every file is opened with O_NONBLOCK (POSIX)
  and its fstat must say it is a regular file. So a FIFO planted as
  .git/index cannot hang the hook until the 8 s deadline. Nothing walks up
  from cwd.
- **When it runs.** git_state is called in prepare()
  (raqib/hooks/capture.py:221-229), before the lock, so neither the 5 s
  lock wait nor the 8 s deadline (:133-134) changes.

Is this set closed as the Table wants it? Should "no ref" and "no index"
stay apart from "unreadable"?

## Q-8 (security) A `.git` file can point the hook at a network path
- CLAUDE.md rule 5 says there are no network calls from the capture path.
- On Windows, a `.git` file reading `gitdir: \\host\share\x` (or
  `//host/share/x`) makes open() go over SMB. That is a network call, and
  the SMB handshake can also send the user's NTLM credentials to the host.
- The agent can write such a file at cwd/.git in a directory that is not a
  repository, or put one in place of a worktree's `.git` file. A symlinked
  HEAD, ref or index inside a real `.git` can do the same.

Reading I would build:
- A gitdir that is a UNC or device path (`\\`, `//`, `\\?\`, `\\.\`) is
  refused with "gitdir" and never opened.
- Every file the reader opens is lstat'ed first, and a symlink is refused
  ("symlink"). On POSIX the open also uses O_NOFOLLOW.
- Residual holes, listed: a gitdir on an automounted network path
  (/net/..., an NFS mount) cannot be told apart, and on Windows a link
  swapped in between the lstat and the open is not caught.
- A cwd that is itself on a share is the user's own choice and is not
  refused.

## Q-9 A fresh repository and a linked worktree
Measured with the prototype:
- `git init` with no commit gives git_head null ("no ref"), and there is
  no index until the first `git add`. So a session in a fresh repository
  that never commits or stages is unknown (partial), not a finding, and
  that is exactly the case the two anchors exist for.
- A linked worktree's `.git` file points to `<main>/.git/worktrees/<name>`.
  Its HEAD and index are there, but its refs are in the common dir named
  by `commondir` (`../..`), which E1's read list does not include. So its
  branch head is null ("no ref"). A detached HEAD in a worktree is read,
  and so is its index.
- A submodule's `.git` file (`gitdir: ../.git/modules/sub`) points to a
  full gitdir. It is read.

Options:
- (a) As written: null is unknown, and both cases are listed holes.
- (b) Compare git_error too: "no ref" at both ends with edits fires
  HEAD-UNMOVED, and "no index" at both ends fires INDEX-UNTOUCHED.
- (c) Read `commondir` (one more file), so a worktree's branch head is
  read.

Reading I would build: (a). (b) and (c) are the Table's call.

## Q-10 The budget
- Measured here: sha256 of 64 MiB in memory takes 43.9 ms (Python 3.13,
  with the CPU's SHA instructions). So the 64 MiB cap is barely reachable
  inside 50 ms on this machine and not at all on a slower one: a large
  index ends in "budget" before "index too large". A 30 000-entry index
  (2.1 MB) took 2.2 ms in all.
- The budget is checked between reads. A read that blocks (a hung network
  file system) is not interrupted. The 8 s deadline then ends the capture
  with RAQIB-SILENCE, and the boundary line is lost. That is an alarm
  (A3), but it is the boundary line.
- On Windows with Python 3.11 and 3.12 (the CI matrix,
  .github/workflows/gate.yml:26), time.monotonic ticks about every 15.6 ms,
  so the 50 ms is measured in steps of about 16 ms. time.perf_counter is
  also monotonic and finer there.

Reading I would build: one budget for the whole call, measured with
time.monotonic as the brief says. Values read before it ran out are kept.
The Windows tick is listed in the THREAT_MODEL.

## Q-11 INDEX-UNTOUCHED hashes bytes, and git rewrites the index without staging
Measured in a scratch repository:
- `touch a.txt; git status` changed the index's sha256 with nothing
  staged.
- `touch a.txt; git diff --quiet` changed it again.
- A `git status` after a content edit did not.

So any git command that refreshes stat data makes the index "touched",
whoever runs it. That is a miss, not a false positive.

Options:
- (a) Bytes, as the HANDOFF says, with this listed as a hole.
- (b) Hash only the entries (mode, object id, stage, path), parsed from
  index versions 2-4 (version 4 has prefix-compressed paths), skipping
  stat data and extensions. That is robust to refreshes but means more
  parsing in the hook.

Reading I would build: (a).

## Q-12 The two rules' shape
- **Overlap.** A session that neither staged nor committed fires both
  rules: two findings for one fact. The alternative is HEAD-UNMOVED only
  when the index moved (staged, never committed), so the two are disjoint.
  Reading: as written, both fire.
- **Class.** DRIFT, as H-7 accepted for the two demands. Severity medium
  (HANDOFF). fp_budget 0.1.
- **The benign corpus.** No benign file carries the keys, so under Q-3 (b)
  the measured negatives are the rules' own fixtures only.
- **The "unknown" fixture.** The fixtures key holds exactly positive and
  negative (engine.py:260-266). A negative the rule cannot judge counts as
  unmeasured (fixtures.py:80-88). Reading: the unknown fixtures live in
  tests/fixtures/rules/<ID>/unknown-*.json, outside the YAML. The tests
  assert them: no finding, and a partial note with its cause.
- **Holes I would list** (under Q-1 (a), Q-3 (b), Q-4 (a), Q-6 (b) and
  Q-9 (a)).

  HEAD-UNMOVED:
  - "the rule sees that the head moved, not why: an empty commit, a commit of other files, a checkout or switch, a reset, or a hash written into .git/HEAD or a ref all count as moved"
  - "only cwd/.git is read: a session started in a subdirectory, a second repository, a nested repository or a submodule edited from the parent's cwd is judged against the cwd's .git or not at all"
  - "GIT_DIR, GIT_WORK_TREE, git -C or --git-dir in the agent's commands act on another repository than the one the hook reads"
  - "a linked worktree on a branch: its refs are in the common dir, which is not read, so the head is null and the session unknown (partial)"
  - "an unborn branch (no commit yet) has no head: a session in a fresh repository is unknown (partial)"
  - "a symlinked .git, a gitdir on a network path, or a head not read within 50 ms is null: unknown (partial)"
  - "a session resumed after the human committed counts that commit as a move"
  - "edits outside the line's cwd are not triggers"
  - "a session with no stop or session_end after its last edit is unknown (partial); SILENCE-OPEN has the session"

  INDEX-UNTOUCHED: the same cwd/.git, GIT_DIR, symlink, budget, resume,
  cwd and no-close items, plus:
  - "the index is hashed as bytes: git status, git diff or any command that refreshes stat data rewrites it with nothing staged, and that counts as touched"
  - "staging any file counts, not the edited ones: git add of another file, git add -N, git update-index, git read-tree"
  - "a commit rewrites the index: a commit of other files counts as touched"
  - "an index over 64 MiB, or not hashed within 50 ms, is null: unknown (partial)"
  - "a repository with no index yet (nothing ever staged) is unknown (partial)"

## Q-13 common.py says it does no I/O
- common.py's docstring says "Pure: stdlib only, no I/O, no network,
  nothing is run" (raqib/hooks/common.py:21-24), and the proxy imports it.
  E1 puts git_state there.
- Reading: the docstring names git_state as the one function that reads
  files. Only capture.py calls it, on the three boundary lines. The proxy
  never does.
- A test asserts that no subprocess, os.system, os.popen, exec, fork or
  spawn, and no eval, can be reached from git_state. It does so by AST
  over its body and by monkeypatching them to fail during a call.
