# M0.2 — questions and readings taken

1. **Where the hash function comes from.** The handoff allows "no
   dependencies beyond node:crypto types", and M2.3 requires the same
   `shared/ledger.verify` and `shared/lottery.finalize` to run in the
   browser on Web Crypto. Reading taken: shared/ never imports node:crypto;
   every hashing function takes the hash as a parameter
   (`Sha256Hex` synchronous, `Sha256HexAsync` asynchronous), with sync and
   async variants (`verify`/`verifyAsync`, `finalize`/`finalizeAsync`,
   `commit`/`commitAsync`) sharing one implementation. The server passes
   node:crypto (synchronous, so `appendLedger` can hash inside one SQLite
   transaction); the browser passes `webSha256Hex`. A unit test proves both
   agree on the vectors and on random chains.

2. **"||" in the hash formula.** Read literally as string concatenation with
   no separator (ADR §2). Unambiguous because every field has a strict
   format that `preimage()` checks before hashing: seq a positive decimal
   integer, ts `YYYY-MM-DDTHH:mm:ss.sssZ`, actor `[A-Za-z0-9_-]{1,64}`,
   type `word.word`, payload a canonical JSON object, prev_hash 64 hex. An
   entry that breaks a format is reported as a `format` break, not hashed.

3. **Canonical JSON numbers.** Only safe integers are allowed (floats,
   NaN, Infinity, bigint, undefined, Date and other non-plain objects are
   refused). Money is integer minor units, so payloads never need a float,
   and integers serialize identically in every engine. Keys are sorted by
   UTF-16 code unit (the default JS sort; payload keys are ASCII).

4. **Lottery definitions made precise.** member-id order = ascending
   code-unit order; a secret = 32 bytes as 64 lowercase hex; the seed
   concatenates only the secrets of members who revealed, in member-id
   order, then the circle id; ties on SHA-256(seed || member_id) (a hash
   collision) fall back to member id; with no reveals at all the order is
   member-id order. Pinned by `tests/unit/lottery.vectors.json`, generated
   by `tests/unit/gen-vectors.mjs` from the written spec with node:crypto
   and none of the code under test. `tests/unit/ledger.vectors.json` does
   the same for the ledger hash (Arabic text, quotes, U+2028, nesting).

5. **Amount input form.** Documented in `parseAmount`: digits, optional
   "," grouping in threes (all or nothing), optional "." and at most
   minor-unit decimals. Arabic-Indic digits and the Arabic decimal (U+066B)
   and thousands (U+066C) separators are read as Latin, because phones with
   an Arabic keyboard type them; display is always Latin digits. Refused:
   signs, exponents, inner spaces, apostrophes, leading zeros ("012"), bare
   or trailing points (".5", "5."). Most restrictive reading on leading
   zeros and bare points.

6. **Bounds.** `MAX_AMOUNT` = 1e11 minor units per single amount and
   `MAX_MEMBERS` = 100, so the largest circle total (1e11 x 100 x 100 =
   1e15) is below `Number.MAX_SAFE_INTEGER`; sums are still accumulated in
   bigint and checked. Currencies are a closed list of ISO-4217 codes with
   minor unit 2 or 3 (ADR: "minor_unit (2 or 3)"); any other code is
   refused.

7. **Schedule.** monthly: round 1 is the first date on or after the start
   date whose day is due_day (1-28), then one month per round; weekly and
   biweekly: due_day is an ISO weekday (1 Monday - 7 Sunday), round 1 is
   the first such weekday on or after the start date, then 7 or 14 days
   per round. All arithmetic on integer day numbers, never on Date in a
   local time zone.

8. **Contribution state with partial payments.** The ADR names four states.
   Reading taken (A5, nothing assumed paid): `confirmed` when confirmed
   amounts reach the expected amount; `reported` when reported amounts
   reach it but confirmation is pending; otherwise `outstanding`, with the
   reported and confirmed partial amounts carried alongside; `waived`
   overrides. Over-payment beyond the expected amount is refused
   (`reportableAmount`).

9. **When members may join or leave.** Only in `draft`. Once a draw opens
   the member set is frozen (a join during commit-reveal would change the
   seed inputs); after start, departures are substitutions (a ledger
   entry type `member.substituted` is reserved; no route uses it in v0.1).
