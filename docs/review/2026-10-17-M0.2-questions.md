# M0.2 policies, decisions, periods - design questions

Readings taken by the builder where ADR-0001 section 5/7 or the handoff
left room. Each is the most conservative reading available.

1. **How `income` and `expense` measures are spelled.** ADR section 5 lists
   `income` and `expense` as measures but shows no YAML for them. Reading:
   `measure: {sum: income, period: P}` and `{sum: expense, period: P}` (the
   group alone sums all its categories); `sum: <group>.<category>` stays as
   shown. Any other spelling (`{income: true}`, a bare string) is `unknown`.
   Question: is this the public spelling?

2. **`measure.period` is mandatory on `sum`** (no default) and not allowed
   on holdings, share or drawdown measures, which are "as of" the date.
   Question: should a cap/floor default to `month` when period is absent?

3. **Limits per type.** cap and floor accept `{value}`, `{pct_of: income}`
   and `{months_of: expense}`; kill accepts only `{pct}`; allocation needs
   `band` with `0 <= min_pct <= max_pct <= 100`. Any other combination is
   `unknown`. `{pct}` on a cap is therefore `unknown`, not "15 absolute".

4. **`snapshot_max_age_days` is required** (positive integer); missing is a
   `MISSING-FIELD` problem, even for a household without holdings.
   Question: default, or keep required?

5. **`categories` must declare the groups `income` and `expense`** (the
   `pct_of`/`months_of` limits and the sign rule rest on them); other group
   names are allowed; a category name may appear under one group only.

6. **`version` must be `1`**; anything else is a problem.

7. **Unknown keys.** An unknown top-level key is a `BAD-FIELD` problem; an
   unknown key inside a policy (or a key foreign to its type) makes that
   policy `unknown`; an unknown key inside a decision is a problem that
   drops the decision.

8. **Undeclared names in a well-formed measure or match** (category, class,
   account) are both a file problem (`UNDECLARED-*`, class `invalid`) and an
   `unknown` policy. Shape errors (unknown type, measure or limit) are only
   `unknown`, never a file problem, as E1 asks.

9. **Numbers.** YAML floats are read from their text into Decimal (never a
   Python float); quoted decimal text is accepted; `true`, `.inf`, `.nan`
   are not numbers. YAML dates are also kept as text and judged by the
   strict `YYYY-MM-DD` rule (PyYAML would otherwise raise on `2026-13-01`
   and accept `2026-10-01 10:00:00`).

10. **Duplicate YAML keys reject the file** (`BAD-YAML` with the line):
    PyYAML would silently keep the last `limit:`.

11. **Decisions.** Top level must be a list; `id`, `date`, `review_by` and
    `status` are required; `title` and `criteria` default to empty text;
    `review_by` before `date` is a problem; `policy` and `closes` must name
    declared policy ids. Whether `closes` must name a `kill` policy is
    M1.2 E4 and is not checked here.

12. **`match.min_amount`** is stored as given; whether it compares against
    the signed amount or its magnitude is a rule question. Reading to be
    taken in M1.1: magnitude (`abs(amount) >= min_amount`), because
    routines and red lines on expense rows (negative amounts) would never
    match otherwise.

13. **`trailing(as_of, months)`** runs from the first day of the month
    `months - 1` months before as_of's month through as_of inclusive, so
    `trailing(2026-09-30, 12)` is `2025-10-01..2026-09-30` and a mid-month
    as_of never includes rows after it.
