MUST-FIX (direction: SILENCE)

R-1. A follow attached again loses the children the earlier follow knew. This is a regression; the docs do not say it.
- Where: os_sysmon.py:660, 667 (`bounded` is true whenever after_record is given; `tree = {}`); host.py:3153, 3176
  (`src.top = old.top`, `after_record=src.top`).
- What I read: before, a resumed follow read the whole channel, so _tree rebuilt the tree from every event 1, and
  after_record only filtered what got appended (build:278-283). Now the resumed follow asks `EventRecordID>top` and
  starts with an empty tree. A child's event 1 is at or below top, so the child never joins.
- Case: kimi's tree is attached as os. Follow 1 reads curl/ssh event 1 (record 602, started after the watch). The tree
  is gone in one round and back in the next (I-4 P5), and is attached again with after_record=603. The child's event 3
  at record 700 has a ProcessGuid that is not in by_guid, so it is dropped. A grandchild's event 1 names an unknown
  ParentProcessGuid, so the whole subtree is dropped.
- Result: every pass "reads", so AI-2 never fires and no host lines are written. Nothing is written about it. A watch
  without Sysmon would write HostChild/HostConnection lines for that tree, so this breaks AI-2's "never judged by
  less" and AI-1's "no event between two passes is lost".
- The builder raised this as question 2, but the GUIDE (103-104) and THREAT_MODEL (780-783) only say "a child that
  started before the watch".

R-2. When the GUID is given but the root is idle in the first window, the root's GUID is kept as given, compared
  exactly.
- Where: os_sysmon.py:271-274, then 335, 346, 349, 364.
- What I read: _root matches the GUID with _same_guid (ignores case and braces). The new branch (`found, root_guid =
  guid is not None, guid`) stores the GUID exactly as host.py gave it. host.py gives discover._guid_text's form,
  `{...}` lower case (host.py:3182, discover.py:1036). Everything after that compares by exact dict key or `==`.
- Case: Sysmon renders ProcessGuid in upper case (older Sysmon versions; I am not certain which versions do), and kimi
  (started before the watch) logs nothing in the first pass's window. Then tree["root_guid"] is the lower-case form
  for the rest of the follow. Every child event 1 (upper-case ParentProcessGuid) fails to join, and the root's own
  events 3/11 are dropped. Nothing is said and every pass counts as read.
- No test reaches this branch: the E1 roots are a bare pid, and the E2 trees appear to have no GUID.

R-3. Cleared channel or restarted record numbers: the follow reads nothing forever, silently, and AI-2 cannot take
  over. Pre-existing in the follow's filter, but AI-1 says "as the round's read does".
- Where: os_sysmon.py:674 and 686-688 (`EventRecordID>top`, no restart rule); host.py:3163-3165 (a pass with zero
  events counts as read). Compare Channel.restart at os_sysmon.py:915 and X-3(c).
- Case: an elevated agent runs `wevtutil cl` on the Sysmon channel, so records restart at 1 while top is about
  5,000,000. The round restarts after three silent rounds and writes its hole. Each follow keeps asking for records
  above about 5,000,000 and gets zero events, a successful read every pass. No hole, no AI-2, no host lines. Every act
  of every tree after the clear is judged by nothing, while the round's restart hole says the reading starts again.

SHOULD-FIX (direction: MORE SAID unless marked)

S-1. When AI-2 starts, host lines start from an empty children set: host.py:3225, 3236. _attach_os never copies
  `children` from an old host source (3140-3153).
- For a REREAD tree (M7.13 host-only, then os, then the follow fails twice), every child the earlier host source wrote
  is written again as HostChild and judged again.
- The same happens when an AI-2 os source then fails (failed_os goes to host, which copies children only from a host
  source, 3106).

S-2. When a pass reads after AI-2, its bound is "since the watch's start" (top is still None), so the acts already
  judged on host lines are judged again on os lines. Test E2-2 (test_host_follow_returns.py:316) pins both the host
  and the os NET-TOOL. THREAT_MODEL says this "two findings of the one act" only for the REREAD case, not for AI-2.

S-3 (SILENCE, latent). follow_kw (host.py:680-690) sniffs the follow's signature. A follow without a `since` parameter
  is silently given the whole-channel read (the bug M7.14 fixes) and never feeds AI-2, with no line. Production uses
  os_sysmon.follow, so this triggers only through os_follow.

S-4. The kept tree (by_guid, by_pid; os_sysmon.py:337-339) is never pruned for the life of a follow. It grows with
  every process of the tree. This is memory, not judgment.

S-5 (SILENCE, rare). While top is None, every pass asks TimeCreated>=since, with since taken at attach. If the wall
  clock steps back before the first pass that returns any event, passes return zero events "read" until the clock
  passes since. The round has Z-5/X-3(c) for this; the follow has nothing. This needs a channel with no event 1/3/11
  at all since the start.
