## 4. AZ-3 machinery (it can only fail towards SILENCE)
- **What it matches:** `(c.pid, c.started)` against the mark. The image is not compared. On Linux, act `started` comes
  from the snapshot (discover.py:2170, 1249), so None means the start was unread.
    - R4 case: a given child X with started None exits. Before the next sample its pid is reused by Y, whose start is
    also unread, and Y sits under another tree. Y's lines on that tree are suppressed.
    - Linux likelihood: very low. It needs pid wrap inside one round (sequential pids; pid_max 4194304 on most current
    systems, 32768 on older ones under heavy fork churn) and an unread start on both processes.
  - Windows likelihood: low. Pids are reused quickly, but same-user children's CreationTime is normally read.
- **When a mark is dropped:** at the top of each `_give_held`, when `processes` is a list and the pid is absent.
  - A round with no sample (None) prunes nothing.
  - A sample that is an empty list drops every mark. Every tree goes gone in that round too.
    - In the next round, a given child that still lives, whose held root has ended, is new on W. That is MORE SAID,
    and low.
    - A pid missing from one partial sample, with the held root still present, is given to the same tree again with a
    new mark. It is already in `kids` and `src.children`, so it is harmless.
- **Can a mark outlive its process and silence another?** Only through the started-None reuse above. Pruning is by
  pid, so a mark lingers while any process holds that pid. With starts read, the reused process does not match.
- **Only another tree?** Yes (`got[0] != key`), so the held tree's own later lines are not suppressed. But with
  first-giving-wins, a mark can point at a tree that never wrote the child. That is the R2 silence in section 5.
- **Sources touched:** only the sample's children are suppressed. `_source_beats` (os, hooks) is not filtered, and
  that is correct.
- **A fourth place:** `trees_of` still counts and cites the orphan in W's HostTree line (`acts`, `cites`,
  host.py:618-619). That is a count, not a finding, so it is MORE SAID and trivial.
    - Not affected: a candidate's first line (`_child_beats` filters before `first`), the suspect layer (META_KEYS
    whitelist, suspect/core.py:42), and footprints (by candidate id).
    - `last_inventory` (host.py:1985) keeps the original inventory, so the round's inventory still shows the child
    under W.
