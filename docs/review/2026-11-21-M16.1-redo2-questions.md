## Design questions

- **Q1. A number that is not finite, where.** The check is in the walk, so a `1e400` anywhere in the line is an
  error document - inside a part kept whole and under a key the spec does not know too, not only at
  `watch.beat` and `rule.fp_budget` where the Table measured the refusal. Is "wherever a number is checked" meant
  as everywhere? A key the spec does not know holding `1e400` was an event before (its value only in the line).
- **Q2. The reasons do not name where.** "a key longer than 256 characters" and "a number that is not finite"
  name no key: naming a key of 40000 characters in `error.message` would write the immense text the check keeps
  out. Should a reason name a path, cut?
- **Q3. A shipper's own `displaced`.** Where the step moves a field aside and a shipper's `displaced` is not an
  object, it is moved too, to `displaced.displaced` (the same rule, for the field the step writes); where it is an
  object, the moved fields are added to it. The ruling names seven fields, not this one.
- **Q4. A shipper's fields of another shape that the step does not move.** `message` that is not a text;
  `@timestamp` that is not a date (on an error document it is kept, `override: false`, and the engine may refuse
  it); a shipper's own `raqib` (replaced on an event, removed on an error document); `event.kind`,
  `error.message`, `event.original`, `event.ingested` that a shipper set (replaced). Not measured, not handled.
- **Q5. The words for a line that is not JSON.** They are the engine's json processor's own. A processor-level
  `on_failure` on the json processor that fails with "not an event: not JSON" would make them the pipeline's,
  but how each engine reports a failure inside an `on_failure` was not measured. Not built.
- **Q6. A real watch whose file gave no line.** X39 holds every line of the real watch's file to be an event;
  where no line of it was fed (the watch failed, or its file is missing), X39 is said n/a with the reason, not
  MISSED and not MET.
- **Q7. How much "not sure" makes X41 n/a.** One group not sure in one of the eight reads makes the whole row
  n/a, if nothing it could judge was wrong; a MISSED anywhere wins over n/a. The letter of R5, read so.
- **Q8. Duplicate keys.** An engine's json processor may refuse a line with a key twice (Elasticsearch 8's
  `allow_duplicate_keys` is false by default, believed); Python's reader takes the last. `check_of` does not
  mirror it; no such line is fed.
- **Q9. `NaN` and `Infinity` written as words.** Python's reader takes them; `check_of` calls them not JSON, as
  the engine's parser is believed to. Not fed.
- **Q10. The `event` text the rig feeds is 1501 units long** (a character outside the BMP at units 1024 and 1025),
  to measure the cut of SB-2 and the pair it must not split - more than the ruling's "a text". If an engine
  refuses it, X39 says so.
- **Q11. The order of the runs with no end, as ruled.** Past 10000 runs, after the runs that said an end, the runs
  with the oldest deadline are cut: the longest killed. The page gives the `composite` form to read them all.

## Choices the HANDOFF did not make

- `check_of` now gives the pipeline's words exactly ("not an event: ...", "not a raqib-event/1 event: ..."), so
  that the stand-in's error documents carry them; X39's table (`REASONS`) is written by hand beside it, and a test
  holds that each of the runner's words is a message the pipeline's text throws.
- A 256-character key the spec does not know is fed as an odd line (`a-256-key`) and must be an event (SB-1's
  MUST NOT TOUCH), its name listed.
- X41 counts `not-events.json` on the main index and on the index of odd lines.
- X40 holds each error document's `message` to be its line, and every shipper field as `shipped_of()` leaves it
  (`host.name` the shipper's on an error document, SB-3 Q2).
- A line that is not JSON sent with a shipper's fields carries its label (`{a line a shipper sent (LABEL)`), so
  that each is a document of its own to X39 and X40.
- `Lost` is an `OSError`: waiting for the engine takes it as not there yet. Any failure of the transport, not only
  an `OSError`, is a failed connection; any answer whose body is not JSON, whatever its status, is lost.
- The pipeline's `description` says what it sets, replaces, removes and moves aside.
- The GUIDE's pointer section names the error documents among the searches (R4 added a search).
