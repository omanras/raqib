### Questions (returned, not answered here)

- Q-7 (B-1, when the stop's words come). The words of a stop are held until the record is kept. A project
  watch's finish() takes milliseconds; a host watch's can wait up to SOURCE_JOIN_SECONDS (5 s) for its os sources
  and SUSPECT_JOIN_SECONDS (5 s) for a suspect call still out, so "stopped (Ctrl-C)" can come up to about 10 s
  later than before. A person who sees nothing may press Ctrl-C again, and a second Ctrl-C (unlike a second
  signal, which is counted) still raises KeyboardInterrupt inside conclude(), as it did before the REDO. Should
  the held stop say one word at once (a write before the record, which B-1 rules out), or should a second Ctrl-C
  be counted as a second signal is (a change to Ctrl-C, which decision 1 does not touch)?
- Q-8 (B-1, A3: the words lost are said nowhere). When the terminal is gone its words are dropped, and nothing in
  watch.json, the state or the registry row says that the final report was not seen. A hole would change the code
  (to 3), which B-1 rules out; a note would not. Should the watch keep a note of the first failed write (its time
  and OSError) in its state and its registry row?
- Q-9 (B-1, a write that blocks). Speech makes a write that fails harmless, and the hold puts the record before
  the stop's words; a write that blocks before the stop (a reader that stopped reading a full pipe, a terminal
  stopped with Ctrl-S) still holds the poll loop and so the stop. Outside B-1's cases (a hung-up tty, a closed
  pipe); recorded, not built.
- Q-10 (D6, the later signals). Stops.later (signals after the first, counted, never acted on) is still said
  nowhere; B-3 rules only the first lines. Should the final report or watch.json say it?

### Questions (returned, not answered here)

- Q-11 (C-3, what the record counts). The state's last write (finish) and the registry row (unregister) are kept
  before the final report is printed (C-1 keeps that order), so the note they carry counts the words lost up to
  then - "stopped (...)" and what conclude said - and not the final report's own write, which comes after. A
  terminal that is gone loses the report, and the record says some words were lost but not that the report was.
  Should the state be written once more after the final report (a write after the words, which nothing rules
  now), or is "lost since <time>" enough?
- Q-12 (C-3, where the project watch keeps it). The project watch's state had no notes field; the note is a new
  top-level "notes": [note], present only when a word was lost (so a watch that lost nothing has its state as
  before). The page and the band do not show it (raqib/ui.py is out of Scope). Is a key that appears only when
  needed what the Table wants, and should the page say it (M9.4)?
- Q-13 (C-3, what is counted). A write and a flush that raise each count one: a block-buffered pipe fails at the
  flush, not at the write, so "N writes" counts the calls that failed, not lines or bytes. Enough?
- Q-14 (C-5, the Windows words). The Windows line keeps the signal's name with the key, "Ctrl-C, SIGBREAK
  (Ctrl-Break) stop it ...", as B-3 built it, so the in-process B-3 test reads the same name on every platform. If
  the Table wants the key alone ("Ctrl-C, Ctrl-Break"), it is a one-line change in Stops.line.
