## Questions (returned, not answered here)

- Q-1 (E4, the keys built from the sentence). Two finding keys carry the summary text: watch.Watch.key (B-2:
  epoch, rule_id, session_id, cited_seq, summary; written as watch.json findings[].key) and host.py's source
  finding key (path, epoch, rule_id, session_id, cited_seq, summary; source_keys, and source_findings[].fkey).
  Not changed, as ordered. Within one watch the sentence of a cited line is deterministic, so each key is
  stable and findings dedupe as before (the tests above show the key equal but for that part); nothing reads a
  key back from an earlier run. But the value written for a DESTRUCT-CMD or NET-TOOL finding differs from the
  one 0e8b007 wrote. The three keys the ADR names - the act registry ((rule_id,) + the act's os events), the
  knock ledger's rate-limit ids and notify's folding (limit_id or event) - hold no sentence. Should a later task
  take the summary out of these two keys (B-2 relies on it to keep two findings of one cited seq apart)?
- Q-2 (E1, nohup). A stop signal whose disposition is SIG_IGN when the command starts (`nohup raqib watch &`,
  a supervisor that ignores SIGHUP) is left ignored, so a nohup'd watch still survives the hangup it was
  started to survive. The ADR did not say; the Table's ruling is asked.
- Q-3 (E4, which predicates name). {matched:...} names the values held by eq, in, has_any, regex, prefix and
  glob - not only the list predicates - so DESTRUCT-CMD's head pattern still names the program of a head-only
  line (command_unread, a pre-M4.2 line, `mkfs.<type>`); with lists only those lines would read "runs -".
- Q-4 (E1, when the stop is taken). A signal ends the wait between polls, not a poll in progress (Ctrl-C still
  interrupts anywhere, as before): the stop comes after at most one poll plus POLL_SECONDS (0.5 s). On Windows
  time.sleep wakes for Ctrl-C only, so Ctrl-Break is seen when the 0.5 s wait ends. A signal ends the host watch
  as Ctrl-C does - at once, not after the outstanding round's reader as the window's Stop does - so a host watch
  stopped while a reader is out reports it as a hole (INCOMPLETE, exit 3; seen once by hand on this Linux).
  Is that the ruling, or should a signal take the Stop's path there?
- Q-5 (E1, a closed terminal). On SIGHUP from a terminal that is gone, the final report is written to that
  terminal and may fail (EIO). The registry row is marked and watch.json written before the report is printed,
  so `raqib report <trace>` still gives the findings; whether the final report should also be written to a file
  is a later question.
- Q-6 (E5, the words). The ALARMS block counts an empty trace, lines that do not parse, findings and
  suspicions that cannot be cited or are malformed; the SILENCE-* rules are findings, below it. The line keeps
  the ADR's words ("A3 silence, A5 a record that cannot be cited"); "A3 an empty trace" would be narrower.
  host.py's own final report has an "ALARMS:" line of its own; decision 5 names the text report, so it is
  untouched.
