## 3. Silent assumptions, and what a rule should have caught (A3, A5)
- **A5, a claim nobody measured: "the record's own process id and user are the system's word"** (THREAT_MODEL.md:1318,
  FORWARD.md:331, from Y-6).
  - The Table measured the ProcessID only.
  - The forwarder passes lpUserSid NULL (forward.py:989). So Raqib's records likely carry no user (`<Security/>`).
  - When a writer does supply a SID, it is likely recorded as given, not checked. I hold that as likely, not certain.
  - A SOC told to ask the user will find nothing.
- **A5, the Windows reason is thrown away.** `use_last_error=True` (forward.py:959), but `ctypes.get_last_error()` is
  never read. `connect` and `write` therefore carry no Windows code and `status` is null. A SOC cannot tell a full
  log, access denied, a stopped EventLog service and an invalid parameter apart.
- **A5, docstrings say "as measured" for what the builder never ran.** EventLogApi says "with their ctypes signatures
  as measured" (forward.py:963-964). `eventlog_read` says "as measured" (forward_run.py:451-452). The questions file
  lists both as still to be checked in the field.
- **A3, nothing says what tells of a loss.** Y-4 says events are pushed out; the documents do not say what reveals it.
  For the journal, THREAT_MODEL.md:1308-1310 names the search for a missing heartbeat. For the event log it is silent.
  - The watched agent can push Raqib's events out on purpose, since any process writes to Application.
  - An administrator's agent can clear the log.
  - Neither is said.
- **A3, a hole is a Warning.** Y-2 rules that a hole is a Warning, not an Error. A3 says silence is of the highest
  class. This is the Table's ruling, recorded here only.
- **The pace's bursts.** A batch is written at full speed (up to 100 lines plus about 17 extra parts within 512 KiB),
  then its share is waited. FORWARD.md:318-319 says so. THREAT_MODEL.md:1323 says "at most 100 events a second"
  flatly.
- **The ctypes import.** `import ctypes` at module top (forward.py:128): a Python without _ctypes loses every
  destination, not just this one. Doubt.
- **The last-resort decode.** The decode branch (forward.py:528-532) can be reached only by a line that is not ASCII.
  Such a line is never an event (classify, :374), so the branch is unreachable today.

## 4. The Table's points 2 to 10

**2. ctypes (64-bit)**
- RegisterEventSourceW returns `c_void_p`, so a HANDLE is not truncated. A NULL handle becomes None, then `connect`
  (forward.py:984, :1014). Certain.
- ReportEventW's argtypes (:978-979) match `BOOL(HANDLE, WORD, WORD, DWORD, PSID, WORD, DWORD, LPCWSTR*, LPVOID)`.
  c_ulong is 32-bit on Windows, and BOOL as c_long is right. Certain.
- The array `(c_wchar_p*n)(*strings)` (:988) is accepted for `POINTER(c_wchar_p)` and stays alive in `texts` for the
  call. Certain.
- The SID and the raw data are NULL and the size is 0. Certain correct. The effect on the record's user is in section
  3.
- wType values 1, 2 and 4 are right. Certain.
- Ids 1000-1009 have zero upper bits (Qualifiers 0), and the viewer shows the low word. Likely fine.
  - Doubt for later: a message file compiled with severity bits would not match these ids.
- Every way out closes the handle (:1017-1029). Certain.
    - A raise of a type outside `failures` is closed too, then ends the run as `unforeseen` (:2202-2204), as for every
    transport.
- GetLastError is never read, on any thread. Certain.
- A plain user's process: doubt; only an administrator's was measured. The symptom would be `connect` or `write` with
  no reason.

**3. Y-3, the parts**
- The longest head is 233 characters: `raqib-part 18/18 id=` + 128 + ` sha256=` + 64 + ` chars=524287`. With a part of
  30000 that is 30233, under 32731. For a 512 KiB line N is at most 18.
- `EVENTLOG_HEAD_MAX` (:174) is never used. The 300 bound holds by this arithmetic only.
- 30000 is one event and 30001 is two (test :387).
- The id rule `[\x21-\x7e]{1,128}` (:183) cannot carry a space, so it cannot forge ` sha256=` or ` chars=`.
- A whole line is a JSON object with one string and id 1000-1008. So it can never be read as a head.
- No batch is taken with a part missing (:1018-1030).
- One forwarder never interleaves its own parts. Two forwarders writing at once do.
    - The documented rule ("put together in order; a part 1 begins anew", FORWARD.md:310-312) cannot rebuild either
    line then. The hash does catch it, so nothing false is taken as whole.
  - Another process's id-1009 events (Y-6) can break a set in the same way.
- **The reader's rule is not enough as written.** It does not say:
  - what bytes are hashed (the line's ASCII bytes, without its newline);
  - to group parts by the record's ProcessID;
  - that a set with no N/N is to be dropped;
  - that a set re-sent whole is a duplicate (at least once).

**4. Y-4 and the state machine**
- The pace is per batch and counted in events (:1559-1564).
- `--batch`, `--once` and small batches do not bypass it, and Stop ends the wait at once.
- During a wait the state is written once a beat with the cursor still before the batch. A kill there re-sends the
  batch.
- A line over 512 KiB is refused locally (:1669-1670). No eventlog test covers this (A7).
- Resuming with another destination is a usage error (:1451-1454).
- An older raqib reads an eventlog state as UNREADABLE (it fails toward the alarm). FORWARD.md:405 does not say this.
- What judge, `--status` and the Link screen say mentions no host, port, facility or framing. The exceptions are
  `stuck` (E1 above), `late`'s halving text "its bytes not written" (forward.py:1584-1586), and the restart message's
  "the collector gets lines twice" (:1854, which predates this task).

**5. Y-5, failures**
- connect, write with halving, and a raise all fail and pass nothing. All are tested.
- A send abandoned between two parts (Stop or the bound) leaves parts 1..k in the log while the cursor stays before
  the line. FORWARD.md:311-312 says this only "after a refusal"; Stop and the bound are not said.
- A retry writes the parts again from 1, and the rule handles that.
- Doubt (exotic): an abandoned send's thread blocked in ReportEventW for more than 30 s can land one event after a new
  send began. That would break the new set while the cursor passes the line as written.
