## 3. P-2 as built: can `written` still be said for lines the collector never read?
Yes, by three paths.

**a. tcp: the collector's end arrives before its reset.** This is Q2's residue, and it is wider than Q2 says.
- ended_first (forward.py:877-884) sees only an end already there at the peek.
- Any later end (FIN) stops the recv loop (:862-865) with b"". On Linux, recv reports the FIN before a reset that
  comes after it. The SO_ERROR look (:866) follows within microseconds.
- So this is not only "a collector that closed at once". A collector that dies, or closes between reads with an empty
  receive queue, while the batch's tail is still in flight sends FIN, then a reset for each later segment.
- Over a real path the reset trails the FIN by the gap between segments. sendall has long returned, since 512 KiB fits
  Linux's send buffer once it has grown.
- The batch is then `written`, and its tail was never read.
- On Windows I do not know whether SO_ERROR reports a reset that came after the end at all.
- Medium; from knowledge.

**b. tls: the collector's close comes before the forwarder's own.**
- The tls branch (:856-858) has no counterpart of ended_first.
- A collector that sends close_notify, or closes, before the batch reaches it satisfies unwrap. The forwarder sends
  its close, reads the earlier close_notify, then reads the FIN. The reset comes about one round trip later, after the
  SO_ERROR look.
- With TLS 1.2 this is the normal order for a server that closes once its handshake ends. tls_context (:336-348) does
  not raise the minimum version, so TLS 1.2 is allowed. The listeners in the tests force TLS 1.3 (:2339).
- On loopback the reset arrives during sendall, so no loopback test can show this case.
- Medium.

**c. tls: an end with no close_notify.**
- Q3 says such an end is a failed send. No test holds that.
- From knowledge:
    - CPython 3.10 and later set OP_IGNORE_UNEXPECTED_EOF on every SSLContext, and test_ssl's test_options expects it
    among the defaults.
  - tls_context does not clear it.
  - OpenSSL 3 then takes a TCP end as the peer's close_notify, so unwrap returns and the batch is `written`.
- If so, Q3, FORWARD.md:36-37, FORWARD.md:216 and THREAT_MODEL.md:1271 do not describe the code.
- Medium-high on the CPython default; medium on the OpenSSL path.

**Hangs and Stop: neither blocks the forwarder.**
- Inside the thread, the tcp recv loop can run past the bound: left() (:719-720) never goes below 1 ms, and a
  collector that keeps sending makes each recv return at once.
- carry (:1320-1334) gives up the send at the deadline, and on Stop within SLICE_S + JOIN_S.
- An abandoned send's result is never used (:1332-1334). That includes a `taken` reached after the shutdown, when recv
  returns b"" and SO_ERROR is 0.
- unwrap is bounded by Python's deadline for the call, set from left() at :857.
- On Linux, data that arrives after the shutdown in FIN_WAIT resets the socket, so the thread ends.
- On Windows I did not check whether a shutdown wakes a wait that uses select. If it does not, the thread lives until
  its own timeout and counts toward `stuck`. Stop is still not blocked.

## Verdict
REDO, narrow:
1. **A test for the tls end with no close_notify.** It shows what the forwarder does when a tls collector reads the
  whole batch and then ends TCP without close_notify (3c); it can be shown deterministically on loopback. Q3 and the
  documents then say what the test shows.
2. **The documents say the limit of `written` as built.** The places are FORWARD.md:34-39, FORWARD.md:216,
  THREAT_MODEL.md:1269-1275 and forward.py:17-19 and :91. The limit is that an end that arrives before the reset to a
  batch's unread tail is taken:
   - over tcp (3a);
   - over tls, where an end before the forwarder's own is not looked for at all (3b).
   Alternatively, the Table rules on Q2 and 3b first. 3a and 3b cannot be shown on loopback.
3. **Windows CI evidence on b0e19a2** for test_m103b_redo_e4_a_collector_that_never_reads_... and
  test_m103b_redo_e4_stop_during_a_blocked_write_... If either fails there, it is part of this REDO.
