## NEW FINDINGS: what root rights open

**G1. should-fix, must-fix-before-merge (service.py:754-766, 795-798)**
- **What is wrong.** With no unit file, remove decides on LoadState alone: `if props["LoadState"] != "not-found":`. A
  unit whose file was deleted, with systemd reloaded while its process runs, is LoadState=not-found and
  ActiveState=active. That is F16's case, which AC-10 closed for X30 by requiring ActiveState.
- **What follows.**
  - remove says "no unit installed ... nothing to stop or remove" and "RESULT: nothing installed", exit 0.
  - With `--purge` it removes /var/lib/raqib under a watch that is still writing there.
  - ActiveState is fetched at 754 but used only in the other branch's words.
    - These then say something false: docs/GUIDE.md:483 ("exit 0 where systemd knows no unit of the name"), cli.py's
    service text, and service.py:37-38.
  - status with no file prints NOT INSTALLED, exit 3 (795-798), without asking systemctl.
- **Who can bring it about.** Root.
- **What would close it.** In the no-file branch, treat any ActiveState other than inactive or failed as "systemd
  still has one": exit 1, nothing touched, no purge (as X30 does). Add a test with `LoadState=not-found,
  ActiveState=active`. Whether status should ask the same is the Table's call.

**G2. should-fix (service.py:543-548, 608-617, 822-825)**
- **What is wrong.** "As installed" means three things only: the first line is the mark, `FragmentPath == UNIT_PATH`,
  and DropInPaths is empty. The rest of the file is not compared with UNIT_TEXT. NeedDaemonReload is not read. The
  running process's start is not compared with the file.
- **What follows.** Each of these gives "RESULT: ACTIVE", exit 0:
    - a unit file changed in place with its first line kept. `systemctl edit --full` does this: it edits the file
    where it is and reloads. ExecStart, the hardening or the watch's arguments can change this way.
  - a file changed but not yet reloaded;
  - a watch still running an older text after `install --no-start`;
  - a foreign unit that carries the mark (F11, still open).
- **Who can bring it about.** Root. THREAT_MODEL.md:1534-1537 counts an agent with sudo or a polkit rule as root, and
  says such an agent "can stop it". A stop shows in status; a change does not (A3).
- **What would close it.** Status compares the whole file (bounded) with UNIT_TEXT for the interpreter its ExecStart
  names, and reads NeedDaemonReload. Or the docs say that "as installed" means where systemd loaded the unit from, and
  that root can change the unit or Raqib's code without status seeing it.

**G3. should-fix (service.py:678)**
- **What is wrong.** `calls = [["enable", UNIT_NAME], ["restart", UNIT_NAME]] if kind == "ours" else [["enable",
  "--now", UNIT_NAME]]`. `kind` is read from UNIT_PATH alone.
- **What follows.**
    - Suppose there is no file at UNIT_PATH, but a unit of the name is loaded and running from a place lower in
    systemd's search order (/run/systemd/system, /usr/local/lib/systemd/system, /usr/lib/systemd/system).
    - The install writes the file and reloads, so /etc becomes the fragment. `enable --now` then starts nothing,
    because the unit is already active.
    - After 3 s: "RESULT: installed, enabled, active 3 s after its start", exit 0, and status says ACTIVE, exit 0.
    Both are false: the process running is the other unit's command.
  - The install also overrides a unit of that name it never read. A-4's "not touched" is held only for UNIT_PATH.
  - A later remove brings that unit back and asks nothing after removing the file.
- **Who can bring it about.** Root, or polkit.
- **What would close it.** Before writing, ask LoadState, ActiveState and FragmentPath as remove does, and refuse
  where a unit of the name is loaded from another file. Or restart in every case.

**G4. should-fix, Table's ruling (service.py:693-698, 477-480; held by test_service.py:555)**
- **What is wrong.** An install that finds the unit active but not as installed prints "NOT AS INSTALLED ... (raqib
  service status says it, exit 1)", then "RESULT: installed, enabled, active 3 s after its start", and exits 0. The
  test holds this: `assert code == 0 and "NOT AS INSTALLED: drop-ins change the unit: /run/x.conf" in out`. Status
  gives exit 1 for the same state.
- **What follows.**
  - The RESULT line, which is what a script reads, says installed.
  - The check runs after the start, so a drop-in that changes ExecStart has already run as root.
    - Because the unit's folder is checked only as itself, no drop-in folder that applies to this unit is checked for
    ownership: raqib-watch.service.d, raqib-.service.d or service.d, under /etc/systemd/system, /run/systemd/system,
    system.control or /usr/lib/systemd/system.
- **Who can bring it about.** Root, unless root left such a folder writable.
- **What would close it.** Read FragmentPath and DropInPaths after daemon-reload and before enable or restart. If the
  unit is not as installed, do not start it, exit non-zero, and say so in the RESULT. Walk the drop-in folders,
  checking the folders above any that are missing.

**G5. should-fix (service.py:629-638; SERVICE.md:124; ADR AC-3)**
- **What is wrong.** "The unit's `-I` only takes entries away" is true only where the install's environment holds no
  PYTHONHOME or PYTHONPLATLIBDIR.
- **What follows.**
    - Those variables move the install's standard library. The unit's interpreter ignores them and loads the stdlib of
    its own prefix. So the install walks a stdlib the unit does not load, and not the one it does.
  - The check reads `sys.flags.no_site` only.
    - An `import` line of a root-owned `.pth` runs in the unit's environment, not the install's. It may add paths from
    the environment, or install a finder (setuptools' editable finders map names to folders that are not sys.path
    entries). The walk does not reach those paths.
- **Who can bring it about.** The administrator's environment. sudo resets it by default; `-E` or env_keep keeps it. A
  user without rights cannot.
- **What would close it.** Refuse where `not sys.flags.ignore_environment` and either variable is set, or require the
  install to run with `-I` or `-E` (the rig already uses `-I`). SERVICE.md should also say what `.pth` import lines
  may reach.

**G6. note, doc (service.py:310-313; SERVICE.md:145-147)**
- **What is wrong.** SERVICE.md says a missing path "is checked as far as it exists: the folders above it, so that no
  user can make it later".
- **What follows.** The system makes paths for a user below root's folders without the user writing there:
  - logind makes /run/user/UID at login;
  - udisks makes /media/USER/LABEL or /run/media/USER/... when the active user mounts a medium;
  - useradd makes /home/NAME.
    On a medium the user brings, the owner a file shows (uid 0 included) is the medium's word. A sys.path entry, a
    `.pth` line or a link's end that names such a place passes while it is missing, and is the user's later.
- **Who can bring it about.** Only after root has put such a place on the interpreter's path.
- **What would close it.** Refuse paths under the places the system makes for users, or say it.

**G7. note (service.py:403-411, 206-217)**
- **What is wrong.** `pth_entries` follows CPython 3.13's site (bytes decoded as utf-8-sig, `str.splitlines()`).
  CPython 3.12's site, which is what Ubuntu 24.04 (the rig's machine) has, decodes with the locale's encoding and
  splits only at \n, \r and \r\n.
- **What follows.** A root-written line holding \x0b, \x0c, \x1c-\x1e, \x85, (U+2028) or (U+2029) is one path for
  3.12's site and several here. Where ".." follows such a character, site's path lands above the site folder, outside
  every walk.
- **Not verified.** This is from reading site.py; I have not checked it on the target.
- **What would close it.** Below 3.13, split the way io's universal newlines do, or refuse a `.pth` holding any of
  those characters.

**G8. note (service.py:414-416, 633-634)**
- **What is wrong.** `_inside` accepts a raqib package anywhere below a site folder, for example a vendored copy, not
  only one directly in it. The unit's `-m raqib` imports the first top-level raqib on its path.
- **What follows.** That code is still root's, since it sits under the walked site folder. But the unit may run a
  different raqib from the one that checked and wrote it, and that is caught only if it fails within 3 s.
- **What would close it.** Require `posixpath.dirname(pkg)` to be one of the site folders.

**G9. note, Table (host.py:1928-1931, 2622)**
- **What is wrong.** The unit's watch prints its `FINDING [...] RULE round N: summary (notice)` lines and its holes to
  stdout, which goes to the journal.
- **What follows.**
    - Root and the journal's groups read the journal: adm on Debian and Ubuntu, where the first user is commonly a
    member; systemd-journal; wheel on some systems.
  - SERVICE.md:101-102 and THREAT_MODEL.md:1565-1567 say who reads the journal, not what the lines carry.
    - AC-1's FOR ("no person and no agent without rights reads what root's watch sees") holds for the port, not for
    the journal.
- **Not verified.** Which fields of other users' processes those lines carry.

## NEW FINDINGS: the rest

**G10. note: what follows from "failed" after remove.**
- The watch's exit 1 at a stop after a finding leaves the unit in memory as LoadState=not-found, ActiveState=failed
  (X30's fact). It stays until reset-failed or a reboot.
- Meanwhile `systemctl --failed` lists it and `systemctl is-system-running` says "degraded"; remove says "RESULT:
  removed" and nothing of this.
- Every stop and every shutdown after a finding records the unit as failed. "Failed" is therefore this unit's ordinary
  end and no longer tells a crash from a stop.
- A monitor that alerts on failed units will fire on every stop, which teaches people to ignore the alarm a crash
  would raise (A3).
- It does not break a second remove (not-found gives exit 0) or a re-install.
- Whether remove should run `systemctl reset-failed` is a question below.

**G11. note, rig (service_run.py:67, 166-170; check.py:679-684; SERVICE.md:200-203)**
- **What is wrong.** X29 sees an ignored directive only where the manager writes a warning that names the unit, at the
  default log level, using one of the matched words.
- **What follows.**
  - As I read systemd (not verified): with no seccomp, the filters are skipped with a debug-level line.
    - With no BPF firewalling, the IPAddressDeny warning reads "does not support BPF/cgroup firewalling".
    `JOURNAL_WORDS` matches "not supported", not "not support". That warning is also shown only for the first unit of
    the boot that uses it.
  - `systemctl show` gives the directives as configured, not as enforced.
    - So X29 MET means configured and not warned of; it does not mean in force. SERVICE.md's "the rig says it" claims
    more than that.
- **What would close it.** Add "not support" to the words, and measure enforcement directly: an AF_INET socket refused
  inside the unit, and the main process's CapEff.

**G12. note, words (service.py:500, 679-680)**

- "Raqib's own unit was there: it is restarted, so no watch keeps the old text" is printed before `enable` and

**G14. note, test (test_service.py:761).** The final "never not run" loop checks the install's timeout output and an
