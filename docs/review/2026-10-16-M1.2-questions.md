# M1.2 rule set v1: questions for the commander

M1.2 exit criteria E1-E4 are met and `tools/gate.sh` is green. The HANDOFF was
drafted by the builder (`docs/handoffs/M1.2.md`) under the commander's order.
Nine mutants (secret capture, DRIFT-FILES, SECRET-OUTPUT) were each killed by
the tests. One of them, unsorted kinds, needed a stronger test first: it
survived until a test used all seven kinds at once.

## What shipped

- **Capture** adds `output_meta` to every post line. It is `{}`, or
  `{"secret_kinds": [...]}` with the sorted names of the secret patterns that
  matched any string in the output: tool_response, or the error of a
  PostToolUseFailure, keys included. The pattern names are aws_access_key_id,
  github_token, google_api_key, jwt, private_key, sk_api_key and slack_token.
  The matched text is never stored (A-5). Tests assemble the fake keys at run
  time, so the gate's secret scan stays green.
- **SECRET-OUTPUT** (class SECRET, severity high, budget 0.05) fires on a post
  whose `output_meta.secret_kinds` is non-empty. It is tested end to end:
  capture.py on a hook input holding a key, then trace.read, then the
  engine.
- **DRIFT-FILES** (class DRIFT, severity medium, budget 0.1) fires when one
  session edits (Write, Edit, MultiEdit, NotebookEdit) more than 2 distinct
  files outside context `scope`. Without a scope it is not evaluated, and
  the engine leaves a note saying so.
- **Benign corpus** gains a scoped session, so DRIFT-FILES is measured with
  a scope in place. Measured rates: DESTRUCT-CMD and NET-TOOL 1/7 = 0.143,
  the others 0.

## Open questions (not answered)

- **Q1 Secrets in tool input are not flagged.** The plan names
  secret-in-output. A secret the agent writes into a file or passes on a
  command line (in `tool_input`) is not flagged. Should capture also record
  `input_meta.secret_kinds`, with a SECRET-INPUT rule?
- **Q2 The pattern list is fixed in capture.py.** Adding a pattern changes
  what capture records, and old traces cannot be rescanned because the text
  was never stored. Should the list be versioned, for example with a
  `secret_patterns: v1` field on post lines?
- **Q3 Where the scope comes from.** It has to reach the engine as context.
  M1.3 will read it from a `--scope PATH` option, or from the `Scope:` block
  of a HANDOFF.md as `.claude/hooks/scope-guard.sh` does. Is the HANDOFF
  format the intended source for watched projects that are not Raqib?
- **Q4 DRIFT-FILES threshold.** It is "more than 2", the N of the plan's ">N
  files". Is N=2 right?

## Assumptions made (confirm or overrule)

- **output_meta on every post line**, `{}` when nothing matched, so a missing
  output_meta means "captured before M1.2", not "clean".
- **Scope entries are paths, not string prefixes.** `src` covers `src/a.py`
  but not `src2/a.py` or `srcfile.py`. They are relative to the line's cwd.
- **Distinct files** are counted by the exact `input_meta.path` string after
  capture. `README.md` and `/work/p/README.md` would count twice; Claude Code
  sends absolute paths for Edit and Write.

## REDO: builder's response to docs/review/2026-10-16-M1.2.md

The M1.1 REDO commit already fixed the engine side of this packet:
- **F13:** a post without output_meta, or without secret_kinds, is "unknown"
  to SECRET-OUTPUT and gives a `partial` note.
- **F14:** a missing or unusable scope is reported (`not-evaluated`,
  `bad-context`), and the runner counts such files as unmeasured, not clean.
- **F16:** relative scope entries are anchored to context `root`.
- **F18:** DRIFT-FILES counts placed, normalised paths (`as: path`); a
  leading `//` collapses.
- **F19:** DRIFT-FILES counts completed edits only (post, ok true).
- **F27:** fixtures are generated (`tests/fixtures/rules/generate.py`). Each
  output has its own hash, and the failure fixture carries error_class.

**Fixed in this commit** (`landed: M1.2 REDO`)

- **F1 [SECRET]:** command_head reads words with shell quoting.
  - `AUTH="Bearer <token>" gh api` gives `gh`, and `"rm"` and `\rm` give `rm`.
  - The head is left out, so rules see "unknown", when it cannot be read
    safely: unbalanced quotes, a word glued to an operator or substitution
    (`ls;rm`, `$(x)`, `(rm`), a name outside `[A-Za-z0-9_.+[-]` or over 64
    characters (no longer truncated), a name that matches a secret pattern,
    or a 16+ character name that mixes digits and both cases.
  - Only the first 64 KiB of a command is read. A word that reaches that
    limit is never used.
- **F4:** `error` is scanned as well as `tool_response` when both are
  present. The hash is unchanged (tool_response if present).
- **F5, new kinds:** auth_header (Bearer/Basic/token), aws_secret_access_key
  (with its key name), GitHub fine-grained PATs, gitlab_token,
  huggingface_token, npm_token, pypi_token, slack `xoxe-`, slack_webhook,
  stripe_key (`sk_live_`/`rk_live_`) and url_credentials (`user:pass@`).
- **F5, changed kinds:** PGP `PRIVATE KEY BLOCK` is now matched. An AWS key
  ID right after a word character (`%3D`) is matched too, because the left
  `\b` is gone.
- **F6:** a match is a placeholder, and is not counted, when its secret part
  meets any of these:
  - it contains a marker (EXAMPLE, XXXX, your, placeholder, dummy, sample,
    redacted, changeme, password, secret, fake, test, `${`, `{{`, `***`,
    `...`), all-lower or all-upper;
  - it has fewer than 8 distinct characters;
  - it is an `sk-` key that does not mix digits and both cases (kebab-case
    names);
  - it is the jwt.io sample token, found by decoding its payload;
  - for a PEM header, no key material (40 base64 characters) follows.
  Placeholder-only kinds are recorded as `output_meta.placeholder_kinds`, so
  the suppression is visible.
- **F8 [SILENCE]:** the jwt pattern starts only where no token character
  precedes it, so starts cannot overlap. Every pattern is linear by
  construction. Six adversarial 240 KB+ inputs are tested to scan in under
  2 s. The old pattern took about 0.2 s on 24 KB, which is quadratic.
- **F9 [SILENCE]:** hashing, input_meta and the output scan run before the
  log lock (tested by call order). Only the log read, seq, ts and the write
  happen under the lock, so lines are still written in ts order.
- **F10:** at most 1 MiB of output is scanned per post. A larger output gives
  `scan: "partial"`, and secret_kinds is present only if something matched,
  so a partial scan never reads as clean. Measured ad hoc on this machine
  (not in git): 0.2-0.36 s per MiB.
- **F12:** `output_meta.scan` is `full`, `partial` or `none` (neither
  tool_response nor error). A fully scanned post always has secret_kinds,
  `[]` included, as E2 says literally.
- **F22, F24:** test ids are kind names, never secret-shaped strings. All
  fakes are assembled at run time and look random (fixed seed), because
  uniform fakes now read as placeholders.
- **M0.3 B4 [SILENCE]:** waiting for the lock is capped at 5 s. The whole
  capture is capped at 8 s by SIGALRM (Linux/macOS, A-6), below the installed
  10 s hook timeout. Either cap ends in one RAQIB-SILENCE line, not a kill.
- **M0.3 M2:** the directory is fsync'd after the rename (not testable here),
  and a new settings file follows the umask.
- **M0.3 M3:** legacy entries are recognised by shell words, so quoted paths
  and a quoted RAQIB_LOG are replaced. Lookalikes stay foreign: an extra
  argument, another file, or an unbalanced quote.
- **M0.3 M4 residuals:** existing entries that disagree on RAQIB_LOG make the
  installer exit 1 with nothing changed (`--log` chooses). A kept relative
  RAQIB_LOG is made absolute against the project.
- **Suspicion prompt:** it now describes `scan` and `placeholder_kinds`.
- **Mutants:** 24 were run ad hoc in scratch copies and all were killed
  (jwt start, AWS lookahead, scan budget, partial key, distinct/mixed/jwt
  placeholder checks, error scanning, head cut at the limit, key-like
  heads, LOCK_NB, scan-before-lock, deadline, secret_part, PEM body, and the
  installer's shlex/disagree/absolute/umask/arity). The harness is not in git.

**Open questions (not answered)**

- **Q5 command_head now differs from the letter of A-1.**
  - A-1 says "first whitespace-separated token ... at most 64 chars".
  - Capture now follows shell quoting, and leaves the head out instead of
    truncating it or keeping a fragment.
  - Wrappers (`sudo`, `env`, `timeout`, `xargs`, `bash -c`) and compound
    commands (`cd x && rm`) still hide the real program (M1.1 3h-7).
  - Should A-1 be amended?
- **Q6 output_meta needs an ADR amendment (F25).** The fields are `scan`,
  `secret_kinds` and `placeholder_kinds`, and the meaning of a missing
  secret_kinds is fixed above.
- **Q7 The judge's "class SECRET -> STOP" (F21).**
  - SECRET-OUTPUT is an engine finding class, and the gate produces such
    findings from its own positive fixtures.
  - Should the judge rule name secrets found in the tree or packet, not
    engine finding classes?
- **Q8 Detection lives in capture, not the catalog (F26).** Pattern and
  placeholder changes alter what capture records, with no A6 signal. Q2's
  pattern-list version would at least mark old traces.

- **F7:** Write and Edit outputs are still scanned in full. Evidence from a

- **F15:** file changes made through Bash or MCP tools are not counted by

- **F23:** `tools/gate.sh` checks fewer secret shapes than capture does. It
