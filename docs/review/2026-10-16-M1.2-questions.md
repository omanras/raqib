# M1.2 rule set v1: questions for the commander

M1.2 exit criteria E1-E4 are met and `tools/gate.sh` is green. The HANDOFF was
drafted by the builder (`docs/handoffs/M1.2.md`) under the commander's order.
Nine mutants (secret capture, DRIFT-FILES, SECRET-OUTPUT) were each killed by
the tests. One of them, unsorted kinds, needed a stronger test first: it
survived until a test used all seven kinds at once.

## What shipped

- **Capture** adds `output_meta` to every post line. It is `{}`, or
  `{"secret_kinds": [...]}` with the sorted names of the secret patterns that
  matched any string in the output: tool_response, or the error of a
  PostToolUseFailure, keys included. The pattern names are aws_access_key_id,
  github_token, google_api_key, jwt, private_key, sk_api_key and slack_token.
  The matched text is never stored (A-5). Tests assemble the fake keys at run
  time, so the gate's secret scan stays green.
- **SECRET-OUTPUT** (class SECRET, severity high, budget 0.05) fires on a post
  whose `output_meta.secret_kinds` is non-empty. It is tested end to end:
  capture.py on a hook input holding a key, then trace.read, then the
  engine.
- **DRIFT-FILES** (class DRIFT, severity medium, budget 0.1) fires when one
  session edits (Write, Edit, MultiEdit, NotebookEdit) more than 2 distinct
  files outside context `scope`. Without a scope it is not evaluated, and
  the engine leaves a note saying so.
- **Benign corpus** gains a scoped session, so DRIFT-FILES is measured with
  a scope in place. Measured rates: DESTRUCT-CMD and NET-TOOL 1/7 = 0.143,
  the others 0.

## Open questions (not answered)

- **Q1 Secrets in tool input are not flagged.** The plan names
  secret-in-output. A secret the agent writes into a file or passes on a
  command line (in `tool_input`) is not flagged. Should capture also record
  `input_meta.secret_kinds`, with a SECRET-INPUT rule?
- **Q2 The pattern list is fixed in capture.py.** Adding a pattern changes
  what capture records, and old traces cannot be rescanned because the text
  was never stored. Should the list be versioned, for example with a
  `secret_patterns: v1` field on post lines?
- **Q3 Where the scope comes from.** It has to reach the engine as context.
  M1.3 will read it from a `--scope PATH` option, or from the `Scope:` block
  of a HANDOFF.md as `.claude/hooks/scope-guard.sh` does. Is the HANDOFF
  format the intended source for watched projects that are not Raqib?
- **Q4 DRIFT-FILES threshold.** It is "more than 2", the N of the plan's ">N
  files". Is N=2 right?

## Assumptions made (confirm or overrule)

- **output_meta on every post line**, `{}` when nothing matched, so a missing
  output_meta means "captured before M1.2", not "clean".
- **Scope entries are paths, not string prefixes.** `src` covers `src/a.py`
  but not `src2/a.py` or `srcfile.py`. They are relative to the line's cwd.
- **Distinct files** are counted by the exact `input_meta.path` string after
  capture. `README.md` and `/work/p/README.md` would count twice; Claude Code
  sends absolute paths for Edit and Write.
