# M0.1 ledger and holdings loaders - design questions

Readings taken by the builder where the handoff or ADR-0001 left room.
Each is the most conservative reading available; none is answered here.

1. **Header mismatch.** A file whose header is not byte-exact yields zero
   rows and one `BAD-HEADER` problem at line 1. The alternative, mapping
   columns by name, is a silent guess about what the file means.
   Question: is "no rows at all" the intended behaviour, or should the run
   continue with every row `invalid`?

2. **Invalid rows and their period.** A row with any problem is excluded
   from `rows`; each problem carries `date` (ISO text) when the date field
   parsed, so M1.1 can mark that period `unknown` (ADR section 3). A row
   whose date did not parse (bad date, wrong column count, bad encoding,
   too long) carries no date. Question for M1.1: does a dateless invalid
   row make every ledger-based policy `unknown`? The conservative reading
   is yes; the builder will take it in M1.1 unless told otherwise.

3. **Holdings `quantity` is mandatory** decimal text, also for cash rows
   where quantity has no natural meaning; an empty field is `BAD-QUANTITY`.
   Question: should quantity be optional (empty) for class `cash`?

4. **No whitespace tolerance.** Fields are not stripped: ` 5` is
   `BAD-AMOUNT`, `a; b` is `BAD-TAGS`, `Salary` is `UNKNOWN-ACCOUNT`.
   Question: tolerate surrounding whitespace, or keep strict?

5. **Blank lines are `EMPTY-LINE`, class `invalid`** (except the newline
   that ends the file). Question: ignore, warn, or invalid?

6. **Currency is checked by shape only** (three uppercase ASCII letters),
   not against an ISO-4217 list, which would need a table to maintain.

7. **Problem vocabulary.** Problems carry `code` (e.g. `BAD-DATE`,
   `UNKNOWN-ACCOUNT`, `COLUMN-COUNT`, `DUP-ROW`, `FILE-MISSING`) and
   `class` (`invalid` or `warn`); ADR-0001 names only `DUP-ROW` and
   `invalid`. Question: are these codes acceptable as the public vocabulary
   that `--json` will print?

8. **DUP-ROW compares the raw text of the seven fields**, so `1.0` and
   `1.00` are different rows. Two holdings rows with the same date, account
   and asset but different values are not flagged; later layers will add
   them as two lots. Question: should a same-asset conflict within one
   snapshot be a finding of its own?

9. **Limits are inclusive:** a line of exactly 1 MiB and a file of exactly
   64 MiB are problems (`LINE-TOO-LONG`, `FILE-TOO-LARGE`); the file size
   is checked with `stat` before anything is read.

10. **Citations use the file's basename** (`ledger.csv:17`), not the path
    as given, since all files live in one directory (`--dir`).
