# M0.1 loader — design questions (returned, not answered locally)

Each question names the reading the builder took. Every reading is the
most conservative one available: when in doubt the file is `invalid`
(red), never silently accepted (A4: nothing is green by default). The
commander may relax any of them; each is one guard in `mizan/loader.py`
with its own fixture and test.

## Q1. `detection.condition` given as a YAML list
Sigma historically allowed `condition` to be a list of strings (OR of
conditions); the current specification deprecates it. ADR-0001 E1 says
`condition (str)`.
Reading taken: a list condition is a problem on `detection.condition`
("must be a non-empty string (a list of conditions is not supported)").
Fixture: `condition_list.yml`.

## Q2. Which UUID spellings are accepted for `id`
`uuid.UUID()` also accepts 32 hex digits without hyphens, braces and the
`urn:uuid:` prefix.
Reading taken: only the canonical 8-4-4-4-12 hyphenated form; anything
else is invalid. Fixture: `compact_id.yml`.

## Q3. Duplicate YAML keys
PyYAML keeps the last duplicate silently, so a rule with two `condition`
keys would be judged on one of them without notice.
Reading taken: a strict SafeLoader subclass refuses duplicate keys in any
mapping; the file is invalid ("not valid YAML ... duplicate key").
Fixture: `duplicate_key.yml`.

## Q4. Size limit on rule files
A7 names limits for fixtures and corpora only; ADR section 4 gives 1 MiB
per line / 256 MiB per file for events.
Reading taken: a rule file larger than 1 MiB is invalid (problem on
`file`). Tested with a generated file, not a committed one.

## Q5. Unknown keys under `x-mizan`
ADR section 3 says unknown *Sigma* fields are kept and ignored; it does not
say what happens to unknown keys inside Mizan's own `x-mizan` mapping.
Reading taken: `x-mizan` is Mizan's namespace, so an unknown key there is
most likely a misspelling (`fp_budjet`) and is a problem. Unknown
top-level fields stay accepted as the ADR says. Fixture:
`xmizan_unknown_key.yml`.

## Q6. Shape of `x-mizan.corpus`
Reading taken: when present it must be a non-empty list of non-empty
strings; an empty list is a problem rather than "no corpus" (which would
turn into `no_corpus` only at M1.2 and hide the author's intent).
Fixtures: `corpus_not_list.yml`, `corpus_empty_list.yml`,
`corpus_bad_entry.yml`.

## Q7. `detection` with a condition but no search identifier
Reading taken: a problem on `detection` ("needs at least one search
identifier besides condition"); search identifiers must be non-empty
strings. Fixtures: `detection_no_selection.yml`,
`detection_bad_identifier.yml`. (The Sigma specification requires at
least one search identifier.)

## Q8. `logsource` values
Reading taken: each of `product`, `category`, `service` that is present
must be a non-empty string; other keys (`definition`) are kept.
Fixture: `logsource_bad_value.yml`.

## Q9. `level` case
Reading taken: exact lowercase match against the five levels; `High` is
invalid. Fixture: `level_wrong_case.yml`.

## Q10. `fp_budget` typing
Reading taken: booleans, NaN and infinities are not numbers; integers are
accepted and returned as `float`. Fixtures: `fp_budget_bool.yml`,
`fp_budget_nan.yml`.

## Q11. Encoding
Reading taken: files are decoded as UTF-8; a UTF-8 byte-order mark is
tolerated (it is produced by common Windows editors and changes no
content); any other invalid byte sequence is a problem on `file`. Both
cases are tested with generated files so the tree stays ASCII-safe.

## Not a question, for the record
- `mizan/__main__.py` is a stub that exits 2 ("no commands available
  yet") until `mizan/cli.py` lands in M1.1; the gate's self-check is
  conditioned on `cli.py`, so it is unaffected.
- `Rule.selections` (detection minus `condition`) is a convenience
  property added for M0.3/M1.1; it adds no behaviour to the loader.
