## 4. Identity (C-1): is every `about` stable for the life of a run?
- **findings: stable.** Only appended (host.py:2237), assigned once (:1531); entries change in place, which is a rev.
- **source findings: stable within a run.** Only appended (:3655); a grown finding is updated in place (:3625-3634),
  which is a rev.
- **holes: NOT stable.**
    - `state()["holes"]` is `self.holes + self.notifier.holes` (host.py:4374), and the report prints them in the same
    order (:4293).
  - The notifier appends its holes during the run (notify.py:444) and merges repeats in place (:439-443).
    - Case: a failed knock at round 2 gives hole:1 = notify-failed. A reader-late at round 5, or reader-out or
    source-out at Stop (host.py:3892,3946), makes hole:1 = reader-late and hole:2 = notify-failed. The entry's `about`
    moves and the old one is reused.
    - Likelihood: medium. It needs a notifier that fails (for example, no desktop notifier on the host) and any later
    watch hole.
- **blind spots: stable.** Only appended (:2522); rounds grow in place (:2518), but nothing in the event changes, so a
  writer cannot see the change.
- **notes: NOT stable for the last entry.**
    - `state()["host"]["notes"]` is `all_notes()`, which is self.notes plus the lost-words note, last
    (host.py:4370,4383-4388).
  - The lost note is note:N+1 until the next note is appended; it then moves, and its `about` is reused.
  - Likelihood: low; it needs a terminal watch that lost words.
    - In-place replacements (host.py:3567,3685) keep their place, with new text (a rev). The dark-note lookup by text
    (event.py:370) is stable.
- **knocks: stable over `knock_rows()`** (append-only, :1812). Over the state's list (`knock_rows(200)`, :4368) every
  index shifts by one per knock after 200. The module cannot tell the two apart.
- **trees: stable.** Keyed by word, never deleted. The word contains colons ("11/2/2026 10:21:05 AM"), so `about` must
  be treated as opaque.
- **Q11.** Within one run, `about` is stable (the list is append-only). Across runs, the same input gives
  "source-finding:i" to different acts.
    - `about` carries no run, and it maps to `metadata.correlation_uid`. So "finding:1" from every run, and "watch"
    from every run of every host, share one correlation id in a SIEM. [MORE SAID, high wherever the SIEM correlates on
    it.]
- **"watch".** Start, heartbeat and end are one `about` at rev 1 each. C-1's rev rule ("one more each time it
  changed") is left to the writer, and EVENT.md is silent on it.
- **Two snapshots of one run** give the same ids to different events (test:285-297 shows the n moving). A collector
  that drops by host+id would drop real events if two snapshots, or a snapshot after a running watch's events, ever
  reach it. EVENT.md says only that snapshot "is not how a running watch says events". [SILENCE, low-medium; depends
  on M10.2/M10.3.]
