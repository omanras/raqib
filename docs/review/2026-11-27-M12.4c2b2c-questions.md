# M12.4c2b2c - questions for the Table (the builder, 2026-11-27)

The Table's note (2026-11-27): these decisions are ruled in ADR-0013 Amendment ZA (ZA-1 to ZA-5).

Task: `raqib service status` on Windows reads the start-again settings the install makes (ADR-0013 Amendment Z).
What was built, what was decided meanwhile and why, and what could not be checked here. Nothing below is answered
locally; each decision is the builder's meanwhile, to be ruled.

## What was built

- raqib/winmanager.py: `System` gains three methods, `actions` (QueryServiceConfig2W level 2), `flag` (level 4)
  and `delayed` (level 3), each by the two asks through `room()` with the structure's own size as the least, on the
  service's handle as opened (0x5). Four structures are declared inside `_win` (SC_ACTION,
  SERVICE_FAILURE_ACTIONSW, SERVICE_FAILURE_ACTIONS_FLAG, SERVICE_DELAYED_AUTO_START_INFO); the first three are,
  field by field, raqib/wininstall.py's own (a test compares the two by their syntax trees). DECLARED is unchanged:
  QueryServiceConfig2W was declared already, with the same argument and result types.
- `array_at()` (a function of the module, tested alone): the count of actions is bounded first (ACTIONS_MAX, 64),
  then the array must be there where the count is not 0 and lie wholly inside the bytes read; the actions are then
  read out of the bytes at that offset (`from_buffer(raw, offset)`), never through the pointer itself. Every value
  (the reset period, the two texts, each kind and delay) is read into plain Python numbers and text before the
  method returns.
- The lines, after the account's and before the state's: what the system does after an end that was no Stop, the
  two texts kept beside the actions (each on a line of its own, only where it is there), the failure flag, the
  delayed start. As installed (Z-2) now also needs: the start 2; not delayed; exactly three actions of the kind 1
  after 5000, 30000 and 300000 ms; the count forgotten after 3600 s; the flag set. Each difference is a line of its
  own, "<what was read>; the install writes <what>". Of a service without the mark the lines are said, nothing
  judged.

## Decisions made meanwhile (to be ruled)

1. **Where the install's numbers are held.** Constants of raqib/winmanager.py (AUTO_START, RESTART, DELAYS,
   RESET_PERIOD, and CONFIG_FAILURE_ACTIONS, CONFIG_FAILURE_FLAG), tied by
   `test_z2_the_numbers_as_installed_are_the_installs_own_and_its_structures_the_same` to raqib/wininstall.py's.
   Not read from wininstall inside the function, because tests/test_wininstall.py holds that wininstall is imported
   only in cli.py's `cmd_service` (an assertion outside this task's scope), and tests/test_winmanager.py holds
   status's one import, winservice.
2. **The names of the three methods**: `actions`, `flag`, `delayed` - not `failure_actions` / `failure_flag`,
   because the stand-in of tests/test_wininstall.py serves both objects and already answers the install's writers by
   those names.
3. **The order of the calls**: description, making, level 2, level 4, level 3, state. A level that fails stops the
   reading there (NOT KNOWN, the call and the number said, nothing asked after it but the closes), as any other call -
   for a service without the mark too, which therefore now reads NOT KNOWN where one of the three levels cannot be
   read, where before it read `NOT INSTALLED BY RAQIB, ...`. Is that as ruled?
4. **The bound of actions, 64**, a bound of its own; and the array placed inside the bytes read, which is stricter
   than E1 asked: an array pointing elsewhere is said (`3 actions whose array does not lie inside the 64 bytes
   read`) and the answer is NOT KNOWN. The measured 64 bytes for three actions (40 of the structure and 24 of the
   array on x64) say the system lays the array inside the same bytes.
5. **The texts are said, not judged.** Z-2 names none of them as part of "as installed": a message or a command to
   run kept on Raqib's service, with its three actions of the kind 1, reads ACTIVE. Should a text that is there be a
   difference? A text is said only where it is there and not empty (None and "" are both "not there"); it is written
   through `_said` and marked "(another party's text)".
6. **The words.** The flag's line: `1, set (an end the service itself reports with an error is such an end too)`;
   the word "exit" was kept out of it, since the tests of the exit hold every line that holds "exit". The reset
   period 0xFFFFFFFF (INFINITE) is said "never forgotten". A delay not a whole second is said with milliseconds
   (`300.001 s`). A kind with no word is said `the kind 7, which this command has no word for,`. The BOOLs are
   judged by 0 or not 0 (a flag of 2 is set; a delayed start of 2 is delayed).
7. **The start's difference** stands among the making's, in their line order (command, type, start, account), then
   level 2's (the actions, then the count), the flag's, the delayed start's.

## Where the real calls could not be checked here (the sandbox is Linux)

- QueryServiceConfig2W at levels 2, 4 and 3 through the real advapi32: that the first ask with no room answers 122
  and the bytes (measured by the probe, not by this code); that level 2's `lpsaActions` points inside the bytes
  read; that `ctypes.cast(<POINTER(SC_ACTION)>, c_void_p).value` and `addressof(raw)` agree on Windows as on Linux;
  that the two texts come back NULL (said nothing) or empty after an install that gave None.
- The sizes: on Linux `wintypes.DWORD` and `BOOL` are 8 bytes, so the measured 64 (three actions) and 4 and 4 are
  asserted on Windows alone (the gate's Windows jobs run that test); here the made-up library uses the sizes of
  this platform.
- Every test hands a stand-in or the made-up library; none asks the real service manager.

## For the Table's wiring (not in this scope)

- **X53 will be MISSED until Z-3 is wired**: its running service is made by hand with the mark and without the
  start-again settings, so status now answers it `ACTIVE, NOT AS INSTALLED`, exit 1, where X53 asks for ACTIVE and
  exit 0. Its refused moment reads `INSTALLED, NOT ACTIVE, NOT AS INSTALLED`, which X53 already takes.
- **X54 asks this reading first**: status after Raqib's own install must still read ACTIVE. A fault of the real
  reading on Windows (any of the points above) would make status NOT KNOWN there, and so `raqib service install`
  itself exit 1 (`installed, NOT ACTIVE as raqib service status reads it (NOT KNOWN)`), its service left made.
