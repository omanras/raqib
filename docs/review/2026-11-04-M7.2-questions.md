## Q-1 What a round reads (E1)
A round is `discover.collect_live` + `discover.run(..., live=True)`: the
path `raqib discover` takes live, called by `host.live_reader`. Linux: one
/proc snapshot (or `--window S` seconds of them, 1 s apart). Windows: one
sample of the OS API through hostwin (`win_samples=1, win_every=0`), so a
round is quick; ADR-0007 A-11's T seconds between samples becomes the
round's T. Elsewhere: the homes only (discover's own hole). It runs in a
daemon thread (`host.Worker`). Rounds start every T seconds start to start
(`--every T`, default 10, 0.1..86400). A reader not back within 2 x T is a
`reader-late` hole and a HOST-HOLE knock ("host, round N, reader not back
in 2T s"); no second reader starts while one is out; its inventory, when it
comes, is that round's, marked `late`, and the next round starts at once.
A reader that raises is a `reader-failed` hole and a knock, and that round
has no inventory. A reader still out at the end is a `reader-out` hole.
Question: is "one sample per round" right on Windows, or should a round be
the README loop's N samples (slower, sees more short-lived acts)?

## Q-2 Where the two rules live (E2, E3; ADR-0002, A6)
They are YAML anchors in `raqib/rules/catalog/` (NEW-AGENT.yaml,
AGENT-DARK-LIVE.yaml), judged by the unchanged engine over "host lines":
each round turns its inventory into one line per tree (tool HostTree) and
one per footprint (tool HostFootprint), in the trace line shape (session
"host", source os, a running seq; `cwd` is the constant "host", since the
shape needs one). The facts across rounds - `history`, `candidate_before`,
`was`, the footprint's `streak` - are computed deterministically by
raqib/host.py and written into the line; the rules match on them. Why YAML
and not a code rule: the gate (tools/gate.py, outside Scope) counts code
rules only from silence.py, cross.py and tree.py, so a code rule in a new
module would not be counted; a catalog YAML is counted and measured by
check-rules with no change outside Scope. The kinds line is now
`signature=4 demand=7 anchor=8`.
Fixtures: `tests/fixtures/rules/NEW-AGENT/` (3 positive: new unknown, new
named, act-root becomes candidate; 3 negative: history only, gone and back,
act-root only) and `tests/fixtures/rules/AGENT-DARK-LIVE/` (1 positive:
dark three rounds; 2 negative: dark two rounds, dark then linked). Each is
the LAST round's host lines of a HostWatch fed the inventories of the
discover fixtures in order (tests/fixtures/host/make.py; generate.py calls
it, so the existing "fixtures are what the generator writes" test holds
them). check-rules: NEW-AGENT ok 0.000 of 0.25 (11 measured), AGENT-DARK-LIVE
ok 0.000 of 0.1 (10 measured); on hook traces neither rule fires (they
match only `tool: HostTree/HostFootprint` with `source: os`).
Budgets: NEW-AGENT 0.25 (the act_root block's, since ADR-0004 B-8 says a
discover budget comes from the field), AGENT-DARK-LIVE 0.1. Both carry
`holes:`.

## Q-3 History, identity, once per tree (E2)
A tree is (root pid, image, `started`): `discover.started_of()` (new, the
"API only" change) gives the creation time the reader recorded - Windows
CreationDate (CSV text or the live ISO UTC) - and candidates and act-roots
now carry `started`. Linux /proc gives none: the key is (pid, image), a
hole said at the start and in the report. History: the candidates of the
first round that has an inventory (B-3). NEW-AGENT fires for a candidate
that is not history and was not a candidate in any earlier round: an
act-root that becomes a candidate fires; a tree gone and back does not
fire again; an act-root alone is listed, never NEW-AGENT (no talk seen).
"named" = the image (or exe basename) is a catalog footprint agent's name,
or the tree talks to a catalog endpoint; else "unknown".
Knocks go through the notifier's rate limit (one per rule per minute):
four new trees in one round give one toast and a fold "3 more (first ...,
last ...)" a minute later. Question: should NEW-AGENT knock per tree
regardless of the rate limit (a separate limit id per tree)?

## Q-6 AGENT-DARK-LIVE streak (E3)
A footprint the round's inventory calls AGENT-DARK counts +1; the rule
fires at streak exactly 3 (once per streak). Linked (to a candidate or an
act-root) or gone from the listing clears the streak, with a note
("round N: AGENT-DARK-LIVE of the <agent> footprint cleared: linked to tree
X") in the record, the page and the final report, when it had fired.
Unjudged (no process or connection records) and a round with no inventory
neither count nor clear. host.DARK_ROUNDS = 3 and the YAML's `eq: 3` are
two copies; a test reads both.

## Q-7 Silence said (E4, A3)
Every round prints one line: "round N: R records read, H holes; ..." and,
with no tree, "NO AGENT SEEN (window ...; <result>). Not a clearance." The
final report repeats it ("NO AGENT SEEN in N round(s) ... Not a
clearance."). Result: alarm (exit 1) for any tree seen, a finding, a
reader hole, an alarm inventory, or no inventory at all; incomplete (3)
for an incomplete inventory or another hole; none-seen (0) otherwise.
Note: discover's own alarm (a candidate) makes every round's inventory an
alarm, so a host with any agent ends ALARM even with no NEW-AGENT; recorded.
