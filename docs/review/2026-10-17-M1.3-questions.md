# M1.3 — questions for the commander (not answered locally)

Each entry: the question, the most conservative reading taken, where it
shows in the tree. Nothing here changes the exit criteria.

## Q1. How the forms write YAML
The forms never re-serialise a whole file (that would drop comments and
the entries the engine could not read). They change one entry's lines:
replace, add or remove one block item of the `policies:` list
(`src/ui/textEdit.ts`), flip one decision's `status: open` line, or
append a decision with the engine's `appendDecision`. The edited text is
then parsed by the engine: the policy must come back `ok` and no problem
may appear that was not there before, else nothing is written and the
engine's reason is shown ("band must satisfy 0 <= min_pct <= max_pct <=
100"). A file not laid out as one block item per entry (flow style) is
refused with "change it in the raw text"; the raw panel always works.

## Q2. One block item re-written by the engine's emitter
An edited policy's block is written by the engine's `policyBlock`, which
quotes a title with a comma (`title: "no margin, no options"`) and writes
`tags` as a single string or a list. The policy reads back identical
(tests/ui/edit.test.ts checks every sample policy) and no other line
changes. Comments inside the edited block are lost.

## Q3. Removing a policy
The confirmation shows the policy's verdict line as of the as-of date,
exactly as the CLI prints it, its findings, and the decisions that name
it (they become UNKNOWN-POLICY problems of decisions.yml after the
removal, which the owner then sees on the dashboard). Removing the last
policy is refused: an empty `policies` list cannot be read (EMPTY-POLICIES,
exit 3).

## Q4. Decision ids and the "New decision" form
The id is `D-<date>-<n>`, the decision's date and the first n not used by
any `id:` line in decisions.yml. The status of a new decision is `open`;
`closes` offers only kill policies (the engine refuses any other, BAD-CLOSES).
"Close" sets `status: closed` and changes nothing else (no closing date is
recorded: the schema has none).

## Q5. Export all / import all
The bundle is every present file, each after a line `=== filename ===`,
its text as is, then one newline; the reader takes text up to the next
header and drops the final newline of the last part, so every file comes
back byte for byte, including one without a final newline. Import all
checks each part like a single import (wrong header, empty, unreadable
YAML are refused) and replaces only the files the bundle names. A line
`=== ledger.csv ===` inside a file would split it; no valid file holds
one at column 0, except a YAML block scalar, which is not used by Qayd's
files. "Download all files" offers the same text as `qayd-household.txt`.

## Q6. Settings in the empty state
After "erase all" the household is empty; the Files and Settings screens
stay reachable from the empty state so that "import all" can follow
(E5). Every other screen shows the empty state.

## Q7. Arabic
Every interface string is translated (tests/ui/strings.test.ts fails on an
Arabic entry with no Arabic letter, a changed {slot}, or an Arabic-Indic
digit). The engine's texts (verdict lines, reasons, declared measures,
findings, the summary line) stay the CLI's English, laid out left to right
(M1.2 Q5). Numbers are Latin digits and dates ISO everywhere.
