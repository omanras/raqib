# M3.2 — questions and the readings taken

## Scope conflict

1. **"`npm version` field set to 0.1.0" (E4) needs `package.json`, which
   is not in this task's Scope** (nor is `package-lock.json`, which carries
   the same field). Scope wins (CLAUDE.md rule 1, SESSION_PROTOCOL 2;
   BUILDER_PROMPT: never widen Scope). Reading taken: `package.json` is
   untouched and still says `0.0.0`, so `/api/health` and the client
   report `0.0.0` until the version is bumped. Everything else that names
   the version says 0.1.0: CHANGELOG.md, the default image tag in
   deploy/compose.yml (`dawr:0.1.0`). The bump is one command for whoever
   tags the release, in a task whose Scope has the two files:
   `npm version 0.1.0 --no-git-tag-version` (rewrites both, nothing else),
   then commit. This is the only exit criterion of M3.2 not met inside the
   tree; it is carried into the v0.1 report as an open item.

## Readings taken

2. **Release tag.** The plan mentions "release tag notes". The notes are at
   the top of the 0.1.0 entry in CHANGELOG.md; no tag was created or
   pushed. Tagging belongs with the merge into `dawr`, which the commander
   does (DEVELOPMENT_PLAN), and should follow the version bump above.
3. **"sqlite `.backup`".** The image has no `sqlite3` shell (no apt
   packages at build, smaller surface). The backup uses SQLite's online
   backup API through better-sqlite3 (`deploy/dbtool.mjs backup`), which is
   the mechanism the shell's `.backup` command uses: consistent while the
   server writes. The copy is switched to a rollback journal so it is one
   self-contained file.
4. **A backup that fails its check.** Most conservative reading: it is
   evidence, not a backup. It is kept as `dawr-<time>.sqlite.broken`, the
   script exits 2, and retention removes nothing in that run, so the older
   good copies survive for as long as the problem lasts. Retention only
   ever matches the exact names of good copies.
5. **Restore never deletes.** The current database and its `-wal`/`-shm`
   are moved aside as `before-restore-<time>.sqlite*`; a copy is restored
   only after the same integrity and chain check. `restore.sh --check`
   checks a copy and changes nothing (used for finding the newest good
   backup). The copy is streamed into the volume rather than bind-mounted,
   because backups are 0600 and owned by whoever ran `backup.sh`, which
   the container's unprivileged user cannot read.
6. **Caddy.** Its site address is `BASE_URL` itself, so the operator sets
   one value, not a host name that must match it (Compose also refuses to
   render the file when a required variable is missing, even for an
   inactive profile, which ruled out a separate `DAWR_DOMAIN`). Admin API
   off; no access log (Dawr logs every request without addresses, A7);
   no response compression (responses carry CSRF tokens; avoiding
   compression-oracle questions costs little at this size); `Server`
   header removed; 1 MB request cap in front of the app's 64 KB.
7. **Exposure.** The app is published on the host loopback only
   (`127.0.0.1:3000`); with the Caddy profile nothing but Caddy reaches it.
   `TRUST_PROXY=1` is set by compose, not baked into the image: an image
   started without it refuses to run in production (tested by hand: "dawr:
   refusing to start: TRUST_PROXY=1 is required in production").
8. **Base image by tag, not digest.** `node:22-bookworm-slim` (and
   `caddy:2.10`): a rebuild picks up Node 22 and Debian security patches.
   Pinning by digest would need an update process this task cannot add.
   `NODE_IMAGE` / `CADDY_IMAGE` let an operator point at a mirror or a
   pinned digest. Question for the owner: pin by digest with a scheduled
   update instead?
9. **Container hardening beyond the HANDOFF.** `cap_drop: ALL`,
   `no-new-privileges`, `init: true`, `mem_limit: 512m`, `pids_limit: 200`,
   json-file log rotation (5 x 10 MB). The memory figure comes from
   measurement (about 30 MB idle; scrypt 32 MB per hash, at most four at
   once).
10. **`docker build` in CI.** Docker is available on GitHub's
    `ubuntu-latest`, so a `container` job builds the image and runs
    `deploy/smoke.sh`: health, non-root, read-only root filesystem, `/data`
    the only writable path and a volume, production headers, a circle
    created through the API, backup, `restore --check`, restore (the circle
    is back with its chain verifying, a later circle is gone, the replaced
    database is kept), and a ledger row changed underneath the app making
    the backup exit 2 with the evidence kept. The same script ran green in
    this session against a local Docker daemon (base image pulled from
    `mirror.gcr.io` because Docker Hub answered 429 to this address). The
    Caddy path was also run here once by hand (`BASE_URL=https://localhost`):
    HSTS present, `Server` removed, http redirected to https with 308,
    `__Host-` cookies working, and a client-sent `X-Forwarded-For` ignored
    (the audit row shows the proxy's view of the client).
11. **Gate check of documented commands.** The gate reads the code spans
    and fenced blocks of README.md and docs/OPERATIONS.md: every `npm run
    <x>` / `npm <x>` that is not one of npm's own commands must be a
    script in package.json, and every `deploy/`, `tools/` or `docs/` path
    must exist (except `deploy/.env`, the operator's own file). It also
    parses every `deploy/*.sh` (`bash -n`) and `deploy/*.mjs`
    (`node --check`).
12. **SECURITY.md contact.** GitHub private vulnerability reporting, with a
    detail-free public issue as the fallback; whether private reporting is
    enabled is a repository setting for the owner. Response times are
    written as aims, and no legal ("safe harbor") promise is made on the
    owner's behalf. Question for the owner: confirm the channel and the
    times, and whether to add safe-harbor wording.
13. **Open sign-up.** Anyone who can reach the site can create an account
    (an account alone sees nothing). OPERATIONS says so. Restricting
    sign-up would be a feature (not in scope); noted for v0.2.
14. **Operator-wide sign-out.** Rotating `SESSION_SECRET` does not sign
    anyone out (session tokens are stored as plain SHA-256, not keyed),
    which OPERATIONS states; members can sign out everywhere themselves.
    An operator command to end all sessions is a feature: v0.2 candidate.
15. **Retention of audit and ledger.** Kept for the life of the database:
    both are append-only by trigger, and nothing here prunes them. Logs
    rotate (Docker json-file); backups keep 30. Measured sizes in
    OPERATIONS ("Resources") show this is small.
16. **docs/THREAT_MODEL.md is outside this Scope.** Its deployment rows
    still say S7.3 "runs once `deploy/` exists" and disk exhaustion "open
    until M3.2". Both are now covered (the S7.3 test runs, deploy/smoke.sh
    checks the running container, OPERATIONS "Retention" and "Resources"
    cover disk use), but the threat model's wording can only be updated in
    a task that has it in Scope. Follow-up for the commander.
17. **README describes the merged state.** It says to `git checkout dawr`;
    until the commander merges, v0.1 is on `claude/dawr-v0.1`.
