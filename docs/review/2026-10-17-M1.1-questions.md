# M1.1 fixtures, test and match — design questions (returned, not answered locally)

Each question names the reading the builder took; each has a test in
`tests/test_fixtures.py` or `tests/test_cli.py`.

## Q1. Blank lines in a JSON Lines file
A7 says a malformed line is reported with its number, never skipped
silently; ADR section 6 says each sidecar needs "at least one non-empty
line", which presupposes that empty lines may exist.
Reading taken: an empty or whitespace-only line is not an event and not an
error; it is counted, reported in the JSON (`blank_lines`) and in the text
output (`<file>: N blank line(s) ignored`), and never changes the verdict.
Any other line that is not one strict JSON object is `unknown`, cited.

## Q2. Strictness of event JSON
`json.loads` accepts `NaN`/`Infinity` and keeps the last of duplicate keys
silently.
Reading taken: both are rejected as malformed (A7: no silent guess about
what an event means); an event must be a JSON object; CRLF line endings
are tolerated; invalid UTF-8 is cited by line.

## Q3. Status precedence
ADR section 6 gives `pass` / `fail` / `unknown`; a rule can have a missing
sidecar (fail) and a malformed line (unknown) at once.
Reading taken: `invalid` > `unknown` > `fail` > `pass`; every citation is
listed whatever the status, so nothing is hidden by the precedence. A rule
whose condition or a referenced selection is unsupported is `unknown`
with the rule file cited (line None); its sidecars are still read and
counted so missing or malformed files are also reported.

## Q4. What a `pass` cites (A5)
Reading taken: every fixture line the verdict rests on, one citation per
line (`<file>:<n> matched` / `did not match`), in text and JSON alike. A
range summary was considered and rejected because a citation's `line` is
an integer in the JSON.

## Q5. Exit code of `match`
ADR section 9 does not define green for `match`.
Reading taken: `match` is green (exit 0, status `ok`) when every line of
the events file was judged, whether or not any line matched; `unknown`
(exit 1) when any line could not be judged or the rule is unsupported;
`invalid` (exit 1) when the rule did not load; exit 3 when the events
file or the rule file cannot be read at all. Matching zero lines is a
complete answer, not a failure.

## Q6. Exit 3 versus `unknown` for unreadable files
ADR section 8: 3 = "could not complete (a path unreadable ...)"; section 4:
"the rule becomes unknown if the problem is in its own fixtures".
Reading taken: the rule file given on the command line, or the events
file of `match`, unreadable or missing -> exit 3 and one line on stderr,
no result printed. A sidecar that is missing -> `fail` (A2, named); a
sidecar that exists but cannot be read or is over the file limit ->
`unknown` citing the file (exit 1), as section 4 says.

## Q7. JSON shape of `test` and `match`
E3 says `--json` "prints the result object"; ADR section 9 says JSON
output is `{"version": 1, "rules": [...], "green": bool}`.
Reading taken: the ADR shape for every command, with one element in
`rules` and an added `"command"` key; the result object is that element.

## Q8. Sidecar names for `.yaml`
Reading taken: the sidecar stem is the rule path minus its last
extension, so `foo.yaml` and `foo.yml` both use `foo.positive.jsonl`.
Only `*.yml` is named by the ADR; `check` (M1.2) will follow the ADR.

## Q9. JSON error wording
Python's decoder reports "line 1 column N (char M)" inside a one-line
event, which reads oddly next to the file's line number.
Reading taken: the citation says `malformed JSON: <message> (column N)`.
