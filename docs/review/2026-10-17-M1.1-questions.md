# M1.1 — questions and readings taken

1. **Which requests the per-IP auth limit counts.** S1.4 says "per-IP
   limit on /api/auth/*: 30 per 15 min". Counting the GETs (`/me`,
   `/csrf`, `/sessions`) would lock a household out after about fifteen
   page loads. Reading taken: every non-GET `/api/auth/*` request counts
   (signup, login, logout, logout-all, password, recovery, recovery-codes,
   session revoke), whether or not it succeeds, and it is counted before
   CSRF and validation; the 31st in a sliding 15-minute window is 429 with
   Retry-After. GETs are free of side effects and not counted.

2. **Lockout key.** Failures are counted per *typed login* (normalized),
   whether or not the account exists, so the 423 itself does not reveal
   which logins exist. A locked login gets 423 even with the right
   password until the window passes. Recovery-code failures have their own
   counter with the same limits. Wrong current passwords on
   `/auth/password` and `/auth/recovery-codes` count toward the login
   lockout.

3. **CSRF before a session exists.** S2.3 binds the token to the session;
   sign-up, sign-in and recovery have none. Reading taken: `GET
   /api/auth/csrf` sets a random pre-session cookie (`dawr_pre`, HttpOnly,
   SameSite=Strict, 24 h) and returns HMAC(SESSION_SECRET, that value);
   once signed in, only the session-bound token is accepted. Setting that
   cookie is the one side effect of a GET; it changes no server state.
   Cross-site form posts are additionally refused by the JSON-only parser
   (415).

4. **Cookie names.** In production the cookies are `__Host-dawr_session`
   and `__Host-dawr_pre` (the browser then enforces Secure, Path=/ and no
   Domain); in development and tests, where there is no TLS, plain names
   without Secure.

5. **Recovery-code storage.** 16 symbols of Crockford base32 (80 bits),
   shown as `XXXX-XXXX-XXXX-XXXX`, stored as SHA-256 salted with the user
   id. A slow hash is not needed at 80 bits, and unlike an HMAC with
   SESSION_SECRET the codes stay valid when the secret is rotated (M3.2).
   Regenerating a set requires the password and voids the old set.

6. **Password normalization.** Passwords are compared after NFKC (NIST SP
   800-63B) so the same text typed on two keyboards matches; length is
   counted in code points. Besides the common list, the login itself is
   refused as a password.

7. **Routes added beyond the handoff list**, because M2.1's Account screen
   (client-only Scope) needs them and they cannot be added later without
   server/ in Scope: `PATCH /api/auth/me` (display name), `GET
   /api/auth/sessions`, `POST /api/auth/sessions/:id/revoke`, `POST
   /api/auth/recovery-codes` (new set, password required). All are in the
   matrix, audited and rate-limited like the others.

8. **Trusting the proxy.** Fastify 5.12 refuses numeric hop counts
   ("fail closed"), so with `TRUST_PROXY=1` the app trusts exactly the
   immediate peer (`hop === 0`): `req.ip` is the address the reverse proxy
   saw, and a client cannot choose its own address by sending
   X-Forwarded-For through the proxy. Without TRUST_PROXY the socket
   address is used.

9. **Matrix convention.** Each row's request targets organizerA's own
   objects (and, from M1.2, circle A); roles vary. A role that may not see
   the object gets 404, not 403 (S8.1). The coverage test fails both on a
   route without a row and on a row without a route.

10. **Common-password list.** `server/auth/common-passwords.txt` holds the
    first 1,000 entries of the ranked `passwords` list shipped in zxcvbn
    4.4.2 (MIT, attribution in the file header). It was taken from the
    npm package tarball; nothing is fetched at run time.
