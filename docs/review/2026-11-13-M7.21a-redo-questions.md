# M7.21a REDO - what the Table checks in the field, and questions (2026-11-13)

Built against ADR-0007 Amendment BM (BM-1 to BM-7) and the packet
docs/review/2026-11-13-M7.21a.md (R1, R2, and the stop() branches of section E).
Scope: raqib/etwnet.py, tests/test_etwnet.py, tools/rig/etw_read.py, this file.
The reader as built read real traffic in the field (BM's preamble); its
structures, constants, argument types and call sequence are unchanged here.
Every change is an addition around them. Nothing new has run on Windows; the
tests run on Linux against the fake system (FakeEtw).

## A. E1 (the packet's R1): no test reads the real system

The one test that reached the real process table on e40849e was
`test_e7_a_loss_not_known_and_live_pids_not_known_are_said`: with `alive=None`
the tool called `etw_read.live_pids()`, which builds `hostwin.Api()` and reads
the live process snapshot. On Windows that snapshot succeeds and the test's
assumptions (pid 111 not alive) do not hold, so the two Windows gate jobs went
red.

Fix: the tool now resolves the live pids through an injectable callable. `main`
takes `pids` (a callable returning `(alive_set_or_None, why_or_None)`). When it
is not given, `pids` is built from `alive` (a resolved set, injected by tests)
or falls back to the real `live_pids` only in production. `leftovers` takes that
callable and calls it after it has listed the sessions (BM-3). The loss test now
passes `pids=no_pids(...)` and never touches `hostwin`.

Every test of the tool (`run_tool` -> `etw_read.main`) was checked for a real
system call on any platform:
- `test_e7_the_tool_stops_leftovers_reads_and_prints_one_line_per_connection`:
  default `alive=frozenset({PID})`, so `pids` is a lambda over that set. No
  `live_pids`, no `hostwin`.
- `test_e7_a_refused_session_is_its_reason_and_exit_3`: default `alive` set;
  refused before any snapshot. No real call.
- `test_e7_not_windows_says_so_and_exits_3_and_its_usage_is_2`: returns on the
  platform / usage checks before `leftovers`. No real call.
- `test_e7_a_loss_not_known_and_live_pids_not_known_are_said`: `alive=None` but
  `pids` is injected. No `live_pids`, no `hostwin`. This test now passes on
  Windows as on Linux.

No `run_tool` call uses `alive=None` without an injected `pids`, and no test
imports `hostwin` or calls `etw_read.live_pids`. The reader's own tests all run
against FakeEtw. The only places that still touch the real advapi32 are the
platform-guarded E1 binding tests (`test_e1_off_windows_the_real_api_is_not_there`,
skipped on Windows, and `test_e1_windows_the_real_api_binds`, skipped off it);
these bind symbols or observe the absence of the DLL and start no session - not a
read of the system's state. `Reader.__init__` calls `os.getpid()` for its own
number (own-pid default); the own-pid tests inject `ownpid`, and `reader()`
defaults it to 0 so the retry branch never fires by accident. os.getpid() is a
benign, deterministic, cross-platform call, not a read of the process table or
traffic. Question A1: is that acceptable, or should the own number also be
injected into the production Reader by the tool?

## B. The lost-event provider GUID (BM-6, E7) - the Table checks it

`LOST_EVENT_PROVIDER = 6A399AE0-4BC6-4DE9-870B-3657F8947E7E`. This is the GUID
the reviewer named for ETW's real-time lost-event notifications (RT_LostEvent),
and it is the one wired into `_take` and counted in `lost["notices"]`. It has
NOT been field-measured on the probe branch. Question B1: confirm the GUID (and,
if it matters, that its notices arrive on the consumer's own callback, so they
are counted there and not in the session's EventsLost/RealTimeBuffersLost). If
the GUID is wrong, such events fall through to `other` (another provider) and
`notices` stays 0; nothing crashes.

## C. The measured version (BM-4, E5)

The four ids are read at version 0 only (`EVENT_VERSION = 0`); an event of ids
10, 11, 26, 27 with any other version is unread as `id N version M` and never
parsed. The probe branch measured the shape but BM/BL do not record the version
number the real events carry. Question C1: confirm that the live ids 10/11/26/27
are version 0. If they are not, every byte event is unread and the counts read
as 0 bytes with a non-empty `unread` - which is at least an alarm, not a silent
wrong number (CLAUDE.md rule 4), but it would make the reader blind until the
real version is set here.

## D. Field checks for the new ways out

- BM-1: start a reader, send SIGINT (Ctrl-C) in its start window; confirm no
  `raqib-net-<pid>` session is left (`logman query -ets`). And: start a reader,
  let the process exit without stop(); confirm the atexit hook stopped the
  session.
- BM-2: `taskkill /F` a reader so `raqib-net-<pid>` is orphaned, then start a new
  reader that is given the same pid number; confirm it finds the leftover of its
  own number, stops it, retries, starts, and prints the `said:` line.
- BM-3: the race is hard to force; at least confirm a live second watch started
  during leftovers() is not stopped (its session is listed before its pid is
  read).
- BM-5/BM-7: on a live machine, confirm `events` is well above the counted
  connections (connects/disconnects/udp show up in `other`), and that the cap of
  65536 is never hit by a normal 30 s run (`beyond=0`).

## E. Addresses and ASCII

The three code/test files use documentation addresses only: 192.0.2.0/24
(192.0.2.10, .11, .12), 198.51.100.0/24 (198.51.100.7) and 2001:db8::/32
(2001:db8::10, 2001:db8::7). This questions file names only those ranges; it uses
no loopback literal. All four files are ASCII
(`test_e8_ascii_and_documentation_addresses_only` guards the code/test three).

## F. Imports added to E1's allowed set

`raqib/etwnet.py` now also imports `os` (own pid, BM-2) and `atexit`
(interpreter-exit stop, BM-1). Both are standard library, load nothing of
Windows at import, and reach no network;
`test_e1_stdlib_only_nothing_of_raqib_no_network_and_nothing_of_windows_at_import`
asserts the exact set `{__future__, atexit, ctypes, datetime, ipaddress, os, re,
struct, threading}`. Question F1: confirm this reading of E1 ("nothing of raqib,
stdlib only") still holds with `os` and `atexit` present.

## G. A design question deferred to the Table

Question G1: when `leftovers` lists the sessions and the live pids then come back
`None` (not known), it still reports both the caller's reason and its own
"leftovers not looked for" line. Is one of the two redundant, or are both wanted?
Left as built (both are said) pending the Table.
