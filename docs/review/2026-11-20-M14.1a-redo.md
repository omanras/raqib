## MUST FIX BEFORE MERGE

1. **`docs/THREAT_MODEL.md:533` and `docs/specs/PROC-EVENTS.md:84-86`.** Change "a pid taken again within one clock
  tick" / "within the tick … is not told apart". It should say: a pid taken again within REUSED_SECONDS (1 s) of the
  exec, and before the read, is not told apart, and the newcomer's program and start are then given as the first
  process's. The code's window is 1 s (`raqib/procevents.py:97, 539-540`), not one tick (G1).
2. **Thread words on `older` and `ends` entries.** Either add a `threads` key to `older` entries' `unread`
  (`procevents.py:616-617`) and to `end()` when `lost` > 0 (`procevents.py:253-258`, which needs `self._lost` passed
  in at 522 and 599), or correct `PROC-EVENTS.md:58-60` and `THREAD_MODEL.md:538-540`. Those lines currently claim
  "that is said" and "a process older than the reader says its threads … are not known". Add a test either way (G2,
  G3).
3. **`tests/test_procevents.py:446-457`.** `Clock.wall` is constant (181-182), so this test would pass if `last`
  simply returned `since`. Move the wall clock before the later datagram and assert that `last` follows it and differs
  from `since` (G9).
4. **New test for the start guard at `procevents.py:554`.** No test fails if that guard is removed. Add one: an exit
  is heard, then an exec of the same pid with a different start must give a new record with NO_FORK, and the ended
  record must not be revived (G4, G10).

## FINDINGS

**G1 (medium; false statement).** `THREAT_MODEL.md:531-533`, `PROC-EVENTS.md:84-86` against `procevents.py:97,
  539-540`.
- The only check at a first exec is `ticks/hz > boot_ns/1e9 + 1.0`.
- So a pid taken again less than about 1 s after the exec, before the read, gives the newcomer's program and start as
  the first process's. That newcomer then shares (pid, ticks) with its own later record.
- The docs say only a reuse "within one clock tick" goes untold, which is 100 times narrower than the code's window.

**G2 (medium; false statement and silence).** `procevents.py:611-618, 603-610, 552-558`.
- An exit with pid == tgid of a process the reader does not hold goes to `older` as an end with its code. That covers
  any process older than the reader that never exec'd since the reader started, and any process refused by the bound.
- It is not remembered in `_gone`, so:
    - In measured order (b), the leader's `pthread_exit` gives an `older` end with code 0. The last thread's real exit
    is then dropped (`_live.get(tgid)` is None at 605), so the real code (7) is never given.
    - In order (a), a following exec is given as a new record with "no fork heard". BR-1 says such an exec "is never
    given as 'no fork heard'".
- The `older` entry's `unread` holds only `began` (617). Nothing says the end may be the leader thread's.
- `PROC-EVENTS.md:59-60` ("a process older than the reader says its threads from before the reader are not known") and
  `THREAT_MODEL.md:538-540` claim more than this.
- Realistic case: an agent already running when the watch starts, multi-threaded, that execs from a non-main thread.

**G3 (medium; silence).** `procevents.py:253-258`.
- `end()` gives `unread: {}` whenever an end was heard. So an end given in `ends` after an overflow carries no
  LOST_THREADS caveat, although it may be only the leader thread's end.
- E1 says "a record says its count of threads is not known". Only `processes` records do (241-248).

**G4 (medium; false statement, conditional on a loss).** `procevents.py:554, 542`.
- The condition `old.started_ticks is None or ticks is None or ticks == old.started_ticks` revives an ended record
  whenever either start is unknown.
- Case: process A ended (heard), and B took A's pid but B's fork was lost to ENOBUFS. If B's stat read fails (common
  for short processes, as the sandbox showed) or A never exec'd, B is given as A going on. B then carries A's `ppid`,
  A's `began`, and A's program in its `earlier`, and A's end, already given, is withdrawn.
- When `_read_exec` itself concludes "another process held the pid", it returns ticks None (542). That also satisfies
  `ticks is None` and revives the old record.
- The only caveat on such a record is LOST_THREADS, which talks about threads, not about which process this is.

**G5 (medium; silence and resource).** `procevents.py:569-570`.
- `rec.earlier` grows by one entry per exec with no bound and no count. Each `read()` copies all of it under the lock
  (249), and up to 32768 ended records keep theirs in `_gone` (288, 597).
- A process that keeps re-exec'ing itself grows the reader's memory without limit and slows its thread, which then
  leads to ENOBUFS.
- `PROC-EVENTS.md:143-145` lists every bound except this one.
- On the brief's question of how long an ended record is remembered: until a fork of that pid (516) or until 32768
  later ends evict it (501). There is no time bound. The count is bounded; the bytes are not.

**G6 (medium; the ruling's words, possibly false).** `procevents.py:650-652`, `PROC-EVENTS.md:139-142`,
  `THREAT_MODEL.md:536` ("what was in the queue is gone"; "how many events the queue held").
- By my reading of the kernel's netlink code (overrun and "congested" handling; the error is reported on the next
  receive), the messages already queued are still delivered after ENOBUFS. What is lost is what arrived while the
  queue was full, until the reader drained it.
- BR measured only that events go on afterwards. The builder used BR-4's words as E4 required, so this is for the
  Table, not the builder.

**G7 (low-medium; false statement in an unmeasured order).** `procevents.py:567, 619-622, 611-618`.
- If a non-leader thread's exec arrives before the old leader's exit (possible by the kernel source, not measured),
  the exec clears `threads`. The leader's exit (code 0) then ends the process while it lives.
- Its real exit then goes to `older` as "no fork heard: it began before the reader, or its fork was lost". Both causes
  are false: its fork was heard and it was held.
- Only the questions file says this (lines 20-21, 92). The spec's "Not measured" list (`PROC-EVENTS.md:202-204`) and
  the threat model do not.

**G8 (low; false in combination).** `procevents.py:599` then `561-563`.
- Case: a record given before is ended at 599, which puts its end in `_ends`, and is then revived by an exec before
  the next read.
- That next read gives both the stale end and the revived record (ended None), with the same pid and ticks. Nothing in
  `unread` says the earlier end was withdrawn.
- The rig's `Heard.take` applies `ends` after `processes` (`tools/rig/procevents_run.py:107-113`), so it would mark
  the process ended.

**G9 (low; test).** `tests/test_procevents.py:446-457`. The wall clock is constant, so `last` is not told apart from
  `since` (both are `text_of(WALL)`).

**G10 (low; untested new behaviour).** No test fails if any of these is removed:
- the start guard at 554 (G4);
- the `leader_ended` reset at an exec (568);
- the per-process thread bound (511-513);
- eviction from `_gone` and `_refused_pids` (501);
- the "ticks of a second not known" `said` (329-334). The tests always pass `ticks_per_second`.

**G11 (low; silence).** `procevents.py:449-452`. If the boot clock fails, `offset = None` and the BR-3 check is
  skipped on every exec without a word in `said`. The missing-ticks case (333) is said; this one is not.

**G12 (low; silence).** `procevents.py:344-347`.
- Linux reports SO_RCVBUF doubled, but it is compared with the undoubled 1 MiB asked.
- So a system maximum between 512 KiB and 1 MiB cuts the queue and nothing is said. The questions file (48-49) shows
  the builder knew about the doubling.

**G13 (low; false statement, words).** `procevents.py:100` used at 523.
- "it runs its parent's program" is false for a child made with CLONE_PARENT. Its `ppid` is its maker's parent
  (`parent_tgid`), but it runs its maker's program.
- `PROC-EVENTS.md:99-100` repeats the wording. It can be fixed by hand.

**G14 (low; by the kernel source, not measured).** `procevents.py:450, 460-461, 539-540`.
- A reader inside a time namespace with a monotonic offset would get a false "another process held the pid" on healthy
  reads. The event's timestamp has no namespace offset, but the reader's two clocks do.
- Event times are put on the wall clock using the monotonic difference (460). An event read after a suspend is
  therefore shifted later by the length of the sleep.

**G15 (low; misattributed cause).** `procevents.py:362-376`.
- The kernel's answer to any user's ask goes to every listener. A flood of asks can overflow the reader's queue during
  `start()` and drop its own answer.
- The refusal then says "did not answer … a process outside the system's first namespaces, as in a container", with no
  word about the overflow. The overflow appears only in `counts()["lost"]`.
- X31 reads it as MISSED, so the rig does not hide it.

**G16 (low; claims beyond measurement).**
- `PROC-EVENTS.md:23-27` and `procevents.py:11-14` sit under "as measured" but include facts from the source or the
  sandbox: "answers every ask to the whole group" and "its seq is the kernel's own count" (6.18 only).
- `THREAT_MODEL.md:547-549` says "whatever shows it escapes it", but no consumer exists yet. X31 prints `exe` raw
  (`tools/rig/check.py:779-780`); harmless there because those are the rig's own programs.
- The spec's sandbox paragraph (`PROC-EVENTS.md:193-200`) gives the first build's nine runs, as E6 asked. It omits the
  REDO's own, worse runs: the real test missed 3 or 4 of 5 (questions file 60-65).

**G17 (low; silence).** `procevents.py:44` ("Every way it loses is counted").
- By the source, the kernel's send of an event can fail at allocation and raise no ENOBUFS. Such a drop is not
  counted.
- The per-CPU connector `seq` that would show the gap is read for answers only (178, 202).

**X31 (low).** `tools/rig/check.py:761-764`, `tools/rig/procevents_run.py:123-125`.
- The facts carry no kernel release, so X31 cannot know whether it is on "a machine where the kernel is known to
  answer" (BR-7, first sentence).
- An EPERM/EACCES refusal on a measured 6.8/7.0 runner (for example from an LSM or a seccomp profile) reads n/a. It
  follows E7's parenthesis, but the gap against BR-7 remains.
- Otherwise I found no way for X31 to read MET where it should read MISSED: parent, program, end and code are each
  checked per act, and lost, beyond, ended and stop problems are checked too.

## SILENT ASSUMPTIONS / A3, A5

- **A3 (silence).** G3, G5, G11, G12 and G17. Also, an exit of a thread the reader does not know, or of a process it
  does not hold, adds only to `threads` (605-610). That is how a real end is dropped in G2.
- **Assumptions.**
    - With `lost` == 0, no fork is missed. Reviving a record (554) depends on this, and a kernel-side drop (G17) would
    break it.
    - The event's stamp is CLOCK_MONOTONIC and stat's start is boot-based in USER_HZ. Both come from the source; only
    the wall conversion was seen in the sandbox.
  - The reader's clocks have no namespace offset (G14).
- **A5 (evidence).** Records keep neither `cpu` nor `seq` of the kernel event they came from, so a later finding can
  cite the reader's record but not the kernel's event.

## QUESTIONS FOR THE TABLE

1. **BR-4's words (G6).** On 6.8 and 7.0:
   - Stop the listener's receives, run a numbered burst of short processes that overflows the queue, then drain.
      - Record which forks arrive after the ENOBUFS. Are the earliest (queued before the overflow) delivered, and
     which are missing?
      - Record whether the per-CPU connector `seq` of the received events has gaps equal to the missing count. That
     decides "what was in the queue is gone" and "how many is not known".
2. **Exec before the leader's exit (G7).** On 6.8 and 7.0, with every CPU busy, run a program whose non-leader thread
  execs, thousands of times. Count how often the exec event comes before the exit with pid == tgid and code 0. If it
  ever does, rule how such an exit is to be taken.
3. **A bound for `earlier` (G5).** Rule the bound and its word or count before M14.1b. Measure the reader's memory and
  the time `read()` takes over a minute of a process that re-execs itself.
4. **Reviving a record after a loss (G4).** Rule whether, once `lost` > 0, an exec after a heard exit with no fork
  between is the same process only when both starts are known and equal. Rule also whether "another process held the
  pid" (ticks None) may revive an ended record.
5. **Processes not held (G2).** Rule how M14.1b is to read an `older` end, which may be only its leader thread's, and
  an exec that follows it.
6. **X31 (BR-7).** Should the facts carry the kernel release, so that an EPERM/EACCES refusal on a measured kernel is
  MISSED?
7. **Uncounted drops (G17).** Measure whether the per-CPU `seq` of events heard is contiguous in a normal run on 6.8
  and 7.0. If it is, a gap is a loss the reader does not count today.
8. **A5.** Must a record carry the kernel event's `cpu` and `seq` so that M14.1b's findings can cite it?
