What holder answers for each state of the file:

| State of the file | holder answers |
|---|---|

2. note, host.py:484. The docstring says "It never raises", but a state nested deeper than the parser's recursion

  change the refusal, which is the Table's call.

**E2 is met in substance. Gaps:**

3. should fix, host.py:2447. The run and the pid go into the hole through `_safe()`, which makes them printable but
  does not bound them; only the heartbeat is cut, at 40 characters. These values come from a file another process
  wrote. On Linux and macOS, for a person's own watch, a watched agent running as that person can write that file.
  Whatever length it writes is copied whole into:
   - the final report;
   - the state, rewritten every tick;
   - the event's summary (raqib/event.py:342 sets no bound).

      The runner bounds the same two values to 80 (winservice.py:347-349). To fix: cut the run and the pid as the
     heartbeat is cut, with a test.

4. note, host.py:2448. N is `int(max(age, 0))`. N can only be clamped where the state's own staleness is negative
  (STALE needs age > stale). In that case "for 0 s" is said of a heartbeat in the future. Amendment H says the seconds
  are "said as read", but the clamp is not said anywhere, including SERVICE.md:431. Also, N is measured at
  `_refuse_second` (:2437), after the Sysmon check (:2329), not at `self.started` (:2242). To fix: the spec says both,
  or the words say the heartbeat is ahead of the clock.

5. should fix (A3; the Table rules). The hole first reaches the events at the first events pass, after round 1's
  reader returns (host.py:2720-2724). But the start already overwrites the state that named the run before: `start()`
  calls register at :6216, which writes the state at :6118. If the new watch is ended inside that window:
   - its hole is never written to the events;
   - the next watch names only the new watch;
   - the earlier gap is in no record that lasts.

      The questions file does not raise this. To fix: the Table rules on the window. Until it does, SERVICE.md:433
     ("written to the events file once") should say when it is written.

**E3 is met in substance. Gaps:**

6. should fix, winservice.py:685. `held["stale"] - held["age"]` raises OverflowError when `stale_after_seconds` is an
  integer too large for a float. holder accepts that integer (host.py:515) and answers FRESH. The runner then ends
  with 23 instead of waiting 60 s and starting the watch, whose own refusal (20) the system should be told. The `%g`
  at :689 would fail the same way. To fix: whatever number holder returns gives a wait within the bound, with a test
  (staleness 10**400).

7. should fix (A5), winservice.py:686-690. For a heartbeat in the future the line reads "heartbeat 0 s ago, stale
  after 30 s ... waiting up to 60.0 s". Those numbers contradict each other (30 - 0 + 1 is not 60), and nothing says
  the heartbeat is ahead of the clock. After 60 s the watch refuses (20) and the service stays stopped until the wall
  clock passes the heartbeat, and the record says nothing. To fix: the line gives the age as read.

8. note, winservice.py:691-699. The 60 s bound covers only the pauses. Two asks fall outside it: the first, which
  imports raqib.host (:321-322), and the last one, after the final pause. So the wait can exceed the bound by one
  ask's time. Small for a local file.

9. should fix (tests). Missing:
   - an exception out of `System.held` reaching STOPPED with 23;
   - a state that becomes finished, absent or unparsed during the wait;
   - a heartbeat in the future;
      - a wait that ends on a fraction of a second. At tests/test_winservice.py:858 the comment says "the last ask
     waits the half second left", but that case goes stale at the third whole pause. So `min(HELD_ASK_EVERY, left)` at
     winservice.py:696 never runs with left < 1, and a runner that paused a whole second there, past the bound, would
     pass every test.

10. note, tests/test_winservice.py:158-161. In the stand-in, the monotonic clock and the wall clock are one value. A
  runner that measured its wait on the wall clock would pass.

## 3. Silent assumptions and what a rule should have caught (A3, A5)

25. should fix (A3; not asked). A state that cannot be read (empty, filled with zeros, torn, not ASCII, permission
  denied) is answered "nothing held" (host.py:500-503). The watch then takes the home with no hole, and the `why`
  holder computes is thrown away. Why it matters:
      - this is the leftover a power loss is most likely to make, because write_json replaces the file without
     flushing it to disk (host.py:527-545);

   - D-6 says "an unknown state is not clearance";
   - E1 puts this case in none of its answers, and the builder put it in "nothing held" without a question.

   The refusal must stay as it is (AH-1 MUST NOT TOUCH). Whether the start says this case is the Table's ruling.

  refusal's own words tell an administrator to remove it, host.py:2462-2465), and a state that disappears during the
  runner's wait (winservice.py:698). In the second case the runner said "ended without its end, or it still watches"
  and nothing after it (Q6).
