## Q-2 What AGENT GONE means

## Q-3 What CAPTURE FAILED covers, and the order of the states
The launching brief says a missing or unreadable watch.json is CAPTURE
FAILED. The tree has other states that the four words of E2 do not name:
- a capture-failed hole: a RAQIB-SILENCE line (watch.py:372-381), or
  disableAllHooks at the start (watch.py:298-304);
- a crashed watch (B-4);
- a stale heartbeat, "CRASHED or stuck" (C-4, watch.py:593-595);
- a finished watch (watch.py:591-592);
- trace holes.

My proposed order:
1. CAPTURE FAILED: watch.json missing or unreadable, a crash, a stale
   heartbeat, or any live capture-failed hole in this epoch. The ruled C-4
   texts follow as the detail.
2. SILENT for N s.
3. AGENT GONE.
4. WATCHING.

FINISHED would be a fifth word, for registry rows of watches that have
ended. A CAPTURE FAILED from a RAQIB-SILENCE line would stay for the rest
of the epoch, since one lost event is a hole for the whole watch. That
hides SILENT behind it. The open window is still drawn in the timeline and
listed as an alarm. Two choices for the Table:
- Is CAPTURE FAILED sticky, or only shown while the newest line is a
  marker?
- Should the band show one state word, or every state that holds?

## Q-4 Where the band is read from
Today the band comes from the watch's in-process state, read under its
lock (Watch.band, watch.py:586-606). watch.json is the same dict, written
on every poll (watch.py:637-656, 664-682).

The brief says "derived from watch.json". There are two readings:
- (a) Each request reads `<trace>.watch.json` from disk again.
- (b) The page uses the dict that watch writes (`Watch.state(now)`). It
  also stats and reads the file on each request, so a file that is missing
  or unreadable, or a `state_error`, is CAPTURE FAILED.

The agent runs as the same user (THREAT_MODEL:201-210) and can write under
`~/.raqib/traces/`. Under (a), a forged file shows WATCHING on any page
built before the next poll rewrites it, up to 0.5 s later. Under (b) it
cannot.

I would use (b) for the page's own band, and (a) for the rows of other
watches, because only their file is there. Either way the change is
`Watch.page` (serve wiring) plus a band builder in ui.py. Is that the
reading?

## Q-5 The registry's lifecycle and lock (E4)
- **Is it serve wiring?** The write goes in `command()`, next to `_serve`
  (watch.py:854-860), and in `finish`. The read goes in ui.py. Is that
  within "serve wiring only"?
- **When an entry is written.** I would add one entry {pid, project, port,
  trace, state path, started} at the start, after the page is bound, and
  set `finished` and `status` at finish. No watch ever removes an entry: a
  dead pid shows GONE (A3). The file then grows without end. Should old
  GONE entries ever be pruned, or is that left to a later ruling?
- **The lock.** The stdlib has no cross-platform file lock. fcntl.flock and
  msvcrt.locking are two code paths. A lock file opened with O_EXCL is one
  path, but it needs stale-lock handling. My proposal:
  `~/.raqib/watches.json.lock` opened with O_EXCL and retried for 2 s; a
  lock older than 10 s is broken, and that is recorded as a hole. The write
  uses a temp file and `os.replace`, as watch.json does.
- **A registry that is corrupt or unreadable** would be an alarm on the
  page and a hole in watch.json. Watch would not overwrite it, since a
  rewrite would lose the GONE rows (A3). Rewrite or not?

## Q-6 Checking a pid without a signal (A4)
- **POSIX:** `os.kill(pid, 0)` sends no signal. ESRCH means gone; EPERM
  means alive.
- **Windows:** `os.kill(pid, 0)` is not a check. 0 is
  `signal.CTRL_C_EVENT`, which Python sends with GenerateConsoleCtrlEvent,
  and any other value calls TerminateProcess. So on Windows I would use
  ctypes and kernel32: OpenProcess(PROCESS_QUERY_LIMITED_INFORMATION), then
  GetExitCodeProcess == STILL_ACTIVE (259), then CloseHandle. Access denied
  would count as alive; an invalid parameter would count as gone.

Two holes remain:
- A pid that another process reuses reads as alive, on both systems.
- On Windows, a process that exited with code 259 reads as alive.

One way to narrow both: a row is alive only if its pid is alive and the
heartbeat in its watch.json is fresh (`stale_after_seconds`). A live pid
with a stale heartbeat would read "pid alive, no heartbeat". Should the
heartbeat be part of liveness?
