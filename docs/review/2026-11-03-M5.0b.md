## Readings taken where the text allowed one reading only (check them)
- R-1 "run.json records the sample count": both run.jsons. The README loop
  writes one before its first sample (`raqib`, `version`, `export`,
  `samples`, `seconds_apart`; no `sources`), so a loop cut short is seen;
  `--save` records the samples a live run took. A run.json without
  `sources` must say `raqib: discover-run` and give `samples`, else exit 2.
- R-2 The loop also writes `win-dns-<k>.csv` per sample (a DNS cache row
  expires; E2 reads it). Only process and connection files are needed per
  sample; a missing DNS file beside others is a hole only.
- R-3 "a catalog endpoint IP" is what a live talk is matched by: a network,
  a loopback port, or a name the host's own DNS record gives that IP. E5
  expects the recent-talk line on the Kimi fixture, so the Moonshot hosts
  are now in the catalog, and `test_e2_catalog_is_a_signature_with_evasion`,
  which pinned their absence (B-10), now pins their presence (Q-6).
- R-4 "owner unknown" is pid None or 0, in state TIME-WAIT only. A Sysmon 22
  row has an owner, so it is never recent talk. A DNS row whose IP a known
  process talks to is already cited by that talk, so it is not repeated.
- R-5 Recent talk changes no exit code and raises no alarm (E2: "evidence,
  never a candidate by itself"); the NO AGENT SEEN line counts it.
- R-6 "no live talk" is the act-root process itself: it owns no talking
  connection in any sample. A child that talks does not stop it ("talking
  through a child", an evasion line: it is never promoted).
- R-7 "descendant chain shell -> ... -> command": the root's child is a
  listed shell, and below that shell is a process that is no listed shell.
  The act-root is the shell's nearest parent that is not a shell.
- R-8 "known shell or system image": `shells` are the shell names of
  `acts.names`; `not_images` are Windows system images and the terminal
  hosts and multiplexers that run the user's own shell (Q-3).
- R-9 `/root` (root's `~`) and macOS `/Users` count as user directories.
- R-10 Act-roots are judged only when a process source and a connection
  source both hold records: with no connection record, "talk not seen" is
  a gap (A3), not an observation. Found by the D-1 test (Sysmon without
  event 3), which would otherwise have turned an incomplete run into an
  act-root alarm.
- R-11 A footprint links to an act-root after a candidate whose root has
  its name, and before a process anywhere in a candidate's tree, so an
  acting agent is not AGENT-DARK and the one-sample Kimi footprint names A1,

## Questions for the Table (not settled here)
- Q-1 An editor's integrated terminal. The benign Windows fixture has VS
  Code installed under `AppData\Local\Programs` with an idle terminal
  (powershell, no child), so act-root does not fire on it. When a command
  runs in that terminal, VS Code's pty host (`Code.exe`, ptyHost) is an
  act-root: user directory, not a shell, powershell -> git below it, no
  connection of its own (its network process is a sibling). The test
  `test_m50b_e3_known_false_positive_a_command_in_an_editor_terminal`
  builds it. Added as a third negative, act-root measures 1 of 3 = 0.333,
  over its 0.25 (`test_m50b_e4_check_fails_over_budget` runs exactly that).
  Should that shape be in the benign set? If it is, A6 disables act-root
  until the class narrows. The ways to narrow it are design choices, for
  example: (a) the act-root's parent is a shell (CLI agents start from a
  terminal; Kimi's parent was cmd), which misses agents inside an IDE;
  (b) no Chromium/Electron helper (`--type=` in argv) is an act-root; (c)
  editor pty hosts in `not_images`; (d) more benign exports, or another
  budget.
- Q-2 Linux places an act-root by argv[0]. A program run through PATH
  (`kimi`, argv[0] relative) and a node or python script under a home
  (`node ~/.npm-global/bin/agent`) are not placed. Both are evasion lines.
  Reading `/proc/PID/exe` changes `snapshot_proc` and the REAL fixture's
  format: M5.3, or a ruling here?
- Q-3 `not_images` includes terminal hosts and multiplexers (mintty,
  tmux, kitty, ...) as "system images" (R-8). Confirm, or narrow it to OS
  images only.
- Q-4 Recent talk raises nothing by itself (R-5). Should recent talk to a
  catalog endpoint with no candidate and no act-root be an alarm (A3: talk
  with no owner seen), and should a DNS row for an IP a known owner talks
  to be listed anyway?
- Q-5 The dashboard's discover tab (`raqib/ui.py`, outside this Scope)
  shows the act-root alarm line and the holes, but not the act-root and
  recent-talk entries. Is that a later Scope?
- Q-6 The Moonshot hosts are in the catalog (R-3): api.moonshot.ai,
  api.moonshot.cn, api.kimi.com, from the vendor's documentation, not
  re-checked offline. Confirm. B-10's blind test is kept by running with a
  `--catalog` copy without them.
- Q-7 The first numbers for the anchor: candidates on 2 of 2 benign
  desktops (explorer talking, as in the field test; the VS Code extension
  host running git; Firefox). B-8 leaves the anchor without a budget. The
  number is printed by `--check` and is not a gate. Record it, or set a
  budget?
