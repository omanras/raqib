## What was built meanwhile, and why (each a question where it says so)

Q1. The mark. `winmanager.MARK = "raqib-service/1"` is a constant of its own, and a test ties it to
`service.MARK[2:]`. It is not imported from raqib/service.py: tests/test_service.py (test_e8) holds that no file of
raqib/ but cli.py and service.py holds the text `import service`, and cmd_service's docstring names service.py's
importers. Is the tied constant what E2 means by "MARK's text without its `# `"? The mark must begin the description
and END there or at a white space: "raqib-service/10" and "raqib-service/1x" are not Raqib's. V-2 says only "begins
with"; the stricter reading was taken so that a later mark is not read as this one. Rule which.

Q2. The account. As installed needs the account `LocalSystem`, compared without regard to case. Amendment V says the
account was read by a caller with no rights; it does not say the text the manager gave. If the probe read another
spelling (for example `NT AUTHORITY\SYSTEM` for a service made with that name), status says NOT AS INSTALLED for it.
Which texts are the system's account?

Q3. RUNNING and not as installed. E3 names `RESULT: INSTALLED, NOT ACTIVE` with `, NOT AS INSTALLED`; V-4 says "as on
Linux", and the Linux command answers `RESULT: ACTIVE, NOT AS INSTALLED` (exit 1) for a unit that runs and is not as
installed. Built as on Linux: a running service not as installed is `RESULT: ACTIVE, NOT AS INSTALLED`, exit 1; one
not running and not as installed is `RESULT: INSTALLED, NOT ACTIVE, NOT AS INSTALLED`, exit 1. Rule which.

Q4. A state number with no word (not 1 to 7). Built: said as "N, a state this command has no word for", and the
answer is `RESULT: INSTALLED, NOT ACTIVE` (exit 1; only 4 is RUNNING); for a service without the mark, `... IS IN A
STATE THIS COMMAND HAS NO WORD FOR`. NOT KNOWN (exit 3) was the other reading: nothing failed, but the state is not
known in words. Rule which.

Q5. A close that fails. V-3: "a call that fails is said with the system's number, and the answer is then NOT KNOWN".
Built so for CloseServiceHandle too: every handle is still closed (each once, the service's before the manager's) and
the answer is NOT KNOWN even where everything before was read. The RESULT line is written after the closes for that.

Q6. The exit is said in every state but RUNNING (stopping, paused, starting too), as "where it is not running" reads.
1066 with a number in winservice.EXIT_WORDS is said by `winservice.told`; 1066 with any other number (EXIT_BASE + 19,
+ 24, 7, 0) as "N (0xN), a number the runner does not give". Only 15 names the text file.

Q7. `platform()` is a method of the system object, beside the six calls of the manager, as raqib/service.py's System
has it: a stand-in must be able to say win32 on Linux. E1 says the methods are "the system's own calls and nothing
else". Is the platform a call of the system for this rule?

Q8. The bound. ASK_MAX = 8192 bytes, for the making and for the description alike (QueryServiceConfigW documents 8 KB
as its most; QueryServiceConfig2W documents the same most). The low end is the structure's own size, so a named size
below it is refused before a read past the buffer. Not measured: the bytes a long description needs. A description
longer than the bound is NOT KNOWN (the call's words said), not cut; one inside it is cut at SAID_MAX (300) when said.

Q9. Out of Scope and now untrue: docs/specs/SERVICE.md, the runner's section, its first paragraph (lines 277-279): "Installing,
removing and asking the state of the service are not here yet (M12.4c); until they are, the line above that there is
nothing for Windows is true of `install`, `remove` and `status` only." - status is here now. And the check's section,
its first paragraph (lines 679-680): "(installing, removing and the state are not built yet: M12.4c2)". The Scope gives SERVICE.md's
new section and the three commands' sentence only, so neither was touched; the Table rights them.

Q10. X53's `refused-words`: built to hold the runner's words for 15 (winservice.EXIT_WORDS[EXIT_NOT_ALONE], whole,
copied as NOT_ALONE_WORDS and tied by a test) and `service.txt`; the tests give it status's lines joined, which is
what I read the job is to keep. `active-command`: a path under Program Files is a drive's letter, then
`\Program Files\`, without regard to case; `Program Files (x86)` is not taken. The job's wiring is the Table's.

## Where the real calls could not be checked (Linux here; each is the field's)

The real object (winmanager.System) was read by its syntax tree in the tests and, off Windows, asked once to show
that it never raises (ctypes has no WinDLL there). Nothing of the following was run:
1. `ctypes.WinDLL("advapi32", use_last_error=True)` and each declaration: OpenSCManagerW and OpenServiceW with
   restype `wintypes.HANDLE` (an SC_HANDLE as a pointer: an int, or None for NULL); QueryServiceStatusEx's second
   argument as `ctypes.c_int` (the SC_STATUS_TYPE enumeration, SC_STATUS_PROCESS_INFO = 0); the buffers given as
   `wintypes.LPVOID` (a `byref` of a structure, a `create_string_buffer` array, None for the first ask).
2. SERVICE_STATUS_PROCESS as nine DWORDs (36 bytes) and QueryServiceStatusEx taking that size; dwProcessId 0 where
   it does not run; dwServiceSpecificExitCode read as the unsigned number the runner set (0x2000000F for 15).
3. QueryServiceConfigW's first ask (NULL, 0) failing with 122 and naming the bytes; the second with those bytes;
   the cast of that buffer to QUERY_SERVICE_CONFIGW and its LPWSTR fields read as text (lpBinaryPathName,
   lpServiceStartName); the buffer's alignment as create_string_buffer gives it.
4. QueryServiceConfig2W at level 1 by the same two asks; and, not measured, what the first ask answers for a service
   with NO description (built: 122 and the structure's 8 bytes, then lpDescription NULL, said as "no description";
   if the system answers otherwise, status says NOT KNOWN with what it answered).
5. `ctypes.get_last_error()` after each call that failed, and CloseServiceHandle's result for each handle.
6. The words of the lines themselves on a real machine: the command's text as the manager holds it (the quoting of
   the path), and the account's text (Q2). This command itself is not measured until the rig reads X53.
