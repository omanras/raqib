## Q-1 (blocking) Where CROSS-SOURCE lives: a new YAML construct, or a code rule the gate cannot count
The rule language has nothing that can express CROSS-SOURCE:
- The engine judges one line at a time (`match`) or counts distinct
  values in one session (`aggregate`) (raqib/rules/engine.py:596-647).
  CROSS-SOURCE has to join lines of two sessions of two sources by time,
  and no construct reads two sessions or a time window.
- "W declared in the rule" would need a new key. compile_rule rejects any
  key outside REQUIRED, OPTIONAL and the kind fields
  (engine.py:82-83, :191-193).

A code rule "like silence.py" cannot reach E4's `anchor=4` inside Scope:
- The gate counts the catalog YAMLs plus `silence.RULE_KINDS`, and
  nothing else (tools/gate.py:233-239).
- Every id in `report.SILENCE_RULES` must be in `silence.RULE_KINDS`
  (:236).
- tests/test_rules.py:940 holds the ADR-0002 table to
  `set(rules) | set(silence.RULE_KINDS)`.
- raqib/rules/silence.py and tools/gate.py are outside Scope. A code rule
  in engine.py or report.py would not be counted, so the kinds line would
  stay `anchor=3`.
- README.md:57-58 says "5 silence rules and 7 YAML rules"
  (test_docs.py:25). A code rule outside silence.py is neither.

Options:
- (a) A YAML construct in engine.py and the rule as
  `raqib/rules/catalog/CROSS-SOURCE.yaml`, `kind: anchor`. The gate,
  check-rules (A6: a measured fp_budget), watch and the page take it with
  no change. A sketch:
  `cross: {window: 10, asked: <node>, done: <node>, asked_key:
  input_meta.command_programs, done_key: input_meta.command_head,
  implied: [...]}`. `match:` is REQUIRED today (engine.py:82), so the
  construct either uses `match` to pick the lines both sides judge, or
  replaces it. It would be three-valued like the rest and never used with
  `aggregate`, as D-1 fixed for `require:`.
- (b) A code rule in silence.py, which adds silence.py to Scope. Its
  module text says all its rules are per-session demands
  (silence.py:31-36), and a code rule has no fp_budget
  (report.py:40-44), so A6 is not measured.
- (c) A new module, raqib/rules/cross.py, with its own RULE_KINDS that the
  gate also reads. That adds cross.py, tools/gate.py, tests/test_gate.py
  and the README sentence to Scope.

Reading I would build: (a), because it keeps W visible in the public
rule, and fixtures and the benign corpus measure it like the other
anchors. Which construct, and in what shape, is the Table's call.
ADR-0002 D-1 did the same for `require:`.

## Q-2 (blocking) "Unknown when either source is absent" makes every single-source trace with a shell call INCOMPLETE
How an unknown turns into INCOMPLETE:
- A rule's unknown lines become a `partial` note (engine.py:577-583).
- Any note that is not `disabled` makes `report` INCOMPLETE, exit 3
  (report.py:130). Watch reads it the same way.

What I measured on today's tree:
- 6 of the 8 benign and real traces (tests/fixtures/rules/benign and
  tests/fixtures/*.log) hold a Bash pre and no os line.
- quickstart-d7841d1-claude-code-2.1.301.log is `RESULT: CLEAN (exit 0)`
  today under `raqib report ... --scope .`. With E3 as written it would be
  INCOMPLETE.
- Linux and macOS have no os source (HANDOFF: not in scope). There, every
  Claude Code trace with a Bash call would read INCOMPLETE until one
  exists, and "a clean watch of such a project ends CLEAN" (ADR-0005
  C-6, :215-218) would no longer hold for any real session.

Options:
- (a) As written: such traces are INCOMPLETE until an os source exists
  on every platform.
- (b) The rule judges only a trace that holds os lines. With none, it does
  not apply and writes no note. When os-sysmon was run and failed, its
  own RAQIB-SILENCE line raises the alarm (A3). Inside a trace that has
  os lines, a line outside every os session's span is unknown (Q-3).
  This is quiet when os-sysmon was never run. Is that against A3? A
  capture that was never asked for is not a gap, but the Table may read
  it otherwise.
- (c) A note with a status of its own, for example `no-source`, that
  report does not count as incomplete. This changes report.py beyond
  "ids".

Reading I would build: (b). The HANDOFF's literal text is (a).

## Q-3 What "the window" is, for unknown and for each side
The HANDOFF gives W for matching and "the window" for unknown. The
prototype tried two readings on the three fixture shapes (asked-not-done,
done-not-asked, matched):
- Reading A: unknown unless the other source covers the whole window,
  [t, t+W] for a pre and [t-W, t] for an os process. The matched
  negative reads partial: its first os processes lie within W of the hook
  session's start. A partial file is unmeasured (fixtures.py:80-88), so
  the one negative would measure nothing.
- Reading B: unknown when t lies outside every session span (first line
  to last line) of the other source. All three fixtures are judged:
  asked-not-done fires on the pre, done-not-asked fires on the os
  process, and matched gives nothing.

There is also the question of what counts as a match on each side:
- "a pre for a shell tool with no os process within W". Literally, that
  is no os process of any program in [t, t+W]. Under that reading a Bash
  call on Windows always has one, Git Bash's own bash.exe.
- "an os process whose program is in no shell pre within W". This needs
  the program in some shell pre's programs in [t-W, t].

Reading I would build: B, with the literal meaning of both sides. W is 10
seconds and the clocks are not compared: hook, proxy and Sysmon all read
the same host clock when they run on one host. A proxy on another host is
a known hole.

## Q-4 What is asked and what is done: shell tools, spelling, the shell itself, the agent's own helpers
- **Shell tools.** common.input_meta reads programs only for tool `Bash`
  (common.py:505). Kimi's shell tool is named Bash (ADR-0003 builder
  note). Another agent behind the proxy may call it anything ("shell",
  "run_command"), and then its lines carry no programs. Reading: the
  asking side is pres of tool Bash from hook or proxy (ADR-0003:42 says
  proxy, the HANDOFF says proxy/hook). A pre with `command_unread` is
  unknown.
- **Spelling.** discover.image_name gives os names in lower case without
  .exe/.com/.bat/.cmd (discover.py:222-231). command_programs keeps the
  command's spelling: `cmd.exe` stays `cmd.exe` (checked), `Python` stays
  `Python`. Reading: fold both sides the same way before comparing.
- **The shell itself.** bash.exe (Git Bash, for every Bash call), sh,
  cmd, powershell and pwsh are in no command_programs. Builtins (cd,
  echo) run no process, and a script runs its interpreter. Reading: a
  shell process is implied by any shell pre in [t-W, t], as in the
  prototype.
- **The agent's own helpers.** In the prototype's combined trace, the
  synthetic rg.exe (a stand-in for a Grep helper the agent starts itself)
  has no shell pre within W, so it fires done-not-asked. It is the one
  false positive in that trace. The same holds for the root's own start,
  git for a status line, MCP servers and node helpers. There are three
  options:
  - Judge every process of the tree. The field test then sets the
    fp_budget (A6).
  - Judge only the children of a shell. This needs the parent's program
    on the os line, and it misses an agent that starts curl directly,
    which is the case done-not-asked exists for.
  - Keep a list of known helpers. That is a signature in an anchor, and
    an anchor may not list evasions (ADR-0002).

  Reading I would build: judge every process, and record the helpers as
  the false-positive source.

## Q-5 The class of CROSS-SOURCE
engine.CLASSES is SCOPE, NET, DESTRUCT, SECRET, SILENCE, DRIFT
(engine.py:78). The HANDOFF gives anchor and high, but no class. Both
cases are one source being silent about what the other recorded. So
SILENCE fits A3, and the engine already forces SILENCE to be high
(engine.py:206-207). A new class (CROSS) changes CLASSES and
check_finding. Reading: SILENCE.

## Q-6 The os record shape, where it changes what the other rules do
- **post.** A post needs `ok` (trace.py:167-168). SECRET-OUTPUT reads
  `output_meta.secret_kinds` on every post (SECRET-OUTPUT.yaml:21), and on
  an os post that has none it is partial. In the prototype's os-only
  trace, SECRET-OUTPUT could not judge 9 lines, so the report was
  INCOMPLETE with no other cause. Options:
  - (i) Guard SECRET-OUTPUT to sources other than os, as
    `any: [{field: source, exists: false}, {field: source, ne: os}]`, so a
    line written before M5.2 is still judged.
  - (ii) os posts carry `output_meta: {"scan": "none", "secret_kinds":
    []}`, a claim about an output that does not exist.

  Reading: (i).
- **cwd.** E1 has no `--cwd`. Sysmon 1 carries CurrentDirectory; 3 and
  11 do not. A cwd per process makes SCOPE-CWD-MOVED fire on an os
  session as soon as two processes run in two directories
  (SCOPE-CWD-MOVED.yaml:13), and SCOPE-CWD-ROOT fire on a process started
  in a home. Reading: one cwd per os session, the CurrentDirectory of the
  root's event 1 if the export holds it, else os-sysmon's own working
  directory (the proxy's default, A-3). Or should E1 gain `--cwd DIR`?
- **net.** NET-TOOL fires on any pre with `input_meta.url_host`
  (NET-TOOL.yaml:27). If an os net line carries DestinationHostname as
  url_host, NET-TOOL fires on every connection of the tree, the model
  API's included. Reading: net lines carry `input_meta: {}`, and the
  destination (ip, port, host) is hashed only.
- **process.** Reading: `input_meta: {"command_head": NAME,
  "command_programs": [NAME]}`, with NAME = common.command_head of
  discover.image_name of Image. common.py decides what a safe program
  name is (HEAD_NAME, looks_like_key). On the raw Image path or command
  line, common gives None or `command_unread` (checked). DESTRUCT-CMD and
  NET-TOOL require tool Bash, so they do not read os lines.
- **file.** Reading: `input_meta: {"path": redact(TargetFilename)}`, as
  input_meta already keeps a path. Its tool is `file`, so SCOPE-PATH and
  DRIFT-FILES, which list tool names, do not read it.
- **Time and order.** os lines carry the event's UtcTime (the time of the
  act), not the time it was read.
  - session_start and session_end take the first and last tree event's
    time. At the read time they would make SILENCE-ORDER fire.
  - SILENCE-GAP then calls a tree that was quiet for more than
    RAQIB_GAP_SECONDS "no capture", though Sysmon was recording.
  - Lines are sorted by UtcTime. An export read newest first (`/rd:true`,
    as README.md:287 exports for discover) is reversed first, so that
    events with the same time keep their order.
- **Sessions and reruns.** One os session per run. discover reads no
  EventRecordID (discover.py:772-781), so a second run over the same
  events appends them again. Reading: the session id is
  `os-sysmon-<root pid>-<first event time>`. The trace is read once at
  start, as the proxy does (A-9), and events at or before the last os
  line of that session are not written again. Or is a rerun simply a
  second session?

## Q-7 Reusing discover's XML reading: what parse_sysmon's records do not keep
os-sysmon would import discover.parse_sysmon (discover.py:748-785,
_sysmon_records :788-841) and not read the XML a second time. Its records
lose four things:
- **The raw CommandLine.** Only argv by win_argv is kept (:802), and
  win_argv drops quotes and collapses unquoted spacing (:234-249). Two
  command lines that differ only there hash the same, so the hash is of
  the argv, not of the command line.
- **ProcessGuid.** If a pid is reused within the export, an unrelated
  process joins the tree. Reading: a later event 1 for a tree pid whose
  parent is outside the tree takes the pid out of the tree, which
  narrows the hole but does not close it.
- **EventRecordID** (Q-6, reruns).
- **UDP event 3.** It gives no connection record (:810, :828-829), so a
  UDP or QUIC connection is no os net line.

discover.py is outside Scope. Options:
- (a) Hash `{"argv": argv}` and name the four losses in THREAT_MODEL.
- (b) Add discover.py to Scope for one shared helper, for example
  `sysmon_events(text) -> (line, event_id, data)`, that parse_sysmon then
  uses. os-sysmon reads the Data fields itself (the raw CommandLine for
  the hash, ProcessGuid for the tree, Protocol for UDP), and there is
  still only one XML loop.

Reading: (b).

## Q-8 What os-sysmon reads, and when it is silent (readings; say if one is wrong)
- **The tree.** The root, plus every pid whose ParentProcessId is in the
  tree at its event 1, in time order. The root's own events are recorded:
  its connections to the model API and its own file writes.
- **Root not found.** No event names the root as ProcessId or as
  ParentProcessId. That is one RAQIB-SILENCE line and no session.
- **Missing event ids.** For each of 1, 3 and 11 that the export does not
  hold, one RAQIB-SILENCE line. This is ADR-0004 D-1's rule for discover,
  extended to 11. Under a configuration without -n, every run writes the
  "no event 3" line, so every report on such a trace is an ALARM. Is that
  the intent? Whether the commander's configuration logs event 11 is for
  the field test to show.
- **Unreadable events.** Each event parse_sysmon cannot read is one
  RAQIB-SILENCE line.
- **Live.** `C:\Windows\System32\wevtutil.exe qe
  Microsoft-Windows-Sysmon/Operational /f:xml`, with no /c and no /q, an
  environment of SystemRoot only, and a timeout. A nonzero exit, an
  OSError or the timeout is one RAQIB-SILENCE line naming the exit
  status; that covers no channel, no rights and no Sysmon. Without
  `--from` on POSIX, nothing is run: it is a usage error (exit 2) that
  says to use `--from FILE.xml`.
- **One run.** os-sysmon reads once and exits. It does not follow the
  channel, because the HANDOFF does not say so.
