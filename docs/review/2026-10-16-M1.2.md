## 3. Bugs, silent assumptions, and things a rule should have caught

### 3.1 Can secret text reach the trace through capture.py?

- **F1 [SECRET; old code, not written in M1.2] command_head can hold a secret verbatim.**
  - `capture.py:104-109` splits the command on whitespace and skips tokens that start with `NAME=`.
  - A quoted assignment value that contains a space spills into the next token, and that token becomes `command_head`. It is stored in plaintext in `input_meta`, up to 64 characters.
  - Example by reading: `AUTH="Bearer <40-char token>" gh api ...`. The first token, `AUTH="Bearer`, is skipped as an assignment, so `command_head` becomes `<token>"`, the whole token.
  - M1.2 does not scan `input_meta`, E2's tests cover only the output side, and questions-file Q1 covers `tool_input` but not this path.
- **F2 [SECRET, low] output hashes become a confirmation oracle.**
  - `output_sha256` (`capture.py:304`) is an unsalted sha256 of the canonical output, and `output_meta` now labels which hashes cover secret-bearing output.
  - Anyone holding the trace can confirm a candidate secret, for example a known leaked key in the expected output shape, against a labelled hash.
  - Recovering a high-entropy token from the hash is not feasible; confirming a guess is. The same applies to `input_sha256` for secrets in `tool_input` (Q1).
- **F3 No leak found in output_meta, summaries, error_class or the stderr line.**
  - `secret_kinds` holds names only (`capture.py:182-189`, `305-306`).
  - The SECRET-OUTPUT summary renders names only (`SECRET-OUTPUT.yaml:8`). The DRIFT-FILES summary renders `input_meta.path`.
  - `error_class` (`capture.py:152-165`) accepts only an identifier of at most 64 characters ending in Error or Exception.
  - The RAQIB-SILENCE stderr line (`capture.py:329-337`) carries exception text, and no M1.2 code path raises an exception containing payload content.
- **F4 The error string is not always scanned.** `capture.py:303` picks `tool_response` whenever that key is present, even if null. A PostToolUseFailure payload that carries both `tool_response` and `error` would have its error string left unscanned. No fixture shows whether Claude Code ever sends both.

### 3.2 Regex coverage: missed formats and false positives

**F5 Common real formats not matched** (`capture.py:72-80`):
- GitHub fine-grained PATs (`github_pat_` prefix).
- Stripe `sk_live_` and `rk_live_` keys. These use an underscore, so `sk_api_key` misses them despite its name.
- GitLab `glpat-`, npm `npm_`, PyPI `pypi-` and Hugging Face `hf_` tokens.
- Slack `xoxe-` tokens and Slack webhook URLs.
- PGP private key blocks. Their header ends in "PRIVATE KEY BLOCK-----", which `[A-Z ]*PRIVATE KEY-----` does not match.
- A PEM key body shown without its header line, e.g. a Read with offset or a `tail`.
- An AWS secret access key shown without its key ID.
- Credentials in URLs (`user:pass@host`), Bearer and Basic headers, and `password=` lines.
- Any base64- or hex-encoded form.
- An AWS key ID directly preceded by a word character, e.g. URL-encoded `%3D` followed by the ID: the "D" defeats `\b`.

**F6 Obviously benign text that matches.** By reading; none of these is in the fixtures.
- AWS documentation example key IDs (`"AKIA" + "IOSFODNN7EXAMPLE"`) and placeholders ("AKIA" followed by sixteen X). These appear widely in AWS SDK docs, moto and localstack tests, and terraform docs.
- `.env.example`-style placeholders:
  - `"sk-" + "your-openai-api-key-here"` matches `sk_api_key`: 24 characters from `[A-Za-z0-9_-]`.
  - `"xoxb-" + "your-token"` matches `slack_token`.
  - The SECRET-OUTPUT negative fixture is exactly a `.env.example` read (`negative-clean-output.json:4-5`). Its `output_meta: {}` was written by hand, not produced by capture.
- PEM private-key header lines in library sources, test certificates, docs and env templates. The pattern matches the header alone, with no key material.
- The widely published jwt.io sample token, found in docs and tests.
- Kebab-case identifiers that start with "sk-" followed by 20 or more characters.

Taken with E1 (no regex FP rate measured) and the 0.05 budget, SECRET-OUTPUT's FP rate on real sessions is unknown.

**F7 The meaning of "output" for Write and Edit is unpinned.** The tree has no real Write or Edit post payload. If their PostToolUse `tool_response` echoes the written content or the original file, then:
- (a) secrets the agent writes are flagged as "output", which contradicts the premise of questions-file Q1;
- (b) every Edit of a file containing one of the F6 strings raises SECRET-OUTPUT.

### 3.3 Slow or stalled capture (A3; "never blocks the agent")

- **F8 [SILENCE] The jwt pattern can take quadratic time** (`capture.py:76`).
  - `[A-Za-z0-9_-]{8,}` is greedy and must be followed by `\.`. Because "-" is both in that class and a non-word character, every "-eyJ" gives a fresh start where `\b` holds.
  - A string of "-eyJ" repeated N times, with no ".", costs about N × (length of the rest of the string) steps, i.e. quadratic in N.
  - By reading (not measured), N in the tens of thousands, a few hundred KB of output, should be enough for seconds to minutes.
  - The other six patterns read as linear: they have bounded counts, or an unbounded count at the very end of the pattern.
- **F9 [SILENCE] The scan runs while holding the log lock.**
  - The exclusive flock is taken at `capture.py:319`; `build_record` runs at `capture.py:322`, and it calls `secret_kinds` at `capture.py:305`.
  - A slow scan therefore stalls every other capture into the same log: parallel tool calls and other sessions.
  - The installed hook timeout is 10 s (`tools/install-hooks.sh:70`). A capture killed by the timeout writes no trace line.
  - Depending on how Claude Code kills the hook, it may also write no RAQIB-SILENCE line: the `||` fallback (`install-hooks.sh:150`) does not run if the shell itself is killed. If only the shell is killed, an orphaned python3 process may keep holding the lock.
  - SILENCE-HALF and SILENCE-GAP (`raqib/rules/silence.py`) may catch part of this afterwards, but capture itself blocks the agent.
  - The agent can produce the triggering output itself, e.g. by writing a crafted file and then reading it.
  - No test bounds scan time or output size.
- **F10 Linear cost with no size cap.**
  - Six of the seven patterns start with `\b`, so (reading CPython's re compiler) they get no literal-prefix search speed-up.
  - Every post is scanned up to seven times, at full length, while the lock is held. The cost has not been measured.
- **F11 Deep nesting: no regression found.** `strings_in` is iterative (`capture.py:168-179`). Deeply nested payloads already fail earlier, in `json.loads`/`json.dumps` (existing behaviour, which gives RAQIB-SILENCE).

  - It means "scanned, nothing found" and also "nothing to scan": `tool_response` absent, null, or renamed in a future hook version (`capture.py:303-306`).
  - In the second case `output_sha256` is the hash of `null`, but no rule and no note looks at that.
- **F13 Lines without output_meta look clean.**
  - The questions file says a missing `output_meta` means "captured before M1.2, not clean". Nothing implements that.
  - SECRET-OUTPUT simply does not fire (`engine.py:243-246`, `nonempty` on a missing field), and `evaluate()` gives no note, so mixed or old traces look clean.
  - Five of SECRET-OUTPUT's seven negatives are such files (see E1).
- **F14 A missing or unusable scope silences DRIFT-FILES.** This happens through `run_rule`/`fixtures.fires` when the scope is missing, and through `evaluate()` when it is present but unusable (see E3). The M1.1 questions file promises "a note is never a clean result (A3)", yet the fixture runner counts these runs as clean negatives.
- **F15 DRIFT-FILES sees only four tools.** It counts Write, Edit, MultiEdit and NotebookEdit only (`DRIFT-FILES.yaml:12`). File changes made through Bash (`sed -i`, redirection, cp/mv, `git checkout`) or through MCP filesystem tools are not counted, and no note says so. A quiet DRIFT-FILES is therefore not evidence of no drift.

### 3.5 DRIFT-FILES path semantics

- **F16 Scope is anchored to each line's cwd, not the project root** (`engine.py:279`).
  - HANDOFF Scope entries are root-relative. If Claude Code starts in a subdirectory, or the session cwd changes after a `cd` (which `install-hooks.sh:13-14` assumes can happen), "src" resolves to a different directory on each line.
  - That gives false positives (in-scope edits counted) or false negatives (out-of-scope files that happen to sit under `<cwd>/<entry>`).
  - The builder declared "relative to the line's cwd" but not this consequence.
- **F17 It disagrees with the project's own scope guard.**
  - `.claude/hooks/scope-guard.sh:14` anchors paths to CLAUDE_PROJECT_DIR, and `:24` matches string prefixes, so "src" admits "src2/a.py".
  - DRIFT-FILES uses path containment anchored to cwd; `test_rules.py:499-502` asserts that "src2" is outside.
  - The same Scope block thus has two meanings in one project, and questions-file Q3 proposes reading the scope "as scope-guard.sh does".
- **F18 Files are counted by raw string but placed by normalised path.** Counting uses the raw string (`engine.py:376`); scope placement uses the normalised path (`engine.py:275`, `309-317`).
  - "README.md", "./README.md", "/work/p/README.md" and "/work/p/x/../README.md" count as four files (FP).
  - The same relative name under two different cwds counts once (FN).
  - There is no case folding, so on case-insensitive file systems both containment and counting give FPs.
  - There is no symlink resolution: an in-scope symlink to /etc makes /etc edits "in scope" (FN).
  - Paths starting with "//" keep both leading slashes under `posixpath.normpath` (FP).
  - The builder declared only the absolute-versus-relative case. It relies on "Claude Code sends absolute paths for Edit and Write", which no fixture verifies.
- **F19 It counts attempted edits.** The rule matches the pre phase (`DRIFT-FILES.yaml:11`), so edits denied by the user or a hook, and edits that failed (ok false), are counted too. This is not declared.
- **F20 The count is per session.** A new session resets it, as the spec says ("in one session"). Recorded only.

### 3.6 SECRET-OUTPUT and the judge rule "any finding of class SECRET -> STOP"

- **F21 "Class SECRET" now has two meanings.**
  - `.claude/agents/judge.md:11-12` STOPs on any finding of class SECRET. Since M1.2, SECRET is also an engine finding class (`SECRET-OUTPUT.yaml:4`).
  - The gate produces SECRET-class engine findings on every run by design: the positive fixtures and the end-to-end test at `test_rules.py:517-532`.

  - Given F6 and the unmeasured FP rate, any loop that feeds Raqib findings to the judge would STOP on benign placeholder reads.
  - The questions file does not raise this overlap.
  - The commander order (`docs/review/2026-10-16-commander-order.md:22-26`) sends SECRET-class items to the questions file. That file lists none, although F1 is one (in existing code).
