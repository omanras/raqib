MUST-FIX (direction: SILENCE)

R-1. A logged time that is there but does not parse falls back to UtcTime with no word anywhere.
- Where: raqib/discover.py:243-245 (event_time), :226-229 (_ts).
- What I read: `if at is None or when is None: return at, None, None`. The tests lock this in:
  tests/test_event_logged_time.py:113-115 passes "not a time" and "" and expects UtcTime silently.
- Case: SystemTime="11/12/2026 20:43:11", or any non-ISO text from a converter, on an event 3 whose UtcTime is 26 days
  behind. Result: ts is UtcTime, it is "before the watch's start", history, never knocked. This is the field's bug,
  back with no note, no hole and no RAQIB-SILENCE line.
- The threat model (docs/THREAT_MODEL.md:498) names only "no TimeCreated".
- Likelihood: low. wevtutil and ToXml write ISO with Z, and Python 3.11+ parses that (see SOUND). But A3 says an
  unread field is a finding.

R-2. One pass sorts by mixed time bases, so an act can sort before its own process's event 1 and be dropped for good,
  silently.
- Where: raqib/hooks/os_sysmon.py:288 (sort by ts), :363-388 (_tree: `continue` when the guid is not yet in by_guid,
  with no word), :734-735 (top = last_record, so the dropped record is never asked for again).
- Case: a child powershell's event 1 has UtcTime 07:54:02.000 and is logged 07:55:03.100 (61.1 s late, so it takes the
  logged time). Its event 3 has UtcTime 07:54:05.000 and is logged 07:55:04.000 (59 s, so it keeps UtcTime). In one
  pass the event 3 (07:54:05) sorts before the event 1 (07:55:03.1). The guid is unknown, so the event 3 is dropped:
  no line, no silence. The next pass asks above the export's last record, so it is gone.
- The same happens to a child's event 1 that sorts before its parent's event 1: the child's whole subtree is lost.
- Before AM-1 both events used UtcTime, so the order was causal and both were kept.
- Likelihood: low. It needs the logging delay to straddle 60 s between a process's start and its act inside one pass,
  for example a backlog draining after a resume. The field's shape does not trigger it, because there the event 1 kept
  UtcTime and the event 3 moved later.
- Not tested.
- It contradicts THREAT_MODEL:504 "nothing is lost once the logged time is used". If the Table holds this ordering to
  be AM-1's prescribed "order of a tree's lines", it is a question, not a local fix.
