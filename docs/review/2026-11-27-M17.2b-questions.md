## Q1. CI-3's failure is a hole of the result, so the watch's exit becomes 3
The host watch says a failed SetDllDirectoryW(NULL) as `self._hole(self.t0, "own-library-folder", ...)` in
`HostWatch.__init__` (raqib/host.py, beside the "host-rule" holes of the start), the road the watch's other holes
of its own at its start take (host-rule, rounds-unreadable, rounds-corrupt). It is said once (one watch, one
hole, the round None) and is never fatal: the rounds run. But a hole changes the result: measured with the
tests' own watch on win32, two rounds, exit 0 without it and exit 3 with it. Chosen: the hole, because what the
watch starts (wevtutil, PowerShell) may then load the packed copies, so what it reads is not what the system's
own programs would read. The other road is a blind spot (`_blind`, "does not change the result"). Which?

## Q2. Only the host watch says it
CI-3 and E4 name the host watch. A packed Raqib on Windows that is not a host watch (`raqib discover --live`,
`raqib doctor`, `raqib ui`) also starts programs, and a failed call is silent there: the result is kept in
`own.LIBRARY_FOLDER` and nothing else reads it. Should each say it on the error stream at its start (CI-3's
"never silent")? Not built: it would change the error stream of every packed command, which no criterion names.
A packed `raqib-app` has an entry of its own (not cli.main) and makes no call at all (CH-5: not ruled).

## Q4. Linux alone has its loader path put back
LD_LIBRARY_PATH is put back where `platform.startswith("linux")`. The packer's bootloader sets a loader path on
other systems of its own too (the BSDs: LD_LIBRARY_PATH; AIX: LIBPATH); CI-5 lists them as not measured, so they
are handed as they are (only the `_PYI_` names and `_MEIPASS2` go). Windows: `_MEIPASS2` is matched whatever its
case too, as the `_PYI_` names are (the system takes a name in any case). On Linux and macOS the case is exact: a
`_pyi_lower` name stays.

## Q5. What the source test (E3, CI-2) recognises, and what it does not

call, check_call or check_output - by the module or an alias of it (`import subprocess as sp`), by a name taken
from it (`from subprocess import run as r`), or by a name bound to one of those by an assignment (an `x or y`
and an `a if c else b` included), a default of a parameter, a keyword argument, or an attribute
(`self.go = subprocess.run; self.go(...)`), followed three steps. It gives an environment where it has `env=`
of a value that is not the constant None, or `**name` where every assignment of that name in its function is a
dict that holds "env". os.system, os.popen, os.spawn*, os.exec* and os.startfile are found whatever they are given.
It finds today seven starts, each naming its environment: discover.py (ss), doctor.py, hooks/os_sysmon.py (two),

webbrowser, os.posix_spawn, os.fork, a CreateProcess through ctypes, a start passed in from another module by a
name the file never binds to subprocess. None is in raqib/ today (searched). Should the test hold them too?

## Q7. E6, run here: what the packed helper was handed, and what /proc/PID/environ shows
A scratch virtual environment outside the tree (Python 3.12, `pip install . pyinstaller==6.11.1`, the network was
reached), packed by `PYTHON=<venv python> sh tools/rig/pack.sh <scratch>`; the packed watch run as the rig runs it
(`watch --host --rounds 4 --every 3 --no-open --no-page`, HOME a scratch folder), handed LD_LIBRARY_PATH = an
EMPTY scratch folder (nothing in it, counted before the run) and no `_PYI_` name. Run twice:
- Read by a second process from /proc once the helper was there: the helper's /proc/PID/environ held
  LD_LIBRARY_PATH = <packed folder>/_internal:<empty folder>, `_PYI_ARCHIVE_FILE` = the packed program,
  `_PYI_PARENT_PROCESS_LEVEL` = 0, LD_LIBRARY_PATH_ORIG = <empty folder> - the same names the watch's own
  /proc/PID/environ held.
- Read at each exec by strace (`-f -e trace=execve -v`): the helper's FIRST exec (the watch's Popen) was given
  LD_LIBRARY_PATH = <empty folder> and no `_PYI_`, `_MEIPASS2`, LD_LIBRARY_PATH_ORIG or DYLD_ name - exactly what
  was handed to the packed watch. Its second exec, the packed start's own (the bootloader executes itself again
  on Linux once it has put its folder first), carried the four names above: that is the packed start's, as the
  watch's own second exec carried them too.
- PROCESS EVENTS said "rounds asked: 4, answered: 4" in both runs (the kernel's process events are read here);
  no helper ended; the watch exited 0; HOLES (A3): 0.
So a reader of a packed helper's /proc/PID/environ sees the packer's names again whatever it was handed: the
system's record holds the environment of the last exec, which on Linux is the bootloader's own. What tells the
handed environment there is LD_LIBRARY_PATH_ORIG: the helper's equals the value handed to the watch (the empty
folder), not the watch's own LD_LIBRARY_PATH (which it would be, with the packed folder first, were the watch's
environment handed on). CI-5's instrument, run on the system's record, should read the first exec, or
LD_LIBRARY_PATH_ORIG, and not the presence of the `_PYI_` names. For the Table to rule how CI-5 is read.
