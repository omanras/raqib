## 3. Silent assumptions and what A3 / A5 should have caught

### Native protocol (forward.py:434-474)
- **Field names:** all fixed and valid; no event content ever becomes a key.
- **Text vs binary form:** the binary form is used only for a value holding `\n`.
  - MESSAGE is a whole line without its `\n`, so it always uses the text form.
  - RAQIB_ values exclude all C0, DEL and C1 characters.
  - PRIORITY and SYSLOG_FACILITY are decimal digits.
- **Odd bytes:** events are ASCII only (classify, 340-351), so MESSAGE never holds a NUL or invalid UTF-8. RAQIB_
  values may be UTF-8 from `\u` escapes; a lone surrogate is left out.
- **Injection:** none possible.
  - journald searches for `=` only up to the field's own newline, so a `KEY=` inside MESSAGE is just value.
  - A second entry needs an empty line at a field boundary, which no build path can produce.
  - The `.` / `#` control lines would have to start a field, and every field starts with a fixed key.
- MESSAGE is the line byte for byte. A trailing CR is kept (Q8).

### Connected-socket deviation (JournalSend, 838-860)
- **Certain:**
    - connect: a missing path gives ENOENT; a file, a directory or a stale socket gives ECONNREFUSED; a stream socket
    gives EPROTOTYPE. All become `connect`.
    - On Linux, sendto with an address on a connected AF_UNIX datagram socket sends to that address and re-resolves
    the path on each call.
- **Likely:**
  - sendmsg with SCM_RIGHTS plus the address works; journald sees n==0 with one descriptor.
    - Full journald queue: Python's timeout mode makes the fd non-blocking; the connected peer registers a wake-up, so
    poll blocks properly. After 30 s it is `late` and the batch is halved. (An unconnected socket would spin; the
    builder is right on that.)
  - Stop: shutdown wakes the poll, and the retry fails with EPIPE (SEND_SHUTDOWN). The abandoned thread ends at once.
- **Doubt:** if journald restarts mid-batch, the connected peer is dead while sendto finds the new socket, so a full
  queue then spins until the bound. Rare.

### Memory file (sealed, 862-883)
- Seals and fallback constants are correct (1033; 1|2|4|8). Short writes are looped. The descriptor is closed on every
  path, so there is no leak per line.
- Passing `os.MFD_ALLOW_SEALING` alone (870) drops Python's default MFD_CLOEXEC, so the descriptor can be inherited
  across exec while it lives.
- **Doubt:** there is no MFD_NOEXEC_SEAL.
  - Kernels from 6.3 log a warning.
    - On 6.3-6.5 with vm.memfd_noexec=2, memfd_create is refused. Every entry over about 212 KB is then a permanent
    `write`.
    - Where the kernel adds F_SEAL_EXEC by policy, an older journald whose seal check compared exactly would treat the
    file as unsealed and drop it silently while the forwarder says `sent`.
- A persistent `write` re-sends the lines before the long one in the same batch at every J-10 retry. The journal gets
  duplicates every 60 s or less; the status shows FAILING, so it is visible.

### W-3 against M-3

### Pace and the forwarder's machine
- The pace runs inside send(), before after_take. If a beat has passed, a state written during the pace still shows
  the previous `failing` and a cursor before the batch it just handed. The window is 0.4 s at most.
- It cannot be bypassed by `--batch`, small batches or `--once`. It does not delay Stop.
- A journal send never yields `refused`, so no line is ever "in question".

### W-7 as written is incomplete (THREAT_MODEL.md:1285-1300; FORWARD.md:278-281)
