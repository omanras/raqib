## Why E3 needs a ruling

A line is "partial" only when its match comes out unknown. The match
language gives unknown in exactly these cases (`raqib/rules/engine.py:36-44`):
a field it reads is missing; a string test (regex, prefix, glob) meets a
value that is not a string (`engine.py:372`); `has_any` meets a value that is
not a list (`engine.py:355`); a path cannot be placed (`outside`,
`outside_any`). E1 makes every drive-letter and UNC cwd placeable. After
that, a Windows cwd is a readable string, and every predicate that reads it
gives true or false. None of today's forms can say "this value can be read,
but this rule does not judge it".

So E3 needs one of these:

- (a) a new match node. Prototype: `unjudged: <node>`. Where the node is
  true, the line is unknown; where it is false, the line is false; unknown
  stays unknown. Four lines in `_compile`, plus a docstring entry and tests.
  In the YAML:
  `- unjudged: {field: cwd, regex: '^(?:[A-Za-z]:[\\/]|\\\\[^\\/])'}`
  as the third alternative of an `any` whose first two are the POSIX
  branch (unchanged) and the new Windows branch.
- (b) no engine change: an always-unknown predicate in the YAML, made by a
  type mismatch, e.g. `all: [{field: cwd, regex: <Windows shape>},
  {field: cwd, has_any: [x]}]` (a string is not a list, so unknown).

Both give the same verdicts. Measured in the prototype with the Q-5 branch
`(?i)^[a-z]:[\\/]+(?:(?:users|temp|windows[\\/]+temp)|users[\\/]+[^\\/]+(?:[\\/]+appdata[\\/]+local[\\/]+temp)?)?(?:[\\/]+\.)?[\\/]*$`:

With either option, `check-rules` on the old fixtures is unchanged. Also with

field it reads is missing or a path cannot be placed". That is the one fixed

## Questions

- **Q-1 Mechanism.** How should SCOPE-CWD-ROOT say that it does not judge
  a Windows cwd outside its list?
  - (a) a new node in `raqib/rules/engine.py`: `unjudged: <node>` (true
    gives unknown), or another name and shape you rule;
  - (b) the type-mismatch predicate in the YAML, with no engine change;
  - (c) another shape.
  Either way, should the partial note say why (e.g. "the rule does not
  judge this value") instead of the fixed text at `engine.py:494-495`? That
  text is shared by every partial note.
- **Q-2 Consequence.** Please confirm the following, or rule the
  alternative below:
  - every Windows session run from a project directory reads INCOMPLETE
    (exit 3) through SCOPE-CWD-ROOT;
  - `tests/test_watch.py:1046` stays skipped on Windows;
  - SCOPE-CWD-ROOT's `C:\` negative fixture is an unmeasured one (no
    finding, a partial note).

  The alternative: a Windows cwd outside the list is a judged negative, as
  a POSIX cwd outside the POSIX list is today. The Windows directories the
  list omits (e.g. `C:\Program Files`, `C:\ProgramData`, a UNC share root)
  would then be known holes in the description, written like "/etc, /usr
  and /var" (`SCOPE-CWD-ROOT.yaml:9`; `tests/test_rules.py:1079-1088`).
  Under the alternative, Q-1 falls away.
- **Q-3 Path forms E1 does not list.** These arise when the anchor (the
  line's cwd, or the context root) is a Windows path:
  - A rooted path with no drive, `\Users\alice\.ssh\id_rsa`, under cwd
    `C:\proj`. Joined as a relative path it reads
    `c:/proj/users/alice/.ssh/id_rsa`, inside the project: a silent
    SCOPE-PATH miss. Windows reads it on the cwd's drive,
    `C:\Users\alice\.ssh\id_rsa`. The prototype treats it as "cannot be
    placed" (partial). Should it be placed on the cwd's drive, or be
    partial?
  - A drive-relative path, `C:x.txt`. It is relative to that drive's own
    current directory, which the trace does not record unless the cwd is
    on the same drive. The prototype treats it as "cannot be placed"
    (partial). Confirm, or place it under the cwd when the drive matches?
  - A POSIX-absolute path under a Windows cwd: `/etc/hosts`, or the Git Bash
    form `/c/proj/a.py`. "POSIX unchanged" keeps such a path POSIX, so it
    is never inside a Windows cwd or root. SCOPE-PATH fires on it and
    DRIFT-FILES counts it: a false positive, not silence. Confirm. Should
    the Git Bash form go into the descriptions as a known hole, next to the
    WSL one (Q-6)?
- **Q-4 `--root` on Windows (E2, E6).** On Windows `os.path.abspath("/")`
  is the current drive's root (`C:\`, or `D:\` on a GitHub runner). That is
  the cause the ruling names for `ui --scope . --root /` exiting 3 there
  (`raqib/cli.py:206`; ruling Amendment 3). The prototype keeps a root that
  is absolute on either system as given. A POSIX-absolute root is
  normalised with `posixpath.normpath`, which is all `os.path.abspath`
  does to it on POSIX, so POSIX output is unchanged. Only a relative root
  goes through `os.path.abspath`. On Windows, then, `--root /x` means POSIX
  `/x`, not `C:\x`. Is that the meaning you want?
- **Q-5 Text that M5.1b makes false, outside Scope.**
  - `README.md:17` ("On Windows the rules place POSIX paths only until
    M5.1b: ..."), which `tests/test_docs.py:88-89` pins verbatim;
  - `docs/THREAT_MODEL.md:213-214` and `:223-227` (section 7, the "silent
    gap until M5.1b" paragraph).

  Should their platform lines join M5.1b's Scope, or wait for the Table's
  next change? (ADR-0005:215 is a record: amended, not edited.)

## Notes for the REDO (no ruling needed)

- engine.py can import no new standard module. `tests/test_gate.py:339-349`
  holds its imports to `PREIMPORT` at `tools/gate.py:65`, which has no
  `ntpath`, and tools/ is not in Scope. The prototype uses `re` and
  `posixpath` only.
- A UNC path must be recognised by its backslashes alone. POSIX `//x` stays
  POSIX and collapses to `/x` (`tests/test_rules.py:328-329`). Once
  normalised, a UNC path (`//srv/share/x`) looks like a POSIX double-slash
  path, so `_under` must know each placed path's system. Otherwise
  `\\srv\share\x` sits "under" the POSIX root `/` (test_ui's `--root /`).
  The prototype gives `_place` and `_under` a (system, path) pair. For the
  same reason, norm_path is not idempotent on its own UNC output.
- `..` must not climb above a drive root or a UNC share. In the prototype,
  `\\srv\share\proj\..\..\other\x` becomes `//srv/share/other/x`, which is
  outside `\\srv\share\proj`.
- Case folding is `str.lower()`, as `ntpath.normcase` does, not
  `casefold()`: Windows does not fold the German sharp s to "ss".
- New fixtures must come from `tests/fixtures/rules/generate.py`
  (`tests/test_rules.py:780-789`), and each must be listed by its rule
  (`tests/test_rules.py:480-488`).
