## Why E3 needs files outside Scope

E3 asks for SCOPE-CWD-ROOT, SCOPE-CWD-MOVED, SCOPE-PATH and DRIFT-FILES to
use one `norm_path()`, with `C:\...` fixtures, positive and negative. Those
four rules do their path work in files that Scope does not list:

| What | Where | In Scope? |
|---|---|---|
| placing a path: anything not starting with `/` or `~` is unplaceable | `raqib/rules/engine.py:375-389` (`_place`) | no |
| "under" test (`/`-separated, case-sensitive) | `raqib/rules/engine.py:391-393` (`_under`) | no |
| context `root` must start with `/`, else `bad-context` | `raqib/rules/engine.py:413` | no |
| "Paths are POSIX" contract | `raqib/rules/engine.py:41` (docstring) | no |
| SCOPE-CWD-ROOT's cwd regex, anchored on `/` | `raqib/rules/catalog/SCOPE-CWD-ROOT.yaml:15` | no |
| fixture lists of the four rules | `raqib/rules/catalog/{SCOPE-CWD-ROOT,SCOPE-CWD-MOVED,SCOPE-PATH,DRIFT-FILES}.yaml` | no |
| `scope_from_handoff` (the only function there) | `raqib/rules/context.py` | yes |

Adding fixtures under `tests/fixtures/rules/<ID>/` without listing them in
the catalog turns the gate red: `tests/test_rules.py:468`
(`test_e4_every_rule_fixture_file_is_referenced`) requires every fixture file
there to be listed by its rule.

`raqib/rules/context.py` has no route into the rules' path logic. The only
way to do E3 from inside Scope would be to monkey-patch `engine._place` from
`context.py`, and that would get around the scope boundary rather than
respect it. I didn't do it.

## Questions

- **Q-1 Scope.** Choose one:
  - (a) widen M5.1's Scope to add `raqib/rules/engine.py` and

- **Q-2 Where does the one `norm_path()` live?**
  - The installed hook runs `python3 -I capture.py` (`tools/install-hooks.sh:168`).
    Isolated mode leaves the script's directory off `sys.path` (checked here:
    `python3 -I p.py` prints no script directory). So `capture.py` can't
    import `raqib.rules.context` unless it adds the checkout root to
    `sys.path` itself.
  - Options:
    - define it in `capture.py` and have `raqib/rules/context.py` import it,
      so rules depend on the hook module;
    - define it in `context.py` and have `capture.py` add the checkout root to
      `sys.path`;
    - wait for `raqib/hooks/common.py` in M5.2 (ADR-0003). That file is not
      in M5.1's Scope.
- **Q-3 Should the hook apply norm_path at all?**
  - "For comparisons" reads as rules-only.
  - Capture compares no paths today, and writing normalised paths would change
    the recorded evidence (A5). It would also change recorded values, though
    not the schema.
  - My reading: capture records paths as given, and only comparisons
    normalise. Please confirm.
- **Q-4 What does case folding apply to?**
  - Folding every path would change POSIX results. Today `/work/example` and
    `/work/Example` are two directories to SCOPE-PATH and SCOPE-CWD-MOVED,
    and existing outcomes must not move.
  - Proposal: fold case only for drive-letter (`X:\`, `X:/`) and UNC
    (`\\server\share`) paths, and leave POSIX paths case-sensitive as now.
    macOS case-insensitivity stays out of scope.
- **Q-5 Which Windows cwds count as "no project boundary" for SCOPE-CWD-ROOT?**
  - Candidates:
    - a drive root `X:\`;
    - `X:\Users`, `X:\Users\<name>`;
    - `X:\Windows\Temp`;
    - `X:\Users\<name>\AppData\Local\Temp`.
  - This changes an existing rule's match. It isn't a new rule, but it does
    change what the rule judges, so I'm asking first.
- **Q-6 Do WSL and Windows forms of one directory compare equal?**
  - Example: `/mnt/c/Users/x` and `C:\Users\x`.
  - Proposal: no, not in M5.1. They are different sessions with different
    cwds.
- **Q-7 Which shell runs hook commands on Windows?**
  - This needs checking, not assuming. The installed command uses POSIX sh
    syntax: an env-assignment prefix, `||`, `echo ... >&2`, and `$?`. E1 asks
    for "same RAQIB-SILENCE behaviour".
  - If Claude Code on Windows runs hook commands through a POSIX shell (e.g.
    Git Bash), the command can stay the same apart from the interpreter name.
  - If it runs them through cmd.exe or PowerShell, the installer needs a
    second command form, and the RAQIB-SILENCE fallback needs its own test.

## Notes for the re-scoped task (no ruling needed)

- E2: `raqib/hooks/capture.py:485` returns without locking when `fcntl` is
  absent, as ADR-0003 says. `msvcrt.locking` locks are mandatory, and they
  cover a byte range from the current position. If the lock covers data
  bytes, a reader without the lock (`raqib report` during a live session)
  could fail on that range. Locking one byte far beyond EOF avoids that.
- E1: the current installer depends on POSIX file modes, `umask`, symlinks
  and directory fsync (`tools/install-hooks.sh:202-233`). The Python
  installer needs a Windows branch for each, and the existing tests in
  `tests/test_install.py` (lines 234, 464) need to be platform-gated.
- E4: `tests/test_capture.py:4` imports `fcntl` at module level, so the whole
  file fails to import on Windows. That has to change for the gate to run
  there.
