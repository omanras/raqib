VERDICT: STOP. The two most serious holes in what root rights open come from the ruling, not the build. (1) E1's
  letter checks the folders of sys.path, not the files the unit loads from them. (2) The watch, which the HANDOFF
  keeps unchanged, serves the root service's page on loopback to every local user, while ADR-0013 and the new docs say
  no person can read the record. A REDO under this HANDOFF cannot close either. The builder-level should-fixes below
  also stand.

  NOT_RECORDED entry with E2's reason word for word. In test_readme_top.py the builder's hunk is SERVICE_ROWS. The

FINDINGS: what root rights open

F1 (blocker, Table). service.py:314-322 checks only the files and sub-folders directly below each sys.path folder? No:
  it checks only the folder itself and the names ending `.pth` in it (`paths += [... for n in system.listdir(entry) if
  n.endswith(".pth")]`). Nothing else below a sys.path folder is checked:
- the standard library's .py files and sub-packages (encodings/, json/, ...)
- their __pycache__/*.pyc
- lib-dynload/*.so
- sitecustomize.py, which `-I` does not stop, for the same reason AB-3 gives for .pth files
- modules that .pth lines import (for example _distutils_hack/)
A root-owned 0755 folder holding a user-owned or 0666 file, or a user-owned sub-folder, passes. The unit then runs
  that file as root at every start. A-3 says "every folder Python loads from"; E1's letter says "every existing folder
  of sys.path". The letter is met, the purpose is not. What would close it: walk every sys.path folder the way the
  package is walked (every file and folder below it).

F2 (blocker, Table). The unit's watch always serves its page, unauthenticated, on loopback port 8765, or on any free
  port if that one is taken:
- host.py:5197-5203 (`server, watcher.port = watch._serve(...)`)
- watch.py:104 and 1181-1196
- ui.py:1417-1426
- `IPAddressAllow=localhost` (service.py:94) lets it through.
What follows:
- (a) Every local user, the watched agent included, reads the root watch's view: trees, findings, and the cwd/exe of
  other users' processes, which /proc refuses them.
- (b) A root process parses HTTP from any local user.
- (c) A user who binds 8765 first (at boot, or in the 5 s restart window) moves the service's page and can serve a
  forged one there.
- (d) A person's own watch and the service compete for the port.
These say the opposite: SERVICE.md:137 "a person without rights cannot read the record", THREAT_MODEL.md:1553-1555,
  and ADR-0013:65. The builder could not change the watch, so the Table must rule.

F3 (should-fix). The package walk does not enter linked sub-folders. System.walk uses `os.walk(top, onerror=fail,
  followlinks=False)` (service.py:163-168, used at 323-326). os.walk lists a link to a folder among `dirs` but does
  not descend into it. The link and its target folder are checked; the files inside are not. A user-owned module under
  a linked sub-folder of raqib passes, so E1's "every file ... of the raqib package" is not fully met. Fake.walk
  (test_service.py:114-124) does not model this. What would close it: refuse any link inside the package, or walk into
  each one, bounded, and check every file.

F4 (should-fix). The package checked is the install process's own (`os.path.dirname(os.path.abspath(__file__))`,
  service.py:151-152), not necessarily the one `-I -m raqib` will import.
- Run as `python -m raqib service install` from a root-owned folder holding raqib/ (a checkout), the install checks
  the checkout's copy, because sys.path[0] is the cwd.
- The unit drops the cwd and imports raqib from site-packages, whose files are never walked.
- The same mismatch follows from any other difference between the install's sys.path and the unit's: `-S`, a
  PYTHONPATH that sudo keeps, a console script's folder.
What would close it: require the package to sit under a sys.path entry the unit also has, or refuse unless the install
  itself runs isolated (sys.flags.isolated), so the two sys.paths are one.

F5 (should-fix). Code run as root, or holding the unit, is not in the list:
- systemctl at SYSTEMCTLS (service.py:176-180), run as root by the install
- ss at discover.SS_PATHS (discover.py:118), run as root by the unit's watch every round
- /etc/systemd/system and the folders above it: a user who can write there rewrites the unit after the check
What would close it: add these fixed paths to owned_by_root's list.

F6 (should-fix, partly Table).
- sys.path entries missing at install time are skipped whole (`if not _exists(system, entry): continue`,
  service.py:314-315), so the folders above them are not checked. A user who can create one later puts code on the
  unit's path (a sitecustomize found there, for example). Usually the zip's parent is also the stdlib's parent and so
  gets checked, but not by rule.
- A path line in a root-owned .pth that does not exist yet is added by site once it exists. AB-3 forbids reading the
  .pth to find these.
What would close it: check the nearest existing folder above each missing entry.

F7 (should-fix, doc; A-6 question). THREAT_MODEL.md:1543-1545 says the hardening "bounds such a defect". As I read
  systemd's and the kernel's rules (not measured):
- With CAP_SYS_PTRACE, a defect can write any process's memory through /proc using ordinary file calls that
  @system-service allows, because ProtectSystem=strict leaves /proc writable. That reaches unconfined root processes.
- CAP_NET_ADMIN together with AF_NETLINK can change the host's firewall, routes and interfaces.
- CAP_DAC_READ_SEARCH reads every file.
The sentence should say what the three capabilities leave open.

F8 (should-fix, doc).
- THREAT_MODEL.md:1533-1534, "only root can [stop it]": an agent whose user has passwordless sudo (common on cloud
  images) or a valid sudo ticket can stop it, and polkit rules may grant manage-units to a group.
- Any user who can make the watch exit non-zero makes it restart every 5 s, with a gap each time (Restart=on-failure,
  and no SystemCallErrorNumber, so a filtered call is a kill). Hostile process names or cmdlines are one way.
- THREAT_MODEL.md:1539-1540, "stays in its sight": an agent in its own network namespace (unprivileged user
  namespaces) has sockets the host-namespace watch does not see, and RestrictNamespaces keeps the watch from entering.

F9 (note). The A-3 check cannot protect the administrator. `sudo raqib service install` from a raqib a user can write
  has already run that user's code as root (.pth files, the package, the cwd under `-m`) before the refusal.
  SERVICE.md:121 ("refused, by design") says nothing about this. The rig's X28 does exactly this: it runs root's
  python, pip and raqib from a 0777 place.

F10 (note, Table). Shared libraries are outside the check: libpython, the libraries extension modules load,
  $ORIGIN/RUNPATH folders. AB-3 forbids reading the ELF to find them.

F11 (note; each needs root to set up).
- read_head (service.py:170-174) opens with O_NOFOLLOW but without O_NONBLOCK, so a FIFO put at UNIT_PATH between stat
  and open hangs status for every user.
- A foreign unit whose first line is the mark is taken as Raqib's.
- Status does not read FragmentPath or DropInPaths, so a drop-in can change ExecStart or the hardening while status
  says installed and ACTIVE.

FINDINGS: the rest

F12 (should-fix, words, A3). service.py:450-458 prints "RESULT: installed, enabled and started" after `enable --now`
  exits 0. With `Type=simple` (service.py:68), systemctl reports success at fork, before raqib loads. A watch that
  dies at once (import error, SIGSYS, MemoryDenyWriteExecute) is still said to be "started", then restarts forever.
  Nothing checks the silence that follows.

F13 (should-fix, words, A5). service.py:442 prints "every path the unit loads code from is root's alone (ADR-0013
  A-3)". This is narrative, false given F1 and F3-F6, and gives no evidence of what was checked.

F14 (should-fix).
- service.py:511-512 and 526: when there is no file at UNIT_PATH, remove says "nothing installed" and exits 0 without
  asking systemctl. A raqib-watch.service still loaded or running (file deleted by hand, a copy in /run, a transient
  unit) is reported as nothing.
- Status says "RESULT: NOT INSTALLED" when the file cannot be read (service.py:534-541). An unknown state is reported
  as absent.

F15 (should-fix, rig). X28 proves less than it claims.
- The 0777 place (service_run.py:105-107) sits inside `work`, a 0700 root folder under /tmp (line 255). No user can
  reach it.
- The refusal therefore names /tmp, which is sticky (the fixture at test_service_rig.py:36 shows this).
- check.py:625 accepts any named path.
- X28 would be MET even if the walk caught only /tmp. The probe's real case, a non-sticky 0777 folder under a root
  parent, is never exercised.
What would close it: make the place under a root-only, non-sticky parent, and have the check require the named path to
  be that place or below it.

F16 (should-fix, rig). check.py:660-663 gives X30 MET on exit 0, no file, and LoadState=not-found. A unit whose file
  is gone while its process runs is "not-found" and still active. ActiveState is not required, and the effect of
  --purge is not checked.

F17 (note). check.py:615 gives n/a for any facts that carry not_run, whatever --platform says.

F18 (note, rig). Outside a throwaway machine, service_run.py:
- runs root code from a 0777 place (X28)
- has pip fetch a build backend from the network and run it as root
- finds useradd, id and systemd-run by PATH as root (lines 170-180)
- leaves a system user and root's venvs behind
- has nothing that refuses to run outside CI

F19 (note, words).
- service.py:405 says "FAILED (not run)" for a systemctl that ran and timed out; the job it queued goes on.
- service.py:553-557 says "systemctl cannot be run" for one that ran and exited non-zero.

F20 (note, A3, Table). Status ACTIVE (exit 0) says nothing about whether the watch is writing. A blind or stuck watch
  is exit 0.

QUESTIONS FOR THE TABLE
1. Does A-3's "every folder Python loads from" mean every file and sub-folder below each sys.path folder (F1)? Is the
  shared-library gap accepted and said (F10)? How should missing entries and .pth path lines be handled (F6)?
2. The page (F2): should the service's watch serve it in S1 at all? ADR-0013:65 is contradicted by the code. Any
  change touches the watch or E3.
3. A-6: were CAP_SYS_PTRACE and CAP_NET_ADMIN measured as needed, given what they open (F7)? Should "who can stop it"
  name passwordless sudo, polkit, and restarts caused by crashes (F8)?
4. Must the install's sys.path equal the unit's, for example by refusing unless the install runs isolated (F4)?
5. Type=simple versus the word "started" (F12), and whether status or S3 should read the heartbeat (F20).
6. Builder's Q1, my view: the choices are on the refusing side and consistent. A replacing install that does not
  restart leaves a state status cannot name: the file is new, the process runs the old text, and status reports
  ACTIVE, exit 0. The Table should rule either a restart on replace or status saying so. Refusing a relative sys.path
  entry is right, but it comes after the cwd's code has already run as root (F9).
7. Builder's Q2, my view: A-6's "said by the status" is a ruled decision that is not met. Until it is built, an
  ignored directive on a root unit is silence (A3). The gap is said in SERVICE.md, but not in THREAT_MODEL or in the
  command's output. It needs its own task, since a second program goes beyond AA-2's one function. Should the rig
  record systemd's own word on the installed unit in the meantime?
