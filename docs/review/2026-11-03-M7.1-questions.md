## Questions
- Q-1 Where the reader's own pid is recorded. The HANDOFF says "the existing
  self_pid mechanism". On Linux that is proc.txt's snapshot line. The tree now
  writes a first line `# raqib-snapshot at=TIME self=PID sample=K` in each
  live win-process-<k>.csv (before the header; the CSV reader skips `#`
  lines), and parse_win_process turns it into the same `snapshot` record, so
  build() is unchanged and `--from` of a saved run keeps it. Side effect:
  a live Windows inventory's `window.snapshots` counts these lines. An
  exported PowerShell CSV has no such line. Is a comment line in the CSV the
  record the Table wants, or a field in run.json?
- Q-2 DNS names and their addresses. DnsGetCacheDataTable gives names and
  types only, not addresses; win-dns needs the IP (Data) for the endpoint
  join. The tree reads each name's A and AAAA records with DnsQuery_W and
  DNS_QUERY_NO_WIRE_QUERY (the local cache only; nothing goes on the network)
  and frees them with DnsRecordListFree. Each entry and its name are freed
  with DnsFree(..., DnsFreeFlat), the documented way to free what dnsapi
  returns; the next pointer is read before the entry is freed. A name the
  cache holds with no A/AAAA answer is counted in one hole. Is DnsQuery_W
  with NO_WIRE_QUERY acceptable as "read-only, no network", and is DnsFree
  per entry and per name the freeing the Table rules?
- Q-3 What the API does not give. CommandLine is always empty (reading it
  needs another process's memory: PROCESS_VM_READ, beyond A4), so argv is
  empty for every live Windows process. The G-1 `--type=` helper test and a
  footprint path in argv cannot fire live, and names come from the image
  only. TCP CreationTime and the cache's Status, Section and TTL are empty.
  All of this is one hole line (hostwin.NOT_READ), said every live Windows
  run and saved in run.json. Is losing `--type=` on live Windows acceptable
  for act-root (its G-1 narrowing then rests on parent, shell and directory
  only), or must the commander's exports stay the way to judge act-root on
  Windows?
- Q-4 CreationDate. It is filled from GetProcessTimes on the same
  PROCESS_QUERY_LIMITED_INFORMATION handle, as ISO UTC text
  (2026-11-02T08:01:02.000000Z), not the cmdlet's local "11/2/2026 8:01:02 AM".
  The G-6 pid-reuse key only compares the text between samples, so either
  works; a denied process has no CreationDate and joins the existing G-6
  "without CreationDate" hole. GetProcessTimes is not in the HANDOFF's list
  of calls; it needs no right beyond the one listed. Keep it?
- Q-5 pid 0 and pid 4. pid 0 is never opened (it has no image and no
  creation time live), pid 4 is opened and usually gives no path; neither is
  counted as denied (as G-4 exempts them). Toolhelp names pid 0
  `[System Process]` where the CIM export says `System Idle Process`. The
  fixture comparison test expects an empty CreationDate for pid 0.
- Q-6 Options per platform. `--samples N --every T` apply to a live run on
  Windows only; on Linux they are refused (exit 2, "use --window S") rather
  than ignored, and `--window` is refused for a live Windows run (it stays
  for files and Linux). Both are refused with --from/--read. Defaults 6 and
  10 s; N from 1 to SAMPLES_MAX (10000), T from 0 to 86400. Refuse or ignore?
- Q-7 A failed snapshot. In sample 1 it refuses the run: one stderr line
  `raqib: discover refused: Windows live discovery: ...`, exit 2. A Windows
  API that cannot be loaded at all (kernel32/iphlpapi symbol missing) is
  refused the same way. In a later sample the run goes on: that sample's
  win-process-<k> is an unread source with the error (incomplete, A3), its
  TCP and DNS are still read. Is a mid-run failure a hole, or must it also
  refuse?
- Q-8 Partial reads. An enumeration that stops early (Process32NextW fails
  with an error other than ERROR_NO_MORE_FILES, or the 100000-process cap)
  keeps its rows and sets the source's error (incomplete). A
  GetExtendedTcpTable failure for one family keeps the other family's rows
  and sets the error. The table buffer starts at 64 KiB and grows on
  ERROR_INSUFFICIENT_BUFFER, 5 tries.
- Q-9 doctor `host`. On Windows: OK when kernel32 (the Toolhelp and process
  query symbols), iphlpapi GetExtendedTcpTable and dnsapi (its four symbols)
  resolve; OK with "names: no" when only dnsapi is missing; MISSING when
  kernel32 or iphlpapi is. Names are resolved with hasattr on WinDLL; no
  function is called. Elsewhere OK: "live discovery reads /proc (raqib
  discover; Linux)" (macOS: OK, "lists the homes only"). A Windows doctor
  run on a non-Windows host (the tests run every platform's doctor) says
  UNSURE "not checked" for `host`, as the trace line does. The line sits
  before `trace`; tests/test_doctor.py's ORDER and the Windows-form list
  were updated, and its run() helper passes a fake prober. Is OK for macOS
  right, given discover there reads only the homes?
- Q-10 Two existing tests changed. tests/test_discover.py used
  `platform="win32"` to mean "no live reader" in
  `test_e6_live_elsewhere_lists_homes_and_says_what_it_cannot_read` and in
  `test_m50b_e1_save_records_the_sample_count_and_replays`; Windows now has a
  live reader, so they use `darwin`. The "no live reader" hole no longer
  says "in M5.0".
- Q-11 run.json of a live Windows run: `export: "windows-live"`, `apis` (the
  API text per kind read), `sample_times`, `seconds_apart`, beside the
  existing `sources`, `holes`, `connections_from`, `samples`. save() gained
  an `extra` argument for them (never overriding its own fields);
  `connections_from` now lists numbered sources too (it listed only
  unnumbered ones before, so a saved Windows sample run had an empty list).
- Q-12 Structure layout. DNS_CACHE_ENTRY {pNext, pszName, wType,
  wDataLength, dwFlags} is 24 bytes on win64; DNS_RECORDW is declared up to
  its Data union, read only, never allocated here (Data at offset 32 on
  win64). The win64 sizes 568 / 24 / 56 are asserted on Windows 64-bit only,
  as the HANDOFF asks; the TCP row sizes are also asserted everywhere, since
  they have no pointer-sized field.
- Q-13 ADR-0004 Amendment A-1 says "Windows is read from exported files only
  in M5.0" and ADR-0007 decision 1 supersedes it for M7.1; the ADRs are the
  Table's to amend (CLAUDE.md rule 8), so neither is touched here.
