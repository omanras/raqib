## Design questions

1. A name judged in two roles. The venv's folder is above its Scripts folder (the interpreter's) and is itself the
   prefix. Each name's reading is kept (`_Walk.got`), so it is read once; it is judged as a folder above first, then
   as the code itself, and counted once, as code (`_Walk._count`: a name taken as code is never counted above too).
   Meanwhile: read once, judged in both roles, counted once.
2. The deepest thing of an entry not there. The walk reads down the entry's path, judging each folder above by K-3
   as it goes, so the deepest folder that is there has passed K-3 before it is judged by K-2 (itself only). Where the
   deepest thing is a file (a name below a file), K-3 refuses it ("not a folder") unless it was already taken as code
   (then the entry is taken: nobody can add below a file). What a real Windows answers when a name below a file is
   opened (error 3, or another number: refused as not read) was not measured.
3. An entry not there whose drive is not there either (`Q:\x`, or ARM64's `D:\`, error 3): refused, no folder of it
   being there to judge.
4. *.pth names: a name ending in `.pth`, case told apart, as site and the Linux check read them; one marked hidden
   (which a recent site skips) is read even so; one ending in `.PTH` is judged as code only, as site does not read it
   either. A name ending in `.pth` that reads as a folder is refused (site would skip it).
5. *.pth files are read in every entry that is a folder, entries made from *.pth lines included (site reads them only
   in its site folders): as on Linux, the stricter.
6. The raqib package's folder is walked wherever it is, outside every entry too (an editable install's finder is met
   only so, as M's not-read list says), and is not refused for being outside. Whether a package outside every entry
   should be refused on its own (the service's `-m raqib` would import from its path) is the Table's.
7. The roots that must be there (the interpreter's folder, its base's, its prefixes, the package's folder): one not
   there is refused as not read, never judged by M-3.
8. `sys._base_executable` None: no base is walked (the interpreter's own folder is). The same folder as the
   interpreter's: met again, not read twice.
9. Entries of `sys.path` are judged as given, never made whole: one of a form K-4 refuses (a trailing `\`, `..`, a
   relative one, `''`) is refused with its own words, not repaired. *.pth lines are joined to the entry and made whole
   with `ntpath.normpath` (site uses abspath; a line that is a drive-relative path or a share is refused by K-4).
10. `System.read_bytes(path, limit)` returns at most `limit` + 1 bytes and the walk refuses more than PTH_MAX, so the
    bound is the walk's own rule and a stand-in can test it; the Linux twin raises instead. Between the reading of
    the file's owner and list and the read of its bytes, only the system could change it (it was found the system's
    alone, in a folder taken whole).
11. The exit-2 words give the command with the interpreter's path in double quotes, `"PATH" -I -m raqib service
    check` (Program Files holds a space); the path is made printable and cut at 200 as every name said. Both missing
    flags are said together where both are.
12. raqib/cli.py's docstring of the service command (about its line 1643) says raqib/service.py is imported by
    raqib/wincode.py "for its WALK_MAX" only; wincode now imports PTH_MAX and PTH_ODD too. Only the action's help was
    in Scope, so the docstring was not changed.
13. SERVICE.md's paragraph of Amendment L's field run said a plain interpreter got exit 2: kept, marked "(0.11.0,
    before Amendment M)".
14. X50 (tools/rig/check.py): one function, `read_check(text, name, counts_said, option, second)`, reads X49 and X50;
    X49's words are as they were. X50's words name its second answer "the job's own Python"; its first is said "the
    copy in Program Files" as X49's. The pass sentence's pattern is `CHECK_PLAIN_COUNTS` (names, folders, files,
    folders above; the first the sum of the rest), and neither claim's pattern reads the other's sentence (held by a
    test).
15. The measured file's comment lines give each interpreter's path with `...`; the tests write those paths from the
    rows' own folders and a test holds that every entry that is there is a row of the file and that the comments say
    the zips as not there. The ARM64 installer's zip name (`python311.zip`) is not in the file ("the same shape on
    both"). Stand-ins, said in the test: the venv's Lib folder and its raqib package (given its Scripts folder's
    reading), the installer's raqib package (its site folder's reading) and distutils-precedence.pth (os.py's
    reading; bytes `import os`), the folders `C:\hostedtoolcache` and `C:\hostedtoolcache\windows` (a taken folder's
    reading), and every *.pth file's bytes. The folders above (`C:\`, `C:\Program Files`) are measured.txt's x64 rows
    for both machines.
16. A folder's short name (8.3) is not compared with its long one: a folder met by both spellings would be walked
    twice and counted twice, never passed by it.
