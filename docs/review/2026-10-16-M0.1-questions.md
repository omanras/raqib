# M0.1 capture hook: questions for the commander

M0.1 exit criteria E1-E4 are met and `tools/gate.sh` is green. The points
below are design choices that HANDOFF.md and ADR-0001 leave open. The builder
did not decide them: each is either deferred, or given the narrowest behaviour
that satisfies E1-E4. All of them need a commander ruling.

## Open questions (deferred, not answered)

- **Q1 `input_meta.command_head` is undefined.** ADR-0001 §3 names it but
  does not define it. Is it the first token, or the first N characters? Are
  env-assignment prefixes such as `TOKEN=... cmd` skipped? This is a trade-off
  between privacy and rule utility, and M1.2 (destructive-command,
  network-from-tool) depends on the answer. M0.1 writes only `path` and
  `url_host`, never `command_head`.
- **Q2 Session events have no owner.** M0.3 points SessionStart, SessionEnd and
  Stop at `capture.py`, and the M0.2 SILENCE-OPEN rule needs `session_start`,
  `session_end` and `stop` lines. M0.1 is scoped to Pre/PostToolUse, so those
  events currently produce no trace line, only one `RAQIB-SILENCE:` line on
  stderr. Which task owns them? And what is `input_sha256` for an event with no
  `tool_input`: a null field, or the hash of `null`?
- **Q3 Pre/Post pairing.** A post takes the seq of the oldest open pre in the
  same session with the same `tool` and `input_sha256`. If another PreToolUse
  hook rewrites the input (`updatedInput`), the hashes differ. The post then
  gets a fresh seq and the pre stays unpaired, which M0.2 will report as
  SILENCE-HALF. Should the trace carry Claude Code's opaque `tool_use_id` for
  exact pairing? That would be a §3 schema change.
- **Q4 Failed tool calls.** Claude Code reports a failed call as
  `PostToolUseFailure`, not `PostToolUse`. `capture.py` records that event as
  `phase:"post", ok:false`, but only if the hook is installed. If M0.3 installs
  only PostToolUse, every failed call leaves a pre without a post. Should M0.3
  install PostToolUseFailure as well?

## Assumptions made (confirm or overrule)

- **ok:** `false` for PostToolUseFailure, or when `tool_response` has
  `success:false`, `is_error:true` or `interrupted:true`. Otherwise `true`.
- **output_sha256:** the hash of `tool_response`, or of `error` for
  PostToolUseFailure.
- **Canonical JSON for hashes:** sorted keys, separators `,` and `:`, ASCII
  escapes (`json.dumps(v, sort_keys=True, separators=(",", ":"),
  ensure_ascii=True)`).
- **seq:** starts at 1 for each session_id. It is derived by re-reading the log
  while holding an exclusive `flock`. Non-POSIX systems get no lock, so on
  Windows two concurrent hooks may be given the same seq.
- **Uncapturable input:** bad JSON, an unknown event, or a missing
  `session_id`/`tool_name`. The same applies to an unwritable log or a missing
  log directory. In all these cases no line is written, one `RAQIB-SILENCE:`
  line goes to stderr, and the exit code is 0. The log directory is never
  created.
- **`RAQIB_KEEP_RAW`** (ADR §3) is not implemented. It is not part of E1-E4,
  and raw storage is privacy-sensitive. Setting it currently has no effect.

## Environment

- The gate needs `pytest`, which the cloud base image does not include. This
  session installed it with pip. A fresh session's gate fails with
  `No module named pytest` until a SessionStart hook or a requirements file
  provides it. That fix is outside the M0.1 scope.
