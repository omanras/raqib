# M13.1 - questions and choices (ADR-0016: a chain in the events file)

The builder's, 2026-11-20. Nothing here is answered locally: each question is the Table's.

## Q1 (design) - the examples of EVENT.md hold no `prev`

ADR-0016's Consequences say "every example of the events' spec gains `prev`". The examples are lines of
`event.snapshot` from the fixture runs of `tests/test_event.py`, and `pathless()` there writes each run's
temporary home as `~`. Were `snapshot` to chain its own lines, an example's `prev` would be the sha256 of the
line before it *as the machine wrote it*, holding the run's temporary paths: it would differ from run to run,
for every example after a run's first line, not only run D's. `tools/event_examples.py --check` and
`test_e7_each_example_is_what_the_module_builds_from_its_named_run` (it compares every example but run D's line
for line) would then fail on each run.

What this task did: `snapshot` is NOT chained (it "is not how a running watch says events"; nothing but the tests
and the tool calls it); only the writer (raqib/eventlog.py) writes `prev`. The examples were made again by
`python3 tools/event_examples.py --write` and are unchanged. EVENT.md says under Examples that the examples hold
no `prev` and why, and the Keys row says `event.snapshot` gives none. `prev` was added to the tool's VARIES as
HANDOFF E6 asks (for run D's labels it is the document's, as id, n and about are), so that a later ruling needs
no change there.

The question: should the examples show `prev`? Two ways, each outside this task's Scope:
- `tests/test_event.py` `example_events`/`pathless` chains the pathless events of each run again (the examples
  then hold a hash a reader can check over the examples' own run, not over the machine's lines); or
- `snapshot` chains, and `prev` is compared as id, n and about are for every label (the tool's VARIES for all
  labels, and test_event.py line ~1023, which compares the other labels line for line).

## Q2 (design) - what the check calls "beside the chain", and which of a break and a line beside wins

HANDOFF E4 is read so: at a line L of a run that does not name the run's line before it, where L names an
earlier line J of the run (or "first", the run's start) and every line of the run between J and L names the one
before it, those lines between are "beside the chain" (the first of them is said, with their count, and the
line J that L names again); otherwise L is the first break. A run is said by ONE line: the first break where
there is one, else the first lines beside its chain. Consequences of this reading, each tested:
- a line added that names the line before it correctly (its hash computed by another hand) is said as beside,
  not as a break: H-2 says the two cannot be told;
- a line added that names "first" in the middle, or an earlier line of the run copied further on, ends as a
  break at a later line (the line after it no longer names the run's line before it);
- a run whose lines name "first" twice at its start (the start's write raised and left its line) is beside,
  "names the run's start again".
Is this the Table's reading? Should a run with lines beside its chain AND a later break say both?

## Q3 (design) - a line that is JSON but not an event is no link

`event.chains` takes as a link only a line that `event.check` passes (H-2: "a torn line is no event and is no
link"). So a line changed so that it fails the check (a value of a closed list, a `prev` of a wrong form) breaks
the chain at the line after it, beside its own problem. `raqib events` also names an id said twice as a problem
of the second line; `chains` does not use that test (it uses `event.check` alone), so an exact copy of a line is
a link, and is judged by the chain.

## Choices the HANDOFF did not make

- event.py: `PREV = "prev"`, `FIRST = "first"`, `HEX64`; the type of `prev` is named `link` in TYPES and in the
  Keys' list of types ("the word first or a sha256 in 64 characters of lower-case hexadecimal"). `prev` is in
  KEYS after `n`; it is allowed in every kind by `check` beside ALLOWED (ALLOWED itself is unchanged) and
  required by none. A wrong `prev` is one problem: `prev: must be first or 64 characters of lower-case
  hexadecimal (ADR-0016)`.
- event.py: `digest(raw)` (sha256 hex of a line's bytes), `chained(ev, prev)` (a copy with `prev` after `n`),
  `chains(rows)` (one dict per run: run, state whole|broken|beside|not chained, lines, line, named, beside);
  `hashlib` is imported by event.py (it reads no clock, file, network or environment all the same).
- eventlog.py: `EventLog.head` (the digest of the last line written; None before the first). The line is made
  with `prev` inside the guarded build (no new way for `say` to raise); the head moves only after the write
  returned. `prev` is in VARY.
- cli.py `cmd_events`: after the problems, one line per run, `  run <run>: chain whole, N line(s)` /
  `chain broken at line N: ...` / `K line(s) beside the chain from line N: the run's next line names line M
  again (...)` (or "the run's start") / `not chained, N line(s) (...)`. The run's name is escaped as a JSON
  string's inside (a control character never makes a line of its own). The RESULT line is unchanged where no
  chain is broken; else it gains `; N run(s) whose chain is broken` and/or `; N run(s) with a line beside its
  chain`. The function that words a run is nested in `cmd_events` (Scope: only cmd_events).
- tools/rig/check.py: X38 reads `--events-check FILE` (the kept answer of `raqib events`); given and missing or
  empty is MISSED (silence), not given is n/a; this watch's run is the report's `run: ... (seqs` line, and a
  report without it is MISSED. Any line of the answer naming a break or a line beside a chain (of any run) is
  MISSED. X38 is a row of `main` only (as X35), so the counts of `read` are unchanged.
- .github/workflows/rig.yml: a step after the watch on both systems, always run, that writes the answer to
  `$RUNNER_TEMP/events-check.out` (its exit printed and not failing the step), passes it to check.py and copies
  it to the artifact.
- docs/THREAT_MODEL.md: the H-5 entry is placed in section 6 (Attacks on the watcher itself), before "Switching
  the hooks off".
