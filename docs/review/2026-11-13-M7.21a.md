## C. ETW against the SDK, 64-bit (item 2)
Each item is marked certain, likely or doubt, with the symptom a wrong one would give in the field.

**Certain:**
- **WNODE_HEADER = 48 bytes** (Guid 24, ClientContext 40, Flags 44).
- **EVENT_TRACE_PROPERTIES = 120 bytes**:
  - LogFileMode 64, EventsLost 88, RealTimeBuffersLost 100;
  - LoggerThreadId is a HANDLE (8 bytes) at 104;
  - LogFileNameOffset 112, LoggerNameOffset 116;
    - the name goes at 120 in a buffer of 120+4096 with Wnode.BufferSize set to the whole buffer; StartTraceW copies
    the name itself; LogFileNameOffset 0 means real-time with no file.
    - If wrong: StartTraceW returns 87 or 24 (refusal "error 87"), or `lost` is read from the wrong field, which can
    be a loss read as 0.
- **Constants:** TRACED_GUID 0x20000; REAL_TIME_MODE 0x100; PROCESS_TRACE_MODE_REAL_TIME 0x100; EVENT_RECORD
  0x10000000; QPC 1; ENABLE_PROVIDER 1; level 4; error codes 5, 183, 234, 1450, 4201 and 7007.
- **EVENT_TRACE_HEADER = 48, EVENT_TRACE = 88.**
- **EVENT_HEADER = 80** (TimeStamp 16, ProviderId 24, Id 40), **ETW_BUFFER_CONTEXT = 4** at 80, UserDataLength 86,
  UserData 96, **EVENT_RECORD = 112**.
    - If wrong: everything is counted as `other` or unread, or a bad UserData read becomes "not read: OSError" or a
    crash.
- **GUID:** Data1-3 little-endian; the test checks against uuid's `bytes_le`.
- **Callback:** `WINFUNCTYPE(None, c_void_p)`. x64 has one calling convention.
  - It is held in `self._callback` (421). While ProcessTrace runs, the consumer's frame keeps the Reader alive.
- **StartTraceW**(PTRACEHANDLE, LPCWSTR, PEVENT_TRACE_PROPERTIES) returns a ULONG error code.
- **EnableTraceEx2**(u64, LPCGUID, ULONG, UCHAR, ULONGLONG, ULONGLONG, ULONG, PVOID) returns a ULONG code.
  - With Timeout 0 the enable is asynchronous, so a failed enable is never returned (see I-2).
- **OpenTraceW** returns a TRACEHANDLE. INVALID_PROCESSTRACE_HANDLE is 0xFFFFFFFFFFFFFFFF on 64-bit
  (0x00000000FFFFFFFF on 32-bit, which is refused at 400). The reason comes from GetLastError, read through
  `use_last_error`.
    - Nit: the refusal text says "(OpenTraceW returned N)" (429), but N is GetLastError's code, not what the function
    returned.
- **ProcessTrace**(PTRACEHANDLE array, ULONG, LPFILETIME, LPFILETIME) returns a ULONG. It blocks and calls the
  callback on its own thread.
- **ControlTraceW**(u64, LPCWSTR, props, ULONG): handle 0 means "by name"; 4201 means no such session.
- **CloseTrace**(u64): 7007 means close pending.
- **TRACEHANDLE** is u64 everywhere.

**Likely (high):**
- **TIME_ZONE_INFORMATION = 172; TRACE_LOGFILE_HEADER = 280** (BootTime padded to 248); **EVENT_TRACE_LOGFILEW = 448**
  (LoggerName 8, ProcessTraceMode 28, EventRecordCallback 424, Context 440).
    - If wrong: OpenTraceW returns 87, or ProcessTrace jumps to a garbage pointer, an access violation kills the
    process, and the session is left until the next run's leftovers().
- **EVENT_HEADER.TimeStamp** is a FILETIME when RAW_TIMESTAMP is not set. If wrong, `last=` shows 1601 or far-future
  dates.
- **Wnode.Guid zero** is accepted. If wrong, StartTraceW returns 87.
- **Keywords** 0x10 = IPv4, 0x20 = IPv6 (as the Table measured).
- **QueryAllTracesW**(PEVENT_TRACE_PROPERTIES*, ULONG <= 64, PULONG): on 234 it fills the first N entries.

**Doubt:**
- **More than 64 sessions:** the documented array limit is 64, so sessions past 64 are not seen. The code says so
  (594-596).
- **Events before OpenTraceW:** whether events between the enable and OpenTraceW are buffered or lost, and whether
  they are counted (the builder's Q14).

## D. BL-2: every way out (item 3)
**How each failure leaves the session:**
- **A failure at any step of start():** the session is undone (`_undo`, 435-456) for:
  - a refused or raising StartTraceW (no `_session`);
  - EnableTraceEx2;
  - anything between enable and open;
  - OpenTraceW;
  - Thread.start.
- **An exception in the callback:** caught (476-479) and counted as unread. The consumer keeps running.
- **stop() from another thread while ProcessTrace blocks:** STOP, then CloseTrace (7007 accepted), then join(10), else
  said. This is sound.
- **Concurrent stop() calls:** `_state` is not locked (543-545). Two concurrent stops both run, and the second
  produces false "may still run" or CloseTrace problems. This is not harmful.

**Left behind other than by a kill. Yes:**
1. **A BaseException during start().** `start()` catches `Exception` only (389). A KeyboardInterrupt or SystemExit
  after StartTraceW succeeded (410-413) skips `_undo`. `_state` stays "new", so `stop()` returns [] (543), and `with`
  never reaches `__exit__` because `__enter__` raised. Code-certain. A Ctrl-C in the tool's start window does this.
2. **Interpreter exit with a started Reader that is never stopped.** The thread is a daemon (431), and there is no
  atexit hook or finalizer. The session outlives the process. E5's parenthetical names only the context manager, so
  the Table must say whether that is the whole of "every way out".
3. **stop() whose STOP fails.** The state becomes "stopped" (570) and is never retried. This one is said.

**Can leftovers() stop a live watch's session? Yes, by a race.** The tool takes the snapshot (etw_read.py:71) before
  listing sessions (etwnet.py:614). A watch whose session appears between the two has a pid that is not in `alive`, so
  its session is stopped. That watch then says `ended`.

**Pid reuse:**
- A leftover whose number is now another live process is kept, and nothing says so. The tool prints nothing about
  raqib-net-* sessions it kept.
- Worse: a new watch that inherits a killed watch's pid N finds raqib-net-N alive (itself). leftovers() keeps it,
  StartTraceW returns 183, and the watch is refused for its whole life. test_e6_the_name_already_there (573-577)
  asserts this behaviour ("not ours to stop"), so it is a rule only the Table can make.

**Sessions that are not Raqib's:** never touched. The regex `raqib-net-([0-9]+)\Z` is anchored by `match` (59, 618)
  and uses ASCII digits. The negative names at test 522 cover search, IGNORECASE, `\d` and a trailing space.

## E. BL-4 and BL-5 (item 4)
**Can a loss read as zero?** Not from the session counters, which are cumulative, asked at each counts(), and
  "unknown" on any failure. The suspicions:
- **RT_LostEvent events are counted as `other`.** ETW sends these notifications
  ({6A399AE0-4BC6-4DE9-870B-3657F8947E7E}, types 32-34) to a real-time consumer. etwnet.py:487-490 counts them as
  `other`, which the tool prints as "another provider". It is a doubt whether RealTimeBuffersLost always counts the
  same loss.
- **LogBuffersLost (96)** is not read. This follows the HANDOFF.
- **Events before the consumer** (Q14) may be counted nowhere.
- **Turn attribution can slip.** counts() asks for the loss (532) before it copies (533), so a loss between the two
  shows up one turn late.

**Version and length:**
- The event version is never checked (491-497). A later version that moves a field is read wrong, not counted unread.
  That conflicts with BL-5's "not the measured shape ... never guessed" (ADR 2784). The probe's measured version is
  not recorded in BL.
- Data longer than the shape is read as its prefix. A 60-byte event with id 10 would be read as IPv4.

**Thread safety:** the callback and counts() both hold `_lock`. `_state`, `_session` and `_final_lost` are not locked
  between stop() and counts(). That race yields "unknown" with a misleading reason ("the reader is not started", 523),
  never zero.

**Growth:**
- `_connections` has no bound (Q25), and counts() copies it under the lock. A large map slows the callback, which can
  cost real-time buffers.
- `_unread` keys are bounded (by id and exception type).

## G. Parsing (item 6)
- **Pid:** from the data at offset 0, little-endian (339). The header pid is ignored, and the test checks that.
- **IPv4:** the four octets in memory order (342; win:IPv4 is network order). Likely.
- **Ports:** `>HH`, network order (341). Likely.
- **Local side:** saddr:sport for both directions (343), as BL states. "Likely" for receive events;
  Get-NetTCPConnection in the field decides it.
- **IPv6 text:** `ipaddress` compressed form, the same function as hostwin.py:372-373, so a join on one interpreter
  compares like with like. No scope id on either side. IPv4-mapped text changes between Python 3.12 and 3.13 (likely);
  this matters only for text compared across interpreters.

## H. The builder's field list and its design questions (item 7)
**Missing from the field list:**
- BL-2 evidence in the field: `logman query -ets` showing no raqib-net-* after (a) a clean run, (b) Ctrl-C during the
  wait, (c) `taskkill /F` followed by a second run that names the leftover.

- The size of `unread` from UDP ids 42/43/58/59.
- RT_LostEvent arriving as `other`.
- The delivery lag (I-3).

**The three design questions.** These are my positions; the rulings are the Table's.
- **Q22 (connect/disconnect counted as unread):** the builder followed E3's text. But ids 12-18 and 28-34, plus UDP
  42/43/58/59, all carry keywords 0x10/0x20. So `unread` will never be zero on a live machine, and stops being an
  alarm (CLAUDE.md rule 4). I would rule to count ids outside {10, 11, 26, 27} separately, and keep `unread` for those
  four ids failing the shape or the read.
- **Q25 (the map with no cap):** harmless for a 30 s tool, but unbounded for an M7.21b watch. I would rule a cap whose
  overflow is a counted hole (A-1), decided before M7.21b. Pruning on disconnect would need ids 13/29, which E3 now
  puts in unread.
- **Q26 (sums and last time only):** this matches Linux, which reads per-socket cumulative bytes_sent/bytes_received
  from `ss -tinp` (discover.py:1345-1414). Two differences need a rule:
  - ETW sums outlive the connection, while Linux's counts vanish with the socket.
    - The reader keeps only the last time, which narrows BL-5's per-event "the time". The Table should state that
    narrowing explicitly.

## I. Not asked about (item 9)
1. **The Windows CI test failure** (B, E7). This is the main finding.
2. **"Heard nothing" is not said (A3).** A failed asynchronous enable or wrong keywords both show as zero connections,
  `unread=0`, `lost=0`. There is no count of provider events seen.
3. **Delivery lag and ordering.**
      - counts() lags the kernel by up to FlushTimer (1 s) plus the per-CPU buffers. The tool reads before stop()
     (etw_read.py:83), so its last second is missing. In M7.21b, a quiet turn can be a late delivery.
      - Real-time delivery is not time-ordered across CPUs, so `last` (507) is the last event delivered, not the
     latest timestamp. Doubt.
4. **UDP/QUIC bytes are counted as "unread: id 42/43/58/59".** An agent on HTTP/3 has no counted bytes. This is a
  blind spot to state for M7.21b.
5. **A non-finite wait crashes the tool.** `etw_read.py SECONDS=inf` makes time.sleep raise OverflowError, with a
  traceback. The session is still stopped by `with`. Trivial.
