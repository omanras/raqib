# M12.4c2b2b - questions (the builder, 2026-11-27)

Task: `raqib service install | remove` on Windows, by the system's own calls (ADR-0013 Amendment X). Built on Linux,
where none of the system's calls can be run. What was built meanwhile is said under each question, with why. Nothing
here is answered locally; each is the Table's.

## What was built

- raqib/wininstall.py (new): one system object, `System`, whose methods are the system's own calls and nothing else:
  `make_manager` (OpenSCManagerW, 0x3), `connect` (OpenSCManagerW, 0x1, for remove), `create` (CreateServiceW, its
  thirteen arguments: the name, `Raqib watch`, 0x10017, 0x10, 2, 1, the command, then five NULLs), `describe`,
  `failure_actions`, `failure_flag` (ChangeServiceConfig2W at levels 1, 2, 4), `start` (StartServiceW(h, 0, NULL)),
  `state` (QueryServiceStatusEx, level 0), `open_to_remove` (OpenServiceW, 0x10025), `stop` (ControlService(h, 1,
  &SERVICE_STATUS)), `delete` (DeleteService), `close` (CloseServiceHandle), `sleep` and `clock` (time.sleep,
  time.monotonic). Each returns (what it did, 0), (None, the system's number) or (None, words); none raises. advapi32
  is loaded as raqib/winmanager.py loads it, at the first call; every call's types are declared; the six structures
  are held field by field (tests/test_wininstall.py STRUCTURES).
- `install(system, out, start, code, place, reader)` and `remove(system, out, reader)` in X-3's and X-6's order;
  `cli_run` for raqib/cli.py. The reader (raqib/winmanager.py's System) is used for three things: to ask whether the
  name is there before the making (its `open`, 0x5), to read the mark (its `description`), and `status` at the end
  of an install; the name asked for again after a removal is asked with it too.
- raqib/cli.py `cmd_service`: install and remove on win32 go to the new module (imported there only); on Linux as
  before; status on Windows unchanged. The help, the module's and `cmd_service`'s docstrings say it.
- tools/rig/check.py X54 (`--service-install FILE`) and its tests; docs/specs/SERVICE.md (a new section after the
  status's, and the three sentences that said install was not built), docs/GUIDE.md (the two rows, one paragraph,
  and the status paragraph's sentence "Raqib does not install a service of Windows yet"), docs/THREAT_MODEL.md (one
  paragraph, and the sentence "Keeping such a tree from running as the system at all is the install's, not built
  yet", which was no longer true).

## Questions

1. **The rights of the made handle: 0x10017, not the 0x17 measured.** HANDOFF E1 says 0x10017; Amendment X measured
   CreateServiceW with 0x17. The DELETE right (0x10000) is added so that a setting that fails can be undone with
   DeleteService on the same handle (E2). The removal measured used a handle opened with 0x10024, which holds DELETE,
   so DELETE was given an administrator; CreateServiceW asked with 0x10017 was not itself measured. Built: 0x10017.
2. **The rights of remove's handle: 0x10025, not the 0x10024 measured.** 0x1 (SERVICE_QUERY_CONFIG) is added to read
   the mark (QueryServiceConfig2W needs it) on the same handle before anything is stopped. Not measured as such.
   Built: 0x10025, as E4 says.
3. **Two objects, not one.** E1 lists the writing calls for one object; the mark, the asks of the name and the
   status are read through raqib/winmanager.py's System (the reader: 0x1, 0x5), as X-2 says the install reads its
   own work back through it. The reader's `open` and `description` are called on a manager handle wininstall opened
   (0x3) and on remove's service handle (0x10025): one process's handles, so they serve both, but each object loads
   its own advapi32 and declares its own types. In tests one stand-in serves both. Is that the form the Table wants,
   or should wininstall's object carry its own QueryServiceConfig2W?
4. **The name asked before the making.** E2 puts "no service of the name" before the command; it is asked with the
   reader's OpenServiceW (0x5) and, where there, its description is read and said (Raqib's: remove it first;
   another's: not Raqib's). CreateServiceW's 1073 and 1072 are said as well (a name made in between; one marked for
   removal). A service marked for removal that OpenServiceW still opens is read by its mark as Raqib's and said as
   "remove it first": not measured how OpenServiceW answers for such a service.
5. **The place's reading (X-8).** `place_judged` reads the place by `winservice.System.read_place` and judges it by
   winservice's constants and its private `_drive_path`, `_why` and `owner_and_list`, as `prepare` judges a found
   place; a test ties each refusal to `prepare`'s number for the same reading. ProgramData is read from the
   installing process's environment, while the runner reads the system's: the same on the machines measured, but
   the two are not the same reading. A place that cannot be read with error 5 says "an administrator is needed",
   since this step comes before the manager is opened. "Not there" is the reader's error 2 or 3 (wincode.NOT_THERE,
   measured in M-3 by the same reader). Should the order put the manager before the place?
6. **The bounds.** The start: (START_WAIT_HINT + CHECK_WAIT_HINT) / 1000 + 15 = 80 s; the stop: STOP_WAIT_HINT / 1000
   + 15 = 45 s; asked every 0.25 s. The margin of 15 s is the builder's; X-4 says "and a margin".
7. **remove's roads not ruled word for word.** A service not STOPPED at the stop's bound: nothing is removed, 1 (not
   DeleteService on a running service, which would mark it and leave it running). A Stop answered by any number but
   0, 1062 and 1052 (e.g. 1061, it is stopping already): said, nothing removed, 1. A second 1052 after the wait:
   said, nothing removed, 1. DeleteService answering 1072: taken, and the name is asked for again.
8. **status's lines inside the install.** They are written indented by two, so that the install's own RESULT is the
   one line that begins `RESULT:` (status's own is `  RESULT: ...`). Called, not copied.
9. **The failure actions' texts.** lpRebootMsg and lpCommand are NULL (documented: unchanged; on a service just made
   they are empty). Amendment X does not say what the probe handed.
10. **The plain road's refusal.** A plain interpreter not started with `-I` (or with `-S`) is refused 1 after the
    check's own words, with one more line: the command to run the install by, `"<python>" -I -m raqib service
    install`.
11. **--no-start.** Ends after the three settings with 0; no status lines (E2: "ends there"). Its line says the system
    starts the service at the machine's next start (automatic): a start at boot is not measured (X-9).

## Where the real calls could not be checked here

Every call below is run only behind stand-ins and a made-up advapi32 on Linux; ctypes there passes the arguments
without the declared conversions (the made-up library takes them raw), so what follows is read against the documents
and Amendment X's paragraph, not run:
- CreateServiceW's thirteen arguments and their declared types, and its HANDLE result (NULL read as None).
- ChangeServiceConfig2W's third argument as `byref(structure)` through an LPVOID (as winmanager's QueryServiceStatusEx
  passes it, which was measured): SERVICE_DESCRIPTIONW, SERVICE_FAILURE_ACTIONSW with its SC_ACTION array set into its
  POINTER field (the array kept alive by the structure and by a local until the call returns), and
  SERVICE_FAILURE_ACTIONS_FLAG (one BOOL). The structures' layout on x64 and ARM64 (the made-up library read the
  fields back from the memory handed, on Linux x64 only).
- StartServiceW(h, 0, None) through POINTER(LPCWSTR); ControlService(h, 1, byref(SERVICE_STATUS)) through
  POINTER(SERVICE_STATUS); DeleteService; OpenServiceW with 0x10025; OpenSCManagerW with 0x3.
- That ctypes.get_last_error() read at once after each failing call gives the numbers measured (5, 1052, 1060, 1062,
  1072, 1073).
- The waits by time.monotonic and time.sleep (each test fails if the real ones are asked; the real-object test makes
  the clock up).
- That `raqib service status` reads ACTIVE within 80 s of a real start from the copy under Program Files.
