These are the design points I met and did not settle (SESSION_PROTOCOL 5).
Each one says what the tree does now. I chose the behaviour in each case only

## What was built
- E1 `raqib app [PROJECT] [--log PATH] [--no-notify] [--port N] [--refresh N]`
  (`raqib/cli.py` -> `raqib/app.py`), and a `raqib-app` gui-script
  (`[project.gui-scripts]`, `raqib.app:gui_main`; on Windows pip builds a
  pythonw launcher). The first screen shows doctor's lines, coloured OK /
  MISSING / UNSURE. Doctor runs in a thread through `doctor.checks()`, a split
  of `doctor.run()` that changes nothing it prints. Then come the Project
  field, Browse..., Check again and Start. The watching screen shows the band
  (the `ui.status` word and detail, the `ui.band_items` badges), the findings
  grouped by `ui.severity_groups`, the holes, the page URL (read-only field)
  and Stop. When the watch ends the screen shows FINISHED, the
  `watch.finish()` final report and Back. `dependencies = []` stays.
- E2 The `watch.command()` loop is split into `start()`, `loop(running,
  stop=None, on_step=None)`, `conclude()` and `close()`, plus a `Stop`
  (threading.Event). `command()` is these four in order, and its output is
  unchanged: every watch test passes untouched, and the only changed line is
  the page line. That line says "Stop stops the watch" only when a Stop is
  given; the terminal still says "Ctrl-C". `app.Session` runs the four in a
  worker thread. `Session.state()` copies `Watch.state()` under the Watch lock
  (0.2 s timeout; after that it shows the last state and a hole line). The
  window reads that state in its `after()` tick every 500 ms. It never reads
  the page. Nothing in app.py or tray.py starts a program, opens a socket or
  signals anything; a test parses both files for this.
- E3 `notify.FirstFinding` covers the first live, settled finding of a watch
  of any severity. It knocks once, through the watch's own Notifier, under
  rate-limit id "FIRST-FINDING (window)". Title: "Raqib: FIRST-FINDING". Body:
  "project <name>, <rule> <severity> seq <n,...>", cleaned to the A-4
  alphabet and 120 characters; the summary is never included. It is called
  from `loop`'s `on_step` in the worker, with the Watch lock held.
- E4 `raqib/tray.py`: ctypes only. A hidden message-only window (HWND_MESSAGE)
  with a WINFUNCTYPE WndProc and Shell_NotifyIconW (NIM_ADD/NIM_DELETE). The
  icon is drawn in code: `icon_masks()` builds AND and XOR bitmasks of an eye,
  passed to CreateIcon at the SM_CXSMICON size. A left click means Show; a
  right click opens TrackPopupMenu(TPM_RETURNCMD) with Show / Stop / Quit.
  "TaskbarCreated" re-adds the icon. Actions are put on a queue that the Tk
  tick drains, so the tray thread never calls Tk. Any failure is a returned
  reason or a `holes` entry, shown in the window's footer as "hole: tray:
  ...". Off Windows, `start()` returns "no tray on this platform (linux): ...",
  shown as "note:" rather than "hole:" (see Q-4).
- E5 Without tkinter: one sentence naming python3-tk, exit 2. This was tested
  here, where it is the real condition. On X11 with no DISPLAY, and when Tk()
  itself fails: exit 2, one sentence. Doctor gains a `tkinter` line
  (OK / MISSING / UNSURE). tkinter and ctypes are imported only inside
  functions. Nothing deprecated or removed is used; a test checks the imports
  against the PEP 594 list. The install CI job runs `raqib app --help` and
  expects the doctor tkinter line on runners.
- E6 README: section "The window", three lines, after "Doctor". The M6.3
  test pins the first three headings, so it cannot come earlier.
- Tests: `tests/test_app.py` (33 tests, of which 2 run only under Tk with a
  display and 1 only on Windows) and 4 tkinter tests in `tests/test_doctor.py`.
  The fake doctor environment now gets DISPLAY and a fake tkinter importer, so
  the old doctor tests keep their meaning.
- Verified outside the tree: this sandbox's python3 has no tkinter. I fetched
  a standalone CPython 3.12 with Tk 9.0 (uv, into the session's scratch
  directory, not the tree) and ran `tests/test_app.py` under Xvfb: 32 passed,
  1 skipped (the Win32 tray). I also ran an end-to-end smoke of `app.run`
  (doctor screen, Start, a DESTRUCT-CMD finding shown, close, FINISHED with
  the final report, exit 1). The Win32 tray itself was not run anywhere. Its
  first real run is the windows-latest CI job
  (`test_e4_real_tray_starts_and_stops_or_says_why`), which accepts "it says
  why" as well as "it is up". See Q-9.

## Questions

Q-1 What the first-finding knock counts. ADR-0006 says "the moment the first
finding of a watch lands". The tree counts the first finding that is live
(not history, B-3) and settled. Pending SILENCE-OPEN and SILENCE-HALF are
excluded because B-1 says they can be taken back. History findings never
knock (B-3). A watch that only ever sees history findings gives no first
knock. Should a pending finding knock at once instead, or should history
count?

Q-2 Where the knock lives. The HANDOFF puts E3 "via the Notifier", and
notify.py is in Scope. So the knock is `notify.FirstFinding`, driven from the
window's worker by `loop(on_step=...)`. `raqib watch` in a terminal does NOT
give the first-finding knock: the tree reads E3 and ADR-0006 as features of
the window. Should `raqib watch` knock on the first finding too? That needs
one line in `watch.command()`, which this HANDOFF limits to "loop split
only".

Q-3 The knock is not written into watch.json or the final report. Its
outcome is in the window's log ("first finding of this watch knocked: ...
(status)") and in the notifier's counts and holes, which are in watch.json.
A failed knock is a notify-failed hole there and a "hole:" line in the
window. Should watch.json carry a `first_knock` field? That would be a
watch.py change beyond the loop split.

Q-4 "Linux: no tray, recorded." The tree records it as a note in the
window's footer ("note: tray: no tray on this platform (linux): the window
stays open; closing it stops the watch"), not as a hole, because it is by
design (ADR-0006), not a failure. It is not written to watch.json. Is a note
enough, or must it be a hole?

Q-5 Close without a tray. While a watch runs, the close button stops it
("window closed", like Ctrl-C) and leaves the window open on the final
report. A second close quits. With a tray, close hides the window and the
tray's Quit stops the watch, waits up to 30 s for the final report and
exits. Should close without a tray ask first, or quit at once after
finish()?

Q-6 The page is not opened in a browser by `raqib app`. The worker calls
`watch.start()` with no_open=True, and the URL is shown in a read-only field
that can be copied. E1 lists "page URL" on the watching screen, and opening a
browser from the window is a second window the person did not ask for.
Should there be an "Open page" button (watch.open_page, same opener) or an
`--open` flag?

Q-7 Exit code and console output of `raqib app`. It exits with the last
watch's final exit (0 if no watch ran, 1 if the last one failed to start),
and writes the final report to stdout after the window closes. Under the
pythonw gui-script stdout is a buffer, and the report is in the window and in
<trace>.watch.json. The watch's own lines also go to stdout as they happen
(tee). Is that the intended contract?

Q-8 Doctor's tkinter line. MISSING when tkinter cannot be imported. On X11
with no DISPLAY it is UNSURE (Wayland is covered only through XWayland's
DISPLAY). Doctor's exit is 1 on MISSING, so a server that only runs
`raqib watch` and lacks python3-tk now gets a doctor exit of 1. Should a
missing tkinter be UNSURE instead, since watch does not need it? The CI
install job expects whichever applies on the runner (setup-python ships
tkinter; the Linux runner has no DISPLAY: UNSURE).

Q-9 The Win32 tray is unverified on a real desktop. The windows-latest runner
has a session but maybe no shell tray. The test accepts either the icon
coming up or a returned reason. It asserts that start/stop never raise and
the thread ends. A field test is needed: the icon is visible, the right-click
menu works, and close hides to the tray. Is CI plus the commander's field
test the acceptance, or is a recorded screenshot wanted?

Q-10 Tk on Windows CI. The two Tk tests run there (tkinter plus a display).
They withdraw the root, use no mainloop, and drive `tick()` and
`root.update()` by hand. If the runner's session cannot create a Tk window,
they skip with the TclError text and do not fail. Acceptable?

Q-11 One watch at a time. The window watches one project; Start is refused
while a watch runs ("a watch is running: stop it first"). Back returns to the
first screen after a watch ends, and a new Start makes a new watch (a new
registry row). More than one project per window is not built.

Q-12 `Session.state()` copies the whole state (deepcopy, as `Watch.page()`
does) every 500 ms. On a very long trace this costs the same as a page
render. It was accepted for the page (B-9 W18); the same is assumed here.
