# M10.3 REDO - the builder's questions (ADR-0011 Amendment L)

The forwarder over HTTP, rebuilt for L-1 to L-11 on claude/M10.3. Each question below is a place where L's
words (or the HANDOFF's) did not decide, said as built; then what could not be tested here. None is answered
locally (CLAUDE.md rule 6).

## Built where the words did not decide

Q1 (L-1, the bound of one try). The lines in question of one try are bounded: at most 100
(`QUESTION_MAX`). When 100 lines in a row are refused alone and no later line is taken, the forwarder is
failing `refusing` and tries again as J-10 says - and each try sends those lines alone again (up to 100
requests a try, the waits between tries 1, 2, 4 ... 60 s). Is 100 right, or should a try stop at the first line
in question and one batch after it?

Q2 (L-1, what waits with a line in question). A line after a line in question that is not an event (skipped)
or is over 512 KiB (refused locally) is not passed on its own: it waits with the lines in question and is
passed, in order, only when a later line is taken. Built so that the cursor never passes a line in question.
A file whose last line in question is followed only by lines that are not events keeps its cursor before that
line until an event after them is taken.

Q3 (L-1, a restart). The state holds no list of the lines in question: a restarted forwarder starts at its
cursor (before the first of them) and sends them again. How many lines are in question is said in the
forwarder's output line ("N line(s) in question from offset O"), not in the state. Should the state say it
(a key J-9 does not have)?

Q4 (L-1, K-2, `--once`). A line refused and passed in a run makes `--once` exit 1 (K-2, Q8 kept), and a run
that ends with lines in question is 1 as failing. A run whose only refused lines were counted in an earlier
run is 0.

Q5 (L-2, behind). Kept as built and accepted (K-2): BEHIND where `behind` is above 0 and the last taken send is
more than a beat older than the state's `written`. A forwarder that has never had a send taken (`last_ok`
null) and is behind is BEHIND at once, not after a beat. A state whose `beat` is not a finite number above 0
is UNREADABLE (3); a beat between 0 and 1 in a state is read (the forwarder itself refuses one at its start).

Q6 (L-3, the start). "After the start" is built as: the pid file taken, the state read, and the first state
written. A usage error before that - a second forwarder of the name, a damaged state, a state of another file
or destination - writes no state, so that the state that is there stays as it was for the person to see.
After the start no usage error is raised by the loop now (a token file that fails is a failed try); the
handler that writes the state before a usage error ends the run is kept for any that comes.

Q7 (L-3, the unforeseen error's word). The state says `unforeseen` and nothing more. The output line names the
error's class (for example `RuntimeError`), never its text or a traceback; the exit is 1. Is the class name
(the interpreter's word, not the forwarder's) acceptable in the output?

Q8 (L-4, the request's own bytes). L-4 bounds the connect (10 s, the handshake included) and the answer (30 s
from the request's last byte). Sending the request is bounded too: 30 s from its first byte (a collector that
does not read the body cannot hold the forwarder). Is the answer's bound the right one for that phase?

Q9 (L-4, a send that does not end). A send abandoned (Stop, or its bound) has its sockets shut down and, after
0.5 s, closed. A send's thread blocked in the system's name resolution has no socket to shut down: the
forwarder goes on without it and the thread ends when the resolver returns. Each such try may leave one such
thread; their number is not bounded by the forwarder. The documents say name resolution is the system's and
`--status` says SILENT for a forwarder held longer than two beats.

Q10 (J-9, after every batch). In the line-by-line sends of L-1, the state is written (and flushed) after each
line taken alone - up to 100 writes for one refused batch - so that a kill between them sends no taken line
again.

Q11 (L-5, the context built by hand). The TLS context is ssl.SSLContext(PROTOCOL_TLS_CLIENT) with what
create_default_context sets for a client (certificate and host name required; from Python 3.13 its two more
verify flags), without the key log. A test compares the two attribute by attribute on the running Python; a
future Python whose default context changes will be seen by that test on the Python that runs it.

Q12 (L-6, a host name). A name with a final dot (an absolute name, `collector.example.`) is refused as no valid
name, as is a name with an underscore. Should the final dot be taken?

Q13 (L-6, a state that is damaged). Built wider than "JSON and not this schema's": a state file that is not
JSON, is empty, or cannot be read is a usage error too, never a first run (`--from end` included).

Q14 (L-8 and K-2, "sent when its newline comes"). E6 says the long tail is "sent when its newline comes". A
tail of more than 512 KiB becomes a line of more than 512 KiB, which K-2 refuses locally (counted, its id kept,
passed, never cut). Built: when its newline comes it is refused locally and passed, and the lines after it are
sent. To name it (its id), that whole line is read once into memory: L-8 bounds the tail with no newline, not
a whole line. Should a whole line over 512 KiB be named from its first bytes only (bounded), or by its offset?

Q15 (L-10, X21). The kill comes while the stand-in collector holds its second request (by its count); the
batch is `min(5, lines // 4)` lines, at least 1. An events file of one line gives no second request: X21 is
then MISSED as "not between two batches" (after the rig's 60 s wait for the held request). The rig's watch
writes more than that; should such a file be n/a instead?

## What could not be tested here

- Windows: Stop by CTRL_BREAK_EVENT on a real process (the test's Windows branch), the pid file published by
  os.rename, a socket shut down from another thread during a send (Stop during a send), the Windows process
  list (Get-CimInstance Win32_Process) that X22 reads, and the token file whose mode is not checked there. The
  tests have their Windows branches; they ran here on Linux only.
- Python 3.11 and 3.12: the forwarder's focused tests (tests/test_forward.py, tests/test_forward_rig.py,
  tests/test_rig_check.py, tests/test_readme_top.py, tests/test_docs.py) ran here on Linux under Python 3.11
  and 3.12 as well as 3.13; the gate ran under 3.13 only.
- The rig itself (.github/workflows/rig.yml): only its text is tested; X19 to X22 ran here over a made-up
  events file, not over a watch's.
- A name resolution that does not return: not tested (no resolver here can be made to hang).
- A real HTTP event collector (J: not here).
