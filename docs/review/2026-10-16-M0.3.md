## 3. Silent assumptions, bugs, and rules that should have caught them

### 3a. Ways the hook could block or crash the agent
- **B1 (high): exit status 2 when capture.py is missing.**
  - The hook is `python3 <absolute path>` (`tools/install-hooks.sh:60`). If that file is gone at hook time (checkout moved, renamed or deleted, a temp clone removed, a branch without the file), CPython exits with **status 2** ("can't open file").
  - Claude Code treats exit 2 as a blocking error: on PreToolUse the tool call is blocked; on Stop, stopping is blocked and stderr is fed to the model on every turn.
  - This contradicts `raqib/hooks/capture.py:14` ("Never blocks the agent"), `README.md:33-34`, and A4.
  - No `RAQIB-SILENCE:` line is written (A3). No test covers removing or moving the checkout after install.
- **B2 (medium): the hook's Python is not isolated.**
  - The hook runs whatever `python3` is on the watched session's PATH, with that session's `PYTHONPATH`. PYTHONPATH entries come before the stdlib, so a `json.py`, `re.py` or `hashlib.py` reachable there shadows capture.py's imports.
  - The imports are at module level (`capture.py:30-41`), outside `main()`'s try. An import failure therefore exits 1 with a traceback and no `RAQIB-SILENCE:` line. A shadow module could also exit 2 (the B1 effect).
  - The watched agent can edit `.claude/settings.json` (builder's Q1), including its `env` key. I did not verify that Claude Code passes that env to hooks.
- **B3 (low): the installer imports from the caller's cwd.**
  - The installer runs its Python from stdin (`python3 -`, `tools/install-hooks.sh:35`), which puts the caller's cwd first on `sys.path`.
  - Run from inside the watched project, as the builder did (`questions.md:13`), it would import that project's `json.py`, `shlex.py` or `tempfile.py` if present.
- **B4 (low): hook latency.**
  - No `timeout` is set (`tools/install-hooks.sh:87`). Every hook reads the whole log under `LOCK_EX` (`capture.py:276-280`, KNOWN-DEBT F2), and session events add more reads per turn.
  - This does not block, but each event can be delayed up to Claude Code's default hook timeout.

### 3b. Shell quoting in the installed command
- **Q1: quoting is untested.**
  - `shlex.quote` is correct for POSIX sh (`tools/install-hooks.sh:60,62`). But the test builds its expectation with the same function (`tests/test_install.py:19,222`), and every path in the gate (`/home/user/raqib`, pytest `tmp_path`) is quote-free.
  - A mutant that drops `shlex.quote` at `:60` or `:62` therefore survives. No test uses a checkout or log path with a space, quote or `$`.
- **Q2:** `--log ""` silently means "no log" (`tools/install-hooks.sh:61`).
- **Q3 (low):** CDPATH is not neutralised (`tools/install-hooks.sh:18,33`). With CDPATH set and a relative argument, `cd` prints the directory, and the captured path becomes two lines.

### 3c. JSON merge edge cases and the atomic write
- **M1: the file is rewritten on every run.**
  - The write at `tools/install-hooks.sh:116-125` is unconditional, even when all six events report "unchanged". Effects:
    - a user's file is reformatted even though nothing "changed";
    - the new file gets `mkstemp`'s mode 0600 instead of the original mode;
    - a symlinked `settings.json` is replaced by a regular file;
    - ownership is not preserved.
  - `README.md:37` and `tools/install-hooks.sh:9-10` ("changes nothing") hold byte-wise only for files last written by the installer. No test checks mode or symlinks.
- **M2 (low): no fsync.** The write is atomic for readers (temp file in the same directory, then `os.replace`), but there is no fsync before the replace, so durability after a crash is not guaranteed.
- **M3: foreign hooks can be deleted silently.**
  - Any hook whose command merely contains `raqib/hooks/capture.py` (`:43,83`) is removed. That includes user hooks that only pass it as an argument, and a deliberate second Raqib entry with a different `--log`.
  - The report prints only "updated" and does not list what was removed.
- **M4 (A3): re-running without `--log` moves the trace.**
  - Re-running without the original `--log` silently changes the trace location (reported only as "updated").
  - The trace then splits across two files, and seq restarts at 1 in the new one. This is a gap the SILENCE rules cannot see.
- **M5 (low):** Python's `json` accepts duplicate keys (last one wins) and NaN/Infinity. The rewrite drops the earlier duplicates and can emit non-standard `NaN`.
- **M6 (low):** user keys added to Raqib's own group (for example `timeout`) are dropped on every run, because the group must equal `want` exactly (`:101`).
- **M7 (low):** unexpected write errors (`.claude` is a file, permission denied) end in an unprefixed traceback with exit 1. That is the same code documented for "settings unreadable" (`:13`).
- **M8 (A3): the installer cannot see when hooks will not fire.**
  - It does not detect settings that stop hooks from running (`disableAllHooks` in `settings.json` or `settings.local.json`, or a managed hook policy).
  - It reports added/unchanged while capture never runs: a hook that does not fire is reported as success.

### 3e. Whether error_class leaks message text
- **EC1:** the string branch keeps only a leading token ending in Error or Exception (`capture.py:64,147-149`). The rest of the message is not stored, and the test asserts this (`tests/test_capture.py:399`). But the token itself comes from the message. The 64-character cap can store something that is no longer a class name: `tests/test_capture.py:414` expects 64 `X`s.
- **EC2:** the dict branch (`capture.py:140-145`) stores any identifier-like value under `type`, `name` or `class`, with no Error/Exception requirement. For example `{"name": "<a user or db name>"}` would be stored verbatim. Only `type` is tested (`tests/test_capture.py:421-422`). Whether Claude Code ever sends a dict `error` is unverified.
- **EC3:** `output_sha256` on failures is an unsalted sha256 of the error string (`capture.py:264`). For short, low-entropy error messages the hash can be confirmed by guessing.
- **EC4 (A7):** PostToolUseFailure was never observed in a real run. Its input shape is taken from documentation (`questions.md:64-66`).

### 3f. Offline, stdlib-only, always exit 0
- **Offline and stdlib-only: confirmed on reading.** The imports are stdlib only (`capture.py:30-41`). `urllib.parse` is used only for `urlsplit`. There is no socket, subprocess or network use.
- **Exit 0: holds for runtime errors only.** All runtime exceptions are caught in `main()` (`capture.py:302-310`), and stdout is never written. Exceptions to "always exits 0":
  - B1: the script is missing, so exit 2.
  - B2: a module-level import fails, so exit 1 with no SILENCE line.
  - `silence()` formats `str(exc)` outside its own try (`capture.py:289-291`). The risk is negligible.
