## Questions

- **Q-1 Who owns an act?** Each act process goes to its nearest talking
  ancestor. In the container, environment-manager (pid 87, talks to
  160.79.104.10) is the parent of claude (pid 95), so bash goes to claude.
  Pid 87 is listed only as a "talking ancestor" and as a "model endpoint
  talker without an act". The alternative is to give every act to the
  top-most talker. That merges a launcher and its agent into one candidate,
  and on a desktop it could merge everything under one updater. Keep
  nearest?
- **Q-2 The act list.** (Ruled by B-6: names only label; list in endpoints.yaml.) HANDOFF E3 names sh, bash, cmd, powershell,
  python*, node and git. I added the other common shells: dash, zsh, ksh,
  fish and pwsh. Not added: perl, ruby, deno, bun, make, cargo, npx. Each
  name added widens the anchor and its false positives. Which way?
- **Q-3 "Outside its config dir" (E3, Sysmon 11).** I defined it without
  names: a write is not an act when its path has a dot-directory, AppData,
  ProgramData, a temp directory, or the writer's own program directory.
  A browser download to `Downloads\` therefore counts as an act. Agree, or
  narrow it?
- **Q-4 Kimi in the catalog.** (Ruled by B-10.) ADR-0004's field test runs "with no prior
  knowledge of Kimi". So `endpoints.yaml` lists no Moonshot or Kimi host,
  and a test checks that. The `~/.kimi` footprint is listed, because
  ADR-0004 layer 4 names it. Should `.kimi` come out for the field test
  too? (`--catalog FILE` already lets the test run with any catalog.)
- **Q-5 False-positive classes of the anchor, with no budget yet (A6).** (Ruled by B-8: budget from M5.4.)
  Each of these talks and acts by the definition, and none is an AI agent:
  - an IDE with an integrated terminal or git integration (VS Code spawns
    git and shells);
  - a package manager running install scripts (`npm install` spawns sh);
  - CI runners and update agents.
  No measured fixture set exists to give discover an fp_budget. Does it need
  one before the field test, or after it?
- **Q-6 Hook hand-off by the name `claude`.** (Ruled by B-7.) Claude Desktop also runs as
  `claude.exe`, and it spawns MCP servers (node, python), so it becomes a
  candidate suggested for "hook". But it does not run Claude Code hooks.
  Tell them apart by path (AnthropicClaude), or leave it to the commander?
- **Q-7 Live Windows reader.** M5.0 reads exported CSV/XML only (README
  gives the commands). The live Linux reader runs `ss`. Running the three
  PowerShell commands from Python would be the same kind of act. I did not
  build it: I could not test it here, and CI has one push. A later task?
- **Q-8 Linux without `ss`.** (Ruled by B-1: /proc/net/tcp first; this text describes the first build.) This container shipped without iproute2. Then
  the live run says `source ss not read: ss not found` and exits 3
  (incomplete). A reader of /proc/net/tcp plus /proc/PID/fd would not need
  `ss`, but HANDOFF names `ss -tnp`. Add the fallback later?
- **Q-9 `/proc/PID/exe`.** HANDOFF lists cmdline, status, environ and cwd,
  so the image comes from argv[0], which the process writes itself. An
  agent can call its child "bash" or its root anything. The exe link is
  harder to forge. Read it in a later task? (Recorded as a hole in every
  Linux run.)
- **Q-10 Facts to check, not assume.**
  - The Anthropic network 160.79.104.0/23 in `endpoints.yaml` comes from
    Anthropic's published API IP list as I recall it. Only 160.79.104.10
    was seen here, in `linux/ss.txt`. Not re-checked offline.
  - The Windows CSV column names (see the fixture table above) are
    unchecked too.
- **Q-11 Command lines in the output.** (B-9 redacts the fixture; the output itself is unchanged.) The trace stores hashes, never
  content. Discover prints bounded argv lines as citations, and `--save`
  keeps the full proc.txt. A secret passed on a command line therefore
  reaches the inventory. Should discover keep argv[0] and argv[1] and hash
  the rest, as capture does?
- **Q-12 Is a found agent an alarm?** Exit 1 for any candidate mirrors
  `raqib report`. But Claude Code with Raqib's hook installed is also a
  candidate, every time. Should a candidate whose suggested source is
  already attached count as an alarm?
- **Q-13 PID reuse.** Records of one pid merge across a window. Sysmon
  ProcessGuid is not used. A pid reused inside a long `--window` would
  join two processes.

## REDO (after review D1-D17 and Amendment B)

Rebased onto main 5c10635. Every B ruling is built:
- B-1: /proc/net/tcp(6) first, `ss` only by absolute path.
- B-2: completeness decides exit 0 against 3.
- B-3: read failures become holes.
- B-4: the anchor's blind spots are named on every run.
- B-5: `/rd:true`.
- B-6: act names moved to `acts:`, which has its own `evasion:`.
- B-7: the hook and proxy criteria.
- B-8: the README states what a candidate is not.
- B-9: the redacted fixture, and the capture script in the tree.

Recorded as asked:

- **A-1 and A-2 were ratified by B-7.** A-1 is `ss -tanp` as the live
  fallback, with `-tnp` parsing kept. A-2 is the outbound inference. **A-5
  was rejected:** there is no `*_BASE_URL` proxy criterion any more. `proxy`
  needs a root that `proxy_capable` in endpoints.yaml names (`codex`,
  `aider`), and a test checks that `OPENAI_BASE_URL` alone gives `os`.
- **B-10** is for the field test, not for code. Copy endpoints.yaml without
  the `.kimi` footprint and run `--catalog COPY`.

Consequences I saw, and questions about them:

- **Q-R1 "talks + has a child" (B-6) widens the anchor.** In this
  container environment-manager (pid 87, talks to 160.79.104.10) is now C1:
  its child is claude. Claude Code (pid 95) is C2, `inside` C1. In the
  Windows fixture msedge.exe becomes a candidate through its renderer, an
  `[unlisted]` child. The output shows how many children carry a listed
  name (`listed_acts`). Is that the intended reading, or should a candidate
  with only unlisted children be marked lower?
- **Q-R2 Native Claude Code on Windows.**
  `%USERPROFILE%\.local\bin\claude.exe` run without arguments has neither
  "claude-code" in its path nor a CLI flag, so B-7 gives `os`. The synthetic
  fixture shows that: C1 claude.exe gets `os`. Should the native install
  path count as the CLI?
- **Q-R3 The ss fallback.** A sample whose /proc/net/tcp could not be read
  but which ss did read is a hole, not incompleteness. A sample that
  neither could read is an error of the `ss` source, so exit 3. Agree?
- **Q-R4 "Ended while read" against "unreadable".** A pid that vanished
  between listing /proc and reading its status is a hole: the process
  ended. A status that exists but cannot be read makes the run incomplete
  (B-2).
- **Q-R5 Byte order.** /proc/net/tcp prints addresses in host byte order.
  The parser assumes little-endian (x86, arm64), so a capture from a
  big-endian host would decode wrongly.
- **Notes:**
  - D10 done cheaply: the A5 test also checks the event's ProcessId in the
    raw Sysmon line.
  - D11 done cheaply: the holes from proc meta counts, footprint scan
    notes and the missing tcp6 cite their lines.
  - D8 and D12 are text in README and holes, as ruled.
  - D9 (PTR and CDN-shared names) and D16 (reused Windows ParentProcessId;
    CreationDate unused) are recorded, not changed.
  - D17 negatives are added for each case: ss absent end to end, a partial
    failure in a window, unowned connections from /proc/net/tcp and from
    ss, an orphan talker, and an unreadable /proc status.

## REDO 2 (after review 2 R1-R16 and Amendment D)

Rebased onto main a59dd5c. The amendments run A, B, C, D, and nothing is
added to the ADR this round. Every D ruling is built:
- D-1: Sysmon needs an event 1 to count as a process source and an event 3
  to count as a connection source.
- D-2: only ENOENT on tcp6 is a hole.
- D-3: fd, cwd and cmdline failures are holes, and sockets become `null`.
- D-4: `run.json` is written by `--save` and replayed by `--from`.
- D-5: `handoff:` in endpoints.yaml, with evasions.
- D-6: snapshot basenames are redacted.
- D-8: R7 wording, R10 (proc-net over ss under `--from`), R11 wording; R5
  is tightened.

Recorded as asked:

- **D-2 settles Q-R3 the other way.** A /proc/net/tcp failure is a source
  error even when ss read that sample, so the run is incomplete.
- **D-5 has a consequence.** The npm-installed Claude Code CLI (`node
  .../claude-code/cli.js`) has image `node`, so it gets `os`. That is listed
  in `handoff.hook.evasion` and tested. Per D-5 the error is safe-side,
  because os still watches the tree.
- **R9 and R16 recorded, not changed.** R9: the text output caps acts at 12
  per candidate, and the JSON holds all of them. R16: under `--from
  --window`, "holds no record" is judged before the window filter, so a
  source the filter empties is not flagged.
- **D-7 noted.** The footprint link order (root name first) is ratified, and
  the ADR's "no browser" sentence is superseded by B-6.

One choice I made:

- **Q-R6 The reader's own fd directory.** Listing `/proc/SELF/fd` opens a
  descriptor that has closed before its link is read back, so ENOENT on
  that one entry is certain on every run. `_sockets` skips ENOENT only
  for the reader's own pid. Every other failure, on any pid, gives
  `sockets: null` and a hole (D-3). The reader's tree is never evidence.
  Agree?
