## Q1 - E3 "`raqib report` shows it": JSON yes, text and page no
Every finding dict now carries `kind`, and `report.build` passes finding
fields through, so `raqib report --json` (and `raqib rules`, and the
findings entries of `<trace>.watch.json`) show it; tests hold this. The text
report (`report.render_text`: `[sev] RULE (CLASS) session ...`), its RULES
table (`report.rule_table`, also written to FILE.notes.json) and the page
(`raqib/ui.py`) do not print it, because `raqib/report.py` is not in the
M4.1 Scope and the UI is out of scope. Is `--json` enough for E3, or should
a follow-up task put `raqib/report.py` (and later `raqib/ui.py`) in scope to
print the kind on each finding line and add a kind column to the RULES
table?

## Q2 - a finding without `kind`
`engine.check_finding` rejects a `kind` that is not one of the three, but
accepts a finding with no `kind`, as it already does for `class`. A findings
file written before M4.1 (`raqib rules -o`) therefore still reports. Should a
finding without `kind` be rejected instead? That would make every older
findings file a `rejected-finding` alarm in `raqib report` and a refusal in
`raqib suspect`.

## Q3 - readings of match blocks that do not fit one kind cleanly
Kept as the table says; written here as the HANDOFF asks.
- SCOPE-PATH (table: signature). Its filter is a signature: nine named
  file tools, and Bash goes round it. Its measure, though, is `outside: cwd`,
  the cwd as the hook captured it, which ADR-0002 names as an anchor. As
  built it is a signature measured against an anchor.
- DRIFT-FILES (table: anchor). The same shape the other way round: an
  anchor (context `scope`) behind a signature-shaped tool filter (Write,
  Edit, MultiEdit, NotebookEdit). Two points:
  (a) the table gives it a "hole" in the evasion column, but the ADR's
  Consequences forbid `evasion` on anything but a signature, so the hole
  stays in its description only. Should an anchor with a known hole get a
  field of its own (for example `holes:`) so the THREAT_MODEL can cite it
  like an evasion?
  (b) ADR-0002 names "the Scope: block of HANDOFF.md at a commit" as the
  anchor. `raqib report --handoff` and `raqib watch` read HANDOFF.md from
  the working tree, which the agent can write (watch already prints the
  scope for that reason, ADR-0005 D-7). As built, an agent that edits
  HANDOFF.md moves this anchor. Is that within the meaning of anchor, or
  should the scope come from a commit?
- SCOPE-CWD-ROOT (table: anchor). It reads the captured cwd (an anchor)
  through a fixed list of top-level and home directories ("a home
  directory elsewhere is not known to this rule"). The list is a signature
  of what a boundary-less cwd looks like, but the agent cannot choose the
  cwd it is started in, so no `evasion:` is added (none is allowed).

## Q4 - what the ratio counts
The gate line counts the 7 YAML rules and the 4 silence rules, the 11 of
the ADR table. It does not count `raqib/discover/endpoints.yaml` (already
`kind: signature` with `evasion:`, ADR-0004 A-4), discover's AGENT-DARK, or
the events watch raises itself (SILENCE-LIVE, TRACE-HOLE, RAQIB-SILENCE).
Should any of them be in the ratio, and with which kind?

## Q5 - the gate line's prefix
E4 gives the line as `rule kinds: signature=N demand=N anchor=N`. The gate
prints every line with its `[gate] ` prefix, so it reads
`[gate] rule kinds: signature=4 demand=4 anchor=3`. Is the prefix
acceptable, or must the line stand alone?

## Q6 - the gate imports the checkout's rules
The kinds check imports `raqib.rules` from the checkout it gates (put first
on sys.path; a module found anywhere else, such as an installed raqib, is
RED) and loads the catalog with that loader, so the gate counts exactly what
raqib loads. The gate's other checks read files only. Is importing package
code in the gate acceptable, or should the gate parse the YAML itself?
(Scratch-repository gate tests now carry a copy of raqib/rules and its
catalog for this reason.)

## Q7 - `kind` means three things in a report
In `raqib report --json`, `findings[].kind` is now the rule kind, while
`alarms[].kind` names the alarm and a suspicion line's `kind` is
`suspicion` or `error` (existing keys, unchanged). A reader that keys on
`kind` across those lists can confuse them. Rename one, or leave it as is?

## Q8 - the added evasion lines are readings, not runs
Each table evasion starts one line of its rule's `evasion:` list. The added
lines come from reading the match blocks and capture.py (command_head is the
first program only, url_host comes from `url` only, the 1048576-character
output scan, paths not resolved). None was exercised against a live agent
(A7). The SCOPE-PATH line "move the cwd first" rests on the hook's cwd
following a Bash `cd`, the reason SCOPE-CWD-MOVED exists (review M1.1 PA1).
Should each evasion line get a fixture that shows the rule staying quiet,
so the list is evidence and not prose?

## Q9 - report.SILENCE_RULES duplicates the silence ids
`raqib/report.py` (out of scope) keeps its own list of the four silence
ids and titles. A test now holds its ids equal to `silence.RULE_KINDS`.
Should report take the ids, and later the kinds, from silence.py?
