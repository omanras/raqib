## 2. Exit criteria unmet, and the evidence missing

2. E5, "a test greps ... the process's own argument list". tests/test_forward.py:360-374 reads /proc/<pid>/cmdline, or
  on Windows the test's own `proc.args`, and checks that TOKEN is not in it. The test never passes the token as an
  argument, so this cannot fail by construction. The one part that could fail is the check that the parser has no
  token option other than `--token-file` (375-377). "Every error's text" is also only partly produced. The test
  produces outputs for a taken send, a 403 and a 503. It never produces the token-file UsageError during a run, a TLS
  failure, or a traceback. Certain.

3. E5, "connect 10 s, answer 30 s". test_forward.py:456-468 asserts the values the code sets (the constructor timeout
  and `sock.gettimeout()`), not what they do. In forward.py:446-456 both are per-socket-operation timeouts, not
  totals. A collector that trickles one byte every 29 s holds a send forever: headers and body are read recv by recv.
  The TLS handshake runs under the 10 s per-operation timeout, and DNS resolution (getaddrinfo) has no bound at all.
  FORWARD.md:57, 60 and 88-89 say "within 10 s" and "within 30 s". Nothing tests a trickling answer. Certain from
  stdlib semantics. The status does catch the hang: with no state written, `--status` says 3 after two beats.

4. E6, "`--status` exits 0, 1 and 3 as J-9 says" (R1). judge() (forward.py:662-696) returns 0 whenever `failing` is
  null and `behind` is 0. It never asks whether the last send was taken. The worst case is a collector that answers
  every request with a 4xx the code counts as refused (any 4xx except 401, 403, 408 and 429; see forward.py:489-490).
  Examples: 404 for a wrong path, 405, 413 behind a proxy, or HEC's 400 "data channel is missing". J-4 then drains the
  whole file into `refused`, and the state shows:
   - refused.count = N, with the latest 50 ids
   - sent unchanged, last_ok null or old
   - failing null, behind 0, cursor at the end of the file
      `--status` then prints "OK (exit 0)" over the line "last taken: none at never". `--once` exits 1 in the same
     case (refused_now, 654); a long-running forwarder's status says 0. The documents disagree with each other:
     docs/GUIDE.md:454 says "exit 0 the last send taken", while docs/specs/FORWARD.md:127 rewords the rule to "Exit 0
     where nothing fails". test_forward.py:520-542 has no refused-only state. Certain.

5. E3 and E6 (R2). read_token (forward.py:163-176) raises UsageError when a token file is readable by others or holds
  something that is not one token. send() (495-500) catches only OSError, so that UsageError propagates out through
  step() and run(). The final write_state at 651 is not in the `finally`, so it is skipped; cli prints the reason on
  stderr and exits 2. Ordinary edits trigger this: `echo t > f; chmod 600 f`, or an editor's truncate-then-write. The
  last state on disk says not failing. `--status` reads it as 0, then as 3 once two beats have passed. Certain from
  the code. That real edits hit this is likely.

6. E6, "Stop writes the state". This is tested only by calling `stop()` directly (test_forward.py:577-587). Nothing
  tests the signal handlers in cli_run (743-751). If they were never installed, SIGTERM would kill the forwarder with
  no state written, and no test would fail. Certain.

7. E8, "the guide's section". It is not built. K-3 records it for a later task, so this is the Table's deferral, not
  the builder's fault. The criterion as written is unmet. Separately, FORWARD.md:19-20 contradicts itself: it says "A
  line is passed when ... skipped ... or ... refused alone", then "The cursor moves only past lines the collector
  took". The second sentence is false for the code. Certain.

8. E7 and X22 (R4). forward_run.py:179 runs the refused-token case with `wrong_file`. check.py:316-322 greps every
  text only for the right token, read from facts["token_file"]. If the forwarder printed its token on 401 or 403, it
  would print the wrong one, and X22 would still be MET. check.py:323 (argv) checks lists forward_run.py built itself,

9. E7, the rig on both machines (R3). rig.yml:56-58 and 100-101: the check.py step has no `if: always()`, so it does
  not run when forward_run.py fails. forward_run.py has no guard around its scenarios. With no events file, X19 exits

## 3. Silent assumptions, and what a rule should have caught (A3, A5)

The lost-event hunt (your item 1). None of these drops a line:
- A batch is a contiguous prefix of event lines (573-580), and the cursor passes only batch[-1], and only on "taken".
- The refused path is entered only on a 4xx outside {401, 403, 408, 429}.
- A batch-wide 400 counts no other line as refused: each line is sent alone. A non-refused failure mid-loop stops the
  loop with only the earlier lines passed (591-594).
- The state is written after the answer.
- A crash between the answer and the rename leaves the old state on disk, so the lines are sent again.
- On a restart the saved state takes precedence over `--from end`.
- Restarting from zero, a file growing during a read, a line longer than the chunk, and `--batch` are all handled
  correctly.
- CRLF lines are sent with their CR in the raqib shape, and the sha includes it.
- A file shorter than the cursor always restarts, because the size check comes first. The same-hash case matters only
  for files at least as long as the cursor, which K-2 accepts.
- The pid race gives duplicates, not loss.

The real losses are items 11 and 12, plus the two K-2 accepted: a change to bytes before the last line passed, and a
  line over 512 KiB.

11. J-4 as built assumes every such 4xx is the line's fault. A collector-wide 4xx turns a misconfiguration into
  permanent, counted loss, and the status says 0 (finding 4). I raise this as suspicion against A3; the ruling's
  wording permits it. Certain from the code; likely in practice.

12. The state file and pid file are writable by the watched account, and the THREAT_MODEL does not say so
  (docs/THREAT_MODEL.md:1116-1125). resume() (forward.py:402-426) trusts the state completely:
      - A forged cursor offset with the matching sha256 of a later line (the agent can read the file) makes a
     restarted forwarder skip silently. No restart is counted and nothing says so. The state shows only the moved
     cursor.
   - A rewritten fresh `written`, or a huge `beat`, keeps `--status` at 0.
   - A live pid written into the pid file keeps the forwarder from ever starting.
   Only the collector-side heartbeat search catches any of this. Certain.

13. The interval clock is the wall clock (`clock=time.time`, forward.py:271, used by pause() 609-621). Take a backward
  step of an hour, during a poll wait:
   - `left` becomes about an hour, and the forwarder sleeps that long, sending nothing and writing no state.
   - `--status` computes now - written < 0, so it never says SILENT, and it exits 0.
   A forward step only causes a short false SILENT. Certain from the code; rare in practice (NTP step, VM resume).

14. Stop is not honoured during a hung or trickling answer. Python retries the recv after the handler runs, so the
  forwarder is held until each read times out, or forever under a trickle. The line-by-line loop (585-594) never
  checks stopped(), so a Stop there can wait through up to 100 sends. On Windows I could not check whether Event.wait
  in pause() is interruptible, or whether Stop waits for the timeout (up to 60 s). Certain for POSIX; not checked for
  Windows.

15. The environment's TLS variables. ssl.create_default_context honours SSLKEYLOGFILE: it writes TLS session secrets
  to a file, and those decrypt the Authorization header from a capture. When `--ca` is not given, OpenSSL's
  SSL_CERT_FILE and SSL_CERT_DIR replace "the system's authorities". THREAT_MODEL.md:1096 and FORWARD.md:84 say "no
  variable of the environment turns that off". That is literally true, but they say nothing of either variable.
  Verification itself cannot be turned off:
   - check_hostname is True and verify_mode CERT_REQUIRED (304).
      - There is no flag for it, and nothing calls `_create_unverified_context`, CERT_NONE or debuglevel anywhere in
     raqib/.
   - `--ca` replaces the trusted set; `cafile=` loads only that file, as FORWARD.md says ("alone").
   Certain from stdlib.

16. Plain http and loopback. loopback() (123-127) accepts IP literals only:
   - "localhost", "127.1" and a trailing-dot host are refused without `--plain`, which is the safe direction.
   - [::1] is accepted, and an uppercase scheme is lowercased (138).
      - An IPv4-mapped address (::ffff:127.0.0.1) is refused or accepted depending on the Python version's
     is_loopback; it is truly loopback either way.
   - No redirect is followed: a 3xx is a failed send.
   - No proxy is used: only urllib.parse.urlsplit is imported.
   - The answer body is read to at most 64 KiB (465), and headers are bounded by http.client's own limits.
   Certain.

17. Some exceptions escape the except tuple at forward.py:470 (HTTPException and OSError only):
   - A non-ASCII path in `--to` raises UnicodeEncodeError from http.client's request line.
   - An IDNA-invalid host raises UnicodeError at connect (451-455).
   - A state with a non-integer offset raises ValueError (419-423, outside the try).
      Each kills the forwarder with a traceback, which holds no locals and so no token; for the first two that happens
     at the first send. destination() (130-155) refuses none of these URLs. A path containing a space raises
     InvalidURL, which is reported as "no-answer" and retried forever: a usage error disguised as a failed send.
     Certain.

18. Pid-file race (forward.py:373-389). The file is created with O_EXCL and its pid is written afterwards. A second
  forwarder that reads it in between sees an empty file, parses it as pid 0 (377), removes the first forwarder's file
  (380-386) and takes the name. unlock() (394-400) then removes whatever file is there. Two forwarders of one name
  give duplicates, not loss: each one's state holds a cursor it really reached. Certain; the window is narrow.

19. whole_lines (214-222) reads an unbounded tail with no newline into memory, with a quadratic `in` scan. It does
  this at every 1 s poll, and behind() and line_before() scan the same tail. Anyone who can append to the events file
  can make the forwarder exhaust memory or CPU. Certain; impact low.

20. Smaller ones, all certain from the code unless marked:
      - No fsync before os.replace (345-349). After a power loss an empty state means a UsageError at start (411); if
     a person then moves it away and restarts with `--from end`, the backlog is skipped. Could not check per file
     system.
      - `--beat inf` is accepted (281-283). The forwarder is then never SILENT, and the state holds `Infinity`, which
     is not standard JSON.
      - `--once` against a live file can race: behind() runs after the loop (654), so lines appended at the end give
     exit 1 while the message says "done".
      - A state that is valid JSON but not of the schema falls into the first-run path (412, 427). With `--from end`
     that skips to the end.
      - classify (179-190) skips valid JSON that is not ASCII. That is stricter than event.check, though B-3 makes the
     watch's lines ASCII anyway.
      - Status 0 with a growing backlog while sends succeed: behind is judged only against last_ok (694). This is the
     Q11 reading, accepted by K-2.

21. The collector-side search for silence (FORWARD.md:133-137, GUIDE.md:455) judges by the event's `time`, which is
  the host's clock. EVENT.md:146-148 tells a reader to judge silence "by the reader's own clock - not by `time`". A
  host clock set ahead hides silence for the length of the skew. Likely.

22. The secret path (your item 2):
      - The token goes from the file through read_token to a local in post() and into the header (459-460). It is
     never stored on `self`.
   - It is never in say(), the state or any UsageError text, and cli prints only `str(UsageError)`.
   - CR, LF, space and non-ASCII are refused by TOKEN (64) after strip, before any header is built.
      - The mode check is os.stat then open, both by path. That is a TOCTOU race, and it follows symlinks, which
     checks the right file (the target). There is no owner or directory check. That matters later, under a root
     service; not now.
      - The query string is kept out of the state, the status and every error. It does sit in the process list as part
     of `--to`, and a collector that takes a credential in the query would put that credential there. Neither
     THREAT_MODEL nor FORWARD.md says so.
      - The rig uploads forward.json (rig.yml:67, 109). It holds every state and output: runner paths, 127.0.0.1, and
     events already in the uploaded events.jsonl. It holds no token unless one leaked, and the token file is not
     uploaded.

  raqib/forward.py opens the events file only "rb" (323, 429, 547); it never writes, moves or locks it. One note: on
  Windows that "rb" handle blocks a rename or delete during each brief read.
   The K-1 guard (tests/test_rhythm.py:1059-1074) can be passed while the rule is broken:
   - `from . import forward` (n.module is None, so the guard sees no names).
   - `from .forward import X` (n.module is "forward", not "raqib.forward").
   - `__import__("raqib.forward")`, or `importlib.import_module(name)` with the name built elsewhere.
      - Calling `cli.cmd_forward` or `cli.main(["forward", ...])` from a capture module. Both guards allow that route,
     yet the guard's docstring (1032-1033) claims "no watch and no capture script can reach its network".
      test_forward.py:111-118 also skips relative imports (level != 0). Its subprocess check (139-142) catches
     module-level imports by any spelling, but not imports inside a function. Certain.
