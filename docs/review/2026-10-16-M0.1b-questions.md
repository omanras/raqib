# M0.1b pairing key + command_head: questions for the commander

M0.1b exit criteria E1-E4 are met and `tools/gate.sh` is green (47 passed,
1 skipped: the read-only-log test, skipped under root as in M0.1). Ten
mutants of `capture.py` (one per behaviour below) were each killed by the
suite. The points below are left open by Amendment A-1/A-2. The builder did
not decide them: each got the narrowest reading of the amendment text, and
each needs a ruling.

## Open questions (not answered)

- **Q1 command_head is not a shell parse, and rules on it can be evaded.**
  A-1 splits on whitespace. Shell metacharacters (`;`, `&&`, `|`, `(`, `<`),
  quoting, backslashes (`\rm`) and wrapper commands (`env`, `sudo`, `command`,
  `exec`, `timeout`) are not seen. `true;rm -rf x` gives `true;rm`;
  `sudo rm -rf x` gives `sudo`; `A=1;rm -rf x` gives `-rf`, because the token
  `A=1;rm` starts like an assignment and is skipped. The M1.2
  destructive-command rule cannot treat a benign command_head as clean (A2:
  never acquit). Should A-1 be tightened (split on metacharacters, skip known
  wrappers), or should M1.2 use command_head only as a hint that raises
  suspicion?
- **Q2 A quoted assignment leaks part of its value.** `TOKEN="abc def" cmd`
  splits into `TOKEN="abc`, `def"` and `cmd`. Only the first token is skipped
  as an assignment, so command_head is `def"`, a piece of the value. The
  64-char cap limits the leak but does not stop it. Should the hook omit
  command_head when a skipped assignment opens a quote it does not close?
- **Q3 What "falls back and is logged" means for an unknown tool_use_id.**
  Reading taken: a post whose tool_use_id matches no open pre falls back to
  the (tool, input_sha256, oldest-open) rule, but only against open pres that
  have no tool_use_id. E1 allows the fallback only when the id is absent on
  either side, and two different ids are two different calls. If nothing
  matches, the post takes a fresh seq (the M0.1 orphan behaviour). Its trace
  line is still written, with its own tool_use_id. Nothing goes to stderr,
  because RAQIB-SILENCE is reserved for events that could not be captured.
  M0.2 SILENCE-HALF will see the orphan in the trace. Should the hook also
  mark such a line (for example `paired:false`)? That would be a schema
  change, so it was not added.
- **Q4 Same tool_use_id, different tool name.** Pairing uses tool_use_id
  alone (A-2: the primary key), so a mismatched tool name still pairs, and
  the pair shows the mismatch in the trace. Should pairing also require the
  same tool?
- **Q5 Duplicate post.** A second post with the id of an already-closed pre
  is treated as unknown (Q3) and gets a fresh seq, not the closed pre's seq.

## Assumptions made (confirm or overrule)

- **tool_use_id** counts only when it is a non-empty JSON string. Any other
  value (null, "", a number, a list) is treated as absent: it is not carried,
  not coerced, and raises no silence. It is stored verbatim, without a length
  cap. It is written after `tool` in the line.
- **NAME=value**: NAME is a shell identifier `[A-Za-z_][A-Za-z0-9_]*`, so
  `9X=1 ls` gives `9X=1`.
- **Whitespace** is Python `str.split()` (any Unicode whitespace, newlines
  included), not bash's blanks.
- **Basename** follows POSIX basename(1): trailing slashes are dropped
  (`/usr/local/bin/` gives `bin`; `/` gives `/`).
- **64 chars** means 64 code points, cut after taking the basename.
- **Post lines** get a command_head too, computed from the post's own
  tool_input. An updatedInput rewrite can therefore change it within one
  pair (fixture `pairing-updated-input.json`: `pytest` then `timeout`).
- **Fixtures** for E3 are scenario files: a JSON list of hook inputs in
  arrival order. They are not `.jsonl` because `.gitignore` excludes
  `*.jsonl`.
