# M7.21a - what the Table checks in the field, and questions (2026-11-13)

Built against ADR-0007 Amendments BK and BL (BL-1 to BL-6) and HANDOFF E1-E8: raqib/etwnet.py,
tests/test_etwnet.py, tools/rig/etw_read.py. Nothing of it has run on Windows. The tests run on
Linux against a fake system (tests/test_etwnet.py FakeEtw) that reads and writes the reader's
buffers at the offsets written by hand in the test, so the module's ctypes layouts are checked
against a second statement of them - but both statements are the builder's reading of the SDK
headers, not a measure. Every item below is something the builder is not certain of; the field
run (`python tools/rig/etw_read.py 30` in an elevated prompt, with some traffic) is how it is found.

## A. Structure layouts (64-bit Windows; asserted on any 64-bit Python by
## test_e8_structure_sizes_and_offsets_of_64_bit_windows)

1. EVENT_TRACE_PROPERTIES = 120 bytes: WNODE_HEADER 48 (BufferSize 0, ProviderId 4,
   HistoricalContext 8, TimeStamp/CountLost/KernelHandle union 16, Guid 24, ClientContext 40,
   Flags 44), BufferSize 48, MinimumBuffers 52, MaximumBuffers 56, MaximumFileSize 60,
   LogFileMode 64, FlushTimer 68, EnableFlags 72, AgeLimit 76, NumberOfBuffers 80,
   FreeBuffers 84, EventsLost 88, BuffersWritten 92, LogBuffersLost 96, RealTimeBuffersLost 100,
   LoggerThreadId (HANDLE) 104, LogFileNameOffset 112, LoggerNameOffset 116. Check: sizeof in C
   on the runner is 120; the query's EventsLost and RealTimeBuffersLost read sensible numbers.
2. EVENT_TRACE_LOGFILEW = 448 bytes: LogFileName 0, LoggerName 8, CurrentTime 16, BuffersRead 24,
   ProcessTraceMode 28, CurrentEvent (EVENT_TRACE, 88) 32, LogfileHeader (TRACE_LOGFILE_HEADER,
   280) 120, BufferCallback 400, BufferSize 408, Filled 412, EventsLost 416, EventRecordCallback
   424, IsKernelTrace 432, Context 440. The least certain: TRACE_LOGFILE_HEADER's 280 (its
   TIME_ZONE_INFORMATION is 172 bytes at 72, so BootTime is padded to 248). If it is wrong,
   EventRecordCallback lands on the wrong field: OpenTraceW may fail (87) or ProcessTrace may call
   nothing or crash. Check: sizeof(EVENT_TRACE_LOGFILEW) == 448 on the runner, and events arrive.
3. EVENT_RECORD = 112 bytes: EVENT_HEADER 80 (TimeStamp 16, ProviderId 24, EventDescriptor 40
   with Id at 40 and Keyword at 48, ProcessorTime 56, ActivityId 64), BufferContext 80 (as
   ProcessorNumber, Alignment, LoggerId), ExtendedDataCount 84, UserDataLength 86, ExtendedData
   88, UserData 96, UserContext 104.
4. GUID: Data1 to Data3 little-endian, Data4 the eight bytes in order (the test checks it against
   Python's uuid bytes_le). The provider check compares the header's ProviderId text to
   7DD42A49-5329-4832-8DFD-43D979153A88.
5. A 32-bit Python is refused at start() (the layouts are for 64-bit only). Is that enough, or
   should the watch say something else on an ARM64 or a 32-bit install?

## B. Constants and calls

6. WNODE_FLAG_TRACED_GUID 0x00020000; EVENT_TRACE_REAL_TIME_MODE 0x00000100;
   PROCESS_TRACE_MODE_REAL_TIME 0x00000100; PROCESS_TRACE_MODE_EVENT_RECORD 0x10000000;
   EVENT_TRACE_CONTROL_QUERY 0, _STOP 1; EVENT_CONTROL_CODE_ENABLE_PROVIDER 1; level 4;
   INVALID_PROCESSTRACE_HANDLE 0xFFFFFFFFFFFFFFFF (64-bit).
7. Wnode.Guid is left zero for the session (the builder's reading: the system assigns one for a
   session that is not a kernel or global logger). If StartTraceW refuses it (87), a random GUID
   must be set.
8. Wnode.ClientContext 1 (QPC), and ProcessTrace without PROCESS_TRACE_MODE_RAW_TIMESTAMP, so
   the builder expects EVENT_HEADER.TimeStamp in the callback to be a FILETIME (UTC). The tool
   prints `last=` per connection: check it is today's UTC time, not 1601 or a far date.
9. BufferSize 64 KB, FlushTimer 1 s, MinimumBuffers/MaximumBuffers 0 (the system's defaults).
   Are there losses (`lost=`) under load with these? They may need raising.
10. LogFileNameOffset 0 at StartTraceW (no file, BL-1); for QUERY, STOP and QueryAllTracesW the
    buffer has room for two names of 1024 characters after the 120 bytes, LoggerNameOffset 120,
    LogFileNameOffset 120 + 2048.
11. Return conventions taken: StartTraceW, EnableTraceEx2, ControlTraceW, ProcessTrace,
    CloseTrace and QueryAllTracesW return the Win32 error code itself (no GetLastError);
    OpenTraceW returns the handle and the reason by GetLastError (the WinDLL is loaded with
    use_last_error=True).
12. The callback type is WINFUNCTYPE(None, c_void_p): the record handed over as its address and
    read with EVENT_RECORD.from_address inside the callback only. The callback object is kept on
    the Reader for its life.
13. The stop order: ControlTraceW(STOP) (its properties' last EventsLost/RealTimeBuffersLost are
    kept as the final losses), then CloseTrace (7007 ERROR_CTX_CLOSE_PENDING taken as success),
    then the consumer thread is joined for at most 10 s, else said. Check that ProcessTrace
    returns after the STOP, and with which code (the builder does not rely on it).
14. `since` is taken when EnableTraceEx2 has returned, before OpenTraceW. Are events between
    the enable and the consumer's first buffer delivered (the real-time buffers wait for a
    consumer), or lost, or counted in EventsLost?

## C. What the system says on refusal (E6 reasons; test_e6_a_refused_start_...)

15. 5 ERROR_ACCESS_DENIED -> "no rights: a tracing session needs an administrator". The SDK
    also lets the Performance Log Users group start sessions; the Table measured "an
    administrator". Is the reason's wording right, and does EnableTraceEx2 on this provider
    need more than the session does?
16. 1450 ERROR_NO_SYSTEM_RESOURCES -> "the limit of tracing sessions"; 183 ERROR_ALREADY_EXISTS ->
    "a session named raqib-net-<pid> is already there"; any other -> "error N". The builder did
    not see whether a policy refusal has its own code.
17. Session names: the builder does not know whether ETW compares names without case. If it
    does, a session "RAQIB-NET-6" blocks raqib-net-6 at StartTraceW (183) yet leftovers() never
    stops it (it matches `raqib-net-<digits>` exactly, by BL-1's "any session that is not
    Raqib's"). Is that the Table's intent?

## D. Leftovers (BL-2)

18. QueryAllTracesW with an array of 64; ERROR_MORE_DATA (234) is taken as "the first 64 are
    filled" and the rest is said as not seen. On Windows 10 and later the session limit can be
    higher than 64: is a larger array wanted?
19. The live pids for leftovers come from one Toolhelp32 snapshot (raqib/hostwin.py
    read_processes, in the tool only); a snapshot that ends with an error is not used and no
    leftover is stopped (said). A pid reused since the killed watch makes its session look alive
    and it is left (not said: nothing can tell it apart). Is that the rule wanted for M7.21b?

## E. The events (BL-5)

20. The data shape taken as measured: PID u32, size u32, daddr, saddr (4 or 16 bytes), dport,
    sport (network order). IPv4 addresses are read as the four octets in memory order (the
    manifest's win:IPv4 is in network order). Check one connection's addresses and ports against
    `Get-NetTCPConnection` on the runner.
21. Event version is not checked: any version of ids 10, 11, 26, 27 with data at least 20 (v4)
    or 44 (v6) bytes is read. A later version that moved a field would be read wrong, not unread.
22. Ids 12 and 13 (connect, disconnect) and every other id of the provider count as unread
    ("id 12"), as E3 says; on a busy machine `unread` will be large from them alone. Should
    connect/disconnect be counted apart from the unreadable, so `unread` means "not read"?
23. Events of another provider (the trace's own header event first) are counted as `other`,
    not as unread.
24. Not measured yet (BL): whether loopback traffic is said at all. The tool's lines will show
    it if it is (127.0.0.1 or ::1 as local).

## F. Design questions for M7.21b (not answered here)

25. The counts are kept per (pid, local, remote) for the session's life, with no cap and no
    pruning of closed connections: a long watch grows without bound. A cap would be a hole with
    its count (A-1); which rule does the Table want?
26. The reader keeps no events, only sums and the last time; BL-5 lists "direction, the time"
    of an event as kept. For the watch's rhythm per turn, sums are enough if counts() is read
    each turn and differenced; confirm that, or say that events are kept.
