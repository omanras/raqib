# M3.1 — questions, readings taken, and fixes made

## Fixes found while proving the requirements (E5)

1. **Open redirect rule tightened (client).** Writing the dedicated test
   showed `?next=/\u0000x` (a control character) was accepted. `safeNext`
   (client/screens/auth.tsx) now refuses control characters as well as
   `//host` and `/\host`; tested in `tests/unit/client-safety.test.ts`.
2. **Ledger head in "Share this round" (client).** The threat model found
   that an operator who can write the database could rewrite the whole
   chain consistently, and only an earlier head would show it. The shared
   round summary now carries "Ledger: entry N, hash <16 hex>", so the
   group chat keeps independent copies of the head. Tested in
   `tests/e2e/circle.spec.ts`.

No server change was needed: the XSS, CSRF, rate-limit, copied-cookie,
IDOR, egress and redaction tests passed against the existing code.

## Readings taken

3. **"Every S-item has a test named with its id".** Enforced by
   `tests/unit/requirements.test.ts`, which reads every `- S<n>.<m>` item of
   docs/SECURITY_REQUIREMENTS.md and fails if no test title contains it.
   Existing tests were renamed to carry their ids. S7.1 and S7.2 are
   checked by tests that read the gate, the lockfile and the CI workflow;
   S7.3 (container non-root) is a test that runs once `deploy/Dockerfile`
   exists (M3.2) and is skipped until then, so the id is present and the
   check is real from M3.2 on.

4. **The full API tour** (`tests/api/tour.ts`) is every route of the matrix
   for every role, each against a fresh world: 44 routes x 4 roles = 176
   requests, error paths included. It drives S5.3 egress.none (fetch, DNS
   lookup/resolve, net/tls connect, http/https request/get stubbed to
   record and refuse: zero calls) and S6.2 logging.redaction (the debug
   log of the tour contains none of the 100+ secrets that passed through:
   passwords, session tokens, CSRF tokens, invite tokens, recovery codes,
   draw secrets).

5. **XSS coverage.** One payload (`<img src=x onerror=...>`, short enough
   for 60-character names) goes into every free-text field: account name,
   circle name, rules, a member's name in the circle, contribution method
   and reference, waiver reason, payout method and reference, cancel
   reason. Eleven screens are visited; on each, no script ran, no `<img>`
   was created, no CSP violation was reported, and the payload is visible
   as text.

6. **CSRF e2e.** A same-origin `fetch` without the header is 403; a
   form-encoded post (what a cross-site form can send) is refused before
   any handler (415).

7. **Rate-limit e2e.** 31 `POST /api/auth/login` from one address: the
   first 30 are refused for other reasons (no CSRF token), the 31st is 429,
   and so is any further auth POST, with Retry-After.

8. **v0.1 exit criterion.** A full circle of four members from sign-up to
   completion now runs in the e2e suite (`tests/e2e/full-circle.spec.ts`):
   every member reports every round, the organizer confirms, pays out, the
   recipient acknowledges, the round closes; at the end the circle is
   completed, the statement balances (320.000 confirmed, 0 outstanding,
   320.000 paid out) and the ledger verifies in the browser.

9. **What remains open** is listed in docs/THREAT_MODEL.md with a plan:
   distributed password-guessing load, a full consistent chain rewrite
   (only partly mitigated by shared heads), readable names in a stolen
   database file, the draw secret against a hostile browser extension,
   and disk exhaustion (M3.2 operations).
