S-1 (AN-2, MORE SAID, can be a knock, very low likelihood). raqib/hooks/os_sysmon.py:403-405 and :434-435.
- What the code does: pid_at[pid] is set only when an event 1 places a pid, or deletes a pid that was already in
  by_pid. An unrelated event 1 that meets a pid not in by_pid leaves no mark.
- So the guard at :434 ("a pid a later event of the walk placed stays that event's") misses a later reuse of the pid.
- Case (a bounded follow, tree kept), in time order:
  - i=0: event 1 of A (pid 500, guid GA, ParentProcessGuid GP; GP not yet in the tree). Set aside; 500 is not in
    by_pid, so pid_at gets nothing.
  - i=1: event 1 of B (pid 500 reused, guid GB, parent unrelated). depth None; 500 not in by_pid, so pid_at gets
    nothing.
  - i=2: event 1 of P (GP, child of the root, logged 61 s late so it sorts last). It joins.
  - Retry: A joins; pid_at.get(500, -1) = -1 <= 0, so by_pid[500] = A's depth.
  - Next pass: an event 3 or 11 with ProcessId 500 and no ProcessGuid (B's act) joins the tree as A's.
- Result: a false os line, which NET-TOOL or DESTRUCT-CMD could knock on.
- Why the likelihood is very low: real Sysmon events 1, 3 and 11 always carry a ProcessGuid, so only hand-made exports
  or exports with stripped fields are keyed by pid alone. The old walk got this case right because A joined in order
  and B then deleted 500.
- No test covers the :434 guard in either branch (see TESTS, E2).
