# M7.24 REDO: the builder's questions (ADR-0007 Amendments BB and BC: a mark, not an omission)

Returned to the Table, not answered locally. Each says what was built, why, and what it costs.

## What was built, in one paragraph

`os_sysmon.follow(..., mark_under=None)` asks `mark_under()` before each pass's build; `build(..., mark_under)`
writes every event as without it, in the same order, and adds `input_meta.under_root` (the root's pid) to both lines
(pre and post) of each event whose process is at or under a told root by ProcessGuid; the root's own event 1 is not
marked. `roots_of` keeps only `(pid, ProcessGuid)` pairs. "Under" is read from one map, `tree["parents"]` (a
member's ProcessGuid -> its parent's, both in `_gkey`'s form), kept only when the follow is asked. The host watch
keeps, per round, `os_nested[key] = ((other key, pid, ProcessGuid), ...)` from the sample (only trees whose
ProcessGuid it holds), and `_told(key)`, the follow's callable, keeps an entry only while the other tree's os follow
lives at that asking (thread alive, no error, not ended, not stopped). `_source_beats` skips any line whose
input_meta carries `under_root`. The `left_out` key, `out_said`, the notes and the block with no event are gone. The
test file is renamed `tests/test_follow_marks_under.py`. HOST-RHYTHM keeps 18 holes (one reworded; the pin in
tests/test_rhythm.py is unchanged).

## Q1. BC-3 skips a marked line of any source, not only of the os source

As ruled ("a line that carries `under_root` gives none"), `_source_beats` skips the line whatever its source. Capture
(the hooks) never writes the key, so on a hooks line it can only be written by something other than Raqib. A line
that carries it gives no beat; its findings are judged as before. Safe as built? The other reading is to skip it only
on an os line (`source == "os"`), so that a hooks line that carries the key still beats.

## Q2. A live follow stays told through failed rounds, from the last applied round's sample

`os_nested` is still refreshed only by an applied round; what changed is that a dead follow is dropped at the asking.
A follow that lives through many failed (or late) rounds is still told from the last applied round's sample, even if
its root has since left the sample. With the mark, what that costs is BC-5's (a marked line whose twin the other
file does not hold gives no beat to either tree), not a lost event. Should a failed round also clear the telling (or
keep it for one round only)?

## Q3. Two told roots on one path: the nearest names the mark; the inner root's event 1 is the outer root's

Where W's follow is told both A and S (S under A), an event of S's subtree is marked with S's pid (the nearest), and
S's own event 1 is marked with A's pid: A started S, so under AZ-1's reading it is A's act, and A is under a told
root. Is the outer root's pid the right mark for it?

## Q4. A parent named only by its pid breaks the chain

An event 1 whose ParentProcessGuid is empty records its process with no parent in `parents` (the parent is named
by its pid alone), so that process's events, and those of its children, are not marked even when they are under a
told root by pid. This is BC-2's "matched by ProcessGuid only", and the cost is that the ancestor counts those
beats as on main. It is not said in the holes separately: is it covered by BC-5's "a root with no ProcessGuid is not
told"? Or should it be said as its own case?

## Q5. The per-pass copy of the map

BC-5 says every os follow under the host watch keeps one more map for the life of the follow. `tree_copy` copies it
at every pass (AK-5: the tree published at the end of each pass), as it copies `by_guid` and `by_pid`, so the
per-pass cost grows with the tree's members too. That is not said beyond "one more map". Enough as said?

## Q6. The E5 twin with no root told is the guid-less agent, not a patched watch

The "with no root told" twin of E5 is the same run with the agent's candidate carrying no ProcessGuid. Then the
watch tells nothing (BC-2; the test checks what the watch told, before the follow's own `roots_of`), and the ancestor
makes AX-4's HOST-RHYTHM at high, as on main. This is a path of the code, not a stand-in for main's code. E1's "the
bytes are main's" is held three ways: the every-fixture hash test (untouched); the same hash with `mark_under=[]`;
and the same hash with every other (pid, ProcessGuid) of each fixture told, once the marks are taken out (more than
fifty lines marked). Enough?

## Q7. A follow that returned or was stopped is told again from its next attach

In the E3 test, after the agent's follow returned or was stopped (its root still sampled, still a candidate), the
next applied round attaches the tree again. The new follow lives, so the root is told again from the pass after
that round; after a raise the tree has a host source, and it is not. The new follow starts after the old one's
`top`, so the events in between are in both files, as on main. Is being told again on a new follow what BC-2 means?
