# M2.1 suspicion layer: questions for the commander

M2.1 exit criteria E1-E4 are met and `tools/gate.sh` is green. The HANDOFF was
drafted by the builder (`docs/handoffs/M2.1.md`) under the commander's order.
14 mutants of the A2/A3/A5 enforcement, the prompt and the backends were each
killed by `tests/test_suspect.py`. One of them, Ollama through a proxy, only
died once the test cleared NO_PROXY.

## What shipped

- **`raqib/suspect/core.py`**:
  - windows of up to 40 consecutive lines per session, plus the findings that
    cite them;
  - a prompt that holds only trace metadata, JSON-encoded with `<`, `>` and
    `&` escaped, so trace text cannot close the `<trace>` frame;
  - strict validation of the answer, and `run()`.
- **`raqib/suspect/backends.py`**:
  - `ollama`: stdlib HTTP, never through a proxy; default model `llama3.1:8b`.
  - `anthropic`: the official SDK, imported only when this backend is chosen;
    `claude-opus-5-5`, effort `high`, structured outputs, and
    `fallbacks: "default"` with beta `server-side-fallback-2026-07-01`.
  - `fake`: canned answers, for tests.
- **CLI:** `python -m raqib suspect` writes suspicion.jsonl and a `.run.json`
  run record. `report --suspicion` shows suspicion with cited lines and
  treats failed windows as alarms.
- **Live check:** the real `anthropic` SDK 1.15.0 sent the request; the API
  answered 401 because no key is configured in the builder's environment. The
  backend wrote an error line ("authentication failed"), not "clean".

## Open questions (not answered)

- **Q1 Credentials and privacy for the Anthropic backend.** A real run needs
  the commander's `ANTHROPIC_API_KEY`. It also sends trace metadata (paths,
  URL hosts, program names) off the machine. Is that acceptable as an
  opt-in, or should the default stay local-only (Ollama), as it is now?
- **Q2 Threshold.** 0.5 is a placeholder. M2.2 should set it from the FN and
  FP measurements.
- **Q3 Windows.** Windows of 40 lines do not overlap, so a pattern that
  spans a boundary (a secret read in one window, the network call in the
  next) is seen by neither. Should windows overlap, or should the model see
  each whole session?
- **Q4 Server-side fallback.** It is on by default, as the API guidance
  recommends for Claude Opus 5.5: a request declined by a safety classifier
  is re-run on another model, and a security-review prompt can trip such a
  classifier. Is that acceptable, or should a refusal stay an alarm?
- **Q5 Effort.** It is `high`, because judging deception is
  intelligence-sensitive. Should M2.2 measure `medium` as well?

## Assumptions made (confirm or overrule)

- **An answer below the threshold** is dropped and counted only in the run
  record as "below threshold", never as clean (A2).
- **Malformed answers are errors, never suspicion:** extra keys (for example
  `benign: true`), a score outside 0..1, or citations outside the window.
- **A raised suspicion needs at least one reason and one citation (A5).**
  Reasons are cleaned of control characters and capped at 8 x 300
  characters.
- **The report rejects suspicion lines** with a score of 0 or no
  cited_seq, so a "clearance" line cannot be smuggled in through a file.
- **Exit codes:** `suspect` exits 1 when anything is raised or any window
  failed, and 0 when nothing was raised. Nothing raised is not a clearance,
  and stderr says so.
