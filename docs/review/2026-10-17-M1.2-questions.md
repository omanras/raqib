# M1.2 corpus, budget and check — design questions (returned, not answered locally)

Each question names the reading the builder took; each has a test in
`tests/test_corpus.py` or `tests/test_cli.py`.

## Q1. Which logsource keys must agree
ADR section 7: "every key the rule sets must be equal in the corpus
declaration". Sigma's `logsource` may also carry `definition` (free
text).
Reading taken: `product`, `category` and `service` are compared; any of
them the rule sets must be equal in the corpus header; `definition` and
other keys are ignored on both sides. (Comparing `definition` would make
almost every rule `no_corpus` for no gain in evidence.)

## Q2. A corpus file whose header cannot be read
E1: such a file "is named and makes its rules unknown" -- but without a
header Mizan cannot know which rules are "its".
Reading taken: a file with no valid header, empty, or unreadable is cited
on every rule that selects by logsource (status `unknown`), since the file
may belong to any of them; rules with `x-mizan.corpus` are affected only
if they name it. Its name and reason also go to stderr once.

## Q3. Exit code when the corpus is damaged
ADR section 8: 3 = "could not complete (a path unreadable, a corpus file
unparseable)"; E3: an Unknown on any corpus line -> the rule is `unknown`.
Reading taken: both. The affected rules are `unknown` with the file and
line cited, and `corpus` / `check` exit 3 instead of 1 whenever any corpus
file is missing its header, empty, unreadable, over the size limit, or
has a line that is not one JSON object. A missing corpus directory is
also exit 3 (every rule `no_corpus`).

## Q4. A file named in `x-mizan.corpus` that does not exist
Reading taken: status `no_corpus`, citing `<dir>/<name> missing (named in
x-mizan.corpus)`. Names must be plain file names (no directory part, no
`..`); anything else is also `no_corpus` with the reason. The override is
exact: a named file is used even when its logsource differs from the
rule's, and logsource matching is not attempted.

## Q5. Header shape
Reading taken: the first non-blank line must be exactly
`{"_mizan": {"logsource": {...}}}` with no other top-level key; extra keys
inside `_mizan` (for example `"generator"`, `"seed"`) are allowed so the
M1.3 generator can sign its output. Logsource values must be non-empty
strings and at least one of product/category/service must be present.
Blank lines anywhere are counted, not events. A header-only file is
"empty: no event after the header" (unknown).

## Q6. Budget comparison
Reading taken: `fp_per_10k > fp_budget` is `over_budget`; equality is
within budget (the budget is "matches allowed").

## Q7. Line numbers in corpus citations
Reading taken: physical line numbers, so the first event of a corpus file
is line 2.

## Q8. Status of `check` when fixtures and budget disagree
Reading taken: the reddest of the two in the order invalid, unknown,
fail, over_budget, no_corpus; `pass` only when both pass. All citations
of both are kept (fixtures first; a rule-level `unknown` that both cite
appears once); the JSON carries both `fixtures` and `corpus` objects.

## Q9. What `check` scans
Reading taken: every `*.yml` under RULES_DIR, recursively, in sorted
order; `*.yaml` and any other file are ignored. A directory with no rule
is red (exit 1, "nothing is green by default", A4) with an empty `rules`
list in the JSON.

## Q10. Text line of the `corpus` command
E4 prescribes `<status> <id> fp/10k=<n> budget=<b> events=<e>` (no
title). Reading taken: exactly that as the first line, followed by the
indented match citations and one summary line naming the corpus files;
`check` keeps `<status> <id> <title>` and adds the same summary line.
Numbers print with up to four decimals, trailing zeros removed.

- A match-everything rule on a large corpus prints one citation per

  added.
