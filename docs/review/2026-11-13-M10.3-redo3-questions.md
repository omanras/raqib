# M10.3 REDO 3 - the builder's questions (ADR-0011 Amendment N)

Each is built as the nearest thing N's words allow, and said here for the Table to rule. None is answered
locally.

## Q1 (N-3) The head: how far it reaches, and when it is hashed again

HANDOFF said to decide whether a head hashed shorter than 4096 bytes is hashed again as the file grows, or keeps
its length. As built: the head covers at most 4096 bytes, and, once the cursor has passed any, only what the
cursor has passed (at the cursor 0: what the file holds). It is hashed again, longer, each time the cursor has
passed more of the first 4096 bytes (at 0: each time the file has grown), and only after its old bytes are
found the same.

Why not "the first 4096 bytes whatever the cursor": then a head of a short file covers lines after the cursor,
and E3's "a file cut to the cursor ... goes back to the cursor" would be a restart instead (the file shorter than
its head). With the head held to the passed part, a change after the cursor is the run's memory (given up back
to the cursor), and a change before it is the file's identity (a restart). At the cursor 0 the head covers what
the file holds, so the first build's case (a long tail, then another file) counts a restart, as E3 asks.

Edge, as built: a head hashed at 0 that reaches past the cursor once the cursor moves (until the next look
hashes it again, shorter: the same try's next read) proves nothing either way; the cursor's line decides. A
change to lines before the cursor's line in that window is not seen (as K-2 accepts for bytes before the
cursor's line).

## Q2 (N-3) A state written before the head

An older state has no `head`: the first look after the start hashes it ("trust at first sight"). A file replaced
while the forwarder was down, before the first look, is then judged by the cursor's line only, as before N.

## Q3 (N-1) The halving and the doubling still alternate on a link of 50 and not 100

As N-1 rules: late halves, taken doubles. A collector that takes 50 lines within the bound and never 100 is sent
100 (late), 50 (taken), 100 (late), 50 ... - one try in two late, as the second packet's finding 7 found; what
changed is that no batch is sent again at the size it was late at, and a collector late at every size goes down
to one line. A late `handshake` (the connect bound) does not halve: it is not the batch's. Holding the size where
it was taken last (or growing it more slowly after a late) would end the alternation; that is the Table's.

## Q4 (N-2) `refusing` stays while lines are in question; a take of an earlier line converts another failing

While lines are in question, a take leaves `failing` as `refusing` (with its since and its tries); a failing of
another word (a `late` before the take, say) becomes `refusing` at that take, keeping its since. `refusing`
ends when no line is in question - at the end of the settling, at the take of the last one in question in
`ask_first`, at a restart, or where what the run held after the cursor is given up. A try that moved and failed
(`refusing` at the cap, or a take and then a failed send) is followed by the next try with no wait.

## Q5 (N-5) `in_question.since` across a restart

The count in question is the run's memory (accepted in N), so a restart begins with none in question; `since`
is then the time the restarted run first refused a line alone, not the time the first run did. `failing.since`
(carried across the restart, M-6) still says how long the forwarder has been `refusing`.

## Q6 (N-8) `behind` is bounded, not looked through with Stop

`behind` is computed inside every state write, so it cannot write the state once a beat itself. As built it
never walks a long line or tail: it looks back at most 1 MiB from the file's end (and never below what the run
knows: the reach, the furthest line end it read, the tail's mark), then reads once forward at most 512 KiB from
what the run knows. Its walk is at most 17 reads, so Stop is never held by it; it does not look at Stop (a Stop
seen there would have to say a value it had not measured). Past that window, where the file ends in a tail
longer than 1 MiB with no newline, `behind` is a lower bound: whole lines further than 512 KiB beyond what the
run has read, and before such a tail, are not counted until the walk reaches them.

## Q7 (N-8) The walks N-8 does not name

- `--from end` on a first run hashes the last whole line once at the start (resume), before the first state;
  it does not look at Stop (a Stop there would leave a first run with no cursor from the end).
- read_lines parses one read of at most 512 KiB, which may hold many tiny lines (the second packet's finding
  11), at once; Stop and the beat are looked at between lines after it, not inside the parse.

## Q8 (N-4) A pid nobody has, and a life that cannot be told

At a state write, a pid file holding a pid no process has (the system says it is gone) is written again with
the forwarder's pid, as a removed one is; a pid whose life cannot be told (the system's answer is neither) is
taken as a life, and the forwarder ends with 1 - as the start already refuses such a name (J-13, L-7).

## Q9 (N-7) Every run of a test on a thread of its own

The tests' autouse fixture puts Forwarder.run - called by a test directly or through cli.main - on a thread of
its own, joined within 120 s, stopped and failed past it. A run inside cli.main therefore never installs its
signal handlers there (cli_run sets them on the main thread before it calls run; the signal's flag is still
seen). The real process's Stop by the system's signal stays tested on a real process.

## Q10 (N-9) The request bound

A try makes at most 201 requests (100 lines alone, at most one refused batch before each, one batch taken or
failed), which FORWARD.md says with its reason. The second packet's example (pairs of events with a line not
sent between them, a collector that refuses everything) makes 150. Whether the bound itself should be lower
(the batches counted toward the cap) is the Table's.
