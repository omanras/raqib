## Questions
- **Q-1 `check-rules` from an installed raqib (`--fixtures-root`, new).** The
  launching brief asked the install job to run `raqib check-rules` from
  outside the checkout. Its fixtures are `tests/fixtures/...` of a checkout,
  and E1 keeps them out of the wheel. So `check-rules` gained
  `--fixtures-root DIR`. The default is still the checkout raqib runs from.
  With no fixtures there, it now says "no rule fixtures in ..." and exits 2,
  where before it was a raw `[Errno 2]`. The install job runs it with
  `--fixtures-root $GITHUB_WORKSPACE`, so it measures the wheel's catalog on
  the checkout's fixtures. The other choices were to ship the fixtures in the
  wheel, which would go beyond E1's package data, or to leave `check-rules` a
  checkout-only command. Keep the option?
- **Q-2 What "foreign" means.** I read HANDOFF's installed / missing /
  foreign as being about Raqib's own entries:
  - installed: the entry this raqib writes (its own capture.py; on Windows,
    this Python; the right matcher);
  - foreign: a Raqib entry unlike that one (another checkout or install,
    another Python, the legacy form, a wrong matcher);
  - missing: no Raqib entry.
  Foreign counts as MISSING, because this raqib's capture is not what runs;
  `raqib watch` replaces it. Hooks of other tools are not reported. In
  test_install.py "foreign" means a hook that is not Raqib's. Is this the
  right reading?
- **Q-3 Notifier verdicts.** notify-send, osascript and the Windows toast
  are OK. "Terminal bell only" and "off" (CI set, untrusted SystemRoot) are
  MISSING. So doctor exits 1 under CI, as the install job expects.
- **Q-4 How Sysmon is checked.** Doctor reads HKLM
  `...\WINEVT\Channels\Microsoft-Windows-Sysmon/Operational`: the key must
  exist with `Enabled` = 1. This reads the registry and runs nothing. It does
  not prove the service runs; only reading the event log would, and that
  means running wevtutil. Off Windows there is no sysmon line, so the screen
  has five lines there and six on Windows.
- **Q-5 The `claude --version` query.**
  - `shutil.which` on the given PATH only. A relative result is refused and
    never run. That covers a relative PATH entry, and on Windows Python's
    search of the current directory. Doctor reports it as MISSING because a
    claude there may shadow the real one.
  - The environment is PATH and HOME (plus LC_ALL=C) on POSIX. On Windows
    it is PATH, PATHEXT, SystemRoot, ComSpec, USERPROFILE, APPDATA,
    LOCALAPPDATA, TEMP and TMP. PATH is kept so an npm launcher
    (`#!/usr/bin/env node`) finds node.
  - The limit is 10 s. A query still running after that is left running and
    recorded, never signalled, as notify.py does (A4).
- **Q-6 The hooks' python3 on POSIX.** The POSIX hook runs `python3` from
  Claude Code's PATH. That is not the venv's Python, even under pipx. Doctor
  checks only that python3 is on its own PATH. It cannot check its version
  without running it, and doctor runs only claude. capture.py has no stated
  floor. Should doctor run `python3 --version` too, or should the hook run
  the venv's Python by absolute path, as on Windows?
- **Q-7 The Python floor.** `requires-python >= 3.11`, the lowest version
  CI tests. `doctor.MIN_PYTHON` is the same value, and a test keeps the two
  equal.
- **Q-8 The package moves.** Hooks installed by an installed raqib name
  `<site-packages>/raqib/hooks/capture.py`. A new venv or another Python
  moves that path. The old hooks then print RAQIB-SILENCE, doctor shows them
  as foreign, and `raqib watch` replaces them. The README says so.
- **Q-9 Build output in a checkout.** `pip install .` from a checkout writes
  `build/` and `raqib.egg-info/` into it. `.gitignore`, which is outside this
  scope, does not list them. The gate reads tracked files only, so this does
  not change the gate.
- **Q-10 stdout of the console script.** `raqib = raqib.cli:main` bypasses
  `__main__.py`. So the `stdout.reconfigure(errors="backslashreplace")` moved
  into `cli.main()`, done only when `out` is None. `__main__.py` now just
  calls main(). This is tested with PYTHONIOENCODING=ascii and an Arabic
  project name.
- **Q-11 The wrapper's sys.path.** `tools/install_hooks.py` puts its checkout
  root first on sys.path. Without that, an installed raqib could run against
  the checkout's capture.py. This is tested with a decoy raqib on
  PYTHONPATH. The trust is the same as running the file itself.
- **Q-12 Tests that read the installer's source.** `tests/test_capture.py`
  (TIMEOUT) and `tests/test_docs.py` (EVENTS) now read `raqib/install.py`,
  where those constants live.
- **Q-13 README beyond the letter of E3.** The sentence "The code is on
  branch `claude/v0.1` until it is merged" and "on `claude/v0.1`" in the
  Status line went with the clone line; they state the same stale fact. In
  the Commands table and the discover examples, `python3 -m raqib` became
  `raqib` (the table says `python3 -m raqib` still works from a checkout),
  and the table gained watch and doctor rows.

## What only a real host can prove
- `pip install .` on Windows: `raqib.exe` on PATH, run from Git Bash; and the
  `.bat` stand-in for claude run through CreateProcess (the gate's Windows
  job runs that test).
- The real registry read on a Windows host that has Sysmon. GitHub's runners
  have none, so CI sees only "no event channel".
- pipx itself: CI uses `python -m venv` and pip. This container has pipx
  (`/usr/bin/pipx`), but it was not used, so that the tree and the user's
  pipx home stay untouched.
