# M10.3b REDO - the builder's questions (ADR-0011 Amendment P), 2026-11-13

Returned to the Table, not answered locally. Each says what was built and what it costs.

## Q1. An older syslog state without `facility` and `framing` (E3 asks how it is read)
Built: `state_problem` takes a syslog state with both keys or neither (one alone is damaged; an HTTP state
with either is damaged). A syslog state with neither is read; the start's facility and framing are taken and
written at the next state write, and the start line says so ("the state held no facility or framing (written
before they were kept): this start's, facility N, framing F, are kept from now"). Over udp the state's
`framing` is null. Cost: the first restart of such a state cannot tell that the earlier run used another
facility or framing (nothing recorded it); every restart after that can. The other way - taking the absence
as 13 and octet and refusing another - would refuse a legitimate restart of a run started with `--facility`.

## Q2. An end of the collector's that came before the forwarder's own (tcp)
Built: before its half-close the forwarder looks (a peek, no wait) for the collector's end; an end already
there is a failed send (`write`): it is no end in answer to the forwarder's. FOR: a collector that accepts
and closes at once (rsyslog past MaxSessions). Costs:
- A collector that half-closes its own side at accept and still reads everything would fail every batch
  (said: `failing`, never silent). None is known to me; not checked.
- A residual race: on Linux, once a peer's FIN is received, recv returns end-of-stream even if a reset comes
  after it. A collector that closed at once, whose FIN reaches the forwarder only after the peek and the
  half-close, and whose reset to the batch comes after the forwarder read that FIN and SO_ERROR, is taken
  as an orderly end. The test makes the order definite (the forwarder's connect waits for the listener's
  close) rather than proving the race away. A proof would need the TCP state (Linux TCP_INFO: TIME_WAIT
  only after the collector's FIN acknowledged the forwarder's), which Windows' Python does not give.
  Should the forwarder do more here, or is this the residue P-2 accepts?

## Q3. Over tls, a collector that ends TCP without its own close_notify
Built: the forwarder sends its close and reads the collector's (unwrap), then half-closes TCP and reads to
its end. A collector that read everything and then closed TCP with no close_notify is a failed send (`tls`
or `write`). rsyslog (GnuTLS), syslog-ng (OpenSSL) and Go servers send close_notify, from what I know of
them; not checked against any of them. If one does not, every batch fails, said as failing.

## Q4. The words of a syslog failure
No new error word: a reset, an end before the forwarder's, or a socket error left after the end is `write`
(its description now says "or the connection did not end in order after them"); an alert after the
handshake is `tls`, or `write` where the collector's reset is read before its alert; no end within the bound
is `late` with the phase `answer`, which halves the next batch as M-4's late answer does (the forwarder says
"no orderly end of the connection"). The status says `late` over syslog in its own words
(SYSLOG_ERRORS: "the batch was not written, or the connection not ended in order, within the bound"). Is a
word of its own for "not ended in order" wanted? It would be a new value of `failing.error` that an older
raqib reads as damaged.
