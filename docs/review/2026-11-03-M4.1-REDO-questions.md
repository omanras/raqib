## R1 - the child can still forge its line
Tree code that prints a well-formed `rule kinds: ...` line and then calls
`os._exit(0)` passes check 2. B-2 records that the pytest step has the same
exposure, and it applies here too: the child runs tree code. A tree
SystemExit, KeyboardInterrupt, `os._exit(0)` without the line, or a forged
line followed by a SystemExit are RED (tests). Is that the intended limit?

## R2 - untracked rule files
Check 2 counts the tracked files directly under raqib/rules/catalog/
(B-5, A8). `engine.load_catalog`, which raqib uses at run time, reads the
directory. So in a dirty tree an untracked rule file is loaded by raqib but
neither counted nor checked by the gate (a test pins this). Should the gate
also go RED on an untracked `*.yaml` in the catalog directory (A3), or is
A8 enough?

## R3 - a no-kind finding is an alarm, not a finding
Per B-3, `check_finding` rejects a finding without `kind` as `NoKindError`,
and the report raises a `no-kind` alarm whose detail holds the whole
finding. It is not listed under FINDINGS, so its cited lines are not
resolved there. Should it also be listed as a finding, with its kind shown
as "-"? A related effect: `raqib suspect --findings FILE` now refuses such a
file (a usage error, as for any rejected finding).

## R4 - an installed raqib in the gate's interpreter
The child puts the checkout at the END of sys.path (B-2). If the
interpreter that runs the gate has raqib installed in its site-packages
(a non-editable `pip install .` into that venv), the installed copy is
imported first, and check 2 is RED ("was imported from ..., not from this
checkout"). `-I` leaves out the user site, so `pip install --user` and pipx
are not affected. Is RED the right answer there, or should the child bind
the `raqib` package to the checkout explicitly?

## R5 - the placeholder filter
SECRET-OUTPUT now lists the placeholder-marker evasion (K6), and a test
shows it working: a real key with `_test`, `-example` or `test` glued into
the match lands in `placeholder_kinds`. No rule reads that field. Closing
the hole would be a capture change or a new rule; both are out of scope.
Which should a later task do?
