## 3 and 4. Findings, sorted by direction

### MORE SAID

**M1. One connection can become two talk beats, so one turn can count two cycles.** (High-severity rule.)
- `round_at` is the time the round is applied, not when the sample was read: host.py:2041, using the `now` of the tick
  that collects the worker (host.py:1949-1958).
- Take a connection opened after round m's sample was read but before round m is applied:
  - Sysmon's UtcTime falls in round m's interval, so `_bin` (host.py:1390) puts the os talk in round m.
  - The sample first sees the connection as new in round m+1, at that round's time (host.py:2847, `"at": None`).
- `one_server` makes these two talk rounds of one destination. `rhythm_of` (host.py:1293-1304) pairs each once. So one
  turn whose children run over two or more rounds within W = 30 s counts 2 cycles. Before AU-3 each destination
  counted 1.
- Result: K = 3 can be reached by two turns, for an agent or for a benign IDE. The YAML's "once per round" does not
  cover this, because the two beats are in different rounds.
- Likelihood: medium on Windows, where the reader takes seconds compared with T.
- No test or fixture has one connection seen by both sources. positive-split-sources has the host's talk in round 1
  and the os talks in rounds 3 and 4 only.

**M2. A5: the cited talk line can be one that does not show the talk came before the act.**
- `one_server` joins cites in insertion order, host first (host.py:1361). Host talks enter the ring before source
  beats (host.py:2721-2727, 2847-2848).
- `rhythm_of` cites `m["talks"][dest][:2]` (host.py:1301), and a host remote carries up to 2 cites (host.py:598).
- In a merged round the pairing time is in practice the os time: an act of round m comes before round m's time, which
  is the host part's only time. Yet the os line may be cut from `talk_cites`. The cited sample line says "seen at the
  round", not "talk then act".
- Likelihood: medium, whenever both sources see one round's connection.
- test_one_destination.py:237 uses only 1 cite per part.

**M3. The name sticks after the sample's talk leaves the ring.** (Words and A5, not the count.)
- `_rhythm` renames the stored ring in place (host.py:2728, `ring[:] = one_server(ring)`).
- A renamed os entry is now named "address:port", and `server_of` (host.py:1327-1334) parses it as a host talk. So
  every later os talk to that server is renamed, as long as any renamed entry is still in the ring. With os talks
  every round, one always is.
- So the name does not go back to the hash when the sample's talk leaves the last R rounds. That contradicts:
  - Q3: "goes back to the hash";
  - AU-7: "by the os talk's hash otherwise";
  - HOST-RHYTHM.yaml:30-34 and :95;
  - THREAT_MODEL:577-579.
- The pure `rhythm_of` (host.py:1283) does go back, and test_one_destination.py:223-234 tests only the pure function.
- Count: unaffected. I checked: no split arises, since every os talk to the server gets the same name.
- A5: a finding written long after the sample's talk names "address:port", while all its cited lines are os lines ("os
  net seq N at T") and none holds that address. A reader can check it only by hashing the address.
- Likelihood: medium in AU's own target case (the sample sees the first turn, the later turns are os-only) once the
  streak runs past R rounds.

**M4. A quiet or gone tree's line can carry an address from an earlier sample** (low; words).

## 5. AU-1: "input_sha256 is unchanged" and "no address is written that it did not write"

- Unchanged input_sha256 is held: the every-fixture hash is equal with the key stripped.
- `dest_sha256` is an unsalted sha256 of compact canonical JSON of {ip, port, protocol} (common.py:179-182). The same
  line carries `dest_port` and `dest_private` in clear (os_sysmon.py:490).
- For IPv4 this is not a guess but an exhaustive search:
  - at most 2^32 hashes, minutes per core in compiled code;
  - about 4e7 hashes for the private ranges when `dest_private` is true;
  - a well-known model server's address is confirmed with one hash.
- IPv6 can only be guessed.
- Compared with input_sha256:
  - For an event Sysmon did not name (hostname "-"), input_sha256 could already be searched the same way.
    - For an event Sysmon named, the address was bound to the name: recovering it needed the name too. `dest_sha256`
    removes that, so every IPv4 address of an os net line is now recoverable.
- "No address is written that it did not write" is literally true: nothing is in clear.
- "MUST NOT TOUCH: what the trace reveals" is not true for named events.
- THREAT_MODEL:135-137 says the hashes are unsalted and a guess can be confirmed. Neither it, nor :568-588, nor the
  rule says that an address whose port is in clear is recoverable outright. THREAT_MODEL:569's "a connection's line
  holds hashes only" suggests the opposite.
- Direction: MORE SAID. Certain whenever a reader of the trace tries.

  read again, has the seam.
