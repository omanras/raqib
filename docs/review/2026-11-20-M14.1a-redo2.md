## FINDINGS

**H1 (high if the source reading holds; false statement). Answers left out of the per-CPU count.**
- Where: `procevents.py:491`; the fake answer at `tests/test_procevents.py:85-86` (cpu 0xFFFFFFFF, seq not from the
  count); the test at 1110-1113; HANDOFF E4's parenthesis.
- What the kernel does, by my reading of `cn_proc.c` (not measured): `cn_proc_ack` sets seq and cpu, then calls
  `send_msg`. `send_msg` overwrites both with this CPU's next count number and its CPU id.
- So every answer, to any listener's ask, uses up a number on its CPU. Because the reader skips answers, the next
  event on that CPU steps by 2. That adds 1 to `lost.events`, said as "a loss the kernel did not tell".
- From then on, every record and every end says its threads are not known, and fork-only records say their program is
  not known. This lasts for the reader's whole life.
- Who can cause it:
  - any plain user in the first namespaces (the reader itself asks as one), with no process activity;
    - a second reader, at its start and at its stop. That is M14.1b's own setting: the watch's reader beside the rig's
    run, or a user's watch beside the service's.
- With the reader as the only listener, it should not happen in practice.
- Evidence beyond the source:
    - The REDO's spec said of the answer "its seq is the kernel's own count". This commit deleted that sentence (diff
    lines 166-172) and did not move it to the sandbox section.
  - The fake answer carries cpu -1, which is the value before the kernel overwrites it.

**H2 (medium; false statement against the measured order).**
- Where: `procevents.py:515-518, 765`; `PROC-EVENTS.md:166-167`; questions choice 5; the test at 1128-1136 locks this
  behaviour in.
- What BS measured: the ENOBUFS is read first. Each CPU's gap shows only at that CPU's first event after the drain. An
  idle CPU may show its gap much later.
- So any `counts()` call in between (the watch will poll it each round) makes the overflow's gap read as "came with no
  ENOBUFS: a loss the kernel did not tell", although the kernel did tell. The numbers stay right.
- Example: events on CPUs 0 and 1, then ENOBUFS, then counts(), then CPU 1's next event. That gap is called untold.
- Keeping, per CPU, whether an ENOBUFS came since its last event would not cure this either: the queued events are
  read after the ENOBUFS.
- `lost.count` is still the number of ENOBUFS (404-407, 459-462). No gap can be counted twice. The wrap at 2^32 is
  handled (514). The first event of a CPU sets its starting point (508-512). A step back is said once and not counted
  (519-522).

**H3 (medium-low; false statement).**
- Where: `procevents.py:701`; spec 69-71.
- A later end comes from an exit whose pid is not its tgid. It is never the leader thread's, yet its `unread.threads`
  (END_NOT_HELD) says "this end may be its leader thread's alone".

**H4 (low-medium; the words are narrower than the source; not measured either way).**
- Where: "what came while it was full is gone" at `procevents.py:758-759`, spec 165 and 231-232, threat model 536-537.
- By my reading of the netlink code: after an overflow the socket is marked congested, and every broadcast is dropped
  until the queue has been read empty, not only while it is full.
- BS's run read nothing while the 300 children ran, so it could not tell these two apart. For a Python reader the
  difference is the whole drain time. The gaps still count those events.

**H5 (low; false statement at a bound).**
- Where: `procevents.py:635` together with 679-681.
- When `_ends` is full at `_finish`, the end is dropped (counted in `beyond`) and `end_pending` stays None.
- If the record is later taken up, `old.given and not old.queued` holds, and ENDED_BEFORE says "the end given before
  ..." of an end that was never given.

**H6 (low; false statement after a memory forgets).**
- Where: `_remember` (557-561), which forgets silently.
- If `_refused_pids` forgot a pid, that pid's exit is given with NO_FORK ("began before the reader, or its fork was
  lost"), although its fork was heard and refused. The test at 1199-1216 asserts exactly that, `(6000, NO_FORK)`.
- If `_gone` forgot a pid, an exec of it says NO_FORK where NO_FORK_AFTER_END is the truth.
- Spec 171-175 lists "the memories of ended and refused pids" under `beyond`, but no forgetting is counted there, and
  `_older_pids` is not listed at all.
- A later end of a refused pid says NO_FORK (701).

**H7 (low; false under a loss).**
- LATER_END (119-120) says outright that the earlier end "was then its leader thread's alone". After a lost fork, a
  thread of a different process that took the pid would be given as that later end. END_LOST is added beside it, but
  the `ended` sentence stays absolute.
- ENDED_BEFORE (121) has the same problem inside the BS-1 one-second window when combined with a lost fork.

**H8 (low; a gap per the ruling).**
- After a loss, a held record that ended at its leader's exit (its thread's fork lost) never gets its remaining
  thread's exit or the real code. That exit only adds to `threads` (688-694); later ends exist only for `_older_pids`
  (695). BS-3 limits later ends to processes not held, so the code follows the ruling.

**H9 (low; words).**
- Module docstring line 47, "Every way it loses is counted", does not cover:
  - the last events on a CPU that has no later event;
  - a CPU first heard after a loss;
  - forgotten memories.
- The `said` line at 487, "no read is held against its exec's time", is stronger than what happens: the check resumes
  on any datagram where the boot clock reads (choice 8).

**H10 (low; tests).**
- Tests that only check the fake or echo the code:
  - 1110-1113 checks the fake's model of an answer, not the kernel's.
    - `tests/test_procevents_rig.py:263` (`refused["kernel"] == KERNEL`) computes the expected value with the same
    `os.uname().release` the run uses.
- No test for:
  - the CPUS_MAX bound (510-512);
  - the wrap at 2^32;
  - `_older_pids` forgetting;
  - an old end still unread when an exec with a different start comes (it must still be given once);
  - the cross-CPU overflow order (H2);
  - H5.
- The real-kernel test checks `lost.count` but not `lost.events` (833).

**H11 (low; rig only).**
- `Heard.take` (`tools/rig/procevents_run.py:113-115`) would join an end to the wrong record when both have `began`
  None and the end's `started_ticks` is None. The rig's own children are always forked under the reader, so the rig
  cannot hit this.
