# M0.2 silence rules: questions for the commander

M0.2 exit criteria E1-E4 are met and `tools/gate.sh` is green. Eight mutants
of `silence.py`, one per behaviour, were each killed by `tests/test_silence.py`.
This task ran under the commander's order to build the whole project without
stopping, so the points below were not returned as a STOP. Each one got the
narrowest reading of the HANDOFF and still needs a ruling.

## Open questions (not answered)

- **Q1 Normal use will raise SILENCE-GAP.** E1 counts any gap over 60 s
  between consecutive lines of a session. That includes a long tool call (the
  gap between a pre and its post, for example a 3-minute build) and the wait
  for the user after a `stop`, which is the agent's turn ending. In an
  interactive session most findings will be of these two kinds. Should a gap
  that starts at `stop`, or that falls inside one pre/post pair, be exempt or
  get a lower severity? A6 says to disable a rule that exceeds its budget, so
  this needs settling before the FP budgets in M1.1.
- **Q2 A session without session_start raises nothing.** If SessionStart was
  not installed, or capture started mid-session, the trace has tool lines but
  no `session_start`, and SILENCE-OPEN never fires. Should a missing start be
  a finding of its own (SILENCE-NOSTART)? Every trace written before M0.3
  would trigger it.

## Assumptions made (confirm or overrule)

- **SILENCE-HALF works in both directions.** A pre with no post (E3) and a
  post with no pre (an orphan, as in M0.1b Q3) are both reported as half a
  call. The summary says which half is missing.
- **Findings carry `session_id`.** seq is per session, so `cited_seq` alone
  is ambiguous. This adds one field to the ADR-0001 section 6 format.
- **A finding's `ts`** is the ts of the last line it cites. `findings()`
  never reads the clock, so its output is deterministic.
- **"Consecutive"** means file (capture) order within a session. Lines whose
  `ts` is missing or unparseable take no part in gap checks. A gap that is
  exactly the limit is not reported (`>`, not `>=`).
- **RAQIB_GAP_SECONDS** is read by `gap_seconds_from(environ)`, outside
  `findings()`, to keep the function pure (E4). A value that is not a finite
  positive number raises an error rather than falling back to 60, because
  `inf` or `nan` would silently switch the rule off.
- **"Within the file"**: a `stop` or `session_end` closes a session only if it
  comes after its `session_start`.
- **Trace parsing**: `raqib/rules/trace.py` reports corrupt lines (not JSON,
  or no session_id or int seq) by line number instead of dropping them, so
  the report (M1.3) can show them (A3).

## Findings outside this scope

- **F1 `tools/next-task.sh` misreads task ids with lowercase letters.** It
  matches `[A-Z0-9.]*`, so `M0.1b` is read as `M0.1` and the script picks
  `M0.1b.md` again. It then has nothing to commit and exits 1. `loop.sh` v2
  already uses `[A-Za-z0-9.]`. HANDOFF was advanced to M0.2 by hand in commit
  `HANDOFF -> M0.2`. `tools/` is outside the M0.2 scope, so this was not
  fixed here.

## REDO: builder's response to docs/review/2026-10-16-M0.2.md

**Fixed in the REDO commit**

- **S2, S3, S5, S13: corrupt lines are reported.** `trace.parse()` and
  `trace.read()` now return `problems` as `{line, reason}` pairs, not bare
  line numbers. Unusable lines are reported and dropped: not JSON, not an
  object, no session_id, or no int seq. Lines with a bad ts, an unknown phase
  or invalid UTF-8 are reported and kept. Line numbers count `\n` only.
  `findings()` still skips lines it cannot cite (A5); the report (M1.3) shows
  the problems.
- **S4: SILENCE-OPEN reads the last line.** A started session is open when
  its last line is not `session_end` or `stop`. That covers more tool calls
  after a turn's stop, and a resume or compact with no later stop. The E2 case
  (no stop at all) still fires.
- **S6: SILENCE-HALF counts lines.** It fires when a seq has more pres than
  posts or the reverse, so a reused seq can no longer hide a missing half.
- **S6, S7: new rule SILENCE-ORDER**, added beyond E1-E3 for ratification. It
  fires when a pre or a session event takes a seq no higher than one already
  seen (truncated, rotated or merged logs), or when ts goes back in file
  order. Posts may reuse old seqs.
- **S12, S16, S17: fuller SILENCE-GAP summary.** It names both ends (ts, phase
  and seq) and prints seconds to 3 decimals. A gap inside one call cites
  `[n, n]` and says pre to post.
- **S14:** a finding whose cited line has no valid ts takes the nearest
  earlier valid ts.
- **S15:** `findings()` rejects a gap_seconds that is not a finite positive
  number (0, negative, nan, inf, bool, str, None).
- **E1 wiring:** `test_e1_environment_value_drives_findings` exercises
  `gap_seconds_from(env)` feeding `findings()`. Production use comes with the
  CLI in M1.3.
- **E4:** the purity test now runs on input that produces findings, and checks
  that results are fresh objects. The mutants (a), (b), (d) and (e) are now
  covered (sorted output, OPEN's last line, ts timezone, bool seq), and 11 REDO
  mutants were run and killed. As before, the mutants are an ad-hoc run, not
  committed.

**Recorded for the commander, not fixed**

- **S1 Empty trace.** A finding must cite a seq (A5), and an empty trace has
  none. The M1.3 report will raise an empty trace as a report-level alarm
  rather than a finding.
- **S8:** HALF still matches by seq. In real capture output, a post that
  arrives before its pre gets a fresh seq (M0.1b), so HALF fires anyway.
- **S9, S10: predictable false positives for SILENCE-HALF.** A tool still
  running and a call denied by a PreToolUse hook or by the user both leave a
  pre with no post, and both raise a high-severity finding. Should a denial be
  captured as a post, for example via a PermissionDenied event if Claude Code
  has one?
- **S11:** fp_budgets for the SILENCE-* rules belong with the rule schema
  (M1.1 and later).
- **P1-P5:** the commander's order is now in the tree
  (`docs/review/2026-10-16-commander-order.md`). The order of events behind
  P4 was: `tools/next-task.sh` failed (F1), then commit e3c837d
  (`HANDOFF -> M0.2`), and only then were `raqib/rules/*` written. That is
  the builder's statement; the tree cannot prove it.
- **P6:** `tools/gate.sh` checks neither scope nor ASCII. The
  `.claude/hooks/scope-guard.sh` PreToolUse hook does check scope, and it
  correctly blocked this REDO's test edit while HANDOFF already said M1.1.
  HANDOFF was therefore put back to M0.2 with a REDO line (commit
  `HANDOFF -> M0.2 REDO`).
