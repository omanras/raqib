## Findings: where the reader can say something false or stay silent

**F1 (should-fix now, blocker for M14.1b until measured).** Lines 375-378 and 533-534.
- On ENOBUFS the reader counts `lost += 1` and keeps reading. Its `why` says "the events it held then are gone, and
  how many is not known".
- By my reading of the kernel source (not verified here): since about 6.6, `send_msg` sets the kernel's count of
  listeners to 0 when an event reaches no socket (`cn_netlink_send_mult(...) == -ESRCH`). A broadcast that only an
  overflowing reader would have received returns -ESRCH. While that count is below 1, the kernel makes no process
  events at all.
- A socket that has already asked to listen does not raise the count again by asking again.
- So if the reader is the host's only listener, one overflow may silence the source for the rest of its life. The
  reader would then show `lost: 1`, and its words imply events still come.
- Nothing in `counts()` shows how long the source has been silent: there is no time of the last datagram.
- An agent can push for an overflow by bursting short processes while the watch's main thread holds the interpreter.
- To close: measure it on 6.8 and 7.0. Until then, the `why` must not imply the stream goes on, and `counts()` should
  give the time of the last datagram heard.

**F2 (should-fix; Table ruling).** Lines 463 and 467-471.
- If a process execs twice between two reads, the record is queued once and its `exe` is overwritten. The first
  program is never given and nothing counts it.
- If the second read fails, `rec.exe = None` (469) throws away a first program that was read correctly. Lines 474-477
  likewise set `started_ticks = None` and drop a value already read.
- So a child can run program X and then exec a harmless Y before the next read, and X is gone without a count.
- `tests/test_procevents.py:607-615` asserts this as correct: /usr/bin/dash is dropped. That follows E5's ruling, but
  the loss is still silent.
- To close: keep every program a process had, or count each replaced one as a loss. Never overwrite a good read with a
  failed one.

**F3 (should-fix; not measured).** Lines 492-506 and 459.
- By the kernel source: when a thread that is not the leader calls exec, the kernel kills the leader thread. That
  leader's exit event has pid == tgid. The exec event then comes with pid == tgid too, in either order.
- A leader thread that ends while other threads go on (`pthread_exit`) also sends an exit with pid == tgid.
- In both cases the reader ends the process with a code even though it lives on.
    - If the exit comes first, the exec makes a new record that says "no fork heard: it began before the reader, or
    its fork was lost". That is false: the fork was heard.
  - If the exec comes first, the real end later shows up in `older`.
- E1's premise ("a thread is tgid not equal to pid") misses the leader thread.
- To close: an exec or exit of a pid whose record ended with no fork of that pid in between means that end was a
  thread's. Say this in the spec and the threat model.

**F4 (should-fix).** Lines 466-484; PROC-EVENTS.md:61-62.
- If the pid is taken by another process between the exec event and the read of /proc, the reader gives the newcomer's
  program and start ticks as the first process's facts.
- Nothing checks this. The stat's start is not compared with the fork's time, and a later record with the same (pid,
  `started_ticks`) is not noticed.
- The spec claims "The start in clock ticks ... and the pid together name one holder of a pid". In this case two
  records share both.
- M14.1b's "once" would then merge the two processes and lose the first.
- An agent can arrange this by holding the pid while it uses up the pid space. The cost grows with `pid_max`.
- To close: compare the start ticks with the fork's time, using the boot clock. Treat a repeated (pid, ticks) as a
  read of another process. Correct the spec sentence.

**F5 (should-fix, words).** Lines 101-102 (`GLOSS`).
- ENOENT is glossed "gone before the read". It is also what a process hidden by /proc's hidepid or the service
  manager's ProtectProc returns.
- EACCES and EPERM are glossed "not this user's to read". They are also what the user's own processes return when they
  are not dumpable: an exec-only or set-id program, or a process that turned dumping off. For a plain-user reader, an
  agent can make its own child's program unreadable this way.
- The service holds CAP_SYS_PTRACE (raqib/service.py:128), so this hits the window and the rig, not the service.
- To close: words that name every cause. Add the non-dumpable case to the threat model.

**F6 (should-fix, words).** Line 97, used at 450; line 99, used at 501-502.
- `NO_EXEC_EXE` says "its program is its parent's" even when `lost > 0` and the exec may have been dropped.
- The `older` record of a process the bound refused says "no fork heard". Its fork was heard and refused. The spec
  admits this (PROC-EVENTS.md:108-110); the record's own words do not.

**F7 (should-fix).** Lines 256 and 411-413.
- The kernel sends every listener's answer to the whole group. The reader's nonce is its pid, which any process can
  see.
- Another process on the host (a plain user can ask, as measured) can ask with that ack and an invalid op. If its
  answer lands between the reader's bind (308) and the reader's own answer, `start()` refuses with "the kernel
  answered the ask to listen with EINVAL". That blames the kernel for a hole the agent made.
- To close: a nonce nobody can guess.

**F8 (should-fix, A3).** Lines 362-364 and 392.
- `_run` has no guard. `ended` is set only when the receive fails (379-382).
- Any other exception that escapes `_once` ends the thread without a word. The clock calls at 392 sit outside the
  `try`.
- After that, `counts()` still says `ended: None`, and nothing reports whether the thread is alive.

**F9 (note; for M14.1b and the threat model).** Line 450.
- The fork's parent is the kernel's `real_parent`. A child made with CLONE_PARENT is given its maker's parent, so it
  falls outside the maker's tree.
- The threat model says nothing about this.

**F10 (should-fix, words).** Line 418; THREAT_MODEL.md:522-523.
- The bound on `_live` counts over the reader's whole life, not "between two reads".
- Entries whose exit was lost never age out. After enough losses every new process is `beyond`.
- The threat-model sentence understates this.

**F11 (note).** Lines 482-484.
- When the fork was heard, the parent from stat is dropped, so reparenting is never said.
- When the fork was not heard, the stat's current parent is given (possibly pid 1 or a subreaper). Nothing marks it as
  the parent now rather than the parent at birth.

**F12 (note; for M14.1b).** Line 467.
- `exe` is the raw link. It can hold newlines, control characters, surrogate escapes (bytes that are not UTF-8), a "
  (deleted)" ending that a real file name can also have, or a "/memfd:NAME" whose name the process chose.
- `stat_fields` is safe against the comm field (it splits on the last ")"). Only /proc/PID/exe and /proc/PID/stat are
  read, both at exec only. Confirmed.

**R6 (note).** Lines 275-276.

**R9 (note).**

## Questions for the Table

1. Measure F1: does the stream keep coming after an overflow when the reader is the only listener? If not, what does
  the reader say or do?
2. F2: should every program a process had be kept, or each replaced one counted as a loss?

7. F9 and F11: which parent does a tree use?

M14.1b must be told:
- `ended` may be only the leader thread's end.
- A process can be given twice: by its fork (no ticks) and again at its exec.
- (pid, ticks) is not always unique.
- `exe` is raw text and must be escaped.
- After `lost > 0`, "no exec heard" and silence both mean little.
- `live` grows with lost exits and is never pruned.
- Only one Reader can run per process (the bind is on the pid).
- The reader shares the interpreter's lock with the watch. Measure `missed` under the watch itself.
