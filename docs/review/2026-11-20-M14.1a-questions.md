## Choices where the HANDOFF was silent

1. **The kernel's answer to the ask.** `start()` waits up to 2 s
   (ANSWER_SECONDS) for the kernel's answer (an event of `what` 0, its errno
   at 16). An errno is a refusal ("the kernel answered the ask to listen with
   EPERM"); no answer is a refusal too ("did not answer ... within 2 s"),
   since by the kernel's source an ask from outside the system's first
   namespaces (a container) is dropped without a word: silence, which rule 4
   makes a finding. Events that come before the answer are taken.
2. **How its answer is told from another listener's.** Seen here (kernel
   6.18): the answer's connector seq is the kernel's own running count, not
   the ask's; its ack is the ask's plus 1. So the ask carries the reader's pid
   in its connector ack (the probe sent 0; E1 fixes idx 1, val 1, len 4 and
   says nothing of seq and ack), and the answer whose ack is pid + 1 is the
   reader's; any other is counted unread as "an answer to another listener's
   ask". To check in the field: that 6.8 and 7.0 answer the same way (if not,
   `start()` refuses with "did not answer", never silently).
3. **The stop asks to ignore.** `stop()` sends the same message with op 2
   (PROC_CN_MCAST_IGNORE) before it closes the socket, so the kernel's count
   of listeners is given back; a failure is one of the stop's problems.
4. **The receive queue.** The socket is asked for 1 MiB (SO_RCVBUF); the
   system may keep less, and a refusal is said in `said`. It lowers ENOBUFS
   in a burst; it switches nothing on.
5. **The exit's code and signal.** The kernel's exit_code is a wait status:
   `code` is the exit status where the process exited, `signal` the signal
   that ended it (as wait(2) reads them). The event's exit_signal field is
   the signal sent to the parent (SIGCHLD, 17; 0xffffffff for a thread), not
   what ended the process, and is not kept. Seen here: `true` code 0, `false`
   code 1, a shell killed by 9 signal 9.
6. **The parent.** The fork's (parent tgid: the kernel's word when the
   process began) where the fork was heard; the stat's only where it was not
   (a process older than the reader). A child reparented before its exec
   keeps the parent that made it.
7. **The shape of read().** `{"processes", "ends", "older"}`. `older` holds
   the ends of processes never heard to begin (E5's "exit with no exec
   heard"), in the shape of `ends`, and `counts()["older"]` counts them.
   `unread` is `{field: why}`.
8. **A process given before that execs again is given again**, whole, with
   the program it became (the common case: its fork heard before a read, its
   exec just after). M14.1b's "once, whichever source tells it" will have to
   take the second as the same process (pid and start in ticks).
9. **A fork never followed by an exec** is given at the next read by its
   fork: its program the parent's, not read (nothing is read at a fork).
10. **The bound.** PROCESSES_MAX = 32768, for each of: the processes kept
    (whose end is not heard), the processes held for the next read, the ends
    and the `older` held for it. A process past the bound has its later
    events counted as of one never heard to begin.
11. **Times.** `began` and `ended` are the kernel's stamps (the monotonic
    clock) put on the wall clock at the datagram's receipt (seen here within
    0.2 ms of the run's own clock).
12. **The bind** is (the reader's pid, 1), as E1 says: a second Reader in
    one process is refused at its bind (EADDRINUSE), in words.
13. **The rig's acts are against this machine alone**: a stand-in HTTP
    server on loopback for the three curls, wget, nc, Python's own client and
    git (`git ls-remote` of a path it does not serve: exit 128, and its child
    git-remote-http is heard); `getent hosts localhost`. No host of the
    internet is named in the tree. The run's own thread does nothing between
    two acts, as the probe's did; it reads after the last act until every
    act's end is heard (at most 5 s).
14. **X31's loss.** `lost`, `beyond`, a thread ended before the stop, and the
    stop's problems are losses; reads missed of processes that are not the
    acts are not (a plain user cannot read another user's program, so a
    runner's system processes would make it MISSED for nothing); they are
    shown in X31's words. A refused start on Linux is n/a with the refusal
    (E6), unlike X28 to X30's "not run on Linux".

## What this sandbox showed (not a field measure)

The sandbox is Linux 6.18 in a small VM (2 CPUs), as root. A real Reader
heard children here: tests/test_procevents.py's one real test passes (it
starts `true` up to 5 times and needs one whose program was read; every one
must be heard with its code). The rig's run here, 9 times: once MET (14 of
14); eight times 1 to 3 of 14 programs not read in time (touch, mv, cp, nc,
sh; each lived 1.4 to 5.5 ms; ENOENT: gone before the read), counted in
`missed` and said by X31 as MISSED. A first run by hand of `true`, `false`
and a killed shell missed all three programs; the next run read all three. Every fork, exec and exit was heard, with the
right code, every time; nothing was lost.

## For the field, and for the Table

- **The read of the program is a race the reader's thread runs inside one
  interpreter.** Its thread shares the interpreter's lock with the rest of
  the process (Python's switch interval is 5 ms): when another thread holds
  it, the read after an exec waits. The field measured 0 of 16 to 20 missed
  with a probe whose main thread was idle; a watch's main thread is not idle
  (samples, rules). M14.1b should measure the miss rate under the watch
  itself; whether a miss of a short child's program is then a hole of its
  round, a note, or something the watch must avoid by design, is the
  Table's to rule.
- Run X31 on the three runners as the runner's own user (the workflow is
  the Table's to wire: `python tools/rig/procevents_run.py --out F.json`,
  then `tools/rig/check.py ... --procevents F.json`).
- That 6.8 and 7.0 answer the ask with ack + 1 (choice 2).
- Not measured, as Amendment BQ says: a kernel older than 6.8; whether a
  plain user hears another user's processes (the events, and then the
  program read: EACCES); a machine that starts thousands of processes a
  second (`lost`, `beyond`); a process inside a container (by the kernel's
  source: no answer, so a refusal).
