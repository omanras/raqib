# M10.3 REDO 2 - the builder's questions and what was built for each (ADR-0011 Amendment M)

Each question is built as the nearest thing M's words allow; none is answered here for the Table.

## How no socket is closed by another thread than the one using it (M-5, E5, read in the code)

- `Send` opens every socket of a send on its own thread (`exchange`, through `hold`), and only that thread
  closes them: `Send.run`'s `finally` (the thread's last act), `Send.hold` (a socket the thread has just made
  and not used, where the send was already abandoned) and `exchange`'s `conn.close()` (the thread's own
  connection). These are the only `close` calls in `Send`; there is no `detach` anywhere in it.
- `Send.abandon` runs on the forwarder's thread. It marks the send abandoned under the send's lock, calls
  `socket.socket.shutdown(s, SHUT_RDWR)` on each socket - the system call on a descriptor that stays open, never
  released - and joins the thread for at most 0.5 s. It closes nothing. A send still alive after that is kept
  in `Forwarder.adrift`, counted until its thread ends; while four are, `post` starts no send (`stuck`).
- A test reads it (test_redo2_e5_an_abandoned_sends_sockets_are_shut_down_never_closed_by_another_thread): the
  methods of `Send` that call `close` are `hold`, `run` and `exchange`, and `abandon` calls `shutdown` and
  neither `close` nor `detach`.
- Not checked here: whether `shutdown` wakes a recv blocked in another thread on Windows. Where it does not,
  the abandoned thread ends at its own per-call timeout (at most 30 s) or when the collector closes; the
  forwarder does not wait for it (it is counted toward the four). The tests' fixture joins a forwarder thread
  for up to 60 s before it fails the test, for that reason.

## Questions

1. M-1, "each try also asks the first line in question again, alone". Built: when that line is taken, the line
   in question after it is now the first, and it is asked in the same try, and so on while each is taken
   (each counted among the try's 100 sends alone). Without it, a collector put right with nothing written after
   the reach would move one line per try, a wait between each (refusing in between). A line refused there stays
   in question (the take of an earlier line is not "a later line taken", M-1's MUST NOT TOUCH).
2. M-1, "at most 100 sends of a line alone" and E1's "each try at most 101 requests". Built: a try ends when it
   has sent 100 lines alone, and sends no batch after that. With the default batch a try then makes at most 101
   requests (one batch and 100 lines alone, or the first in question, one batch and 99). With `--batch N` below
   100, a try whose batches are refused makes 100 sends alone and up to 100/N + 1 batches.
3. M-2, the settling. Each line in question before a taken line is asked alone once more, also within the try's
   100 sends alone; the next try goes on settling at once (no wait: something moved). A night of heartbeats a
   collector refuses by kind is then each sent alone once more when the finding is taken: n lines cost n more
   sends. The refused ids keep the latest 50.
4. M-3, "named by its offset". Built: the `ids` entry of a line too long to be read is the text `offset N`
   (N its first byte), and the output says "its id not read". The schema's `ids` were ids; a reader that takes
   each entry for an event id will see a text that is not one. A line of at most 512 KiB whose hec envelope is
   over 512 KiB is read and named by its id.
5. M-4, the halved batch. Built: only a request `late` while being sent (the send phase passed its 30 s) halves
   the next batch (half the lines of the batch that was late, down to one); a taken send gives back `--batch`.
   A late answer (the collector slow to answer a large batch) does not halve: M-4 names "a link too slow for a
   batch". Should a late answer halve too?
6. M-6, "carries the `failing` its state held until its first try has an answer". Built: also until a first try
   that finds nothing to send (the file read, nothing waits). Otherwise a forwarder that ended `unforeseen` or
   `token` with nothing behind would say FAILING until a new line comes, though nothing is failing.
7. M-7, the name lost. Built: at the state write that finds the pid file not holding its pid (another pid, no
   file, a file that cannot be read), the forwarder writes nothing over the state, says the reason, leaves the
   pid file, and ends as a usage error (exit 2). Is 2 the code the Table wants (it is not the person's usage)?
8. M-8, the file read further in a try. Built: every read inside a try opens the file again and makes the
   pass's check (the length and the last line passed); where it fails, the try ends with nothing more moved,
   and the next pass counts the restart. The file is not held open across a send (on Windows an open file
   cannot be renamed by its writer: J-3, never locked).
9. A tail of more than 512 KiB with no newline after lines in question: the try ends `refusing` (one word); the
   tail is said as `file` only when the cursor reaches it.
10. The `stuck` count: a send abandoned at Stop is counted too while its thread lives; a restart begins at
    zero. Four is M-5's number; it is not an option.
