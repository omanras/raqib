## 3. D-1 to D-6 and E-1
**D-1: built** (event.py:393-397, 401-407, 517-521; EVENT.md:14-20).
- The rule "the entry that holds a count" is right for every entry the watch makes today:
    - A watch's hole is made only at host.py:1777, as {kind, detail, at, notice, round}, never with `count`. No other
    `holes.append` for HostWatch exists under raqib/.
    - A notifier's hole always holds `count` (notify.py:444). It has three callers (:296 "notify-off" at start, :428,
    :473). The notifier is made once per watch (host.py:1489) and I found no restart. Its list only grows: a repeat of
    the same kind and detail raises `count` in place.
    - A blind spot lives in host.blind, a separate list, and reaches hole() only as "blind:i" (event.py:398-399).
    check's count test applies only to "hole:" and "notifier-hole:" (:517-521), and "blind:" is bound to the class
    "blind spot" (:513). So D-5's new blind-spot `hole.count` is never taken for a notifier's hole, by snapshot or by
    check.
- [SILENCE, low] Nothing guards this rule. The test uses the module's own rule again (test:332, `"count" not in e`).
  If host.py ever gave a watch hole a `count`, that hole would quietly be named "notifier-hole:i".
- [SILENCE, low for a snapshot; higher for a running watch] The lost-words note gets its name only when `lost ==
  notes[-1]` exactly (event.py:402). Its text carries a count of lost writes (watch.py:1280), and it is read twice:
  inside state() (host.py:4387) and again by the caller (test:116-118).
    - If one write is lost between the two reads, the texts differ. The note is then silently "note:N", the name the
    next note of the watch will take. That is D-1's failure again, and nothing reports it.

## 6. For the writer of M10.2
Reading only EVENT.md and the signatures, they would still have to guess:
1. How to tell the lost-words note from the watch's own notes without snapshot. `note()` takes `about` from the
  caller; the test (`lost == notes[-1]`) and its race are inside snapshot only.
2. How to tell a watch hole from a notifier's when calling `hole()` entry by entry. "The entry that holds a count"
  names a field of the entry, while a blind spot's event now holds `hole.count` too.
3. Whether a changed notifier-hole count or last, a blind spot's count (it grows every round) or a new lost-words text
  (every lost write) counts as "changed", to be said again with rev+1. EVENT.md:12-13 names only three changes, so one
  event per lost write is possible.
4. What a raised builder becomes. ADR D says a hole; EVENT.md says nothing about its kind, `about`, or which list it
  joins.
5. Where `about` and `summary` go in OCSF for Base Event kinds, and what "the rest" means (E-3 is not in EVENT.md).
6. What time to give a plain-text note and the lost-words note in a running watch.
7. The real order of `end`, `exit` and `lost` in snapshot.
