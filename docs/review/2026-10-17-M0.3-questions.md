# M0.3 — questions and readings taken

1. **Where reported/confirmed amounts live.** ADR §3 lists one
   `contributions` table while §2 says partial payments are several
   entries and totals are recomputed from the ledger. Reading taken:
   `contributions` holds one row per (round, member) obligation (expected
   amount, waiver); the individual reports and confirmations are ledger
   entries, and M1.4 adds an index table for them in its own migration. No
   stored total is ever the truth.

2. **Draw state tables.** Not created now; M1.3 adds what it needs in a new
   numbered migration (server/ is in its Scope). Migrations are never
   edited after they run: the migrator records a SHA-256 of each file and
   refuses to start if an applied file changed or disappeared.

3. **Audit is append-only too.** The ADR requires triggers on the ledger.
   Reading taken (most restrictive): the `audit` table gets the same
   no-UPDATE / no-DELETE triggers, since it is evidence shown to
   organizers. Retention (M3.2) is therefore "kept for the life of the
   instance" unless a later ADR amendment says otherwise.

4. **Durability.** `synchronous = FULL` with WAL (not NORMAL): a ledger
   entry acknowledged to a member must survive a power loss. Busy timeout
   10 s so concurrent writers wait instead of failing.

5. **User-agent and user-id hashes.** Keyed (HMAC with a key derived from
   SESSION_SECRET), truncated to 16 hex characters, so a dictionary of
   common user agents cannot reverse them. The raw IP and user agent are
   never stored; the IP is cut to /24 (IPv4, including IPv4-mapped IPv6)
   or /48 (IPv6).

6. **"HTTPS awareness" in production.** Reading taken: production requires
   SESSION_SECRET of at least 32 characters, `TRUST_PROXY=1` (TLS is
   terminated by the reverse proxy) and an `https://` BASE_URL; any one
   missing stops the start with a message on stderr and exit code 1.
   Outside production a set SESSION_SECRET must also be >= 32 characters;
   an absent one is generated into `DATA_DIR/session-secret` (mode 0600).

7. **Concurrent-append test.** "Two transactions" is proven with four OS
   processes, each with its own connection, appending 150 entries to the
   same circle at the same moment through the real `appendLedger`. Node
   22 strips TypeScript types natively; `tests/unit/support/ts-resolve.mjs`
   maps the sources' `./x.js` imports to `./x.ts` for the child processes.
   Result: 600 entries, seqs 1..600, chain verifies, writers interleaved.

8. **Payload storage.** The ledger row stores the canonical JSON text, so
   the row itself is the hashed text and a raw-SQL reader can verify it
   without re-serializing.
