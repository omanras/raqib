# M0.3 condition — design questions (returned, not answered locally)

Each question names the reading the builder took; every reading has a
test in `tests/test_condition.py`.

## Q1. Static validation before evaluation in `evaluate_rule`
E3 mandates the three-valued table (Unknown and False = False). Applied
alone, a referenced selection with an unsupported modifier would never be
reported when a sibling is False: `selection and filter_bad` would be
`False` on every event where `selection` is False, and the rule could pass
all its fixtures while using a feature Mizan does not evaluate (A4).
Reading taken: `compile_rule` compiles every selection the condition
references *before* any event is looked at; if any is `Unknown`, the rule
is `Unknown` on every event. The table of E3 is applied unchanged by
`evaluate(ast, results)` on the results of compiled selections (which are
True or False). Selections the condition does not reference are never
compiled or evaluated (E4). Tests:
`test_referenced_unsupported_selection_makes_the_rule_unknown`,
`test_unreferenced_selections_are_not_evaluated`.

## Q2. Keyword case
Sigma's reference implementation (pySigma) accepts `AND`, `Or`, `NOT`.
ADR section 5 lists the keywords in lowercase.
Reading taken: lowercase only. An uppercase keyword is `Unknown` with the
reason "keyword 'AND' must be lowercase ('and')"; a selection that is
actually named `AND` still resolves as an identifier.

## Q3. Wildcard position in `1 of` / `all of` patterns
ADR section 5: "an identifier with an optional trailing `*`". pySigma
accepts a wildcard anywhere (`*_filter`, `fil*er`).
Reading taken: trailing only; any other placement is `Unknown` naming the
pattern. `1 of *` (every selection) is accepted as a trailing wildcard on
an empty prefix. A pattern without a wildcard (`1 of selection`) resolves
to that one selection.

## Q4. Quantifiers other than `1` and `all`
Reading taken: `2 of them`, `0 of filter_*` and the like are `Unknown`
("only '1 of' and 'all of' are supported").

## Q5. Identifier characters
Reading taken: identifiers are `[A-Za-z0-9_.-]+`; anything else at an
identifier position (`&`, quotes, `=`) is `Unknown` ("unexpected token").

## Q6. Aggregations and `near`
Reading taken: a `|` anywhere in the condition is `Unknown` with the whole
tail quoted (`'| count() > 5'`); the token `near` anywhere is `Unknown`.
Both are detected before parsing, so the reason names the construct and
not a downstream parse error.

## Q7. Desugaring of quantifiers
Reading taken: `1 of X*` is parsed to an `or` node over the matched
selections and `all of X*` to an `and` node (a single match collapses to
the identifier). The AST therefore has four node kinds only: `id`, `not`,
`and`, `or`. A later reporter that wants to show the original form keeps
`rule.condition`.

## Q8. Results that are neither True, False nor Unknown
`evaluate` receives results from callers. Reading taken: a result that is
not exactly `True`, `False` or an `Unknown` instance (for example `1`,
`None`, a truthy string) is `Unknown` naming the selection; a missing
result is `Unknown` too, but only when the table actually needs it
(`a and b` with `a` False is False without consulting `b`).

## Q9. `evaluate_rule` on a `Problems` list
Reading taken: an invalid rule (the loader's `Problems`) evaluates to
`Unknown("rule is invalid: ...")` rather than raising; the fixtures layer
(M1.1) is expected to report such rules as `invalid` before evaluation.
