# M0.3 — questions for the commander (not answered locally)

Each entry: the question, the most conservative reading taken, where it
shows in the tree. Nothing here changes the exit criteria.

## Q1. The reference engine's source was read (read-only)
The M0.2 builder worked from `reference/` alone. The Python engine is on
branch `qayd` of this repository (`qayd/*.py`, commit 6e0aeb1), and A10
asks for byte agreement, so it was read with `git show` / `git archive`
and ported module by module (measures, rules, report, cli). SESSION_PROTOCOL
§7 forbids writing protected branches; nothing was written there. Reading
taken: reading a protected branch is allowed; writing is not.

## Q2. The M0.2 loaders were realigned to the CLI
E2 asks for invalid-row findings "in the same ids and texts as the CLI", and
a loader problem *is* that finding. So `src/engine/` loaders now follow
`qayd/ledger.py`, `rates.py`, `policies.py`, `decisions.py` exactly. This
supersedes M0.2 Q1-Q4 and Q6-Q8:
- a problem is the CLI's dict `{file, line, code, class, reason}` plus
  `date` (row problems whose date parsed), `dup_of` (DUP-ROW) and `field`
  (policies, decisions); `line` 0 = the whole file;
- codes are the CLI's: COLUMN-COUNT, BAD-CSV, EMPTY-LINE, LINE-TOO-LONG,
  FILE-EMPTY, FILE-MISSING, FILE-TOO-LARGE, BAD-HEADER, BAD-DATE,
  BAD-AMOUNT, BAD-CURRENCY, UNKNOWN-ACCOUNT, UNKNOWN-CATEGORY, BAD-TAGS,
  BAD-ASSET, UNKNOWN-CLASS, BAD-QUANTITY, BAD-VALUE, BAD-RATE, BASE-RATE,
  CONFLICT-RATE, DUP-ROW (warn), BAD-YAML, BAD-SHAPE, BAD-FIELD,
  MISSING-FIELD, EMPTY-POLICIES, UNDECLARED-CATEGORY / -ACCOUNT / -CLASS,
  DUP-ID, BAD-STATUS, UNKNOWN-POLICY, BAD-CLOSES, INTERNAL;
- a row reports every faulty field, not the first; a blank line inside a
  CSV is EMPTY-LINE (invalid, undated, so it touches every period), a file
  is split on "\n" and each line is one CSV record (no multi-line quoted
  fields), the header is compared as raw text;
- an unknown policy shape is not a problem (the CLI keeps it as `unknown`
  silently); a policy with a bad id, a duplicate id or a non-mapping is
  dropped with a problem; every policies.yml problem is fatal (exit 3);
- `files` counts valid rows, as the CLI does.
Reading taken: the CLI's behaviour wins over the M0.2 guesses everywhere.

## Q3. YAML 1.1 as PyYAML reads it
`src/engine/yaml.ts` gives js-yaml a schema with PyYAML's implicit
resolvers (yes/no/on/off booleans, 010 octal, 0x.., 1_000, 1:30, ~) and the
engine's overrides (a float is a Decimal from its text, a date stays text),
and records the line where each mapping starts (`lineOf`). Known
differences, all outside the example household:
- the wording of a YAML parse error is js-yaml's (file, line and code agree;
  the duplicate-key and multi-document cases are mapped to PyYAML's text);
- js-yaml turns every mapping key into a string (`1: x` has key "1"; PyYAML
  would give an int and a BAD-FIELD);
- explicit `!!set`, `!!omap`, `!!pairs`, `!!binary` are rejected (BAD-YAML)
  where PyYAML's safe loader builds them; the bare `=` scalar is text;
- BAD-ENCODING cannot happen: the engine receives text, so decoding is the
  store's job (M1.1).
Reading taken: these are documented divergences, not normalised away.

## Q4. An absent file and an empty file
`HouseholdText` values are `string | null`: `null` is a file that does not
exist (FILE-MISSING, fatal; for the optional rates.csv an empty table and
`files["rates.csv"]` null), `""` is a file that exists and is empty
(FILE-EMPTY, fatal, rates.csv included, as in the CLI).

## Q5. What `check()` returns for a household the CLI cannot read
The CLI prints no JSON for exit 3, only the problems (`fatalText()` is that
message). The app still needs a result, so `check()` returns the check
shape with `policies: []`, `green: false` and every fatal problem as a red
finding; `routine()` has `all_done: false`, `decisions()` has `due: true`.
Reading taken: never green when nothing could be judged (A3).

## Q6. Normalisation in the tests
`tests/differential/oracle.test.ts`: none. Every oracle file is deep-equal
and byte-equal (`JSON.stringify(result, null, 2) + "\n"` equals the file).
The wider suites (`cli.test.ts`, `loaders.test.ts`) normalise one thing:
the wording of a YAML parse error (Q3).

## Q7. A wider differential suite, recorded from the CLI
`tests/differential/generate_cli.py` ran the reference CLI (Python 3.13.16,
PyYAML 6.0.1, branch qayd at 6e0aeb1) on its 11 rules fixtures, the
example household and 40 variants of it (a breach and its reversal, duplicate
and invalid rows, missing and conflicting rates, YAML 1.1 numbers, unknown
shapes, stale snapshots, a backdated closing decision, absent files...),
check / routine / decisions in text and JSON at many dates: 1215 runs in
`tests/differential/cli/*.json` (2.8 MB, 250 KB compressed), plus the
loaders on their own fixtures in `loaders.json`. The JSON is committed;
the gate replays it and never runs Python. Regenerating needs the qayd
branch (command in the script's docstring).

## Q8. The CLI's test fixtures were copied
`tests/engine/fixtures/qayd/` holds the CLI's `tests/fixtures/` (synthetic,
A9) so its unit tests could be ported with their expectations
(`ledger`, `policies`, `decisions`, `rates`, `measures`, `rules` tests).
The two invalid-UTF-8 fixtures were left out (Q3).

## Q9. One message the port cannot spell exactly
"peak value of account.X in the window is not positive (P)" prints Python's
str() of a computed sum, which keeps trailing zeros ("-500.000"); decimal.js
does not keep them ("-500"). Only a drawdown measure whose window peak is
zero or negative reaches it. Reading taken: documented, not emulated.

## Q10. Engine API for the screens
M1.1-M1.3 have no `src/engine/` in Scope, so what the screens need from the
engine is here now: `commands.ts` (check, routine, decisions, their text
and exit codes, fatalText), `report.ts` (verdictLine, summaryLine,
measureDisplay, limitDisplay, scopeDisplay, jsonText), the loaders'
`append*` writers, and `policies.ts` (policyBlock, serializePolicies).
