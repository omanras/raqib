# Review packet - M12.4c2b2b (the builder's commit d03b9c2)

Verdict: NEXT - Amendment X can stand as ruled and no finding needs the module rebuilt, but E7 is not met as written
  and four small code changes and three document changes are needed (findings 1 to 8, each small enough to make by
  hand). This is not an approval: nothing of these two commands has run on Windows, and the field (X54) still decides.

## Findings

1. **A percent sign in the path is not refused, so the command may name a different program from the path the check
  judged.** raqib/wininstall.py:349-357 (`path_refused`). It refuses a quote and characters that are not printable. It
  does not refuse `%`, and neither does wincode's `path_refused`/`_part_refused` (NOT_IN_A_NAME has no `%`). The
  system's own services keep their commands in a form it expands at a start (`%SystemRoot%` in theirs). If it does the
  same with Raqib's, a path holding `%NAME%` is judged as a literal folder but could be started as another path, and
  status would not see it, because `winmanager.COMMAND` accepts `%` and the manager returns the stored text. Not
  measured. This is the X-10 guarantee itself. Smallest change: refuse `%` in `wininstall.path_refused`, with words
  such as "holds a percent sign, which the system may expand in a service's command", and add one row to the
  parametrize at tests/test_wininstall.py:442. Until then it is a field item (below).

2. **The documents say more was measured than was.** Amendment X measured the created handle with 0x17 and remove's
  handle with 0x10024. The code asks 0x10017 and 0x10025, as the HANDOFF rules, and neither was measured as asked (the
  builder's Q1 and Q2 say so). Sentences that over-claim:
   - docs/THREAT_MODEL.md:2345 "with the rights measured and no more";
      - docs/GUIDE.md:644 "What each call needs was measured on real Windows ... before this was built", held word for
     word at tests/test_readme_top.py:448;
   - docs/specs/SERVICE.md:725 and :747 give 0x10017 and 0x10025 without saying they were not measured as asked.
      Smallest change: say "with the rights measured, and on two handles one right more, not measured as asked: DELETE
     on the handle CreateServiceW gives (0x10017), to undo a failed setting; SERVICE_QUERY_CONFIG on remove's
     (0x10025), to read the mark", and re-hold the GUIDE sentence.

3. **GUIDE does not say the second half of X-10.** docs/GUIDE.md:635-646 says the install asks the check first. It
  never says that the check is still run by the code it judges (N-2): an administrator who installs from a tree a user
  already changed runs that code as himself. THREAT_MODEL.md:2196-2198 and :2350-2352 and SERVICE.md ("What they do
  not do") say both. Smallest change: one sentence in the GUIDE paragraph, held in SERVICE_INSTALL_WINDOWS
  (tests/test_readme_top.py:443-450).

4. **The RESULT line can report success while the exit is 1.** raqib/wininstall.py:640-643 and :754-758. When a
  CloseServiceHandle fails, `held.failed` sets exit 1, but the RESULT words are kept. The output can then end `RESULT:
  installed and started: raqib service status answers ACTIVE` (or `RESULT: removed`) with exit 1. winmanager.status
  changes its RESULT to NOT KNOWN in the same case. The test at tests/test_wininstall.py:513-514 does not assert the
  RESULT. Smallest change: where `held.failed`, append "; NOT KNOWN: a handle was not closed" to the RESULT words, and
  assert that in the test.

5. **A service left without the mark is out of reach of Raqib's own remove, and the words do not say so.**
  raqib/wininstall.py:568-572 (LEFT) and :637-639 (FAULT). When `describe` fails and DeleteService then fails, the
  service of the name has no mark. `raqib service remove` will then call it not Raqib's and leave it, and a second
  install will refuse it too. A FAULT after CreateServiceW leaves the service with no undo tried. Smallest change: in
  the LEFT line, say whether the mark was set; where it was not, say that `raqib service remove` will not touch it and
  the system's own tools remove it.

6. **Error 3 at the place is said as "the runner makes it", which the runner cannot do.** raqib/wininstall.py:391-392
  takes `wincode.NOT_THERE` (2 and 3) as absent. By its name, 3 is a path not found (a folder above not there). For
  that, `winservice.prepare`'s CreateDirectoryW would fail and the runner would refuse with EXIT_UNREAD, so the
  printed line is untrue. tests/test_wininstall.py:398-399 holds 3 as absent, and no `prepare` tie covers it. Smallest
  change, for the Table to rule: take only 2 as absent and let 3 fall into the existing refusal branch, or keep 3 as
  absent and say it plainly.

7. **Paths are written without being made printable (W-3).** raqib/wininstall.py:502-510, :393-406 and :544-545 write
  the place's path and the command as they are:
   - the place's path comes from the installing process's ProgramData;
   - the command is a printable path that may still hold letters of another script.
      winmanager and wincode pass such text through `_said`, so a look-alike letter is shown by its number and a line
     break in an environment value cannot split a line. Smallest change: wrap the path and the command in
     `winmanager._said` in those output lines only. The command handed to CreateServiceW stays as it is.

8. **The undo says "removed again" without checking that the service is gone.** raqib/wininstall.py:573-574. The line
  is written once DeleteService is done. The name is not asked for again after the handles close, which remove does. A
  service held open elsewhere (for example the services console) stays, marked for removal. Smallest change: say
  "DeleteService done; it goes once every handle on it is closed", or ask the name again after `held.close()`, as
  `_remove` does.

9. **Test gap: the stand-in accepts any open handle for a call on the service.** tests/test_wininstall.py:72-74
  (`Manager._held`). If describe, start, stop, state or delete were handed the manager's handle instead of the
  service's, every stand-in test would still pass. The Library test does not check handles either. "The same handle
  throughout remove" (mark, Stop, wait, DeleteService) therefore rests on reading the code alone. By reading it is
  right: `service` from `open_to_remove` serves all four. Smallest change: the Manager keeps which handle is the
  service's and records a breach when a service call gets another.

10. **Scope.** Each item below is named in the questions file:
        - docs/GUIDE.md:625 (a sentence of the status paragraph) and docs/THREAT_MODEL.md:2196-2198 (a sentence of
      another paragraph) are outside the letter of "the rows of install and remove, one paragraph" and "one

    - tests/test_winmanager.py's four changes fall under the HANDOFF's allowance.
        - The import test at tests/test_winmanager.py:490-494 now holds a set where it held an exact list, so any
      count of the three imports passes. Smallest change: an exact list.
        - Nothing else is out of Scope: winmanager.py, winservice.py, wincode.py, service.py, pyproject, the ADR,
      CHANGELOG and the version are not in the diff.
    - No byte outside ASCII in the changed non-doc files.

11. **The `--no-start` line states as fact what X-9 says was not measured.** raqib/wininstall.py:577-578 says "the
  system starts it at the machine's next start (automatic)". Smallest change: "set to start automatically at the
  machine's start (not measured, ADR-0013 X-9)".

12. **Minor.**

## The builder's questions

1. 0x10017: keep. DELETE on the handle CreateServiceW gives is what lets an undo hit only the object just made, with
  no reopening by name. The field must show the handle granted. Its 0x1 is used by no call on that handle; keeping it
  as measured is harmless.
2. 0x10025: keep. Reading the mark through the very handle that is stopped and deleted is what makes "the one marked
  is the one removed" hold. For the field.
3. Two objects: keep. X-2 puts the writes in wininstall and the reads in winmanager, and a second QueryServiceConfig2W
  would copy the reader. The cost is two loads of advapi32 with the shared calls declared twice in the same words,
  which the two DECLARED tables hold.
4. Asking the name before the making: keep. It lets Raqib's and another's be said before anything is made, and 1073 at
  CreateServiceW covers a service made in between. How OpenServiceW answers for a service marked for removal is the
  field's.
5. Order:
      - Place first (as built, and X-3's ruled order): the place is judged before any handle that can make a service
     exists. The cost is that a non-administrator whose place is there hears "could not be read ... an administrator
     is needed" from the place, an indirect road to the same refusal.
      - Manager first: one plain "administrator needed" sooner. The cost is a manager handle with the right to make a
     service held while the place is read, and a departure from X-3 that the Table would have to re-rule.
   - My view: keep as built.
6. Bounds 80 s and 45 s: keep. Summing the 5 s and 60 s hints is right, since the runner tells them one after the
  other. The 15 s margin should go into the ruling as a number, because X-4 says only "a margin".
7. The unruled answers of remove: keep. Each removes nothing and is said, as "at the first that fails nothing more"
  asks. The Table may later rule 1061 (stopping already) as a wait for STOPPED; for now it is a field item.
8. Status's lines indented: keep. The install's RESULT is then the only one at column 0. The rig's wiring must anchor
  on it (For the field).
9. NULL reboot message and command: keep. The system documents NULL as "unchanged" and a new service has neither;
  M12.4c2b2c's reader will show them.
10. The plain road refused with 1: keep, as E3 says 1 for anything refused after Windows and the flags. SERVICE.md
  should say that `raqib service check` answers 2 for the same cause, so the two exits differ on purpose.
11. `--no-start` exit 0 with no status lines: keep. Reword the line (finding 11): the start at boot is not measured.

## Silent assumptions

- `%` in the path, the error 3 reading, the undo's "removed again", and the mark-less LEFT/FAULT service (findings 1,
  6, 8 and 5) were decided without being filed as questions.
- `code.program()` is read again after the check (wininstall.py:537); the value the check judged is not handed out.
  This assumes sys.executable cannot change in between.
- The description's words after the mark are the builder's (75 characters). The probe's description read back 116
  bytes, a different text.
- The mark is read once. A change to the description by another administrator between that read and the Stop is not
  seen. The same object is guaranteed, not the same text.
- On the 1062 road, a failure-action start may begin between the reading of STOPPED and DeleteService. The service
  would then be marked while starting, and that is said only as "marked for removal, not yet gone".
- A Ctrl+C during the 80 s wait ends the command with no RESULT line and the service as made and started.
- The plain road's command names sys.executable. Where that is a venv's launcher, what the system starts is shown only
  if the job's copy is one.
- X54 MET does not show that the installed copy was the one under Program Files, nor that the refused one was the
  job's own Python. Both rest on the Table's wiring and `asked-by-administrator` as the job declares it.
