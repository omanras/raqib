# M2.3 — questions and readings taken

1. **Which code runs in the browser.** "Verify chain" runs
   `shared/ledger.verifyAsync` with the browser's Web Crypto SHA-256
   (`shared/hash.webSha256Hex`), and "Recompute" runs
   `shared/lottery.finalizeAsync` and re-checks every reveal against its
   commitment (`commitAsync`) on the record the server sends. Both live in
   `client/trust.ts`; `tests/unit/browser-verify.test.ts` runs that module
   against the committed vectors and against node:crypto, and checks that a
   doctored order or reveal is refused.

2. **Web Crypto needs a secure context.** `crypto.subtle` exists only over
   https or on localhost. On plain http (a self-hoster testing on a LAN IP)
   the Verify and Recompute buttons are replaced by a notice saying a
   secure connection is needed, instead of silently doing nothing.

3. **"Last verified fetch" and stale data (A10).** The ledger screen shows
   the time of the copy on screen; when a refresh fails or the browser is
   offline it says the copy "may not be current" (and the global offline
   banner appears); after five minutes without a refresh it asks for one.
   A verification result belongs to the copy it ran on and is cleared when
   a new copy arrives.

4. **The draw secret.** Generated with `crypto.getRandomValues` (32 bytes,
   hex), written to localStorage under `dawr.draw.<circle>.<member>`
   *before* the commitment is sent (a lost answer cannot lose the secret),
   shown once with Copy and a warning, never sent until the reveal. On a
   device without it the reveal screen asks for the saved copy.

5. **Statement CSV.** The Statement screen downloads the server's
   `statement.csv` (already escaped, S4.4). The ledger CSV export is made in
   the browser with `shared/csv.ts`, the same rules as `server/csv.ts`
   (server/ is out of this Scope, so the server keeps its own copy of the
   twelve lines; a later task may make it import the shared one).

6. **Tamper in the e2e.** `tests/e2e/db.ts` edits a payload in the running
   server's SQLite file the way someone with file access could: the table
   is recreated without its append-only triggers, the row changed, the
   triggers restored. The browser's Verify then reports the break at that
   entry (seq 2, "its content no longer matches its hash").

7. **Ledger links from the statement.** Each statement line lists the seqs
   it rests on as links to `/circles/:id/ledger#seq-N`; the ledger scrolls
   to and highlights that entry.

8. **Readable entry summaries** (`client/summary.tsx`) are written per type
   in both languages; the raw entry (seq, ts, actor, type, payload, hashes)
   is one click away under each summary.
