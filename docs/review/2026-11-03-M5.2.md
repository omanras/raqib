## Readings taken where the text allowed one reading (check them)
- R-1 "one silence-class record" is one line starting with
  `RAQIB-SILENCE:` appended to the trace (and the same line on the proxy's
  stderr). ADR-0005 A-3 already makes such a line a capture failure in
  `raqib watch`; `raqib report` reads it as a corrupt line, an alarm. No
  new phase and no new rule (silence.py is outside the Scope). trace.py's
  reason for it stays "not JSON", so old reports are unchanged (Q-7).
- R-2 "upstream failure" is a failure to complete the exchange (no
  connection, TLS, timeout, an answer cut short) or an answer with status
  5xx. A 5xx is relayed unchanged ("unchanged in status"); with no status
  from upstream the agent gets 502, or 504 on a timeout. A 4xx is relayed
  and writes nothing (Q-4).
- R-3 `source` is the last key of a line, so a hook line of 721bb55 is a
  byte prefix of the line written now for the same event (a test holds
  this). Session events carry it too.
- R-4 trace.py never adds `source` to a record: `source_of()` reads a
  missing one as `hook`. Records load as they always did; an unknown value
  (not hook, proxy or os) is a trace problem.
- R-5 The finding head line is pinned by `tests/test_report.py`, so the
  source is its own line under it (`      source: proxy`), several sources
  joined by `+`, `-` when no cited line is in the trace. The header gains
  one `sources:` line with records per source ("report groups by source",
  ADR-0003 Consequences); JSON gains `sources` and each finding `source`.
- R-6 One proxy session per run, `proxy-<UTC start>-<pid>`. `cwd` is the
  proxy's working directory, as capture.py's fallback is its own (Q-2). ts
  is taken under the lock.
- R-7 A post's input hash and input_meta come from the call as the
  request's own history holds it (the agent's account); if the history
  lacks it, from the open pre; if neither, the hash of null and `{}`, tool
  `?`.
- R-8 A post pairs with the oldest open proxy pre with its call id anywhere
  in the trace (so a restarted proxy closes the calls of the run before),
  never with a hook line: Claude Code's hook tool_use_id is the API's
  tool_use id, so a mixed trace holds the same id twice.
- R-9 A pre is written before the bytes that complete its call are passed
  on (the SSE event, the last byte of a sized body, the end of a chunked
  one), so an agent's next request can never be read before the pre.
- R-10 Every request repeats the conversation: a result whose id was posted
  before is skipped. A result without an id (both APIs reject one) is
  posted once per run, kept apart by its output hash in memory.
- R-11 The plain upstream needs `--allow-plain-upstream` and a loopback IP
  literal (127.0.0.1 or ::1); a name such as `localhost` is refused.
- R-12 Read paths: ending in `/chat/completions` (OpenAI) and `/messages`
  (Anthropic); `/messages/count_tokens` is relayed and not read (no tool
  is called there). A JSON request with `model` and `messages` or `tools`
  on any other path writes one RAQIB-SILENCE line per path per run.
- R-13 The proxy connects to the upstream directly; HTTPS_PROXY is not
  used (A4: no connection of its own kind). Behind a forward proxy the
  upstream fails visibly (Q-9).
- R-14 Test edits outside the new file, each forced by a criterion:
  `tests/test_capture.py` SESSION_FIELDS gains `source` (E3), and the
  pure-function check reads command_programs' body from common.py (E1);
  `tests/test_ui.py` reads bands with `colspan="11"` (E4, the source
  column). No fixture file and no other assertion changed.
- R-15 The co-author line is the serving model's (Claude Opus 5.5 in this
  session), not the one the launching agent proposed, as in M4.2 R5 and
  M5.0b R-13.
- R-16 The proxy writes no session_start, session_end or stop (the
  binding names pre and post only; Q-1).
- R-17 THREAT_MODEL names ADR-0003, not the task id: `tests/test_docs.py`
  accepts a task citation only with a `2026-10-16-` review file.

## Questions for the Table (not settled here)
- Q-1 Should the proxy write session events: `session_start` when it
  starts, `session_end` at Ctrl-C, `stop` for an answer that ends the turn
  (finish_reason stop, stop_reason end_turn)? Without them SILENCE-OPEN
  and SILENCE-EMPTY never judge a proxy session, and a proxy killed between
  two calls leaves no sign.
- Q-2 cwd is the proxy's own working directory, so SCOPE-CWD-ROOT,
  SCOPE-CWD-MOVED and SCOPE-PATH judge where the proxy was started, not
  where the agent works. Is a `--cwd DIR` option wanted, or should proxy
  lines carry no cwd (rules that need one then report partial)?
- Q-3 The rules' tool lists are Claude Code's names (Bash, Read, Write,
  ...). An OpenAI-style agent whose shell tool has another name gets no
  command_head, and only url_host, SECRET-OUTPUT and the silence rules
  judge its lines. Kimi Code CLI's docs name its shell tool Bash. Should
  the proxy (or the rules) map tool names, and by what list?
- Q-4 Is a 5xx answer a silence (R-2)? Each one makes `raqib watch` knock a
  capture failure, and overloaded APIs answer 529/503 often. Is a 429 or
  401?
- Q-5 Kimi Code CLI has Claude-Code-like hooks (above). Should a later task
  install capture.py as a Kimi hook, so Kimi has the hook source as well as
  the proxy (two sources, one agent: CROSS-SOURCE material for M5.3)?
- Q-6 A result re-sent for a posted id with a different output (the agent
  rewrote its history) is skipped without a word. Should that be a
  finding, or a line?
- Q-7 `raqib report` shows a RAQIB-SILENCE line as "trace-problem: not
  JSON". Should trace.py name it ("a RAQIB-SILENCE line: capture failed"),
  at the cost of the text of old reports that hold one?
- Q-8 A prompt with example tool calls and results (few-shot) gives posts
  with no pre: SILENCE-HALF fires on each, once. A known false-positive
  source; accept, or skip results whose call is in the same request's
  history but was never answered by the model through the proxy?
- Q-9 Should the proxy reach the upstream through HTTPS_PROXY (CONNECT)
  where a forward proxy is the only way out (R-13)?
- Q-10 The proxy listens on 127.0.0.1 with no check of who connects: any
  local process can write post lines. Is a check wanted (a token in the
  base URL path, or an Origin refusal), knowing that the watched agent can
  forge posts anyway?

### Readings (REDO)
- RR-1 (A-11) The review packet with R12's list is not in the tree, so
  the list could not be read. Every path A-1..A-13 names has a test, and so
  has every refusal and failure branch of proxy.py (the `test_a*` and
  `test_e2_*` tests above). If R12 names a path not among them, it is open.
- RR-2 (A-3) The key is `canonical_sha256([model, messages[0]])` of the
  parsed request, messages[0] taken literally (null when absent). For the
  Anthropic API the system prompt is a top-level field, so it is not part
  of the key. The session id is the full 64-hex key.
- RR-3 (A-3) session_start when the key is new or its last line is a
  session_end; session_end at shutdown for every key still open, those read
  from the trace included ("every open key").
- RR-4 (A-3) stop: a complete answer with no tool call and finish_reason
  "stop" (OpenAI) or stop_reason "end_turn" (Anthropic); "length",
  "max_tokens" and "stop_sequence" write none.
- RR-5 (A-3) A result's position counts: the i-th result with an id in a
  request is the i-th answer to that id in its key (numbered ids repeat).
  A history that drops an earlier result while reusing its id shifts the
  alignment; a known hole.
- RR-6 (A-4) The history line is phase `history`, tool `-`, `results`
  (the count), `tool_use_ids` and `output_sha256s` (parallel, so a
  restarted proxy rebuilds the index from it). trace.py knows the phase and
  the fields; no rule reads them. Only a key's first request (the key not
  in the trace) can give one.
- RR-7 (A-5) One line per key, id and position per run; the line is a
  RAQIB-SILENCE line (a trace problem, an alarm).
- RR-8 (A-2) "sha256:" + 16 hex of the value's canonical JSON; printable
  ASCII is space to tilde; one `tool_hashed` flag, after `tool_use_id`,
  when either field was replaced.
- RR-9 (A-6) Host must be exactly one header `127.0.0.1:PORT`; `localhost`
  is refused (the README says so). Every refusal is folded, and the count
  still unwritten at shutdown gets its own line.
- RR-10 (A-8) Upgrade is refused before the body is read; every method
  but the seven relayed (CONNECT and TRACE too) is 405. An interim 1xx is
  read past and not relayed; a 101 is an upstream failure (502). "An
  abandoned stream" is read two ways, each a line: the agent leaving
  mid-answer, and an event stream that ended without [DONE] (or every
  choice finished) or message_stop.
- RR-11 (A-1) The catch-all catches Exception (KeyboardInterrupt and
  SystemExit pass). After a failure while reading an answer, that answer is
  no longer read. A failure in the middle of `Recorder.request` can leave
  memory ahead of the trace for that request; nothing is undone.
- RR-12 Recorded, not built (as ruled): HTTPS_PROXY is ignored (Q-9);
  429 and 401 are not silence (Q-4); doctor's common.py check (A-7) and
  capture.py as a Kimi Code CLI hook (Q-5) are later tasks.
- RR-13 Consequences of the key as ruled, written in the README and the
  threat model, not questions: a conversation whose first message changes
  (compaction, a first message rebuilt each turn) is a new session and its
  results pair with nothing there; two conversations with the same model
  and first message share a key.
- RR-14 The co-author line is the serving model's (Claude Opus 5.5), as in
  R-15, not the one the launching agent proposed.
