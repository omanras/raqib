== 2. A WRONG MARK / silencing a tree ==

- No spurious marks found (CERTAIN). The ancestor's own events are never marked: the follow's own root is dropped from
  told roots twice (roots_of :385 and build :369), and `_under` (:392-406) climbs only the genuine Sysmon parent chain
  in `parents` (guid→guid). The pid maps are gone, so there is no pid path to mark a non-descendant. The told root's
  own event 1 is skipped (:402 `not (own and e["event"]==1)`); its own event 3/11 are marked, as BC-2 requires.
- Two told roots on one path (Q3): CORRECT and consistent. In W's follow an S-subtree event is marked with S's pid
  (nearest told); S's own event 1 is marked with A's pid (climb past S). In A's own follow, S's event 1 is NOT marked
  (A is the own root, not in told) → A counts S's creation as its beat (AZ-1). No double count, no loss. Safe as
  built.
- ProcessGuid reuse / _gkey mismatch (CERTAIN, safe): guids are unique; both the telling (trees[other]["guid"] →
  roots_of → safe()) and the follow's parents go through _gkey before comparison (_under :398, link uses _gkey,
  roots_of dedup via _same_guid). No normalisation mismatch between what the watch tells and what the follow keys.
- The chain-of-nested-trees total-silence attack is DEFUSED by the liveness check, with a bounded seam (CERTAIN on
  mechanism). For an inner tree's events to be marked in a parent's follow, the inner tree must be a held os tree,
  sampled under the parent, AND its follow live at the asking (_told, host.py:3749-3762). If the innermost follow is
  dead or was never an os source, _told drops it, the parent stops marking it, and the parent writes those events
  UNMARKED → the nearest LIVE ancestor gets the beats. So beats cannot vanish for every tree persistently; they are
  routed to the nearest live ancestor. The only loss is the seam: events the parent already wrote marked between the
  inner follow's last written event and the parent's next asking that observes the death, when the inner follow never
  wrote its own unmarked copy. Those lines give a rhythm beat to no tree; their act findings (NET-TOOL etc.) are still
  judged where written (findings come from feed rules, not from _source_beats). This is exactly BC-5 and is said in
  HOST-RHYTHM.yaml:97 and THREAT_MODEL.md:689-700 ("a marked line whose twin the other tree's file does not hold ...
  gives no beat to either tree ... its commands are still judged where they are written"). The deliberate multi-link
  chaining is not called out as an adversarial construction, but the per-link cost is the same bounded rhythm loss.
- Two missed-mark cases that are NOT fully said (LIKELY, low severity, safe direction). Both leave the ancestor
  counting the beat as on main (never a lost event), so they are a quieter-ancestor regression, not a hole BB had:
    (a) pid-only parent (Q4): an event 1 with empty ParentProcessGuid links to None in `parents` (link, :467), so its
    subtree's chain breaks and is not marked even under a told root. The ancestor counts those beats as main. Arguably
    covered by "matched by ProcessGuid only" but not stated as its own case in the hole.
    (b) a descendant whose event 1 the ancestor's follow never read (a late attach past a restart, or an overwritten
    circular channel): its guid is absent from `parents`, so `_under` returns None → unmarked → ancestor counts it.
    Under BB this was a LOST event (first review F4/F5); under BC it is only a missed mark. Not stated in the hole
    beyond the general BC-5 seam wording.

== 3. Q1: BC-3 skips a marked line of ANY source ==

Verdict: ANY source (CERTAIN). host.py:3135-3136 is `if "under_root" in meta: continue` inside _source_beats with no
  `source == "os"` guard, so a hooks Bash line that carries under_root yields no act beat. Capture itself cannot write
  the key: common.input_meta (common.py:987-1026) builds input_meta field-by-field from known keys and never copies
  arbitrary keys from tool_input. BUT the trace file is writable by the agent's user (THREAT_MODEL.md section 6,
  :1111). An agent that writes `"under_root": N` into the input_meta of its own hooks Bash lines silently removes
  those lines from its own rhythm act beats while the lines stay intact: strict_problem does not inspect input_meta
  contents (trace.py:177 checks only top-level FIELDS, and input_meta is in FIELDS), so no schema problem; seq/time
  are untouched, so no SILENCE-ORDER. This is a new, rule-invisible beat-suppression primitive that evades the silence
  rules (an A3/CLAUDE-rule-4 concern). Cost: a missed HOST-RHYTHM act beat on the agent's own tree. It is inside the
  already-acknowledged trace-tamper model (an agent that can write the trace can also delete/alter the Bash line), so
  the marginal capability is small, but under the omission there was no such tidy primitive. The Table's BC-3 ruling
  is written source-agnostically ("a line that carries under_root gives none"), the code implements it faithfully, and
  the builder correctly returned Q1 asking whether to restrict to `source=="os"`. I raise it as suspicion; the
  restrict-to-os alternative removes the primitive.

== 4. BC-2 liveness / races / mark_under raising ==

- No crash or dead-tell found (LIKELY). _told runs in the follow's own thread and reads self.os_nested (replaced whole
  each applied round, host.py:2316, never mutated in place) and live attributes (thread.is_alive, error, ended,
  stop.is_set) with no lock; these are plain reads, CPython-safe here. Liveness is read LIVE at the asking, so even a
  stale os_nested (Q2) cannot tell a dead follow. A re-attached inner tree (new src at the same key) is seen as alive
  and is told again (matches Q7).
- If mark_under() raises: follow.py:890 (`roots = ... roots_of(mark_under(), pid, guid)`) is inside the pass loop; an
  exception propagates out of follow into run() (host.py:3705-3711), caught by `except BaseException: src.error =
  ...`. So the ANCESTOR's own os follow dies, becomes errored, and the tree falls to a host source next round
  (failed_os, :3450). This is handled (not a watch crash) and shows up as a source-ended/error hole, but the specific
  "mark_under raised" cause is not separately documented. _told and roots_of are defensive (getattr defaults, type
  guards) so a raise here is unlikely. Low concern.

== Q1-Q7 ==

- Q1 (skip any source): NOT clean as built — it is source-agnostic (host.py:3135), so an agent that writes under_root
  into its own hooks lines silently drops its own rhythm act beats without tripping a silence rule. Within the
  existing trace-tamper model but a new rule-invisible primitive. Cost: a missed HOST-RHYTHM beat. Safe only if the
  Table accepts the source-agnostic reading; the restrict-to-os alternative removes the primitive.
- Q2 (live follow stays told through failed rounds from a stale sample): safe — stale telling keeps marking a
  still-live, genuinely-nested tree (parentage is guid-stable); no lost event. Cost: the BC-5 seam at the eventual
  death. Dead follows are dropped live by _told regardless of stale os_nested.
- Q3 (two told roots; inner root's event 1 marked with outer pid): safe and consistent — in the outer's own follow the
  inner creation is unmarked and counted there (AZ-1); in the grandparent's follow it is marked so the grandparent
  does not count it. The specific pid value only affects reporting, not beat routing.
- Q4 (pid-only parent breaks the chain): safe direction (ancestor counts as main, no loss). Not stated as its own
  hole; arguably covered by "matched by ProcessGuid only." I would have the Table decide whether to say it.
- Q5 (per-pass copy of the map): true and unavoidable given AK-5 tree_copy; a memory/per-pass-copy cost, not a
  correctness issue. "One more map ... for the life of the follow" understates that tree_copy re-copies it every pass
  and it is never pruned, but that is true of by_guid/by_pid already. E1's "as on main" holds for bytes, not for
  memory.
- Q6 (E5 twin is the guid-less-agent path, not main's code): acceptable — E1's byte pins cover "as on main"; the
  guid-less path is a real code path and the >50-marked count guards against a vacuous comparison.
- Q7 (told again on a new follow after return/stop; not after raise): consistent with BC-2 as the ADR reads it; the
  new follow starts after the old top, so the in-between events are in both files. Safe.
