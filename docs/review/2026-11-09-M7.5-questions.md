## E3 - the missing knock: root cause (written before the fix)

Replay, before any change to the code (main 0dbb2cd), with the fake runner of
tests/test_watch.py and the discover fixtures: rounds 1-9 `kimi-gone` (the
`~/.kimi` footprint, no tree), round 10 `kimi/two-samples` (kimi a named
candidate), rounds 11-13 `kimi-gone`; T = 10 s, so round 3 is t+20 s, round 10
t+90 s, round 13 t+120 s: the field's order by round number, as Amendment M records it
(rounds 3, 10, 13; its only clock time is kimi's first seen, 18:10:30Z; the hours
given here before the REDO were not in the record and are struck, N-6). What the
notifier did, call by call:

| round | event | rate-limit id | title | status |
|---|---|---|---|---|
| 3 | AGENT-DARK-LIVE | `AGENT-DARK-LIVE C:\Users\user\.kimi` | `Raqib: AGENT-DARK-LIVE` | sent |
| 10 | NEW-AGENT | `NEW-AGENT pid 10728` | `Raqib: NEW-AGENT` | sent |
| 13 | AGENT-DARK-LIVE | `AGENT-DARK-LIVE C:\Users\user\.kimi` (120 s after the first: not limited) | `Raqib: AGENT-DARK-LIVE` | sent |

Counts: sent 3, folded 0, failed 0; `folded_waiting` empty. Each suspect, checked:

1. **Shared limit id: no.** host.py `_apply` gives every tree finding its own id
   `"<RULE> pid N"` (C-5) and every footprint `"<RULE> <path>"`; the field's ids were
   `NEW-AGENT pid 9176` and `AGENT-DARK-LIVE <~/.kimi>`. Nothing held NEW-AGENT behind
   the first AGENT-DARK-LIVE.
2. **FIRST-FINDING "by the rule": no.** A host-line finding (NEW-AGENT) never passes
   through `notify.FirstFinding` or `_source_knock`; only a SOURCE finding of a tree
   takes the per-tree FIRST-FINDING path, under its own id `FIRST-FINDING pid N`. The
   field's report lists three findings and no source finding on the kimi tree, so that
   path never ran.
3. **A fold token: no.** Nothing was folded (folded 0). There IS a latent bug next to
   this path, found while checking it: `HostWatch._folds` wrote the fold outcome of ANY
   token whose container has a `tree_key` into `tree["knocked"]` - the field the report
   prints as the NEW-AGENT status. A source finding of the same tree (which carries
   `tree_key`) folded under its own id would have overwritten the tree's NEW-AGENT status
   with "folded: sent as 1 more". It did not happen in the field (the report said
   `[sent]`), but it would make the report lie; fixed (only NEW-AGENT / NEW-AGENT-UNKNOWN
   entries write `knocked`; HOST-UNWATCHED, HOST-RHYTHM and the source entries write their
   own fields) with a test.
4. **Title collision: no.** The NEW-AGENT toast's title (`Raqib: NEW-AGENT`) differed
   from both AGENT-DARK-LIVE toasts, and the two AGENT-DARK-LIVE toasts, which DID share
   a title, both arrived. Two toasts with one title are therefore not what Windows drops.
5. **Delivery status: "sent".** `sent` means notify.run_program started
   `powershell.exe -File toast.ps1 TEXTFILE` and it exited 0 within 10 s; toast.ps1 runs
   with `$ErrorActionPreference = 'Stop'`, so a failing `Show()` would have been exit 1
   (`failed`, a hole). The report's `[sent]` therefore says `Show()` returned.

**Root cause, as far as this repository can see it:** none in Raqib's code. The knock
was made under its own id, not folded, not consumed, and handed to Windows, which
accepted it ("sent"). What became of it after that is unknown, and cannot be
established from the record we have (N-8: an explanation through PowerShell's
AppUserModelID was offered here without a source and is struck as a cause; it stays a
question, Q-10): the field report keeps no per-knock title, id or
time, so it cannot be held against the notification centre. That is the gap this task
closes on our side (Q-8): the final report now prints a KNOCKS ledger - every knock the
watch made, its round, event, title, rate-limit id, body and status (with a fold's
outcome written back) - so the next field run can be compared toast by toast. The
NEW-AGENT title is made distinct as asked (`Raqib: NEW-AGENT kimi`, Q-7), knowing from
point 4 that a shared title was not the cause.

## Design points (recorded; the Table rules)

- **Q-1 (E1) What makes a footprint "live".** `was_live` becomes true when, in a
  round of THIS watch, the inventory links the footprint to a CANDIDATE
  (`f["candidate"]`), as the HANDOFF says ("whose linked tree was a candidate").
  A link to an act-root only (a tree that acts with no talk seen) does not make it
  live, so an act-root agent that ends still knocks after three dark rounds
  (test `test_e1_a_link_to_an_act_root_only_does_not_make_the_footprint_live`; the
  YAML names it as a hole). A candidate of round 1 (history) counts: it was live in
  this watch. Alternative for the Table: count act-root links too.
- **Q-2 (E1) How long `was_live` lasts.** For the rest of the watch: once live, every
  later streak of three is a note, once per streak (the note is said at streak 3, as the
  rule would have fired; a re-link clears the streak, and a new streak notes again).
  The HANDOFF's "unless the tree was never seen in the watch" reads this way. The
  evasion it opens (an agent that ran once and then runs only between rounds, or a
  silent one replacing it at the same footprint) is a hole in the YAML.
- **Q-3 (E1) The line and the match.** Every HostFootprint line carries
  `input_meta.was_live` (true or false), and the match requires `eq: false`, not
  `ne: true`: a line without the field (a record of an older Raqib) does not fire,
  rather than firing on an unknown. That made every fixture holding a HostFootprint
  line change by that one field (12 files, `was_live` added; nothing else moved),
  regenerated with `python3 tests/fixtures/rules/generate.py` (make.py).
  The note is host.py's (`_dark_note`): text, round, path, live round and tree,
  the HostFootprint line's (run, seq) and the inventory's cites (A5); in the record
  (rounds.jsonl `dark_notes`, the round line), NOTES, the report's own section
  "DARK AFTER A LIVE TREE (notes, not alarms, not knocked)", the page's section and
  the window's "NOTES (not alarms)". It never enters `findings` or `result()`.
- **Q-4 (E2) One reading for every source.** `HostWatch._source_beats(key)` reads
  what the tree's os / hooks source feeds gained since the last round (a cursor on
  each Feed, reset with its epoch) once per round; `act_beats(...)` returns the host's
  new children (unchanged K-5 logic) plus os process lines (depth >= 1, the root is
  not its own act) and hooks Bash calls (phase pre); `talk_beats(...)` returns the
  host's K-5 talks plus os net lines. History lines of a feed are not beats. Host
  lines of a host source (HostChild, HostConnection) are not read again: they are
  the inventory's children and connections already.
- **Q-5 (E2) Where a source beat goes, and when it counts.** A source beat carries
  its own time (UtcTime, a Bash call's ts) and is put in the ring round whose
  interval (from, at] holds that time (`_bin`; older than the ring: its oldest
  round). `rhythm_of` pairs an act with a talk by the talk's own time where it has
  one (`talk_at`), else the round's time as before. Source lines are read by the
  tick's poll, which runs after the round in the same tick, so a source's beats of
  round k are counted at round k+1: HOST-RHYTHM fires one round after the cycle that
  completes it (the os fixtures fire at round 5 for cycles in rounds 2-4). In a live
  watch the tick runs every 0.5 s, so the lag is one round at most. Several cycles
  within one round count as one (the burst rule of M7.4), named as a hole.
  `act_basis` on the HostTree line names the bases of that round's acts (`os`,
  `hooks` join `started`, `stat`, `round`); no new field was added to
  `input_meta.rhythm`, so no host-only fixture changed for E2.
- **Q-6 (E2) The os destination.** The os source keeps no remote in clear (I-7: it
  hashes the destination), so an os talk's destination is `os:` + the first 12 hex
  of the line's `input_sha256`. An os talk and a host talk to the same server are two
  destinations (no join between a hash and a host:port without keeping the clear
  text); a hole in the YAML. The Table may want os_sysmon to keep ip:port (the field
  NET rules read) - out of this Scope.
- **Q-7 (E3) The title.** `Notifier.notify(..., subject=)` puts a word after the
  event in the title, cleaned like the rest (A-4 alphabet, 40 characters, title at
  most 120). Only NEW-AGENT and NEW-AGENT-UNKNOWN pass one (the image name):
  "Raqib: NEW-AGENT kimi". ADR-0005 A-4's "Raqib: <event>" gains that word; the
  Table may want it written there. A fold delivered by tick() keeps the subject of
  its first folded knock.
- **Q-8 (E3) The KNOCKS ledger.** Every notify of the host watch goes through
  `HostWatch._knock`: round, time, event, title, body, rate-limit id, the status at
  the call, and the status now (read back from the entry's notice, where a fold's
  outcome is written). The report prints it ("KNOCKS: N"), and the state carries
  it (`host.knocks`). The project watch (raqib/watch.py, out of Scope) keeps no such
  ledger; its FINDINGS lines already carry each notice.
- **Q-9 (E3) The latent `_folds` bug** (point 3 above): fixed with
  `TREE_FIELDS` (rule -> the tree field that holds its knock status); a source
  finding's fold (an entry with `fkey`) writes only its own entry. Test
  `test_e3_a_folded_source_knock_never_writes_the_trees_new_agent_status`.
- **Q-10 What the field still owes.** The next field run should compare the KNOCKS
  ledger with the Windows notification centre toast by toast; if a "sent" toast is
  missing there too, the cause is in Windows' handling of PowerShell's
  AppUserModelID (a registered AUMID for Raqib, or a scenario="reminder" toast that
  stays until dismissed, would be the next step - a change to toast.ps1 and A-4 that
  this task did not make without the Table).

- **Q-11 A flaky test found on the way (tests/, in Scope).** test_rhythm.py's
  `test_redo_k2_a_record_shape_the_builder_cannot_send_is_a_hole_once_per_tree`
  asserted `"900" not in` the prompts sent; the prompts carry hashes salted with the
  run id, which holds the process id, so the hex "900" turns up by chance: 3 of 40
  run ids failed it on main 0dbb2cd (measured by patching run_id; it failed twice in
  this session's local runs). The assertion now looks for the proxy lines' own seqs
  (`"seq": 900/901`) and their session and source words; 0 of 40 fail. What it
  guards (K-2: an unsendable shape is never sent) is unchanged.
