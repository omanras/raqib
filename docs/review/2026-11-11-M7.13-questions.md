## Q-B (E4): the HOLES header and the window
AF-4 says the HOLES count "says how many lines hold them". The window (raqib/app.py `text_tags`, out of scope)
marks the lines under "HOLES (A3): n" as holes only when the rest of that line is a number; words after the
count would leave every hole line of the window's report unmarked. So the header stays "HOLES (A3): N" (the
number of holes, as before) and, only when lines were folded, the first line under it says "(N hole(s) in L
line(s): ...)". The coordinator accepted this for this build; the Table may want the header itself, with the
window's parse changed in a task that has app.py in scope.

## Q-C (E1, AF-1): a tree sourced by the host's record while the channel was unread keeps that source
A source that runs is never replaced (`_attach` keeps it). So a tree attached while no round had read the channel
keeps the host's record after a later round reads it; trees first seen after that read get the os source. Its
source text says when it was attached ("no round up to round N read its channel"). Should such a tree be moved
to the os source at the first kept read (its os follow would then read the channel's past of it as history)?

## Q-D (E4, AF-4): the query's start is taken for a time
While no read is kept, each round's query starts at the watch's start as that round computes it (the live
reader's adjusted start, ADR-0007 T-3: the earlier of the start on the wall clock and the wall clock now minus the
monotonic time since). That value can move by a clock tick from round to round (in the tests round 1's is
07:49:29.998Z and the later rounds' 07:49:30.000Z). The fold takes it for a time, not for other words: the
folded line keeps the first hole's words and adds "the query's start ... moved from A to B" where it moved.
Without this a clock tick would split the field's 216 holes into several lines. Confirm, or rule that a moved
start is other words.

## Seen, not changed

bound is the watch's start, not a record). Not in AF-3 (the SYSMON line only); left as it is.

### REDO-2: what the os source attached again reads first
AG-1's os source starts as any new os follow does: its first pass reads the tree's records in the
channel, the ones from before the attach too. The host record's lines are not judged again (the
os feed starts at the end of the tree's file), and an act both sources saw is one act (tested:
the second curl, in round 2's sample and in the os lines). An act the host record did not see (one
that lived between two rounds while no read was kept) is read then for the first time and judged as
the os source's lines are. Whether such an act is to be judged as live or as history is not ruled.
