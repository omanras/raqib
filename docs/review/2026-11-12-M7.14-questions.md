1. Seeding a follow with a child older than the watch (AI-1, said). The round's
   sample gives a child's pid and its start time, never its ProcessGuid; the
   follow knows the tree's members by ProcessGuid (by pid only where an event
   carries none). Seeding by the sample's pid admits pid reuse (the pid the
   sample named can be another process by the time the channel gives an
   event under it). The ways seen: (a) seed by pid, the sample's start time
   checked against nothing the channel gives; (b) a bounded query for that
   pid's event 1 (an integer Raqib parsed, but older than the watch: the
   unbounded past again); (c) leave it unseen, as built and said. Not chosen:
   built as (c). The guide and THREAT_MODEL say a child that started before
   the watch is not known to the follow.

2. A follow attached again (resumed with after_record) starts with an empty
   tree: the children its earlier follow knew are not known to it (question 1,
   one level down). Should the TreeSource carry the follow's tree (the root
   found, ProcessGuid and pid to depth) across attaches? Not chosen.

3. A bounded pass's window holds seconds, not the channel: built so that a
   bounded pass does not write "the export holds no event 1 / 11" nor "root
   pid N is in no event 1, 3 or 11 of the export" (either would be a
   RAQIB-SILENCE line, a source-line hole, in nearly every round). A
   person's `raqib os-sysmon` and a follow given no bound still say them. The
   round's record keeps the kinds the channel gave. Should a follow say a
   kind none of its passes gave after some number of passes, and how many?

4. AI-2 is built as written: two passes and none that read, counted from the
   follow's attach. A follow that read once and then fails in every pass is a
   hole of each pass, not the host's record (said in THREAT_MODEL). Should
   "none that read" be "the last two passes did not read" (an episode, as
   AF-2's after-kept-reads knock)?

5. A source finding made from a host line of an os tree under AI-2 carries the
   source "host" (the host's record judged it, not the os follow); a hooks

6. The follow's first pass asks since the HostWatch's start (start_eff, T-3's

## REDO 2 (ADR-0007 Amendment AK): the present state

The REDO's STOP (one count red in tests/test_app_meet.py) was fixed by the Table
(9e1aaa1). REDO 2 changes how an os tree gets its host lines:

- AK-1: an os tree has two files under ~/.raqib/host/sources/: its os follow's
  `<run>-<pid>-<started>.jsonl` (the catalog; its history as before M7.14) and
  the host's own record's `<run>-<pid>-<started>-host.jsonl` (the host's rules;
  the host source's history: the round-1 rule of `_host_lines`, a restart by
  `Feed.poll`). `host_from` is gone. `_host_lines` writes to `src.host_path` for
  a host, hooks or os source alike (one code path); a host source that follows
  an os source goes on in that source's host file. `carry_host` is unchanged.
- AK-2: only `host_error` (that file's own write failure) stops the host lines;
  an os follow's error, end or pass does not.
- AK-3: done for the tree: a tree no sample holds (its entry never sampled, or
  brief in the round) has no host line. Not done: a child or talk of a sampled
  tree that only the round's channel gave (question 11).
- AK-4: `said_by(entry)`: the terminal line, the "grown" line and the knock's
  body name the entry's source (the listing's).
- AK-5: `on_pass` publishes `tree_copy(src.os_tree)` in the follow's thread;
  `_attach_os` hands the next follow `tree_copy(old.os_published)`, never the
  live dict; a follow that finished no pass publishes what it was handed.
- AK-6: an os source attached after a restart whose follow reads from it says
  "(it reads the channel from the restart's time T, not from the watch's start)".
- AK-7: `TAKEN_SAME`; `told_twice` reads each entry through its own file's feed
  and joins nothing across a restarted file (another epoch).
- The gate is run once before the commit; the commit is `landed:` only if green.

## Questions (REDO 2)

11. AK-3: a sampled tree's child or talk that only the round's channel gave.
    `trees_of` builds "children" from t["acts"] (how "process") and "remotes"
    from t["talks"]; discover's act and talk records do not say which source
    gave them: their "cites" are the first CITES_PER_CLAIM records of the
    process (`_cites(p["recs"])`), so a sample record can be cut off, and
    `HostWatch.sampled_now` holds the round's (pid, image) while an act's image
    can be the catalog label of another image of the process; a talk has no
    such set. Telling them apart needs a choice: (a) discover marks each act
    and talk with its source (raqib/discover.py, not in this scope); (b)
    host.py tests a child against sampled_now and a talk against the round's
    connection rows; (c) leave it said. The builder did (c): THREAT_MODEL says
    it ("Said, not fixed: a child or a talk of a sampled tree ...").
12. AK-1 with AG-1 (a tree host in round 1, os from round 2): its host record
    goes on in the os tree's host file (the os follow keeps the untagged file
    the host source wrote); `carry_host` keeps the children and remotes, but
    the HostChild seq starts again at 1 in the new file (`file_seq` is per
    file), so a FIRST-FINDING knock's "seq N" can differ from the watch without
    Sysmon there. Should the os follow take a tagged name instead (the host's
    record always the untagged file)? That renames every os tree's file and
    changes two pinned tests (tests/test_host_sources.py e1a,
    tests/test_host_third_field_run.py e1_ag1).
