## 3. Silent assumptions, and what A3/A5 should have caught

### A. A talk the tracing did not match is recorded as a measured 0/0 (BO-1, A3/A5)
At 595-597, every talk of the round's trees that is missing from the sums gets bytes 0/0 and sockets 0. `_bytes_of`
  treats 0/0 as read (3945), so K-5 records "unchanged" from then on. The fill is needed: without it, the first burst
  on an idle connection older than the watch would not count as a change. But when the match fails, the zero is
  recorded as if measured, with no hole. Ways the match can fail:
- **Remote spelling.**
    - Brackets: neither side uses them. Compression: both sides use `str(ipaddress.IPv6Address)` (hostwin.py:372-373,
    etwnet.py:352). Zone ids: hostwin drops the scope, discover strips `%`, ETW has none. So these all match.
    - **IPv4-mapped.** discover normalises the table's `::ffff:a.b.c.d` to IPv4 (discover.py:344-345), and an IPv4
    event (ids 10/11) sums as the same IPv4 text, so that case matches.
  - The questions file's field note says the opposite and is wrong.
    - The case that is not handled is the reverse: an IPv6 event (ids 26/27) carrying a mapped address. `sums` spells
    it as an IPv6 text (etwnet.py:670, no normalisation), and that never meets the talk's IPv4 text.
- **Pid.** The sums use the pid from the event data (etwnet.py:349, 577); the talks use the table's owner pid,
  dwOwningPid (hostwin.py:375).
  - For a process's own sockets they are the same, per BM's field run.
  - Not measured: inherited or duplicated sockets, and senders in kernel mode.
- **Unread events.** host.py never reads `unread`, `unread_why` or `other_ids`.
  - So an IPv6 version mismatch (BM-4) gives 0/0 with no hole and no note, despite BM-5's "unread stays an alarm".
  - This is the builder's Q2.
- **`sockets` means something else on Windows.** It counts every local end seen since the session started (closed ones
  included), and is 0 for a talk never seen. On Linux it is the sockets open now. The record line uses the same field
  name (1301).
- **The bytes mean something else on Windows.** They count since the session started; Linux's count the socket's whole
  life. The line does not say which (1301).
  - Round 1's "new" lines carry `{"sent":0,"received":0,"sockets":0}` for every connection.
  - BL-5's "said with them" is met only in `conn_bytes.from` of the latest inventory.

### B. A connection closed and reopened to the same remote
Talks are keyed by remote (2939-2954), and the sums run over all local ports and outlive the sockets. If the
  connection is reopened between rounds and has carried no payload yet, the sum is unchanged, so no talk is recorded.
  Linux would show the new socket's counts, which differ, and so give a "bytes" talk. This is a narrow missed talk. I
  found no false talk beyond the lag.

### C. The deaf-session check (BO-5, 584-590)
- **False alarms:**
    - **Lag.** FlushTimer is 1 s (etwnet.py:90). At round 2, events may still be 0 while the talks moved. The gate's
    own Windows watch runs `--every 1 --rounds 2` (gate.yml:191), which is the likely place. The exit code is
    unchanged, but the report falsely says the session hears nothing.
    - **The whole set is compared.** The check compares the union of every tree's "PID REMOTE" keys. A process that
    becomes, or stops being, a candidate while holding an idle connection reads as "moved in the table" when the table
    did not change.
- **Misses:**
    - `events` accumulates, so after one event the check is off for the whole run. A provider switched off from
    outside while the consumer lives freezes the sums; every kept connection then reads "unchanged", with no hole.
  - `events` counts every id of the provider (564-566), so a session that hears only connects or UDP still passes.

### D. Ways out of the watch (BO-2)
- **Lock order is safe.** finish takes `self.lock` and then `tracing_lock`; the worker takes only `tracing_lock`
  (2241).
- **Races at the stop:**
  - Stop before the start: nothing is ever started (2242-2243).
  - Start still running at the stop: the stop waits, then stops the reader.
  - A round in flight after the stop gets a "watch is ending" hole.
- **KeyboardInterrupt.**
  - It never reaches start(), which runs on the worker thread.
  - If it interrupts the consumer join inside finish, close() finds `self.tracing` already None (2282).
    - atexit still covers it: the hook stays registered (etwnet.py:652-656 is not reached) and stops the session by
    handle (438-440).
- **Ways a session can survive without a kill:**
  - A stop that says "may still run" is only a note; atexit retries at exit (Q3).
    - Interpreter exit while the worker is inside start(), between StartTraceW and atexit.register
    (etwnet.py:459…426). Reachable only if finish/close's wait on the lock is itself interrupted (repeated Ctrl-C at
    round 1).
- **Other problems on the way out:**
    - Notes from `tracing_stop` called in close() after a failed finish are added after the report was made
    (2289-2290), so they are lost.
    - A factory whose start() raises an Exception escapes `_tracing_round`, because 2244-2246 sit outside the try at
    2249. The round becomes reader-failed (exit 3), against "Raises nothing" (2239) and BO-3. This cannot happen with
    etwnet.Reader (etwnet.py:402-405).
  - finish holds `self.lock` through the consumer join, up to 10 s (etwnet.py:92, 647).
- **A second watch in one process:**
    - One after another is fine (BM-2), though the note calls the previous watch's session "a leftover of a killed
    reader".
    - Two at once (different homes) share the session name, and the second would stop the first's session. Reachable
    only in tests.
- **The app's watch is covered.** It goes through hostmod.start/loop/conclude/close (app.py:2168, 2201-2212), and its
  reader wraps live_reader on the same thread (app.py:1508, 2177-2184).

### E. LIVE_ROUND (202, 508-509, 2225, 2228)
- It is set to False before each read and to True at the end of a successful win32 live read, on the same thread. Each
  Worker is a new thread (609).
- A look sets it on its own thread, where nothing reads it. No leak found.
- **Why not a parameter.** Everything calls `reader()` with no arguments (the CLI, the app's wrapper, the stand-ins).
  A key in the inventory would change the latest inventory and exports byte for byte; the thread-local touches
  neither.
- **Cost.** A reader that runs live_reader on another thread gets `TRACING_NOT_LIVE`. That is said as a blind spot, so
  it is not silent.

### F. Linux, exports and looks (`--once`)
- Linux: unchanged except the order inside close(), where `tracing_stop` is a no-op.
- Look and export inventories: unchanged byte for byte.
- Only the win32 non-live blind-spot text changes.

## Q1-Q4 and the builder's choices (my lean only; the ruling is the Table's)
- **Q1.** Lean yes: each kind of cause should be said. Per-round reasons do not survive past the next round (2637), so
  the report pins later rounds on the first cause's words (A5).
- **Q2.** `unread` growth is the one way a 0/0 match failure shows at all; today it reaches neither a hole nor a note.
- **Q3.** BL-2 is FOR "leaves nothing running". Whatever the class (note or hole), it must not be lost on the close()
  path.
- **Q4.** The check compares the union of keys, so candidate churn counts as movement. That is wider than "the tree
  holds connections".
- **Start at the first round:** fits BO-2. The cost is the zeros in round 1 (A).
- **Default factory only from start():** every real caller goes through start(). The win32 branch is untested.
- **`by` holds only the trees' talks:** enough for `_bytes_of`. The 0/0 fill is point A.
- **Unknown loss is a hole:** fits BL-4/A3. Untested.

## Verdict
This is not an approval. **REDO, narrow:**
1. **E4 with mixed causes.** The blind spot names only the first cause (2924 with 2885-2889). This is pending Q1; if
  the Table rules that once is enough, this item falls away.
2. **The interrupt test** at test_host_bytes_win.py:189-204 depends on thread timing.
3. **The questions file's `::ffff:` field note** has the mismatch the wrong way round. The case to field-check is ids
  26/27 carrying mapped addresses (etwnet.py:670 against discover.py:344-345).

Worth adding in the same REDO but not blocking: tests for close() as the stopper, the win32 default wiring and "loss
  not known"; the threat-model placement; and the stale sentences at THREAT_MODEL.md:602-605 and 1208-1216.

If Q1 is ruled "first cause suffices", NEXT, given green CI and a clean field check. The field check should include
  IPv6 with mapped addresses, BO-5 at the gate's 1 s rounds, and the extra note on a non-administrator run.
