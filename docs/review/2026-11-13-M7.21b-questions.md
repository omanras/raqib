# M7.21b - questions for the Table (ADR-0007 Amendment BO)

The builder answers none of these locally; each says what was built so the Table can rule.

## What was chosen, and why

1. **Where the watch takes the counts.** `HostWatch._owned_read` (the reader's thread), after the round's
   reader returned: when the watch is on win32 and the round was read by `live_reader` on Windows, the
   inventory's `conn_bytes` is set from the tracing (`tracing_bytes`). `live_reader` says so on a
   thread-local (`host.LIVE_ROUND.win32`), not in the inventory: tests/test_rhythm.py (not in scope)
   holds that a Windows look carries no `conn_bytes`. A look outside a watch never starts a reader
   (BO-2). The app's watch is covered: its reader wraps `live_reader` and runs in `_owned_read`.
2. **When the reader starts.** At the watch's first live round, on the reader's thread: the leftovers
   first (`etwnet.leftovers`, the sessions listed before the pids are read, `host.tracing_live_pids`),
   then `start()`, once. Not at the watch's construction: only the first live round tells the watch it
   is live. Round 1's sums are therefore about zero; round 2 is the first to compare. Is that the
   ruling's "when a live watch starts"?
3. **The default factory is given by `host.start()`**, not by `HostWatch`: `tracing_reader`
   (`etwnet.Reader(os.getpid())`) where `sys.platform` is win32, else `OffTracing` (refused with
   `TRACING_OFF`, nothing of Windows loaded, no leftovers looked for). A `HostWatch` built directly
   without `tracing=` has none (`TRACING_NONE`). Reason: the gate runs pytest on windows-latest as an
   administrator; tests that build a `HostWatch` around the real `live_reader` must not start a real
   session there. A test that goes through `host.start()` with the real `live_reader` on a Windows
   runner and no `tracing=` would still start one: the Table may want a guard for that.
4. **The wording of the blind spot.** Exactly `WIN_BYTES_HOLE + "; " + reason + BLIND_TAIL` for a
   refused start (the reader's own reason), for a watch off Windows (`TRACING_OFF`), for a watch whose
   rounds are not the live reader's (`TRACING_NOT_LIVE`: every existing win32 test watch, which so far
   said `WIN_BYTES_HOLE` alone) and for one given no factory (`TRACING_NONE`). The test of
   tests/test_rhythm.py passes unchanged (`startswith`); no existing test asserted the whole text.
5. **A round of the tracing with a hole** (lost events, buffers or notices since the round before,
   `beyond` grew, the consumer ended, what the session lost not known, the counts not readable, or BO-5)
   has `conn_bytes` `{"from", "hole", "by": None}`; the watch says the blind spot `bytes` as
   `"bytes: " + hole` and forgets every last-read pair (K-5's `conn_state[*]["bytes"]` and K-6's
   `last_bytes`), so the round after compares with nothing; `_bytes_of` and the talk logic are unchanged.
   "What the session lost is not known" (a failed query) is taken as a hole too, beyond BO-4's list.
6. **`by` holds the round's trees' talks only** ("PID REMOTE" of each candidate's and act-root's talk),
   0/0 where the tracing saw none of it, `sockets` the tracing's local ends summed (0 then). Linux's
   holds every socket of the host.
7. **Notes, never failures:** the leftovers stopped (`TRACING_LEFTOVER`, by name), a leftovers problem,
   what the reader said (BM-2) and the stop's problems are notes of the run.

## Questions

- Q1. The blind spot `bytes` is said once a run with the first cause's text; a later cause of another
  kind (a loss, then the consumer ended) adds its rounds but not its words (they are in that round's
  `conn_bytes`). Should each kind of cause be said once?
- Q2. `unread` (BM-5: an event of the four ids not read) means bytes not counted. BO-4 does not name
  it: it is not a hole here. Should it be?
- Q3. A stop that says the session may still run is a note. Should it be a hole (exit 3)?
- Q4. BO-5 compares the trees' talks of two rounds of the reader's life; connections of processes
  that are not trees do not count. Is "the tree holds connections" meant so?

## What must be checked in the field (a Windows runner, an administrator)

- That a live `raqib watch --host` starts `raqib-net-<pid>` once and none is left after Ctrl-C, Stop
  or a crash; that a killed watch's session is stopped by the next and said as a note.
- That a kept connection's counts move between rounds and give talks of change "bytes" (HOST-RHYTHM
  sees a long connection's rhythm), IPv4 and IPv6 (ids 26, 27 are not measured yet).
- That REMOTE as the TCP table spells it meets the tracing's: a dual-stack socket the table lists
  over IPv6 as `::ffff:a.b.c.d` while the tracing says IPv4 would read as zero.
- That a quiet runner is not taken for a deaf session, and the gate's own Windows watch still exits 0.
- Without an administrator: the blind spot as before with the reason, the exit code unchanged.
