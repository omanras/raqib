## Findings

1. docs/specs/SERVICE.md:385-389 and docs/THREAT_MODEL.md:2188-2194 - "a tree a user may change is refused before it
  watches, not before it runs" claims more than N-2 allows. The check the runner asks is run by the code it judges
  (N-2; SERVICE.md:746-749): where a user has already changed the tree, the changed code gives the check's answer and
  may pass, and then it is watched. The documents say plainly that the check does not keep the tree from running
  (question 1, rightly), but they say without condition that it keeps the tree from being watched. GUIDE.md keeps N-2
  in the same paragraph (578-580), so it can stay. Smallest change: after "not before it runs", in both files add:
  "and, as for the command (N-2), it is a reading of the tree as its own code tells it: a tree a user already changed
  may make its own check pass, and is then watched".

2. raqib/winservice.py:823 - `except (Exception, KeyboardInterrupt)` lets any other BaseException out of the check
  (SystemExit, GeneratorExit, a direct BaseException subclass) leave `_own_code`. `run()`'s `except BaseException`
  (750) then catches it, so the system is told 23 ("the runner ended by ..."), not 15, and the text file gets no line
  of the check. It is never RUNNING and never watched, but E2 ("an exception out of the check ... 15") and
  THREAT_MODEL.md:2185 ("or ends by an exception") do not hold for it. The Stop's interrupt cannot be raised there
  (`watching` is False), so catching every exception loses nothing legitimate. Smallest change: `except BaseException
  as exc:` at 823, and `SystemExit(3)` added to the parameters of test_winservice.py:1156 (question 6).

3. tools/rig/check.py:1441-1453 - X52 is MET on any `refused-text` holding "NOT the system's alone" and a drive path,
  and any `taken-text` holding the pass words with counts. Lines that `raqib service check` itself prints (the X49/X50
  files) meet both, so the reader cannot tell the service's own text file from the command's output. That is to the
  HANDOFF's letter, but T-3's claim is "its text file names what was refused". Smallest change: also require the
  runner's head `raqib service run: its own code, checked at this start` in both values (a constant tied to winservice
  by a test, like REFUSED_SAID), with one MISSED case for each value.

4. docs/specs/SERVICE.md:349-350 - "One folder is made, the place; two names are read: the place's, and the state of
  the watch before" is no longer true: the same process now reads, through the check, every name of its own code.
  winservice.py:68-71 was corrected; the spec was not. Smallest change: the docstring's wording ("the runner itself
  reads two names ...; the check of its own code reads the names of the code this process runs, and writes nothing").
  In the same spirit, winservice.py:13-14 ("only then is RUNNING reported") still omits the check from the road's
  paragraph; one clause there.

5. docs/specs/SERVICE.md:285-287 and 377-378 - "the check asked by the system's own account in a service" and

## The builder's questions

1. The builder is right: the check at the start keeps a tree from being watched, not from running. By N-2 it does not
  even keep a tree from being watched where it was already changed (finding 1). The three documents say "not before it
  runs" plainly and do not claim prevention, but they need N-2's clause. T-1's FOR over-claims in the ADR. That is the
  wording of the reason, not a fault in the rule, so it is not a STOP; the Table narrows it.
2. Kept as built. Four parts is the least that leaves wincode untouched and imported only in the method, and the
  copied heads are tied by a test (packed road only: finding 8). A wincode function that makes the line belongs to a
  later task in which wincode may change.
3. From the code: `set_status` always sends check-point 0 (winservice.py:285). Both START_PENDINGs carry 0, the second
  with a hint of 60000, and nothing is reported during the walk. What the manager and the start command do with that
  is for a field measurement: a check slower than 5 s, and one slower than 30 s (AF-2's stated limit). Rule after it;
  any change belongs in `set_status`, a separate task.
4. From the code: `_status` accepts no control in any state but RUNNING (winservice.py:675), so both START_PENDINGs
  tell the system no Stop is accepted. A Stop that did reach the handler is acted on as tested. Whether the system
  delivers it or refuses it to its caller is for the field (SERVICE.md:557 already lists it as not measured). Kept; a
  change to AF-2's "no control accepted" is the Table's, after measurement.
5. Kept. "At every start" and A3 favour asking: a refusal hidden behind a Stop would be a lost finding. Not filed: the
  walk then runs under STOP_PENDING's 30-s hint (silent assumption 2).
6. Rule 15 for every BaseException out of the check (finding 2). Nothing legitimate is raised there, and 23 misnames a
  check that did not finish.
7. Kept. Strict and refusal-biased: only the exact pass shape passes, which matches "what was not read is never the
  system's".
8. Kept at 4000. "The whole refusal" outweighs "cut as the runner cuts" (80 would lose the words). The Table may also
  want the trace made printable (silent assumption 4).
9. Kept. 1066 is the natural reading of "the exit as the system gives it" and equals `winservice.SERVICE_SPECIFIC`.
  The Table's wiring must write WIN32_EXIT_CODE under that key.
10. Kept; the spec says both. In the ADR, AF-1 replaced the closing before AG-6 landed 0.9.0, which suggests no
  released version told 15. Not verified in CHANGELOG.md (the Table's).

## Silent assumptions

1. The check runs after HOME and USERPROFILE are set to the place and with stdout/stderr as the text file, unlike the
  administrator's `raqib service check`. I read no environment use in wincode.py (no `environ`, `getenv` or
  `expanduser`), so the answer should be the same; but this was neither said nor tested.
2. After a Stop that came before the check, the walk runs under STOP_PENDING's 30-s hint (STOP_WAIT_HINT). By the
  reckoning in winservice.py:109-111 a walk near WALK_MAX may need about 38 s. Not filed, not measured.
3. CHECK_WAIT_HINT (60 s) against AF-2's "the manager's limit is 30 s": the documents do not connect the two.
  SERVICE.md:563-564 keeps "the manager's limit of 30 s under a slow start" as not measured, without saying that the
  check now makes a slow start likely on a large plain tree.
4. The trace of an exception out of the check is written raw (not made printable, not cut), as `_own` and `_finish`
  already do. E2's "made printable" was read as applying to the line only.
5. A Stop that comes before or during a refused check is not said in the text file (only STOP_PENDING in the
  statuses). On a pass, AF-4's line says it. A Stop asked is an event (A3).
6. After this lands, the rig's X48 service, made from the job's own Python (T-3), refuses with 15 until the Table's
  wiring moves it to the copy under Program Files. X48 reads MISSED on the rig until then. The questions file does not
  say so.
7. test_winservice.py:1182-1205 calls the handler synchronously on the main thread. That stands for a real
  cross-thread Stop only because the check runs outside `self.lock`. If a later change takes the lock around the
  check, the test hangs (no timeout) rather than fails.
8. The plain/packed pick of the pass words is copied from `cli_check` (finding 8), and the heads are copied too (filed
  as question 2).
