# M13.1 REDO - questions and choices (ADR-0016 Amendment A, HA-1 to HA-10)

The builder's, 2026-11-20, on the REDO of HANDOFF (R1 to R11). Nothing here is answered locally.

## Q1 (design) - after a break, where the walk goes on

HA-7 asks that every break of a run be said. A break says that a line does not name the run's line before it;
the walk then goes on from that line (it is the run's line before the next). So one line added that names no line
gives two breaks (at it, and at the line after it, which names the line before it); two lines swapped give three.
Each is true by the definition, and the first is where the file was touched. Should the check look ahead (e.g.
skip a line that names nothing, and say "a line added" once)? Not done: it would guess what was done to the file.

## Q2 (design) - a line of OTHER that names no host and id

`--against`: a line of OTHER (the collector's) that is not whole JSON or names no `watch.host` and `id` is counted
and said ("N not read") and is not a problem (exit unchanged). HA-5 names "missing" and "differs" as the problems.
Should such a line be a problem of OTHER?

## Q3 (design) - a carriage return before the newline

`event.chains` and `event.against` take one carriage return before a line's newline as part of the line end
(`event.bare`): a copy of the file, or a collector's export, whose line ends were made Windows' is checked as the
file. The writer never writes one, and a JSON line cannot end with a bare one. Without it, every link of such a
copy would be broken and every line of such an export would differ. Is this the Table's reading of "byte for byte
(a line end aside)"?

## Choices the REDO did not make

- event.py: `CHAIN_SINCE = (0, 4, 0)`, `BOUND = 10`, `VERSION` (N.N.N, any first number: "1.0.0" is read and is
  at or above 0.4.0; "0.4.0rc1", "dev", "v0.4.0" are not read). The HANDOFF writes `0.N.N`; a later major number is
  read too, as a version later than CHAIN_SINCE.
- event.py: `chains` returns per run {host, run, lines (each line once), twice, late, problems, more, versions,
  state}; state is WHOLE, NOT_WHOLE, UNCHAINED or TAKEN; a problem is {what BROKEN, line, before, why: names |
  prev | none} or {what BESIDE, first, last, count, named, again}. Every dict is made fresh: nothing stale.
- event.py: a run's line is a JSON object naming a string `watch.host` and `watch.run`; it is a link where its
  `prev` is of the right shape (HA-1). A line of a chained run without `prev`, or with one not of its shape, is a
  break ("none" / "prev"). A run is chained where any of its lines holds the key `prev`.
- event.py: a run whose first line holds a hash is late (said "begins before this file", exit 1) and the walk goes
  on from it; a later line that names "first" in such a run is a break (the run's start is not here).
- event.py: "said twice" is told by the line's sha256 (equal digests: equal bytes); such a line is left out of the
  walk and out of `lines`. `raqib events` still names its id as said twice (a problem of the line, as before).
- event.py: `against(rows, held)` keys by (`watch.host`, `id`); a line of held is the same where its digest is one
  of the file's lines of that key; "behind" counts the file's keyed lines held does not hold.
- cli.py: the run's line is `  run <run> (host <host>): ...`; under a chain not whole each problem is a line of its
  own, indented by four; the RESULT line gains `; N run(s) whose chain is not whole` (a run taken out counts) and,
  with OTHER, `; N line(s) of the collector's not in the file` / `with other bytes`. The `--against` block is
  printed after the runs. A name read from a file is escaped (JSON's escapes, no control character).
- cli.py: a line whose reading raises RecursionError is "not an event: not JSON (nested deeper than can be read)".
- tools/rig/check.py: X38's patterns follow the new lines; a run said not whole, taken out, begun before the file,
  broken or with lines beside the chain (any run) is MISSED; "N said twice" beside a whole chain is MET.
- .github/workflows/rig.yml: the Windows step prints its error stream and copies it into rig-out (the Linux step
  already sends it into the kept answer, 2>&1).
- docs/specs/EVENT.md: the made-up run (two lines the writer wrote, version 0.4.0, run `made-up-run` of
  `host.example`) is under `### a chained run, made up`, at the end of the section for a reader of the file, in a
  `jsonl` fence; the "changed, added" limit of the last line is said in each bullet that says it.
