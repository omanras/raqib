# Review packet: M14.1b (a661e0d, "landed: M14.1b the reader in a process of its own"), 2026-11-20

This was a read-only review. I wrote no file. The packet is meant for `docs/review/2026-11-20-M14.1b.md`. All of it
  comes from reading the code. I ran nothing: no gate, no test, no helper.

## VERDICT: REDO
The helper, the client, the section and X35 cover nearly all of E1 to E7, and every file is in Scope. But there are
  three problems:
- The client can hang the whole watch and its Stop, so E2's "never blocks past its timeout" and BU-3's result rule are
  broken.
- Two of the report's statements can be false: "lost: none" after a restart, and the healthy Linux words under a
  backlog or the reader's bound.
- X35's count test cannot fail on the rig.

The fixes are small, but #1 sets when an ask is written, which the Table may want to rule first. I recommend this
  verdict to the Judge; it is not an approval.

## SCOPE
No scope violation found. Every path in the diff is listed under `Scope:`:
- docs: GUIDE, THREAT_MODEL, PROC-EVENTS, SERVICE, the questions file
- code: raqib/host.py, raqib/procevents.py, tools/rig/check.py
- tests: the two new test files, X35 in tests/test_rig_check.py, and the two guard tests named in the questions file

## MUST FIX BEFORE MERGE
1. **The ask write can block forever** (raqib/procevents.py:1013-1017). Send a new `read N` only when the previous ask
  was answered (a stale answer clears it). Otherwise wait for that answer within the timeout and return LATE without
  writing, so the pipe never holds more than one ask. Add one test with a fake whose input never drains. (L1)
2. **A restart erases the loss** (raqib/host.py:678-681 and 3131). Keep a loss heard from an earlier helper of the
  same watch; do not replace it with the new Reader's zero. Add a test: helper 1 loses events, ends; helper 2 answers
  clean. The section must not say "lost: none" and X35 must not be MET. (L2)
3. **The healthy words can be false** (raqib/host.py:3147-3161 and 397). Make "the last answer had `more`" a reason in
  `procevents_unhealthy`. Then either carry and say the reader's `beyond`, or drop "each process that began is
  counted" from BETWEEN_HEARD until it is carried. (L3)
4. **A false sentence in SERVICE.md** (docs/specs/SERVICE.md:224). "the rig's service run says whether the unit's
  watch heard" is false: nothing does this. Say it is not yet checked, and add that BU-5 sentence as a question in the
  questions file. (L8)
5. **Docs that claim more than the code does.** docs/specs/PROC-EVENTS.md:237 ("reads nothing but its input") and
  :248-249 ("never waits past its timeout"), docs/THREAT_MODEL.md:525-526 ("opens no file"), and the Helper docstring
  at raqib/procevents.py:919. Say what the helper does: its Reader reads the kernel's socket and each exec's
  /proc/PID/exe and /proc/PID/stat. Keep "never waits past its timeout" only once #1 makes it true. (L10)

## FINDINGS
**L1 (high, hang).**
- What is wrong: every ask writes `read N` (procevents.py:1016-1017), even when earlier asks are still unanswered. The
  write is blocking. A late round never stops or restarts the helper (host.py:657-658).
- A helper that stops reading its input but stays alive is late every round, and that is said once. A same-user agent
  can cause this by stopping the process; anything that stalls serve()'s loop does too.
- After about 64 KiB of asks (roughly 6,000+ rounds; far fewer where the user's pipe quota is exceeded), `flush()`
  blocks inside `ProcEvents.round` while it holds `ProcEvents.lock` (host.py:644-649).
- From then on:
    - the round never returns, so a `reader-late` hole of the result is written (host.py:2399-2406) and no other round
    starts;
    - the watch's Stop blocks forever in `ProcEvents.close()` waiting for that lock (host.py:689, reached from
    host.py:4787). There is no final report.
- How I know: reading the code; not run.

**L2 (medium, false statement).**
- Each answer replaces `self.lost` with the current Reader's count (host.py:678-681), and a restarted helper's Reader
  starts at zero.
- `_procevents_note` then keeps the new dict, because a dict of zeros is truthy (host.py:3131). The section prints
  "lost: none" (host.py:3170-3172).
- X35 then reads MET (check.py:887). The holes in the section do not make it MISSED.

**L3 (medium, false statement plus silence).**
- One answer per round carries at most 2000 entries (serve, procevents.py:866-874). More than 2000 new processes per
  round (about 200 per second at T=10, which an ordinary build reaches) builds a backlog in the Reader's `_pending`.
- At 32768 the Reader counts `beyond` and keeps nothing more (procevents.py:547-560). `ProcEvents.round` never reads
  `counts["beyond"]`.
- `procevents_unhealthy` ignores both `more` and `beyond` (host.py:3147-3161). So BETWEEN_HEARD, "each process that
  began is counted" (host.py:397), can be printed when that is false. `beyond` reaches no output at all (A3).

**L4 (medium, silence).**
- A late answer that arrives at a later ask is thrown away whole (procevents.py:1029-1031). The helper and the Reader
  already count its processes as given, so they are never counted.
- `Helper.stale` reaches no output.
- Likewise, the numbers of an answer whose reader ended are dropped: the hole is set at host.py:683-684, and only
  hole-free rounds are summed (host.py:3127-3130).
- "processes that began" therefore undercounts, with only a "late" or "ended" hole beside it.

**L5 (medium, silence in the threat model; for the Table).**
- In a non-isolated (user) watch, the helper starts Python with `-m`, its directory set to the package's parent
  (procevents.py:950), and the environment inherited.
- That puts the package's parent first on its import path, ahead of the standard library, and reads the user's site
  folder. All of this is read from disk again at each start, and a same-user process can cause the restart by ending
  the helper.
- The helper is in the watch's record, and BH-3 takes whatever it starts for the watch's own tree
  (discover.py:2030-2031). BU-1 says it starts nothing, yet a child under it would be absorbed silently.
- THREAT_MODEL.md:524 says "the watch's own interpreter and isolation"; the import path differs.
- For the service I found no difference: the unit runs `-I` (SERVICE.md:55, 94), the helper copies `-I`
  (procevents.py:901-902), the directory is a site folder the install walked, and `-I` keeps it off the path.

**L6 (medium, false statement and a changed watch).**
- When the interpreter file is replaced on disk (a package upgrade), /proc shows the helper's image as "...
  (deleted)".
- `own._base` then fails BI-2's comparison (own.py:105). The record forgets the helper at the next whole sample
  (own.py:109-110).
- From then on, every round says the watch "did not start" it, as a hole (discover.py:1970-1973).
- This is the first long-lived recorded helper on Linux, and nothing tests it.

**L7 (medium, a changed result).**
- `--every` may be as low as 0.1 s (cli.py:1406), and the reader's deadline is 2×T (host.py:287, 1823). A late ask
  adds up to 2 s to a round.
- With T below about 1 s, a late helper makes the round's reader late, which is a hole of the result. Examples: a
  container where the kernel never answers, so the ready line comes after about 2 s; or a stopped helper.
- E3 fixes the 2 s, so this is a question for the Table.

**L8 (medium, false statement).** SERVICE.md:224, see Must fix #4.
- X35 reads the user watch's report (rig.yml:110, 132). tools/rig/service_run.py is unchanged.
- BU-5's last sentence is unmet, and the questions file does not say so (A3/A5).

**L9 (medium; X35 can read MET where it should not).**
- (a) `began` counts every process on the machine. That includes the watch's own `ss -tinp`, which runs every round
  after the sample and before the ask (host.py:552; discover.py:1332), and `ss` is not in own.RECORD. Sixteen rig
  rounds already exceed the stand-in's two children, so the `began` test cannot fail.
- (b) No hole except a refusal makes X35 MISSED (choice 15). A run where the helper ended for good at round 2, or was
  late in 15 of 16 rounds, can still be MET.
- (c) The lost-reset in L2.
- (d) A workload with no `start` lines passes the count.
- check.py:876 says "where the kernel is known to answer", which the check does not know.

**L10 (low, false statement).** See Must fix #5.

**L11 (low; a hang or memory growth with a misbehaving helper).**
- (a) After the deadline, `_next` keeps taking queued lines with `get_nowait` (procevents.py:970-972). A stream of
  stale-numbered lines therefore keeps `ask` looping past its timeout.
- (b) `readline` has no length bound and the queue no size bound (procevents.py:908, 937). The size of one answer is
  set by program paths that processes chose: 2000 records, each with its program plus up to 16 earlier programs.
  Parsing it happens after the deadline.
- (c) A RecursionError from `json.loads` is not caught (procevents.py:983-985), so it escapes `round()` and the round
  fails as `reader-failed`.

**L12 (low, a changed result).**
- `round()` raises on a record whose pid or began cannot be used as a key, or on `counts["missed"]` that is not a dict
  (host.py:667-668, 675). That gives a `reader-failed` hole of the result.
- A helper of another raqib version, started again after an upgrade, is the plausible source; the protocol carries no
  version.
- A ready line with extra keys gives `not a line` once, then `late` forever, and the cause is never said
  (procevents.py:1006-1008).

**L13 (low, against E1).** `read` followed by a Unicode digit for which `isdigit()` is true but `int()` fails (for
  example a superscript two) makes serve raise and the helper die (procevents.py:863, 870). Only the watch writes the
  helper's input, so this cannot happen today.

**L14 (low, labels that are inexact).**
- "began and ended between two samples" (host.py:3176-3177) really counts what began and ended between two asks. With
  `--window S` the gap is S seconds.
- "rounds asked" counts rounds in which nothing was asked after a final hole (host.py:3125).
- "programs not read" counts reads, not programs (choice 8).

**L15 (low, unbounded output).** There is one report line and one terminal BLIND SPOT line per episode, with no cap
  (host.py:3137-3140, 3182). A helper that is late in every other round grows the report for the whole watch.

**L16 (low, test gaps).**
- Untested behaviour:
    - Nothing tests `helper_started`, the record or the realpath image (host.py:573-582). Removing
    `started=helper_started` (host.py:588) fails no test.
  - No test proves the real helper is the watch's own in a /proc sample.
  - L1 to L4 have no tests.
- The BU-4 test (tests/test_host_procevents.py:328) goes through a stand-in that returns dicts, never through
  `Helper._parse`.
- Guard tests the builder changed:
    - tests/test_procevents.py:860-861 now allows `subprocess` anywhere in the module. The change is only the list
    this task changes, but nothing now guards E1's "the helper starts no program" for serve() and the Reader.
  - tests/test_procevents.py:898: its name is now false, as the builder said.
  - tests/test_readme_top.py: the change is only the six guide sentences.
- Tests that only echo a fake: `procevents.ASK_SECONDS == 2.0` (test_host_procevents.py:117) and `Helper().argv ==

## ANSWERS TO Q1-Q4
- **Q1:** Yes for M14.1b; it keeps BU-3. Rule now that it ends at M14.1c. Once discover judges from these processes, a
  refused, late or ended helper is a gap in what is judged and must be a hole of the result. An end the watch did not
  cause should be said as such.
- **Q2:** Yes. Make a loss a blind spot of its own kind, said once. Do the same for `more` at the end and for `beyond`
  (L3). L2 shows that today a loss can be erased.
- **Q3:** Keep (pid, the reader's fork time) for the count: `began` exists only from a heard fork. `started_ticks` is
  often missing for exactly the short processes being counted. BU-6's pid plus start ticks stands for M14.1c's join,
  which must say what it does where the ticks were not read.
- **Q4:** This is not evidence in the tree (A8) and is one run (A7). It is also hard to square with the code: each
  Linux round runs `ss` before its ask (host.py:552), so "10 began" fits only a sandbox without `ss`. Record the run
  or drop the numbers.

## FOR M14.1c
- The watch's own short children are heard but are not in own.RECORD (discover.py:1332): `ss` every round, and the
  notifier. Tell them apart from a tree's children.
- Decide whether a child under the helper is a finding (L5, BH-3).
- Measure throughput under a fork storm. One answer of at most 2000 per round falls behind and then hits `beyond`.
  Decide whether to ask until `more` is false (bounded) and how `beyond` is said.
- Join by the reader's own times against the sample's time, not ask to ask, especially with `--window`.
- Say the gap of a restart: a new Reader hears no fork from before its start.
- BT-5: after a loss, words about threads and ends are hints.
- Measure how often `started_ticks` is missing for short processes (the BU-6 join).
- The helper holes become holes of the result (Q1).
- Settle the 2 s ask against T (L7) and the "(deleted)" image (L6).
- Bound an answer's bytes before any program name is read through the name gate (L11b).
