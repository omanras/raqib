## Findings

**1. BLOCKER (the ruling). `pyvenv.cfg` beside the interpreter's folder is judged only by a folder above that K-3 lets
  others add a file to.**
- **Files:** wincode.py:79 (ABOVE_ALLOWED holds 0x2), 233-243, 368-376, 421-431; ADR M-2 (665-669) and K-3 (544-552).
- **Input.** A System as the tests make one:

    Files\Drop\Py`;
  - the copy's path shape under it, and every name under `...\Py` reading as python.txt's copy rows;

    - `C:\Program Files\Drop` reading `(0x10, "O:BAD:(A;;FA;;;SY)(A;;FA;;;BA)(A;;0x1200ab;;;BU)")`, which gives users
    read and execute plus add a file (0x2), in an entry that applies to the folder itself only.
- **Trace.**
  - `_plain` 528-538: the four roots are all `...\Py`.
  - `road` 421: chain = [C:\, C:\Program Files, C:\Program Files\Drop, ...\Py].
    - At k=2, `folder_above` -> `_judge(ROLE_ABOVE)`: it is a folder (220); owner BA (225); SY and BA are skipped

- **Why it matters.**
    - CPython's site.py `venv()` is called by `site.main()` whatever -I says. It looks for `pyvenv.cfg`
    (`os.path.isfile`) in `dirname(abspath(sys.executable))` and in the folder above it.
    - Where it finds one, it sets `sys.prefix` to that folder above and adds it and its `Lib\site-packages` as site
    folders. Their *.pth files are read and their import lines run.
  - PEP 405 says the same of the interpreter's own start (the executable's folder or one folder above).
  - So the one file that changes what the service runs may be added by a name the walk took the folder above for.
- **What the ADR says.**
  - K-3's reason, "adding a thing beside does not replace what is there", does not hold for this folder.
    - M-3's own reason, "Whoever may add the missing thing decides what runs", applies but is ruled for entries of the
    path only.
  - The code follows M. The fault is in the ruling.
- **Measured lines.** None is misjudged. Every measured interpreter's folder has `C:\Program Files` above it, which
  gives users read and execute only. `C:\` gives "add a folder", not "add a file", and pyvenv.cfg must be a file.
- **How sure.** Certain from site.py as I know it; I could not read it in this tree. Settle by reading `def venv` in
  the copy's `Lib\site.py`; that is a reading only.
