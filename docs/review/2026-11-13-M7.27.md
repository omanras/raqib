FINDINGS (file:line — what I read — why it matters — confidence)

1. raqib/discover.py:1273-1274 (Linux forget is more aggressive than Windows; A5 silent assumption). `snapshot_proc`
  computes `since = record.clock()` (1209) and then always calls `record.alive({...}, since)` — there is no equivalent
  of hostwin.process_text's `whole = error is None and len(procs) < PROCESSES_MAX` / `since if whole else None`
  (hostwin.py:534-536). But `snapshot_proc` can legitimately omit live processes: `unreadable`/`gone_while_read`
  counters (discover.py:1215-1223, 1242-1244) drop any pid whose status or PPid could not be read, and those pids
  never enter `procs`. own.alive()'s own contract (own.py:64-67) says to pass `since=None` "where the sample may not
  list every process." A helper that is alive but momentarily unreadable in one snapshot (transient OSError/ValueError
  on /proc/PID/status, not FileNotFound) is absent from `procs`, so alive() hits the `elif since is not None and at <
  since: del` branch (own.py:74-75) and forgets it. On the next snapshot the helper is judged as any other process — a
  false finding on the watch's own helper (the Linux notifier is the recorded helper that could hit this). Why it
  matters: this is exactly the "false finding on the watch itself" the task warns against, and it is asymmetric with
  the deliberately-guarded Windows path. Confidence: high that the asymmetry/contract-violation exists; medium that it
  bites in practice (needs an alive-but-unreadable own-child, rare for a same-user process; a genuinely gone process
  is correctly forgotten).

2. raqib/discover.py:2975, 2984, 3005 (BH-4 in `_act_roots` likely untested). The three `ancestors(procs,
  q|pid|r["pid"], self_tree)` additions are the act-roots half of BH-4 ("no member of the watch's tree is anyone's
  ancestor"). I could not find a test that exercises them non-vacuously. test_e7_the_act_roots_*
  (test_own_tree.py:1304-1312) both build with `self_=None`, so self_tree is empty and these walks behave identically
  with or without the argument — they only test broken-link handling, which predates BH. test_e5_the_bridge
  (test_own_tree.py:1199-1216) is the only act-roots+reader scenario, but its talker 2400 is a candidate, so
  `inv["act_roots"]` is empty and the assertion `not any(set(a["via"]) & members for t in inv["act_roots"] ...)` (line
  1213) is vacuously true. So reverting the three `self_tree` args in `_act_roots` would, as far as I can see, fail no
  test. (The candidate-side BH-4 exclusion IS covered non-vacuously by test_e3a's `assert not {732,7400,7410} &
  acted(inv)` at line 1119 — only the act-roots side is the gap.) Why it matters: concern 6 asked to name any guard
  that cannot fail; this one cannot. Confidence: medium — I reasoned the scenarios through without running; the
  builder's "each break failed a test" may have broken ancestors() globally (caught by the candidate path) rather than
  the act-roots lines specifically.

3. raqib/discover.py:2011-2019 (narrow SILENT blindness: reused pid inside the +2s window). A recorded helper pid h is
  proven and its whole subtree pulled into the tree via `out["started"] |= _descendants(procs, h, proven=True)`
  (2017-2018). The only guard against h being a different process is own.alive()'s window STARTED_BEFORE=60 /
  STARTED_AFTER=2 (own.py:24-25, 71-72) plus "start not before the reader's" (2013). If the real helper dies and an
  agent reuses pid h and starts within (T, T+2] of the record time T, alive() accepts it, discover proves it, and the
  agent + its children become the watch's own tree with NO hole (they are not strangers, not unproven, not taken).
  This is silent. The 60s-before side cannot be abused (a reused process starts after the helper dies, i.e. after ~T,
  never 60s before), so only the 2s-after side is the hole. Why it matters: it is a real "watch blind" path, silent.
  Confidence: medium — the logic permits it; real exploitation needs exact pid reuse within ~2s. The threat model (E8)
  documents "a program started by a helper is taken by dates" but not this reused-pid-within-2s variant specifically.

4. raqib/discover.py:2017-2018 (documented residual blindness, not silent in fixtures but silent in effect). Because a
  proven helper's entire proven subtree is absorbed (`_descendants(h, proven=True)`, no hole), a process that names a
  proven helper as its parent and starts after it is left out silently. This is the known residual and IS disclosed in
  docs/THREAT_MODEL.md (the added "a program started by a helper is taken for the watch's by its dates ... is left out
  with it"). I flag it only to confirm it is the remaining hiding vector and that there is no test asserting the shape
  (by design it is accepted, not caught). Confidence: high it exists and is disclosed.

5. raqib/discover.py:2193-2194 (`_instances` helper re-key under pid-reuse is untested). The new branch re-keys
  snapshot `helpers` by CreationDate instance (`[key(h, sample) for h in r["helpers"]]`). I reasoned it is consistent
  with how the matching proc rows are keyed (a Windows helper in the `helpers` list is always present as a proc row in
  its own sample, so `seen[(sample,h)]` exists when the pid is reused), so I did not find a drop-a-real-tree bug. But
  no test in test_own_tree.py exercises a reused helper pid within a window (no `reused`/REUSE case). Why it matters:
  a wrong key here is exactly concern 1d (a dropped real tree / a mis-attributed helper). Confidence: medium that it
  is correct, high that it is untested.

6. own.py:46-51 (bound eviction is by record-age, not liveness). When the record exceeds KEPT_MAX=256, `add()` deletes
  `next(iter(self._kept))` — the oldest-recorded pid, even if still alive. A long-lived recorded helper evicted by 256
  newer short-lived starts would then be judged as any other process. In practice the recorded helpers (wevtutil per
  channel read, the notifier) are short-lived and are forgotten by the sample-ended rule first, so 256 is a backstop;
  I found no long-lived recorded helper that would be wrongly evicted. The threat model says "past 256 the oldest is
  forgotten" but not "even if alive." Confidence: low practical impact; noting for completeness.

7. own.py itself (concern 3) — clean on the points asked. Every read/write is under `self._lock` (add 47, kept 55,
  alive 69). started() calls add() without holding the lock, so no re-entrant deadlock. alive() iterates
  `list(self._kept.items())` and deletes from the live dict — safe. Imports are `threading`, `time`, `__future__` only
  (own.py:18-21); test_e1 (test_own_tree.py:999-1004) asserts stdlib-only and excludes
  socket/ssl/http/urllib/asyncio/ctypes/subprocess/raqib, so rule 5 (no network from capture path) holds and own is
  not a network bridge. The thread-safety test (test_own_tree.py:1028-1035) is a real smoke test (8 threads x 200
  adds, asserts the bound holds) but does not assert WHICH entries survive. Confidence: high.

8. E2 forward-incompatibility (disclosed in Q2). discover.py:2001-2002 (WIN_SNAPSHOT regex) now has an optional
  trailing `(?P<record> helpers=...)?`; a NEWER parser reads an OLD line (backward-compat, required by E2 — satisfied,
  test_e2 line 1060-1067). But an OLDER Raqib's regex ends at `sample=N` and will NOT match a new line, losing the
  whole snapshot line and thus the reader's self/launchers for that sample — i.e. an older build could then judge the
  reader itself as an agent. Not required by E2, disclosed in Q2, cross-build mixing unsupported. Confidence: high it
  is as described.

  stranger and BH-4 gives it no ancestor. ss does not make outbound connections, so it is never a
  talker/candidate/act-root. Cost: one possible stranger line in the inventory under overlap. The proposed change

  it out.

- Q4 (mixed record/no-record round built as a record round): safe; a helper that appears only in a no-helpers sample
  is then judged as any other and named — errs toward judging, not hiding. Cost: a legitimate helper can be named a
  stranger in a mixed round. Disclosed.
- Q5 (60s/2s window + forget rule): the -60s side is safe (a reused pid starts after the helper dies, never 60s
