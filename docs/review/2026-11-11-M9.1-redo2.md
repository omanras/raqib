## Findings
**G1 should-fix (Q-11): the record's count misses everything written after the record is kept.**
- Case: `raqib watch ~/p` over ssh. The ssh drops and SIGHUP stops the watch.
  - The "stopped (SIGHUP)" write fails, so the count is 1.
  - The state's last write (at unregister, watch.py:863) and the row (watch.py:822) keep "1 write to the terminal was lost since T".
  - Then the final report's write fails (watch.py:1355; host.py:4251), and so may conclude's hole line (watch.py:1500-1501). By the end, 2 or more writes were lost, and nothing records that the report itself was lost.
- README.md:24 says the note carries "how many". The note is true when it is written, but it is a lower bound.
- The order follows from C-1, so this is the Table's to rule.

**G2 note (Q-13): "N writes" counts failed calls.**
- Each failed write() or flush() on either stream counts 1 (watch.py:1269, 1292-1303).
- So one `_say` line is 2 (watch.py:306-307), one `print` is 2 (install.py:380), and the unit test calls a write, a flush and a write "3 writes" (:1312-1313).
- On a block-buffered pipe that was closed, writes go to the buffer and only flushes fail. N can then be far below the lines lost, and "since <time>" is the first failed flush, not the moment the reader left.

**G3 note (README wording):** "Such a watch prints nothing." now directly follows the new Ctrl-S sentence (README.md:24; cli.py:129-131). A terminal that stops reading and later drains does print its report. It also delays the record, because "stopped" is now written before conclude.

**G4 note (C-2 coverage; the builder's account):**
- Indented lines, the install block, non-prefixed lines and the host report's content are not compared.
- The PROJ first lines are matched as a subsequence. So a new "raqib watch: ..." line inserted between them would pass.
- The stated reason, "a platform's hooks check may add a line between", does not hold in the code: the hooks check speaks through `_say` ("[HH:MM:SSZ] ...", watch.py:306, 369), not with the prefix.

**G5 note (Windows robustness):** the stop-line matcher accepts only the plural "stop it with" (:1000-1001).
- On Windows that needs both SIGINT and SIGBREAK not ignored in the job. Otherwise the line says "stops it" (cli.py:362-364).
- They are not ignored by default, so the test should pass. The other first-lines test accepts both forms (:1211-1212).

**G6 note (C-3 FOR test):**
- In the PROJ case nothing is written while the terminal is dead before the stop, so n = 1 and only the stop line is lost.
- The case "gone and still gone" is not asserted for the note anywhere. test_b1 (a) does not read the note.
- "The code does not change" is checked only as code == the watch's own final_exit (:1358), plus the no-hole check (:1357).

- The page does not show it: ui.py reads only host.notes (1240). Other watches' lists do show the row's note (ui.py:923).
