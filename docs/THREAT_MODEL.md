# Mizan threat model: how the gate is fooled

Mizan admits a rule on evidence. Evidence can be thin, staged or hostile.
This document lists the ways a rule author (careless or not) or an attacker
(who controls the logs, or a pull request) gets a bad rule through the gate
or a good rule rejected, what Mizan does about each today (v0.1), and what
is open. "Status today" is the verdict Mizan gives; "open" is what it does
not yet do. Nothing here is theoretical: every item is either tested in
`tests/` or named in a `docs/review/*-questions.md` file.

The constitution's articles are cited as A1..A9 (`docs/CONSTITUTION.md`).

## 1. Happy-path-only fixtures

**The trick.** The positive sidecar holds the one event the author had in
mind; the negative sidecar holds an event that has nothing to do with the
rule (`{"Image": "notepad.exe"}` for a PowerShell rule). Both pass, and the
rule has been "tested" against nothing.

**Status today.** `pass`. A2 requires at least one positive and one
negative line and Mizan enforces exactly that (`fail` when a sidecar is
missing or empty, the file named). The example set is held to a stricter
bar by `tests/test_examples.py`: at least two lines per sidecar and at
least one *near miss* (a negative line that equals a positive line except
in one field), but that bar is a test of the examples, not a rule of the
engine.

**What limits the damage.** The corpus. A rule whose negatives prove
nothing is still measured on 1,000 benign events per logsource and goes
`over_budget` if it is wide. The report cites every line a `pass` rests on
(A5), so a reviewer sees in one glance that the negative fixture is
unrelated.

**Open.** A near-miss requirement in `fixtures.judge` (for each positive
line, a negative line sharing its keys); a minimum number of lines per
sidecar by `level`; a check that negative lines carry the fields the rule
tests (a negative event without `CommandLine` cannot exercise a
`CommandLine` condition); mutation testing (flip one value of each positive
line and expect no match).

## 2. Too-clean corpora

**The trick.** The benign corpus is small, uniform, or generated by the
same person who writes the rules, so no rule ever has a false positive and
every budget looks generous. The three corpora shipped with Mizan are
exactly that: synthetic, 1,000 events each, produced by
`tools/make_corpus.py` with planted benign matches so that the budget
mechanism is at least exercised.

**Status today.** `pass`. Mizan measures what it is given. The corpus
header names the generator and seed; `tests/test_examples.py` proves the
committed files equal the generator output, so a quietly edited corpus
(a benign match deleted by hand) turns the gate red. `x-mizan.corpus`
lets a rule choose its own corpus files; the report prints
`selected_by: x-mizan.corpus` so the choice is visible.

**Open.** A minimum corpus size per logsource; corpus provenance in the
header (source, date range, sanitisation) and a rule that a corpus smaller
than N events cannot clear a budget below M; diversity metrics (distinct
values per field) printed by `corpus`; a policy that a rule naming its
own corpus needs a reviewer; real, sanitised logs beside the synthetic
ones.

## 3. Match-everything wildcards

**The trick.** `CommandLine|contains: '*'`, `Image: '*'`, an empty
`contains`, or a regular expression like `.*`, so that the rule matches
every event that has the field.

**Status today.** Caught in two places, both conditional on evidence.
The negative sidecar: any negative line carrying the field matches, so the
rule is `fail` (`<file>:<line> matched (must not match)`). The corpus:
every benign event with the field matches, `fp/10k` becomes 10,000 and the
rule is `over_budget` (every match cited). The trick works only when the
negative lines lack the field *and* no corpus carries it -- which is
`no_corpus`, red.

**Open.** A static lint before evaluation: a value that is only wildcards,
an empty string, `contains` of a single character, a regex that matches the
empty string; a warning when a selection matches more than a fraction of
the corpus even inside budget.

## 4. Budgets raised to pass

**The trick.** The rule is `over_budget` at 10; the author edits
`fp_budget: 500` and it is green.

**Status today.** `pass`. The budget is declared in the rule file under
the author's control; Mizan measures against it and prints both numbers
(`fp/10k=200 budget=500`) so the raise is visible in the report and in the
diff, but it does not refuse it. The example set is capped at 50 by
`tests/test_examples.py`; that is a test of the examples.

**Open.** A repository policy file (`x-mizan.max_budget` per `level`, or a
`mizan.policy.yml`) enforced by `check`; `check` printing the budget
utilisation (`fp/10k=200 budget=500 used=40%`) so a budget ten times the
measurement stands out; a `--max-budget` flag for CI.

## 5. Evasions the rule does not cover

**The trick.** The rule looks for `-EncodedCommand`; the attacker writes
`-EncodedCo`, `/enc`, or `-ec`, uses an unquoted path, mixed case, a
different binary path, a nested interpreter. The positive fixtures are the
cases the author knows; the rule passes them and misses the rest.

**Status today.** `pass`. Mizan judges a rule against its own evidence;
it has no opinion about evidence that is not there. What it does provide
is the ground for the comparison: case-insensitive matching by default,
`windash` for `-`/`/` variants, keyword search over the whole event, and
an `unknown` (never a silent plain match) when a rule asks for a modifier
Mizan cannot evaluate, so an author cannot *think* a `base64` variant is
covered while the engine quietly ignores the modifier.

**Open.** Shared evasion fixture sets per technique (case, `windash`,
quoting, short flags, encodings) that any rule tagged with that technique
must pass; a `mizan evade` command that derives variants from the positive
lines and reports which ones the rule misses (not as a verdict -- as a
list for the author); a status for rules whose positives are all trivially
similar.

## 6. Malicious fixture and corpus files (A7)

**The trick.** Fixtures and corpora are data that anyone with a pull
request controls: a line of 2 GiB, a JSON document nested 100,000 deep,
`NaN`, duplicate keys that mean one thing to one parser and another to the
next, invalid UTF-8, a file that is a directory, a path in
`x-mizan.corpus` that climbs out of the corpus directory, a YAML rule with
aliases that expand to gigabytes.

**Status today.**
- No `eval`, no `exec`, no format strings built from events; events are
  parsed with the standard `json` module in strict mode: `NaN`/`Infinity`
  rejected, duplicate keys rejected, a non-object line rejected; each is
  `unknown` with `<file>:<line>` (tests in `tests/test_fixtures.py`).
- Limits: 1 MiB per line and 256 MiB per file (ADR section 4), checked
  before parsing; an over-limit line is cited and the run continues; an
  over-limit file is cited as a whole. Rule files are capped at 1 MiB.
- Deep nesting: the JSON decoder's recursion limit turns into a
  `malformed JSON` citation; the keyword walk and the condition evaluator
  are iterative or guarded against `RecursionError`.
- `x-mizan.corpus` entries must be plain file names; a path is refused
  (`no_corpus`, reason printed).
- Blank lines are counted and reported, never silently dropped; a
  malformed line never silently disappears (A7).
- A corpus file without a valid header makes every logsource-selected rule
  `unknown` and the exit code 3 (M1.2 Q2/Q3): a damaged corpus cannot
  quietly shrink the evidence.

**Open.**
- Regular expressions come from rules, events from fixtures; a crafted
  event against a backtracking pattern (`(a+)+$`) can stall the gate.
  Python's `re` has no timeout. Options: a pattern linter, a worker with a
  wall-clock limit, or the `re2` engine as an optional dependency.
- YAML alias expansion ("billion laughs") inside the 1 MiB rule-file cap:
  `yaml.safe_load` still expands anchors. Options: refuse aliases in rule
  files, or cap the expanded node count in the strict loader.
- A rule with a huge value list (100,000 patterns) is legal and slow; no
  cap today.
- The gate reads the tree as given; it does not verify that `rules/` and
  `corpus/` were not swapped for the run (CI checks out the commit, so
  this is the CI system's integrity, not Mizan's).

## 7. Choosing the evidence: `x-mizan.corpus` and unsupported features

**The trick.** Point `x-mizan.corpus` at the smallest friendly file, or
rewrite a rule so that it no longer uses the modifier that made it
`unknown` (replace `|base64` by a plain `contains` of the encoded string
the author happened to have), and the rule is now green with weaker
semantics.

**Status today.** Both are visible, neither is refused: `selected_by:
x-mizan.corpus` and the file names are printed; the rewritten rule is an
ordinary rule and passes on its own evidence. `unknown` cannot be hidden
inside a selection (an unsupported modifier makes the selection and the
rule `unknown` whatever the other fields say, M0.2 Q1 / M0.3 Q1).

**Open.** Policy and review, not engine: named corpora need a reviewer; a
`docs/review/` note when a rule loses a modifier.

## 8. Two rules, one id; one rule, two names

**The trick.** A new rule reuses the id of a good one (or a copy of a rule
is committed under another file name), and downstream tooling that keys on
`id` (export, suppression lists) merges or overwrites them.

**Status today.** Not detected: `check` judges files independently. The
example set's test asserts unique ids among the ten examples only.

**Open.** `check` refusing duplicate ids across the rule directory, and
reporting rules whose `detection` is byte-identical.

## 9. The verdict depends on the machine

**The trick.** Case-insensitive comparison, floating-point formatting,
random corpus generation or dictionary order differ between machines, so
a rule is green on the author's laptop and red in CI (or the reverse).

**Status today.** Determinism is designed in (A1): string comparison is
Python `re` with `IGNORECASE` (Unicode simple case folding, the same on
every platform); numbers print with four decimals; JSON text of non-string
values is canonical (sorted keys, no spaces); the corpus generator uses
only `random()`, `randrange()` and `choice()` of a seeded `random.Random`,
whose output is stable across Python 3 versions, and the test suite
regenerates and compares bytes on every run (verified on 3.11, 3.12 and
3.13 during the build). Rules are walked in sorted order.

**Open.** Locale-dependent case rules (Turkish dotless i) are not handled
specially: `IGNORECASE` is locale-independent, which is deterministic but
may differ from a SIEM's collation. Export output depends on the pySigma
version installed and is not part of the gate.

## What the gate guarantees, in one paragraph

A green `check` means: every rule file loaded with the required shape;
every rule has at least one positive and one negative fixture; every
positive line matched and no negative line matched, in a deterministic
engine that refused to guess about anything it does not support; every
rule was measured on at least one benign corpus compatible with its
logsource (or one it named, visibly) and its false-positive rate was at or
below the budget it declared; and every one of those facts is cited to a
file and line. It does not mean the fixtures are good, the corpus is
representative, the budget is reasonable, or the rule catches what it was
written to catch. Those are the open items above, and they belong to
reviewers until Mizan can measure them.
